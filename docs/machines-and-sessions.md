# Session links and the Machines panel

What this page covers: how the board links to a session, and what the Machines panel shows for each machine and package. Back to the [README](../README.md).

**Session links.** Both come from the fleet tool (see [The fleet tool](fleet-tool.md#the-fleet-tool)), and both are off until configured.
On the web pages (the board, the item pages, the project pages and inline mentions) a session's name links to its view in
the fleet tool's web UI, `client.session_view` with the name url-quoted for `{name}` (on an instance run with sala, sala's
`https://sala.example.com/#s={name}`), in a new tab, while the session holding that name has a live pane by the one
presence rule (`fleet.present`: running, or relaunching within the grace); a name with no live pane, a cloud or Cowork
session's included, is plain text (link the board and sala both ways). board.md, the brief
and the `sessions` tool give the `url` the fleet tool writes for that transcript id in its own live store
(`client.session_links`, `<dir>/<letter>/sessions.json`): on such an instance a web-terminal link for a pane on the server
box. A session the store has no row for, or a row with an empty url, is named there without a link, whatever its Remote
Control bridge does; a missing or unreadable store is logged once and leaves every pane without a link. A cloud or Cowork
session (`cse_…`) keeps its claude.ai link from `stackshot/core/cloud.py` there. This is the one read of the fleet tool's files the server
makes since an earlier change; names, machines and presence still come from the
server's own clients.

**The Machines panel.** The board shows one card per machine, its name as the card's bold first label, with a row per
package in `[machines_panel]`: the installed version and `latest ✓`, `→ <latest version>` (in the text colour, on the row's own line), `offline` (from the puller's check-ins) or
`latest unknown`, against the latest from npm or GitHub releases (`stackshot/fleet/versions.py`). A failed setup step or update is a card of its
own under the machine's. The cards are the fleet's machines (sala's letters, less the ones `[fleet] retired_letters` lists: a retired box has no card, no name in `fleet.names()`, no entry in the versions read, no alert card and no line in the sessions tool's Machines list, while its folder and its sessions stay as they are, so what it owns stays named; the publisher is never left out) and then the `[machines_panel] ssh_hosts`, machines with
every `[publish] every_minutes`, and `bump`), 10 s at most, with each package's version command (`ssh_cmd`, else the `cmd:` command, else
`self_cmd`); a package the host lacks gets no row, an unreachable host shows `offline` with the versions it last had. A machine card, fleet or ssh host,
carries no hover text at all. The publisher is the box the server runs on, found from its hostname (`[fleet] publisher_letter` overrides it), so its card is first and live after a move; a host in `ssh_hosts` that is that box (its OS hostname or its fleet name) is read by running the commands on it, never over ssh, and the other hosts are read over ssh from it, so the same list serves wherever the server runs. The read is cached in `<state>/site/versions.ssh.json`.

**The machine list, while a fleet manager is paired.** When a fleet manager is paired with the board (an approved caller key and a machine token, see [The client contract](client-contract.md#the-machine-list-the-fleet-manager-posts)), the machine list it posts (`POST /client/machines`) chooses which machines the Machines panel shows and in what order. Each machine has one card, the machine's own (its name, its package rows and its failure lines), joined to the list by name (by hostname when the name finds none, and never one that another listed entry names; every entry is joined by its name before any by its hostname); a machine the list names that has no reading yet shows its name and one muted offline line, and a machine the list marks `retired` has no card at all. A name is drawn once (names compared ignoring case and white space round them, the first entry wins), and a name that is blank has no card; a machine that is also an ssh host of its name is one card, never two. A machine the list does not name has no card either; a failure of such a machine keeps its own alert card. The list draws nothing else on a card: no hostname, letter, role words or hover text. Under the cards, the file names the sender could not read (`not read: ...`, 20 named, then how many more). While the list is fresh no line about it is drawn; a list older than 15 minutes (from when the board received it) is still used, with one amber line over the cards saying how old it is and that no newer list has arrived lately. Paired with no list yet, one muted line reads `no machine list received yet` and the cards are the ones a board with no list draws. A board that was never paired shows none of this and its panel is unchanged. Everything in the list is shown as text, never as a link or markup. The package cards, `ssh_hosts` and `host:` words work as they did. The sender may add four optional readings to a machine's entry (online, last seen, versions, when read); the board stores them but the cards do not draw them yet, so they look as they did ([the contract](client-contract.md#the-machine-list-the-fleet-manager-posts) has the rules).
