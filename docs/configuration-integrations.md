# Configuration: project agents, runners, anchor-hub, router, auth and client

What this page covers: the config keys for project agents, steps, runners, the item model, the Machines panel, gbrain and second brains, anchor-hub, the pilot and router, the For you list, the portal, sign-in and the client. Back to the [README](../README.md).

The keys are grouped in three pages by what they set: [Configuration](configuration.md), [Configuration: project agents, runners, anchor-hub, router, auth and client](configuration-integrations.md) and [Configuration: keywords for another language](configuration-keywords.md). Each has the same four columns.

| `project_agent.form_senders` | `[]` | The `--sender` labels of the fleet tool's New session form (sala's: `["sala-web"]`; empty = the form is off). ## Gmail query anchors: the query

An anchor `gmail:q:<query>` (every mailbox the anchors service reads) or `gmail:q@<mailbox>[,<mailbox>]:<query>` (only those) tells a project's agents about each new mail whose headers match the query. The mailbox scope is described under `anchor_hub.gmail_names` above; this section is the query.

**Terms.** A term is `key:value` with a key of `from`, `to`, `cc`, `subject` or `person` (`person` is from, to or cc), or a bare value, which is a subject term. A value is a quoted phrase or the words up to the next key, operator or parenthesis, so `subject:anchor test person:sam@example.com` is two terms and `subject:quarterly numbers` looks for the phrase "quarterly numbers". A term matches when the header contains the value, in any case. Keys are lowercase.

**Combining terms.**

| Write | Meaning |
|---|---|
| `from:a subject:b` or `from:a AND subject:b` | both must match (a space is an AND wherever a key, a quoted phrase or a parenthesis starts a new term; plain words run together are one phrase) |
| `from:a OR from:b` | either |
| `( ... )` | grouping |
| `from:(a OR b)` | the key applies to every term in the group: the same as `from:a OR from:b` (no other key may appear inside) |
| `"a b"` | a quoted phrase, for text that holds a parenthesis, a colon, a quotation mark or the words OR and AND |

AND binds tighter than OR: `from:a OR from:b subject:x` is `from:a OR (from:b AND subject:x)`. Write parentheses when it matters; the add reply shows how the query was read. `OR` and `AND` are operators only in capitals (Gmail's rule); `or` and `and` are ordinary words. There is no negation (a leading `-`) and no other Gmail operator (`label:`, `has:`, `after:`, `in:`, ...); `{a b}` is not supported either, write `a OR b`.

**An unsupported query is refused when it is added**, with one line naming what is wrong, and nothing is stored: a parenthesis or quotation mark that is never closed, a closing parenthesis with no opening one, `OR` or `AND` with nothing on one side, empty parentheses or an empty quoted phrase, a key with no value, a key inside `key:( )`, negation, `{ }`, a Gmail operator the matcher cannot read, any other `word:value` that is not one of the five keys (put it in quotation marks to match it as text), and a parenthesis or quotation mark glued to a word. An anchor stored before the grammar whose text the grammar refuses keeps the meaning it always had (every term must match, a value runs to the next key). An anchor stored before the grammar that the grammar now accepts is read by the grammar, so it can read differently than before: `Terms OR Conditions update` was one phrase and is now an OR, and the parentheses of `subject:invoice (urgent)` were literal text and are now a group.

Examples: `gmail:q:from:(billing@example.com OR accounts@example.com) subject:invoice`, `gmail:q@work:(subject:report OR subject:summary) cc:sam@example.com`, `gmail:q:subject:("quarterly numbers" OR "q3 numbers")`.

**Reading the mailbox.** The reader asks Gmail for the mail added since its last position, page by page (500 records a page, up to 10 pages a poll), and fetches the headers of at most 200 mails a poll; the 200 is checked between history records, never inside one, so a single record that names more than 200 mails is read whole in one poll (it makes that many gets) and the next record waits for the next poll. A busier mailbox is read on from where the poll stopped, straight away. A mail in a mailbox that no query anchor reads, and whose thread no thread anchor watches, is not fetched. A mail is delivered once: the last 1000 mail ids handled are remembered with the reader's position, so a history record that comes back (or names a mail twice) is not delivered twice.

**A restart resumes from the saved position.** The anchors service saves each reader's position (Gmail's history id, Drive's page token) with its other read positions, each minute and at a clean stop, and a start keeps it: mail that arrived, and Drive changes made, while the service was stopped are read from it and delivered once (Drive's changes are read a page of 100 at a time, the next page at once). A save made while a receiver's start is still being retried (the network down at boot) writes back what that receiver loaded, so a second restart before it comes up loses nothing. A position is saved only while an anchor of its kind is bound, so a kind with none saved (never bound, or unbound for a while before the stop) starts from now when an anchor is bound to it, as does a kind that becomes bound after the start. A saved position that Google answers with 404 (Gmail keeps its history for about a week) is replaced by the current one: nothing from before it is delivered, and a failed get saved from before it is dropped with the rest. A saved value of the wrong shape (a number where a text belongs, a list holding other things, a missing field) is ignored for that field and the rest is used.

**A mail whose get fails** is not lost: it is tried again at later polls, 3 tries in all (the failures are saved with the position, 500 at most, each with the time of its last try), and then given up on with a log line, so a mail that Gmail never serves (one deleted in between, say) cannot hold the reader back or be fetched again for ever. A mail's tries are at least 60 seconds apart however many polls come in between, so a short failure of Gmail cannot use them up, and the tried-again gets count against the 200 a poll, the ones over it waiting for the next poll.
