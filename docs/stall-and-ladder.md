# The silence pass, the stall pass and the ladder

What this page covers: the silence pass, the stall pass, the one ladder of nudges, and how the hand-off record follows the mover. Back to the [README](../README.md).

**The silence pass** (`stackshot/audit/silence.py`, `server._silence_tick`, a ten-minute entry after the dates pass; it needs `[audit] enabled`, script mode). It replaces the daily run's two silence rules, the stale check's 12 hours without a write on an item with no date of its own and the board report's idle-on-agent (6 hours), with one clock on the item: `activity.at`, the time of its last real activity (a step done or added, a state change, a new next step or description, the owner's answer, a message written onto the item, an event on one of its anchors). An audit's own write and a bare confirm do not move it, so the pass's message cannot reset the clock it reads. An open item that the board shows on an agent (a session is its mover, its state is not the owner's move, and its phase is not waiting: `silence.on_agent`, which asks `model.shown_waiting`, the board's own phase test, shared with the stall pass) with no activity for 45 minutes (`silence.LIMIT`) is found. What the board shows as waiting is left alone: an item on hold with a dated wake, behind an open item, with a stored wait (a release, a CI run, any event wait, a relay, an outside party), with a wake that carries a `wait_basis`, or whose open steps are all dated after the wake. A date alone is a wait until it (outside a hand-off), so the item reads as waiting and is left alone; only a wake kept as a hand-off's backstop leaves the item on agent, so it is found like any other (the finding says the wake is only a backstop and no wait, and what would make it one). A real hold carries a date (the server refuses one without), and a hold with no stored state derives parked and waits; only an artificial shape, a stored `state: doing` on a hold with no wake, reads on agent. A wake never silences a first open step that is already overdue and names no date of its own, a step the front-step rule moved or found stuck (`front_step.overdue`). An item with a hand-off to a back agent that nobody took yet is left alone as well (the hand-off audit clocks it, as the stall pass defers to it for a back agent); a hand-off to a front agent is checked here, because the hand-off audit never clocks one and the stall pass defers it to this pass. An item whose record the board's model cannot read is on an agent as the board lists it (`home.classify`), so it is found too, with evidence that says the record cannot be read; the stall pass still leaves it alone ("not readable"). The dates pass finds the same `stale` finding when a wake passes on an item already found here; each pass counts the other's sends (`silence.sent_record`, the dates record), so one message goes out per episode. The count starts at the later of that activity and the moment the item left a hold, a wait or an after link (a wake, a lifted hold and a released after link are saved by the server with no writer, so the activity clock does not move for them): an item parked for a day is not found the round it wakes. Silence is judged per item, never per pane: the pass does not read the mover's pane, so a busy pane (a builder directing subagents is nearly always busy), a background agent's `shell` pane or a pane this box does not show hides no silent item. Before it sends, the pass asks one view (`server._silence_skip`): an item the stall ladder is already on (`_stall_active`) is left alone, and a view that cannot be built sends nothing (fail open). A subagent's work that writes nothing to the item is not activity, so a builder keeps a long job visible by writing it onto the item; one such write is read beyond the clock: an item whose mover is its project's builder and which has a step with a status in progress (changed within 90 minutes, `silence.subagent_running`; a job that runs longer changes the status's words or writes to the item, since a status sent again unchanged keeps its old time) has a build subagent running on it and counts as taken, while a builder's item with no such line and no event in 45 minutes is silent whatever its pane shows. A finding is the daily run's `stale` finding in its wording ("no write for N minutes and no date of its own", the same fix; a span past four hours reads in hours and minutes), so the two share one `finding_key`; it goes to the mover (else the project's -main agent) through `deliver_findings`, once per silence episode: an episode ends when the item has activity again, and the send stamp is compared with the item's activity, not with its last write. The pass's record is `<state>/audit/silence.json` (`started`, `findings` with their send stamps, `carried`: the stamps of findings that went away with no activity on their item, so a wait filed and lifted does not restart the episode); like the filing and dates passes it does nothing while a daily run is in progress, and the stall pass stays (it watches the pane of a front agent or a session no page lists as a background agent: a session with no turn running, the ladder to the cold call and the builder; a background agent's rungs after the ask go by the item's own step status, and a live one's silence ends at its project's -main agent, see **The one ladder**; with `[ladder] silence` on it takes the rungs of the items this pass brings instead of starting its own). By default it sends the ask rung only, as one message per silence episode; with `[ladder] enabled` and `[ladder] silence` both true that message is the ask of the one ladder and the item goes on it (below). **The backstop** (`silence.uncovered`, `server._silence_backstop`, looked at once an hour from the ten-minute silence tick): an item the board shows on an agent that has had no activity for 2 hours (`silence.BACKSTOP_S`) and has no silence finding (and is not left to another chaser: the stall ladder, a build subagent running) is a defect of the pass, whatever exemption hid it. The builder is told once per item in one message that asks nothing of the owner and makes no board item, with one stderr line; it is told again only after the item has had a finding in between. The told ids are kept in `<state>/audit/silence-backstop.json` (`silence.read_backstop`, `silence.write_backstop`; written before the message goes out, read once per process), so a restart of the server does not tell the builder again; a record that cannot be read counts as empty. The backstop is given the pass's own environment (`server._silence_env`), so it judges a hand-off by the server's answer to who is a front agent, as the pass does. Suites: `tests/quiet_item_checks_scenario.py`, `tests/ladder_silence_scenario.py`, `tests/silence_scenario.py`, `tests/runner_scenario.py`, `tests/runner_order_scenario.py`. A stored `until` is read where a wake is read (`waiting.wake_value`) and the board shows an item that stores one waiting, so the silence pass, the stall pass and the backstop leave it alone, as they leave a wake that carries a wait_basis; once the date has passed the wait is due and the server's watcher turns it, which is the board's own reading and so theirs.

**What counts as news on an item.** Any session's write to the item ends a stall episode (`server._stall_ver` reads `updated` and `state_updated`) and moves the activity clock the silence pass reads: that includes a write to a step's status (`update work={…}`, one line on the sender's open step; a filing edit that moves `updated` and the activity clock, not the state clock or the confirm), to `next`, and to the description. A status written again unchanged is still a write, but keeps the status's own time, so it does not extend the 90 minutes a status in progress holds a build subagent "running". Before the one list a `work` line was counted the same way (a filing edit) and the line's own time was the only thing read from it.

**The stall pass** (`stackshot/waits/stall.py`, `server._stall_tick`). Every `[stall] every_seconds` (20; the stall pass runs on the runner's 60-second pace, so a smaller value still runs once per round) it looks at every open, live item whose mover is a session, front agents included. **The signal** is the CLI's registry (`~/.claude/sessions/<pid>.json`, read by `server._handoff_status`, the same read the hand-off clock uses): the mover's live process has `status: idle` (or `shell`, which the CLI writes for a pane whose turn is over but which has a `run_in_background` Bash task running; a background subagent keeps the pane `busy`, which is left alone) and its `statusUpdatedAt` is `[stall] minutes` (10) old or more. A pane that starts a turn goes busy and, back to idle, has a later `statusUpdatedAt`, so a turn starting restarts the count; an item that only just reached its mover counts from then, not from the pane's age. A pane the registry does not show on the server's box (another machine's, a dead process) says nothing, and its items are left alone. **The ladder**, each step `minutes` after the one before it, counted from the later of the pane going idle, the item reaching its mover and the previous step: (1) the notice goes to the mover once more (one message per mover, items batched; **a front agent is sent none**, because no item notice wakes a front agent: its step 1 is the History line alone, and steps 2 and 3 cover its item; at most `[stall] max_per_tick` (5) first steps a tick, the rest on the next ticks (the cap is per tick, so with one tick a minute a burst of 30 idle panes after a deploy takes about 6 minutes); **no clock starts before the pass first ran**, recorded under `_pass` in `<state>/stall.json`, so a deploy or a restart does not step every long-idle pane at once); (2) the hand-off's cold call (`server._handoff_cold`, through the same writer, [model] `cold_call`) names who takes it, at most once per item in 24 hours (**a stall cold call never asks the owner**: the record's `stall` marker gives it `cold_call.STALL_RUBRIC`, which offers `hand_to` and `close` only and answers `none` when unsure; an `ask_owner` answer, a `none`, an answer it could not give or a write the item refused is not written, so no `needs`, ask or mover changes, a `stall:` journal line and a History line say "the cold call named no taker: to the builder", and the item goes on to step 3 at once; the ordinary hand-off cold call keeps its three answers); (3) the project's builder (`server._handoff_builder`, through `_handoff_exec`, which reads the builder as section 5 does); (4) when none of them can take it, the last rung: a History line ("stackshot: …") and a journal line, and ONE message to the fleet's builder (`[fleet] operator_session`, `server._recovery_tell`), first line `[stackshot] fleet recovery: <item> …`, naming the item, its mover, why and what was tried, and asking it to take the fix through its usual path. **A front-only project** (`anchors.front_only`: its `agents:` map lists no `background:` agent, so there is no builder to have tried) ends at its -main agent instead (`server._recovery_target`): the same one message, marked `[for <owner>]` on its first line like every message a front agent takes, asking it to decide whether to bring the session back, message it or hand the item on (`update mover=<session>`); the fleet's builder is asked only when the project has no -main agent to name or the quiet mover is its -main agent itself. The recipient is chosen once per request (`_recovery_target`, on the quiet session itself) and the record (`recovery_by`: who was asked, in words), the History line, `get`'s hand-off line and the message's "what the ladder tried" all follow it; a front-only project is never said to have tried a builder, whoever is asked. The hand-off record carries it (`recovery_at`), so the pass sends it once, and the mark is written before the send on purpose (a failed send is not retried every pass: `metadata.undelivered` records it and the audit's unmoved digest is the backstop); the History line is written after the send and says what happened (asked, or why nothing was sent); a write by the item's mover, or the item moving on, ends the record and a later episode may send another. The item stays with its mover and does not go to the owner; no list of his carries it. A stall record (`metadata.handoff.stall`) runs no clock of the hand-off ladder (`no_clock`) and never returns the item to a sender. **Not looked at:** an item on hold, on a wait or moved by the owner or an outsider (the model derives no session mover for them), a hand-off in flight to a session that is not a front agent (the hand-off ladder, `[model] handoff_minutes`, owns it), a cold call running, **an item whose work is not due now, whatever its mover's role** (`stall.not_due`, which asks the same `model.shown_waiting` as the silence pass: an item the board shows as waiting, that is a hold with a dated wake, a park, an `after` link to an item still open, a stored wait, or a wake that carries a `wait_basis` (an idle pane is not a stalled one: a builder that ended its turn while a background task runs shows `shell`, which counts as idle once the item is due, and one with a background subagent running shows `busy`); and the owner's and an outsider's lanes, a wait on the owner (`needs` decision, his step) or on someone outside (`needs` external). A date alone is a wait that holds the pass off until it has passed; a wake kept as a hand-off's backstop holds nothing off and counts no due time until it has passed). Such an item gets no step and **no record is kept for it**, so a leftover ladder position does not carry over: when it falls due (the wake passes, the hold lifts, the answer comes) its clock starts then, the mover's idle time counted from the later of the pane going idle and that moment), an item already raised in the last 24 hours, and an item whose pane status is unknown. Every step is written on the item (`metadata.stall.log`, one History line each, "stackshot: …"; the last three show in `get` as `stall:` lines) and a `stall:` line in the journal; the episode's progress is in `<state>/stall.json` (an entry restarts when anyone writes the item or its mover changes). It needs `[model] handoff` on and not paused. **A pause of the pass always ends on its own** (a pause that is forgotten would otherwise leave idle builders asleep). Two keys pause it, both read live on a config reload: `[stall] paused_until` (an ISO-8601 time with an offset, such as `"2099-03-14T21:00+00:00"`) holds the pass until then and it runs again with no edit; `[stall] enabled = false` holds it for at most `[stall] max_pause_hours` (default 4) counted from when the server first saw the pause (the reload or start that read it; the start time is kept in memory and in `<state>/stall_pause.json`, so a restart does not reset the clock). The cap covers a `paused_until` too: one further out than `max_pause_hours` from when it was first seen is cut to the cap, and a changed setting is a new pause seen at that moment. After the end the pass runs although the file still says `enabled = false`; edit the file to start another pause. The journal has one line when a pause starts, `stall: paused until Fri Mar 14th 2098 21:00 (paused_until)` (the reason is `paused_until`, `enabled=false, capped at 4 h` or `paused_until, capped at 4 h`), and one when it ends, `stall: pause ended, the pass runs again`, which is also a line on the routing log (ruled `dropped` by `stackshot (auto)`, under the page of the fleet operator's project, `[fleet] operator_session`). A reload logs `config reload: warning: the stall pass is paused and takes no step until …`, and `bin/stackshot doctor` and the server's start print a `[stall] the stall pass is paused …` note with the end time. **An agent never switches the pass off**. The server honors `enabled = false` or a `paused_until` still ahead only when `[stall] pause_item` names a board item that carries the owner's own answer approving a pause (`metadata.answers`, written only by his board login or his GitHub comment, never by a session's `update`; the chosen option or the comment says "pause", and an unrelated answer of his does not count) dated no earlier than 4 hours before the server first saw the setting (an answer that comes only after the pause's cap has passed starts it then, with a new clock and one `stall: paused until … (started late …)` line); the cap on any pause is at most 24 hours (`max_pause_hours` above 24 is read as 24). Any other setting is refused: the pass keeps running, the journal has one line, `stall: pause refused, the pass keeps running: <why>` (once per config load, not per tick; a reload or a restart logs it again once), and `bin/stackshot doctor`, the server's start and a reload print the same reason. **When the pass takes a wrong step on an item**, an agent (1) undoes the step on the item with `update`: a hand-off (`cold`, `builder`) is undone by setting `mover` and `next` back, a close by `status=open` with a new `next`, a recovery request needs nothing undone (the message to the fleet's builder cannot be unsent; the item stayed with its mover); the `stall:` line in the item's History stays as the record; a notice already sent (`resend`) cannot be unsent and needs nothing; (2) fixes the cause through a normal PR to stackshot (`not_due`, `action` or the registry signal read the item wrong, which is code), handed to my-engineer; (3) if wrong steps reach the owner before the fix lands, asks him for a pause that ends by itself: he answers on a board item, and `pause_item` names it. The same text is in `stackshot/waits/stall.py`'s docstring and in the `get` tool (the `update` tool has a short clause pointing to it).

**The one ladder** (`stackshot/waits/ladder.py`, `server._ladder_*`, `[ladder] enabled`, off by default). The hand-off ladder (a reminder for a background agent, the project's builder, the cold call, the sender, the fleet's builder asked) and the stall ladder (the notice again, the cold call, the builder, the fleet's builder asked) were two orders on two records, and an item could climb both. With `[ladder] enabled = true` an item whose mover went quiet has one record, its entry in `<state>/stall.json` (its `via` says which audit brought it: `handoff` for a hand-off nobody took, `stall` for a pane with no turn running), and one order: (1) **ask**: the mover is sent the notice again (a hand-off's own notice for an untaken hand-off, the stall notice for a silent pane; a front agent gets the History line alone); (2) **look**: `[ladder] look_minutes` (30) after the ask, and only then, the pane is looked at: with no turn running the notice goes again, with a turn running nothing is sent and the look comes when the turn ends (a background agent's pane is not looked at, see **Background movers** below); (3) **cold**: `[stall] minutes` (10) later the cold call names who takes it (it never asks the owner); (4) **builder**: `[stall] minutes` later, or at once when the cold call named no taker, the project's builder takes the item; with none able, ONE message asks the fleet's builder to recover the session (the project's -main agent for a front-only project, see the stall ladder above), the item stays with its mover and is not put to the owner. The two audits that bring an item stay apart: the hand-off tick (`_handoff_tick`) brings an untaken hand-off (not taken in `[model] handoff_minutes`, a turn that ended with no write, a gone pane, two failed pushes: those last two start at the cold call, there being nothing to ask), the stall tick (`_stall_tick`) a silent pane, and both take the rungs after the first here. An untaken hand-off to a session is the hand-off audit's alone (the stall tick does not start it) and the hand-off tick leaves an item already on the ladder, so one item never climbs two ladders at once. The sender rung is gone (an untaken hand-off is not sent back to the session that handed it over), and so is the reminder as a step of its own: a background agent is asked like any mover, so one whose turn ended with no write is now asked after the idle grace period rather than after the `handoff_minutes` clock, and the reminder's extra wait is gone. A write to the item by anyone but the mover, or the mover's own confirm (at most `stall.RESTARTS` times), restarts the episode but keeps the item on the ladder: the ask is not sent a second time, the look comes `look_minutes` after the last rung taken, and the hand-off tick does not bring the item again; the mover starting work on the item takes the hand-off and ends the ladder, as does a new mover, and the entry is for the hand-off it was made for (`ho_at`: a later hand-off of the item to the same mover starts a ladder of its own). The rungs after the ask are taken by the stall tick, so while the stall pass is paused (`[stall]` paused, or `[model] handoff` off) the ladder waits where it is and goes on when the pass runs again; the cold call is made at most once per item in 24 hours. With the flag off both ladders run as they did; turning it off in the middle of a ladder hands the item back to them, the stall ladder reading the ladder's steps in its own shorter table (`ladder.unwind`: a builder rung still to come stays reachable). The idle pass leaves an item the ladder has a step on for the whole ladder (`_stall_active`). **Background movers** (`ladder.action(background=, live=)`, `server._stall_tick`). A background agent's pane is nearly always busy or showing a background shell (a CI watch, a release), and that says nothing about one item, so with `[ladder] enabled` the rungs after the ask (the look, the cold call, the builder) of an item whose mover is a background agent wait on the clock alone, never on its pane, and a background shell no longer exempts a builder. The evidence that the mover is working on the item is the item's own step status: a status in progress on a step that opens with the mover's own name (another agent's stale status holds nothing), changed within 90 minutes (`silence.subagent_running`) holds the ladder where it is, and the rungs go on 90 minutes after the line was last changed. Three limits: only a background agent (a front agent, and a session no page lists as a background agent, keep the pane rule); one notice per background agent per stall pass (its other items wait for the next pass); and a background agent whose pane is live (the registry shows it, or the heartbeat holds it running; a heartbeat that is empty or unreadable is unknown, and counts as live) goes no further than the look on its own, since the cold call and the builder replace a mover that cannot answer and a live one can: they are taken only when its pane is not live (or the hand-off audit entered the item as gone: two failed pushes, no delivery, whatever the heartbeat shows), and a builder is never handed its own item (the last rung is then the one message to the fleet's builder). **A live mover's silence goes up instead** (`ladder.MAIN`, `server._ladder_main`): `[stall] minutes` (10) after the look, when the item has still had no activity (`silence.LIMIT`), a notice goes to the project's -main agent (`_main_agent`, a front agent): ONE per -main agent per pass, listing every item due for it (a lone item reads as a sentence), marked `[for <owner>]` on its first line like every message a front agent takes, saying each item has had no write from its background mover since the time of its last activity, asking it to decide whether the item needs a nudge or a different mover, and saying how to stop the repeats (write to the item, hold it or set its wait). It is no rung of its own: the entry stays where it is (so the cold call and the builder are still reachable if the pane stops being live), a History line says it, and the entry's `main_at` is its clock, so the same notice comes again only every `[ladder] main_hours` (4 hours by default; `ladder.MAIN_EVERY` is the default) while the silence lasts, never once per pass; activity on the item ends it (the silence entry's own rule), a fresh step status of the mover holds it (above), a front mover's item and a mover whose pane is not live get none, and a project with no -main agent (or whose -main agent is the mover) gets the History line alone, the rung taken. The ladder never lets an item whose mover is live and silent sit unseen for a day. The ask of a ladder a pane with no turn running brought (`via` = `stall`) still waits for that pane. **The silence switch** (`[ladder] silence`, off by default, and it does nothing unless `[ladder] enabled` is true as well; only a TOML true turns it on, read at use): the ladder has a third way in, and the pane with no turn running stops being one. With it on, the ten-minute silence pass (an open item on an agent with no activity for 45 minutes) and the dates pass (an item past its own wake with no write since) send their message to the mover as before, and for each fresh finding that reached someone (`silence_pass(entered=)`, `audit_run.dates_pass(entered=)`, `server._ladder_enter_quiet`) the item goes on the ladder with `via` = `silence`: that message is the ask, so the entry starts on the look, with its clock started when the message went and a History line ("asked for news"). The look comes `look_minutes` (30) later, and only if the mover's pane has no turn running (a turn running waits; a front agent gets the History line alone; a background agent's pane is not read, see **Background movers** below); the mover is told once more in the silence wording ("nothing written for N minutes", N from the item's last write; `server._ladder_quiet_look`), then the cold call `[stall] minutes` after the look, then the project's builder, then ONE message to the fleet's builder, the item staying with its mover and off the owner's list, as above. The entry is for this silence alone: it ends when the item has activity (its `activity` clock moves past the entry's `act`) or its mover changes, so a bare confirm by the mover and a write that is no activity restart nothing (the stall pass's `RESTARTS` do not apply to it), and a leftover entry of the cold call's 24-hour bound is kept. A pane with no turn running no longer starts a ladder (`_stall_tick` only takes the rungs of an entry the silence audit or the hand-off audit made; an untaken hand-off is still the hand-off audit's). A finding sent before the switch was turned on is not entered (no flood: such an item climbs from its next silence). Turning `silence` off (with `enabled` on) lets an entry already made finish its rungs and brings the pane trigger back; turning `enabled` off reads the entry in the old stall table (the look maps to the cold call). Suite: `tests/ladder_silence_scenario.py`.

**An item that is not moving goes up the same way** (`model/progress.py`, `server._ladder_stuck`, `[ladder] enabled` and `[ladder] main_hours`, 4). The pings to the mover and the silence rungs above judge writes; a busy mover that answers "no change" every hour keeps them satisfied while the item sits. So an alive item (open, a session moves it, not waiting, not the owner's move) with no progress for `main_hours` is handed up to the project's -main agent in the notice above, in the same message when both ways bring items in one pass: it names the item, the mover, how long the item has not moved and what it is queued behind (the mover's other alive items, by priority and then age, at most five, "no other item of its mover" when there are none, "unknown" when the store cannot be read). **Progress** is the item's own `progress` clock, stamped by every save: a step marked done or dropped, a state change (the item's status, its phase and the kind of its wait, its mover, its state, its needs), a pull request recorded as merged for the item (an entry of `metadata.released_told` starting `merged `, or a key of `metadata.merged_seen`, below), or the item being created. **A merged pull request is progress for the item it is tied to, whether or not it settles a step** (`stackshot/anchors/merge_log.py`, `stackshot/model/merge_tie.py`, `server._merge_progress_tick`, which rides on the minute anchor pass). The hub appends one line to `<state>/merges.jsonl` for every pull request it sees merge (`Hub.emit`, before any lane a notice takes, so the routine lines of the fleet's own repository and a direct anchor's are covered), from the read it already makes, with the item ids the pull request's body names as plain words (`board#N`, a temporary id, a legacy `gNN` id or an item link, read as a session's message is: code, quotes and glued ids are blanked): no GitHub read is added. The pass reads that file from a byte offset (`<state>/merge-progress.json`) and, on every pass, skips a malformed line (the offset moves past it: a line that is not JSON, or is nested too deep to parse, is dropped by `merge_log.read` without a log line; so is a line that parses but is not an object with a repository and a number (`{}`, `[1]`, a number of 0, an empty repository); a line that has both but is of the wrong shape (a repository that is not text or `owner/repo`, or longer than 140 characters; a number below 1, above a billion or too large to hold; a time that is not finite; the writers apply the same two caps, so a repository longer than 140 characters or a number above a billion in an anchor or a link writes no line at all, and the digit runs of the patterns that read them are bounded to match) is logged by the pass as its exception class, the first 80 characters of its message and a bounded look at it (at most 80 characters), never the whole line; a ref that is not a string is left out of its line, which is kept) and a merge older than `main_hours` plus two hours, so the backlog of a day of downtime stamps nothing and ties each merge to the open items it names: (a) an anchor scoped to the item names it (a project-wide anchor names no item, or every merge would reset every item's clock), (b) the pull request's body names the item (in this public repository this rule cannot fire: a public pull request's body may not carry a board id, so the item-scoped anchor of (a) is the case that works), (c) the item's own words name it (its description, its steps, the status tag of each open step and the lines of its `next`: a session often writes "PR 136 released; PR 137 in review" on a tag before any step text says it), by its URL, or by its number (`#n`, `PR n`) when the item has no URL for it and the pull request is in this repository or one the item has a pull request anchored in. It stores the key in the item's `metadata.merged_seen` (the last 20) through a save of the server's own (activity kind `event`, a History line saying why), which is what stamps the clock; a key the item holds is not saved again, and a closed item, one the board shows waiting or held and one in the owner's lane are left alone (they are not on this ladder, and a stray mention must not reset their silence clock). A bare number ties only an item whose project page holds an anchor in that repository, or that has a pull request of it anchored to it (an item that meant another repository's number is still tied: a limit); a full pull request URL ties any item. Only merges the hub sees are logged: a pull request with no anchor, which the owner's GitHub account is not notified about either, is not seen. A pass whose offset is past the end of the file (replaced or shrunk) reads from the start, and an item that cannot be read or saved is logged and skipped, the offset still stored. `merged_seen` is a list of its own, not `released_told`: an entry there tells the mover and settles a step, and a merge that settles nothing must not stop the settle path from telling the mover later. A status line (`work`), a note, a reply, a message, a confirm, a new or reworded step and a description edit are not: they move the activity clock the silence pass reads, not this one. A save that is no one's write about the work (a migration, an audit, the server's own bookkeeping) counts only as a status or phase change (a wake, a close), so renaming a session in every item's mover moves nothing. An item saved before the clock existed reads as having moved when it was last written, changed state, was active or had a step marked, whichever is latest, so a deploy does not hand up every item that lacks the field. **A parked item is not handed up for the park.** The clock is counted from the later of the item's last progress and when the stall pass first saw it due again (`<state>/progress_alive.json`, kept by the pass: the phase sweep and the wake's release write around the save that stamps progress, so neither can restart it). An item the pass has not seen yet counts from the first pass that sees it, so a deploy or a restart of this record delays a first hand-up by `main_hours` and never causes a false one. **Once per stretch**: the hand-up stamps `metadata.progress_up_at` (the silent-mover notice stamps it too) and the item is not handed up again until `main_hours` have passed since, and it has been `main_hours` without progress. The History line on the item says it; a project with no -main agent, or whose -main agent is the mover, gets the History line alone (worded for which it is), once per interval. The ~90 minute pings to the mover are unchanged.

**The hand-off record follows the mover** (`handoff.follow`, `server._handoff_follow`, called by the save (`stackshot/service/writes.py`) on every save). An item has one open hand-off record (`metadata.handoff`), and it never names someone but the item's effective mover: a session's write hands over through `handoff.apply` as before; any other save ends a record that names a mover the item left (it goes to `handoff_history` as "handed on, not taken", or "the item no longer has a mover"), and a save of the server's own that changes the mover to a session (a wake that makes the post-wake mover the mover, an event wake, the stall pass, a release of `after`) records the hand-off to the new mover, from the server, marked `no_clock`: **the 10-minute take clock still starts only on a session's hand-off**, never on a server-made record, and the timing of a woken mover stays with the stall pass, which leaves a busy pane alone. A taken record to the same name does not count as already naming the mover: a wake that hands the item back to a session that took it before makes a new record (the taken one goes to the history as "handed on"). The record is marked delivered only when a notice actually reaches the mover: a record to a front agent, one whose wake notice is held, and one whose notice goes to a session in needs other than the mover stay undelivered. The owner's answer, a script's save and a hand-back out of the owner's state end a stale record and make none; a record that carries a recovery request (the ladder's last rung) of an open item is left, unless a save of the server's own moves the item on to another session: that ends it as "handed on" and records the new mover (so the stall pass is not silent for it); the open record of a closed item is ended. Delivery is recorded on every notice path: the message tool, the router's push, the keeper's page-owed batch and the anchors prompt mark the open record of an item the text carries the notice link of to that session, and the message tool one the text cites (`server._handoff_told_text`; a batch that only cites another item in a subject marks nothing for it), so a lost notice can be told from a fast take. Records the older code left are repaired by a pass in the server's start (`server._handoff_repair_pass`, after the mover migrations and before the wake pass and any thread; idempotent, one log line with the count): it ends each open record that names someone but the mover and makes nothing new. `stackshot/tools/handoff_repair.py --store <copy of the store>` is the rehearsal (a dry run unless `--apply`); `--live` is a read-only dry run, and `--live --apply` is refused while the user unit `stackshot.service` is active.

**A hand-off is taken only by work started** (`handoff.started`, `handoff.touch`, called by the save (`stackshot/service/writes.py`) through `handoff.apply`). The mover's write takes its open hand-off only when the write shows work begun: a step marked done (the checklist's own mark), a step status (`update work={…}`) new or moved to `in progress` or `done`, or the item closed. An anchor scoped to the item added since the hand-off counts through `plan` as before. A note, a confirm, a reword of `next` or the description, a queue or wait line, a hold or wake, a dropped or new step and a timeline line do not, so they leave the 10-minute clock and its reminders running; the sentence of a note is never read, only the marks. The hand-off notices tell the mover so.

**A background agent that does not take a hand-off is reminded first** (with `[ladder] enabled` off only: on the one ladder there is no separate reminder, see above) (`handoff.plan`, `handoff.remind`, `server._handoff_exec`). When a hand-off to a background agent is due and not taken (delivered and `[model] handoff_minutes` old; for such an agent a turn that ended with no write does not hurry it, the clock alone does), the first step is one reminder to that agent's own session, through the normal push: the item was handed over, no work on it has started, start its subagent alongside the current work. The recipient is checked fail closed (`server._handoff_reminder_target`): the name must resolve to a live session that the role map lists with a background role and not retired, so a front agent, a page's name-line session, an unknown name, a keeper entry, or an unreadable role map gets no reminder and the ladder is what it was. The record gets `reminded_at`, its delivery is forgotten and the clock restarts from the reminder's own push result (delivered, or queued plus the inbox grace); a reminder whose push fails twice goes down the ladder. After a reminder only the clock counts (not the turn-end rule): when the item is still not taken after another `handoff_minutes`, section 5 goes on as before (the project's builder, the cold call, the sender, then the recovery request to the fleet's builder). Several reminders due in one pass for one agent go in one message. A new hand-off of the same item is a new record and is reminded again. An anchor scoped to the item and added at or after the hand-off counts as taken, for every mover (a pull request in flight is a build started; an older anchor says nothing about this hand-off): such an item is neither reminded nor moved on; the anchors are read once per pass and only for an item that would act. A `no_clock` record (one the server made) and a front agent stay without a clock.

**The last-activity record** (`stackshot/model/last_activity.py`, `stackshot/anchors/event_log.py`, `stackshot/service/writes.py`'s last-activity stamp, `server._event_activity_tick`; `tests/last_activity_scenario.py`). The rule it prepares: no item an agent moves goes more than an hour without visible activity. Part A records it and shows it: the home page's On agent rows and the item page draw the time since it and what it was (see the row bullet in [board-ui.md](board-ui.md)). No flag guards it and no notice or clock changes: `activity` and `progress` are exactly as they were. Each open item can carry `metadata.last_activity = {"at": epoch seconds, "kind": ..., "what": "short words"}`, the newest visible activity and what it was. **One definition of activity**, in `last_activity.py`: a save that moved the item's progress (`progress.moved`, the same test: a step marked done or dropped, a state change, a pull request recorded as merged, the item created), and an event on a pull request tied to the item (a CI result, failed or passing on a new head, whatever the head before it was; a comment by a person, a review, a merge, a new head commit). Each is a signal of a named kind: `step_done`, `step_dropped`, `state_change`, `pr_merged`, `ci_result`, `review`, `comment`, `commit`, and two the module defines and tests that nothing stamps yet, `update` (a mover's status write whose text differs from the previous status text) and `audit` (a line the audit wrote saying what it verified: a pane in a turn, a subagent running, a commit, a review or CI on the pull request); for those two the words are the short text itself. A later part stamps them by adding the signal, not by changing the record. **Not activity:** a status line, a reply or a "no change" answer, a note, a message, a confirm, a new or reworded step, a description edit, and what the server writes about the item itself (a History line of the ladder or the silence pass, the ask, the step made for the owner): none moves the record. **Newest wins**: a signal replaces the record only when strictly later, a signal that is torn (no time, no words, an unknown kind, a time that is not a number: a bool or a string is none, whatever it spells) is skipped, a time ahead of the pass reads as the time of the pass, and a stored record dated after the pass is ignored (it would otherwise hide every later signal). **How a page reads it**: `read(item, now)`, `at` and `age_s` treat a stored record dated more than an hour ahead of the reader's clock (`SKEW_S`, the window an event's own time is allowed) as no record, never as "just now" (a clock that jumped is not a time that happened); one ahead by less is a skew of clocks and reads as just now. The band of an age is amber from 45 minutes up to and including an hour and red only past an hour (`band`: strictly more than `BAND_BAD_S`). **Saves** stamp it in `writes.save`, next to the progress clock, at the time of the save. **Events on a tied pull request** come from the hub: `Hub.emit`, the funnel the merge log already uses, appends one line to `<state>/events.jsonl` for each kind of activity an event is (`{"ts", "repo", "n", "kind", "refs"}`; the merge log and its readers are unchanged, and a burst of types is a line for each kind). A comment or review whose every author is a bot (a login ending in `[bot]`, or an account the comment's own payload types as a bot, which costs no extra read) is left out; a CI event on a repository's notifications with no pull request is left out. `server._event_activity_tick`, on the minute anchor pass beside the merge pass, reads the file from a byte offset (`<state>/event-activity.json`), skips a line that is malformed (logged in a bounded line), older than a day or stamped more than an hour ahead, and ties each line to open items with the same rules as a merge (`merge_tie` through `_merge_tied`: an anchor scoped to the item, the pull request's body naming it, the item's own words; a project-wide anchor ties nothing, and a closed, waiting or held item is left alone), except that only a merge ties through the body. Many lines for one item are one save, the newest of them. It saves an item only when the record changes, and only after reading the item again under the lock (one closed, held or begun to wait since the tie is left alone), as the server's own bookkeeping (activity kind `bookkeeping`, no History line), so the `activity` clock, `progress`, `updated` and the board are unmoved. An item that cannot be read or saved is logged and skipped, the offset is stored, nothing raises out of the pass, and a read-only standby copy or a held board runs nothing. **Only a merge ties through the pull request's body** (the rule the merge log has always had). A comment, a review or a CI result ties only through an anchor scoped to the item or the item's own words, because in a public repository anyone can open a pull request whose body names an item and comment on it, and that must not stamp the item; a line of the log that carries board ids for any other kind has them dropped when it is read. A comment on a plain issue anchor is worded `comment on #n`, since the hub does not say whether the thread is a pull request. **Who counts** (one filter, `event_log.lines_for`, where an event becomes a line): in a public repository anyone can comment, and a fork's pull request runs CI without the repository's say, so an event that is not a merge is activity only when its source vouches for it. A comment or review counts only when its author's `author_association` in the payload (no extra read) is `OWNER`, `MEMBER` or `COLLABORATOR`; `CONTRIBUTOR`, `NONE`, `FIRST_TIMER`, `FIRST_TIME_CONTRIBUTOR`, `MANNEQUIN`, any other value and a missing one do not. A CI result counts only when the pull request's head repository is its base repository (`head.repo.full_name` equals `base.repo.full_name` in the pull request read the hub already makes), so a fork's branch, a deleted fork and a payload that does not say do not count. The receiver (`github.py`) sets `Event.vouched`, the kinds of the event it vouches for (a burst of comment and review is judged per kind; a thread of the repository's notifications vouches for a kind when any of its authors qualifies); the log writes no line for a comment, review or CI result that is not vouched for, whoever the item and whatever the tie. A merge is not filtered here: it keeps the merge log's rule and the body tie. The notice a session receives is not changed by any of this. **When it happened:** a line is written at the event's own time (`Event.ts`) when it can be read and lies within a day before and an hour after the hub's clock, so a backlog read after a restart or downtime stamps the time it happened at, not now; an event with no time, or one that cannot be read, is written at the hub's clock; an event older than a day or more than an hour ahead writes no line (the window the pass has always applied to a line it reads; a time far ahead is a torn clock). A naive time is read in the instance's timezone, as the hub writes its own. **Which time the receiver gives:** a comment or review read from a thread of the repository's notifications is stamped at the newest `created_at` or `submitted_at` among the items the repository's own side wrote (the vouched ones), not at the thread's `updated_at`, which a stranger's later comment in the same batch also moves (an owner-side comment at 05:44 and a stranger's at 07:42 stamp 05:44); a batch with no vouched item, and a merge, keep the thread's time. A CI result is stamped at the newest `completed_at` of the check runs it was read from (the moment the last one finished), when that lies inside the same window (a day before, an hour after the hub's clock); a result with no `completed_at`, or one outside the window, is stamped at the hub's clock as before, so a result seen after downtime is not stamped as now. The History's confirm test ignores `metadata.last_activity` (as it does `phase` and `waits_on`), so a confirm and the pass's stamp saved in one publish window still show the `confirmed` line. **A commit** (`commit on PR n`): GitHub sends no push notification, so the receiver finds it in the pull request read it already makes for every anchored pull request. It keeps the head sha it last saw per pull request, and when it last looked at the pull request, in its saved CI state; when the sha differs it logs a `pr_commit` event. Seen live (the last look was within ten minutes), the event is stamped at the time the hub saw it and no request is added: the push is what happened now, whenever the commit was made, so a commit made at 10:00 and pushed at 11:30 shows as just now, a force-push of an old commit does too, and a committer's wrong clock does not matter. Seen after the hub was away (the last look is older than ten minutes, or unknown, as after a restart or a stretch of downtime), the commit is read once (the only extra request, and only then) and stamped at its committer date, never later than now and never older than the event log's day-long window; a read that fails (the hourly cap, a refusal, a date that cannot be read) stamps the time seen instead, so the signal is not lost. A first sight of a pull request only keeps the sha, an unchanged sha and a 304 record nothing, and a pull request from a fork (or a deleted fork) is neither read nor recorded: only the repository's own branch counts, as for CI. Any new head counts, a merge of main pushed under the builder's account included, so a pull request that only takes in main can reset an idle agent's clock. A read that fails after a long outage (no committer date to use) stamps the time seen, which is later than the commit was made. A commit event is logged for this record and told to no session, on the direct lane too. The record keeps the newest, so a stamp older than it never moves it back. **The gaps:** Three limits are accepted: a pull request whose first read after a restart answers 304 has no `own_branch` mark (the payload that sets it is not sent), so its CI results are not vouched for until the payload changes; a merge line older than a day is dropped as last-activity (the window above applies to every kind); and a pull request from another repository of the same organization gets no CI credit, since only a head branch in the repository itself counts as the repository's own side. A review is seen only when the hub reads it: for a pull request with its own anchor the hub reads the issue comments, CI and the merge, and a repository's notification thread is skipped for it, so reviews arrive mostly for pull requests reached through a repository-root anchor. Comments made under the hub's own account are never emitted (the hub drops them upstream), so they are never seen here. No GitHub read is added for this; the audit's later "verified" line covers it by reading the pull request itself. The words of a signal are one line of at most 80 characters, control characters turned to spaces, whoever writes them. **A late anchor still counts a merge from the last day** (`anchorhub/github.py` `late_merge`): when the hub first reads an anchored pull request that merged within the last 24 hours (at most 120 s ahead of the hub's clock, which allows for GitHub's clock; further ahead is a torn time and writes nothing), it writes the merge line instead of seeding silently, so an anchor added after the merge still credits the item it is scoped to. The line goes to the event log and the merge log, both stamped at the time the pull request merged (not when the hub found it), so the last-activity record takes the merge from the last day while the merge pass, which skips a merge older than `[ladder] main_hours` plus two hours, moves the progress clock only for a recent one. The body's ids are not read on this path (a body can be edited long after the merge): the anchor's own scope is the tie. A pull request closed unmerged, still open or merged longer ago is a silent seed, a line that could not be written leaves the anchor unseeded so the next pass tries again (at most three tries, then the anchor is seeded without the line and a warning says so), writing only the log that lacks the line (a merge log write that succeeded is not repeated when the event log's failed), the sessions of the anchor get no notice for the line, and an item-scoped anchor added after the line was logged gets no credit for it (the passes tie a line once, when they read it).
**The backfill** (`stackshot/model/last_activity_pass.py`, `stackshot/tools/last_activity_backfill.py`, the ops `lastact` and `unlastact` of `POST /client/migrate`; `tests/last_activity_backfill_scenario.py`). An open item nobody has touched since the record shipped has none, so its On agent row has nothing to show. The tool fills `metadata.last_activity` for the open items that have no record that reads, from what is recorded about them, and writes that key and nothing else (no clock, mover, needs, state, step or History line, nobody told). **Where the time comes from:** the item's own History, the store's git versions of its file (the path alone: never `git log --follow`, whose copy detection takes the file of another, similar item for a rename), replayed oldest first through the function a save goes through (`last_activity.save_signals`, which asks `progress.moved`); whether a version was someone's write about the work is read from the item's own `activity` clock, which a real write moves and the server's bookkeeping leaves; the first version is the item being created; a version of the file on disk that git has not got yet is the last one. Then the hub's merge log and event log, tied to the item as the live pass ties them (`server._merge_tied`), each line at the time the hub saw it, a line stamped more than an hour ahead of the clock dropped as the live pass drops it. The record is the newest of them, newest wins. **The refused class:** an item whose History cannot be read (the store outside git, git not answering, a version missing from the repository or not JSON; an item file that git saw deleted and then added back is such an item, since no version of it stands at the deleting commit) or holds a version stamped more than an hour ahead of the clock is refused, named in the output with the reason, and left as it is; the time is not guessed. A record is never written dated after the clock (a time inside the skew is written as now). An item that already has a record that reads is left alone; a torn one, or one dated further ahead than the skew, counts as none and is replaced, its old value kept in the undo entry. **Modes**, as `tools/until_migrate.py` (whose run-directory lock, undo-file reading, unfinished-pass check and pruning it uses): the dry run is the default (the store copied into a private folder, its git read from the live store read only, the whole pass run on the copy twice, one block per item, the refused class and the totals); `--apply --sender <session>` asks the server for the plan (each item with the time and kind it would get; the apply writes nothing and says so ("the items to fill, the times they would get or the refused ones differ from the dry run in --plan", or "… changed while the plan was being read"; exit 1) when an item, a time, a kind or a refused item differs from the dry run's `--plan` file or from the plan read a moment before, a time that is just "now" excepted, unless `--allow-changed-plan` is passed; the time written is worked out once more under the item lock, and the undo file records what was written), prints the refused class, writes a backup of every touched file byte for byte and the undo file before the first write, then writes in batches under the item lock with a sha256 check (an item written meanwhile is `moved` and its write stands); `--undo <file> --sender <session>` puts back only a record that still is what the pass wrote (the key goes when it had none; a later write is `kept`), and a second undo does nothing. The route needs `[model] migration = true` and the sender in `[model] migration_senders`. **The hub's logs:** when the merge log or the event log cannot be read, or the events cannot be tied to the items (the anchors that tie them cannot be read included), an item would be filled from its History alone and a newer event left out; the dry run prints a warning in its summary and `--apply` refuses (nothing written) until they read. A bool, a numeric string, NaN or infinity as a stored time or clock is no time here, as in the record's own reader. Exit codes: 0 `--apply` wrote every planned item and none is left as it is, or there was nothing to fill and none is left as it is; the dry run finished and its second pass on the copy would change nothing (it exits 0 whether or not it lists items to fill or refused ones, so read its output); `--undo` put every entry back or found it as it should be. 1 a failure (the plan could not be made, a batch was refused or got no answer, an item could not be written, the plan differs from the one shown, the hub's logs or the anchors cannot be read, another run holds the run directory, the undo file cannot be used or an entry of it was refused, or the dry run could not make its copy or its second pass would still change something). 3 `--apply` only, not a failure: items are left as they are for a person to look at (refused, kept because their History holds no activity, written by someone else meanwhile, closed between the plan and the write), also when there was nothing to fill.

**The hourly audit line** (`stackshot/audit/hourly.py`, `server._hourly_tick`, called from the ten-minute silence tick; `[audit] hourly_line`, off by default; it needs `[audit] enabled`, script mode). An item an agent moves is never to sit an hour with nothing on it. The mover writes the update; when it has nothing new to add, the audit checks that the item is moving and writes the line itself: one History line, `Audit 14:05: verified the mover's pane is in a turn, CI passing on PR 12` or `Audit 14:05: idle, nothing verified`, the time in the instance's zone. It is an entry of its own log, `metadata.hourly_audit.log`, kept apart from the ladder's `metadata.stall.log` so it neither crowds out the ladder's entries nor reads as a step of the stall pass (`get` prints the newest as `audit:`), with kind `audit` or `audit_idle`; the History shows it and a later part can read which items are idle. Nobody is messaged, a front agent included, and the save is the server's own bookkeeping: it moves neither the activity clock nor the progress clock, so the line cannot make the item look written. No line is stamped as the item's `metadata.last_activity`: a builder's pane is busy nearly all day, and stamping it would keep every silent item looking fresh on the On agent row, and a line that rests on a recorded event (signal 3 below) has that event in the record already. A line that rests on live states alone (signals 1 and 2) says so in its words, `Audit 14:05: verified the mover's pane is in a turn (live state only, nothing recorded on the item)`; one that rests on a recorded event does not.

*When.* An item is owed a line when it is open and on an agent as the silence pass reads it (a session moves it, the state is not the owner's, the board does not show it waiting), has had no activity for an hour (`silence.clock`, the same clock: a bare confirm, a "no change" reply and the audit's own lines do not move it), and has no audit line lately (a line dated more than an hour ahead of the clock is a torn entry and is not counted): one an hour for the first 24 hours of silence, then one every 6 hours, so a week of silence is about fifty lines, not 168. A hold, a parked item and any stored wait (a dated wake, an item it waits after, a CI run, a relay, an outside party) are skipped, an untaken hand-off to a back agent too (the hand-off audit's), one to a front agent is not, and otherwise a front agent's item is treated like any other. A second pass in the same hour writes nothing, and a clock that goes backwards only delays the next line. The gap since the last line is judged with five minutes of slack (a line is owed 55 minutes after the last one, 5 hours 55 minutes in the slow stretch): the tick reads its clock a few seconds later or earlier each time, and without the slack an hour on the grid would sometimes fall seconds short and push the line a whole tick on, to 70 minutes. The tick runs every ten minutes, so a line lands within about ten minutes of the hour.

*What is verified.* Recorded data only; nothing is read from GitHub. (1) The mover's pane is in a turn: the CLI's registry on the server's own box shows it `busy` (`server._handoff_status`, the stall pass's read; a session that box does not run shows nothing, and a pane showing `shell` or `idle` is not a turn). A busy pane says the session works, not which item it works on. (2) A subagent is running: a step status in progress, changed within 90 minutes, on a step that opens with the mover's name. (3) A pull request tied to the item had a CI result, a review, a comment by a person or a merge in the last hour, as `metadata.last_activity` holds it. A commit or push is not recorded by anything yet, so it is not a signal. When none holds, the line says idle and the item is only marked so (its log entry's kind, `hourly.idle_marked`); handing it on to a free builder is the next paragraph.

**Handing an idle item on** (`stackshot/audit/hand_idle.py`, `server._hand_idle_tick`, run from the ten-minute silence tick right after the hourly line; `[audit] hand_idle`, off by default; it needs `[audit] hourly_line`). An hourly update is mandatory: with nothing verified the item is idle, and it goes to a free builder and the project's -main agent is told, never the owner. The pass reads the line the hourly audit left: an item is handed on when its newest line is `idle, nothing verified` (`hourly.idle_marked`) and not older than 6 hours 15 minutes (an older line means the hourly pass is off, or the item left the agent since), nothing has moved the item since that line (`silence.clock`: a step done, a state change, the mover's own write, an anchor event or the owner's answer all count, a bare confirm does not), it is open and on an agent as the board shows it, not held, its hand-off if it has one was taken (an untaken hand-off is the hand-off audit's), and its mover is not a front agent (an item a front agent moves is the owner's work and stays). *Which builder.* The first free one of the item's project's background agents, best first (the project's builder before the rest), else of any project whose mandate says build. A builder is free when its pane is not in a turn on this box (`server._handoff_status`, the read the stall pass and the hourly line use; a pane that box does not run reads as not in a turn) and it is the mover of no open item that is on an agent (an untaken hand-off to it counts: it is about to take that item; an item on hold or behind a wait does not); a name known to have no pane, or whose pane cannot be read, is not free, and the item's own mover is never picked. *The move* is the minute hand-off pass's own write (`_handoff_exec` → `_handoff_write_move`, the path of the audit's orphan hand-over): the builder heads `needs`, the stored mover follows, the hand-off record is made from the server (so the hand-off audit clocks it as any other) and the builder is told by the hand-off notice. One History line says why and names the mover it left, `handed to team-back: no activity for an hour, nothing verified (it was with home-peer)`, and `metadata.hand_idle` ({`handed_at`, `from`, `to`}) keeps the limits. The project's -main agent gets one message through the notice path the ladder uses for it (the front agent's mark on its first line, tag `stall`) that says what happened and asks nothing; no message goes to the owner, no row is made for him and no step is his. *No builder free.* Nothing moves; one History line says so and -main is told once per item per 24 hours (`hand_idle.none_at`); a project with no -main agent gets the History line alone. *Limits.* At most 3 items per pass (the next pass goes on with the rest), one per item per 24 hours; an item handed on once and idle again after 24 hours may be handed again, and a builder that took an item in a pass is no longer free for the next. A torn log entry or a torn `hand_idle` stamp (not a number, dated ahead of the clock) is no signal and raises nothing.
