# The audit lines, the stall pass and the ladder

What this page covers: the readings the audit passes share, the stall pass, the one ladder of nudges, the hourly audit line and the idle hand-over, and how the hand-off record follows the mover. Back to the [README](../README.md).

**What replaced the 45-minute news ask** (`stackshot/audit/silence.py`, `_silence_tick` in `stackshot/service/audit_ticks.py`, a ten-minute entry after the dates pass; it needs `[audit] enabled`, script mode). The ten-minute pass that sent an item's mover a `stale` message after 45 minutes without activity, with its two-hour backstop, is retired: nothing asks a mover for news at 45 minutes any more. An item an agent moves is covered by **the hourly audit line** and **the idle hand-over** below, and by the stall pass and the ladder. The file keeps its name for the readings the passes share, and `audit_ticks._silence_tick` (the runner's key) now runs only the hourly line and then the idle hand-over, each by its own `[audit]` key. `silence.reading` says how the board stands toward an open item: on an agent (a session is its mover, its state is not the owner's move, and its phase is not waiting: `model.shown_waiting`, the board's own phase test, shared with the stall pass), unreadable (the board's model cannot read the record; `home.classify` lists it on an agent), or not on an agent. What the board shows as waiting is not on an agent: an item on hold with a dated wake, behind an open item, with a stored wait (a release, a CI run, any event wait, a relay, an outside party), with a wake that carries a `wait_basis`, or queued behind its mover's other item; a wake kept as a hand-off's backstop leaves the item on agent. `silence.clock` is where an item's quiet time counts from: `activity.at`, the time of its last real activity (a step done or added, a state change, a new next step or description, the owner's answer, a message written onto the item, an event on one of its anchors), or the moment it left a hold, a wait or an after link if that is later (the server saves those releases with no writer, so an item parked for a day does not read as long quiet the round it wakes), or the moment the front-step rule moved a step to its mover. An audit's own write and a bare confirm do not move it. Quiet time is judged per item, never per pane: a busy pane (a builder directing subagents is nearly always busy) says nothing about one item. A subagent's work that writes nothing to the item is not activity, so a builder keeps a long job visible by writing it onto the item; `silence.subagent_running` reads a step with a status in progress (changed within 90 minutes; a status sent again unchanged keeps its old time) as a build subagent running on it, and the stall ladder and the idle hand-over leave such an item alone. `silence.queued` reads the queue below once per round. The dates pass keeps its ladder entry (the third way in, below). The old records `<state>/audit/silence.json` and `<state>/audit/silence-backstop.json` are no longer read or written and can be deleted. A stored `until` is read where a wake is read (`waiting.wake_value`), and the board shows an item that stores one waiting, so the hourly line, the idle hand-over and the stall pass leave it alone; once the date has passed the wait is due and the server's watcher turns it. Suites: `tests/silence_scenario.py` (the shared readings), `tests/quiet_item_checks_scenario.py`, `tests/ladder_silence_scenario.py`, `tests/runner_scenario.py`, `tests/runner_order_scenario.py`.

**What counts as news on an item.** Any session's write to the item ends a stall episode (`stall_ver` in `service/stall.py` reads `updated` and `state_updated`) and moves the activity clock the hourly audit line and the idle hand-over read: that includes a write to a step's status (`update work={…}`, one line on the sender's open step; a filing edit that moves `updated` and the activity clock, not the state clock or the confirm), to `next`, and to the description. A status written again unchanged is still a write, but keeps the status's own time, so it does not extend the 90 minutes a status in progress holds a build subagent "running". Before the one list a `work` line was counted the same way (a filing edit) and the line's own time was the only thing read from it.

**An item queued behind its mover's other item** (`stackshot/model/queued.py`, `silence.queued`, `audit_ticks._queue_map`; `[model] queued_behind`, off by default; `tests/queued_behind_scenario.py`). A session that moves several open items works on one at a time. With the key on, the board reads each of the mover's other items on an agent that has had no activity (`metadata.last_activity`) for more than an hour as waiting, queued behind the item it has the newest activity on (the rule and its edges are on *[The item model and the stored state](item-model.md)*), and the passes leave it alone as they leave any waiting item: `silence.reading` takes the queue, so the hourly audit line and the idle hand-over see it as not on an agent, the hourly audit line writes none (`hourly.due`, `hourly.pass_` read the same queue once per pass), and the stall pass takes no rung on it (`_stall_tick` skips it beside `not_due`). It is derived at read and stored nowhere, so activity on it (the mover moving it, an event on its pull request), the item in hand closing or an hour without activity on the item in hand brings it back to on agent and under every pass at the next round. A front agent's items are never queued.

**Where the queue is deliberately not read.** The queue is read by the readers that decide what is shown or chased from the item as it stands now: the board's lists and counts, board.md and the brief's head and cards (`Board.mod_of`, `home.wait_phrase`), the item page, the items sheet's list word (`service/client_reads.py`'s `_item_list`), the hourly audit line and the stall pass. These keep the stored reading on purpose, and a queued item is on agent for them: (1) the hand-off audit and the ladder's entry points (`ladder_enter_quiet` (`service/ladder.py`), `ladder_enter` (`service/ladder.py`)) are reached only from a pass that has already skipped a queued item (`_stall_tick` skips it before it builds the rung), so they hold no test of their own and re-check only that the item is still open, due and its mover's; an item that becomes queued between a pass reading it and the entry being written is entered once, and ends by the usual rules; (2) the end-of-turn `items?key=` list carries the queue's list word (`list`, from `_item_list`) but not a wait (`held`, the `wait` fields and `state` are as stored), so a session sees an item as waiting by its list and reads its stored lane; (3) the daily run's `audit_checks.date_only_wait`, which asks whether an alive item is all waiting for a dated wake, reads the stored model, and the queue is never what it reports; (4) `Board.agent` (`stackshot/web/render.py`, `stackshot/web/ui/render.py`), the list the brief's `N stale` count walks, is the stored on-agent list, so that count still includes a queued item, while the lists and the other counts follow the queue; (5) the idle-hand pass (`audit/hand_idle.py`: `due`, `busy_movers`) reads `silence.reading` without the queue. It still sees a queued item as on an agent. The balancer (below) is the one pass that reads the queue itself, over its own window and whatever `[model] queued_behind` says.

**The stall pass** (`stackshot/waits/stall.py`, `stall_tick` in `service/stall_tick.py`; its state and steps are `service/stall.py`, the one ladder `service/ladder.py`, and what they still reach in the server comes through `service/stall_hooks.py`). Every `[stall] every_seconds` (20; the stall pass runs on the runner's 60-second pace, so a smaller value still runs once per round) it looks at every open, live item whose mover is a session, front agents included. **The signal** is the CLI's registry (`~/.claude/sessions/<pid>.json`, read by `handoff_status` in `stackshot/service/handoff.py`, the same read the hand-off clock uses): the mover's live process has `status: idle` (or `shell`, which the CLI writes for a pane whose turn is over but which has a `run_in_background` Bash task running; a background subagent keeps the pane `busy`, which is left alone) and its `statusUpdatedAt` is `[stall] minutes` (10) old or more. A pane that starts a turn goes busy and, back to idle, has a later `statusUpdatedAt`, so a turn starting restarts the count; an item that only just reached its mover counts from then, not from the pane's age. A pane the registry does not show on the server's box (another machine's, a dead process) says nothing, and its items are left alone. **The ladder**, each step `minutes` after the one before it, counted from the later of the pane going idle, the item reaching its mover and the previous step: (1) the notice goes to the mover once more (one message per mover, items batched; **a front agent is sent none**, because no item notice wakes a front agent: its step 1 is the History line alone, and steps 2 and 3 cover its item; at most `[stall] max_per_tick` (5) first steps a tick, the rest on the next ticks (the cap is per tick, so with one tick a minute a burst of 30 idle panes after a deploy takes about 6 minutes); **no clock starts before the pass first ran**, recorded under `_pass` in `<state>/stall.json`, so a deploy or a restart does not step every long-idle pane at once); (2) the hand-off's cold call (`handoff_cold` in `stackshot/service/handoff_cold.py`, through the same writer, [model] `cold_call`) names who takes it, at most once per item in 24 hours (**a stall cold call never asks the owner**: the record's `stall` marker gives it `cold_call.STALL_RUBRIC`, which offers `hand_to` and `close` only and answers `none` when unsure; an `ask_owner` answer, a `none`, an answer it could not give or a write the item refused is not written, so no `needs`, ask or mover changes, a `stall:` journal line and a History line say "the cold call named no taker: to the builder", and the item goes on to step 3 at once; the ordinary hand-off cold call keeps its three answers); (3) the project's builder (`handoff_builder` in `stackshot/service/handoff.py`, through `handoff_exec`, which reads the builder as section 5 does); (4) when none of them can take it, the last rung: a History line ("stackshot: …") and a journal line, and ONE message to the fleet's builder (`[fleet] operator_session`, `_recovery_tell` in `service/pane_recovery.py`), first line `[stackshot] fleet recovery: <item> …`, naming the item, its mover, why and what was tried, and asking it to take the fix through its usual path. **A front-only project** (`anchors.front_only`: its `agents:` map lists no `background:` agent, so there is no builder to have tried) ends at its -main agent instead (`_recovery_target` in `service/pane_recovery.py`): the same one message, marked `[for <owner>]` on its first line like every message a front agent takes, asking it to decide whether to bring the session back, message it or hand the item on (`update mover=<session>`); the fleet's builder is asked only when the project has no -main agent to name or the quiet mover is its -main agent itself. The recipient is chosen once per request (`_recovery_target`, on the quiet session itself) and the record (`recovery_by`: who was asked, in words), the History line, `get`'s hand-off line and the message's "what the ladder tried" all follow it; a front-only project is never said to have tried a builder, whoever is asked. The hand-off record carries it (`recovery_at`), so the pass sends it once, and the mark is written before the send on purpose (a failed send is not retried every pass: `metadata.undelivered` records it and the audit's unmoved digest is the backstop); the History line is written after the send and says what happened (asked, or why nothing was sent); a write by the item's mover, or the item moving on, ends the record and a later episode may send another. The item stays with its mover and does not go to the owner; no list of his carries it. A stall record (`metadata.handoff.stall`) runs no clock of the hand-off ladder (`no_clock`) and never returns the item to a sender. **Not looked at:** an item on hold, on a wait or moved by the owner or an outsider (the model derives no session mover for them), a hand-off in flight to a session that is not a front agent (the hand-off ladder, `[model] handoff_minutes`, owns it), a cold call running, **an item whose work is not due now, whatever its mover's role** (`stall.not_due`, which asks the same `model.shown_waiting` as `silence.reading`: an item the board shows as waiting, that is a hold with a dated wake, a park, an `after` link to an item still open, a stored wait, or a wake that carries a `wait_basis` (an idle pane is not a stalled one: a builder that ended its turn while a background task runs shows `shell`, which counts as idle once the item is due, and one with a background subagent running shows `busy`); and the owner's and an outsider's lanes, a wait on the owner (`needs` decision, his step) or on someone outside (`needs` external). A date alone is a wait that holds the pass off until it has passed; a wake kept as a hand-off's backstop holds nothing off and counts no due time until it has passed). Such an item gets no step and **no record is kept for it**, so a leftover ladder position does not carry over: when it falls due (the wake passes, the hold lifts, the answer comes) its clock starts then, the mover's idle time counted from the later of the pane going idle and that moment), an item already raised in the last 24 hours, and an item whose pane status is unknown. Every step is written on the item (`metadata.stall.log`, one History line each, "stackshot: …"; the last three show in `get` as `stall:` lines) and a `stall:` line in the journal; the episode's progress is in `<state>/stall.json` (an entry restarts when anyone writes the item or its mover changes). It needs `[model] handoff` on and not paused. **A pause of the pass always ends on its own** (a pause that is forgotten would otherwise leave idle builders asleep). Two keys pause it, both read live on a config reload: `[stall] paused_until` (an ISO-8601 time with an offset, such as `"2099-03-14T21:00+00:00"`) holds the pass until then and it runs again with no edit; `[stall] enabled = false` holds it for at most `[stall] max_pause_hours` (default 4) counted from when the server first saw the pause (the reload or start that read it; the start time is kept in memory and in `<state>/stall_pause.json`, so a restart does not reset the clock). The cap covers a `paused_until` too: one further out than `max_pause_hours` from when it was first seen is cut to the cap, and a changed setting is a new pause seen at that moment. After the end the pass runs although the file still says `enabled = false`; edit the file to start another pause. The journal has one line when a pause starts, `stall: paused until Fri Mar 14th 2098 21:00 (paused_until)` (the reason is `paused_until`, `enabled=false, capped at 4 h` or `paused_until, capped at 4 h`), and one when it ends, `stall: pause ended, the pass runs again`, which is also a line on the routing log (ruled `dropped` by `stackshot (auto)`, under the page of the fleet operator's project, `[fleet] operator_session`). A reload logs `config reload: warning: the stall pass is paused and takes no step until …`, and `bin/stackshot doctor` and the server's start print a `[stall] the stall pass is paused …` note with the end time. **An agent never switches the pass off**. The server honors `enabled = false` or a `paused_until` still ahead only when `[stall] pause_item` names a board item that carries the owner's own answer approving a pause (`metadata.answers`, written only by his board login or his GitHub comment, never by a session's `update`; the chosen option or the comment says "pause", and an unrelated answer of his does not count) dated no earlier than 4 hours before the server first saw the setting (an answer that comes only after the pause's cap has passed starts it then, with a new clock and one `stall: paused until … (started late …)` line); the cap on any pause is at most 24 hours (`max_pause_hours` above 24 is read as 24). Any other setting is refused: the pass keeps running, the journal has one line, `stall: pause refused, the pass keeps running: <why>` (once per config load, not per tick; a reload or a restart logs it again once), and `bin/stackshot doctor`, the server's start and a reload print the same reason. **When the pass takes a wrong step on an item**, an agent (1) undoes the step on the item with `update`: a hand-off (`cold`, `builder`) is undone by setting `mover` and `next` back, a close by `status=open` with a new `next`, a recovery request needs nothing undone (the message to the fleet's builder cannot be unsent; the item stayed with its mover); the `stall:` line in the item's History stays as the record; a notice already sent (`resend`) cannot be unsent and needs nothing; (2) fixes the cause through a normal PR to stackshot (`not_due`, `action` or the registry signal read the item wrong, which is code), handed to my-engineer; (3) if wrong steps reach the owner before the fix lands, asks him for a pause that ends by itself: he answers on a board item, and `pause_item` names it. The same text is in `stackshot/waits/stall.py`'s docstring and in the `get` tool (the `update` tool has a short clause pointing to it).

**The one ladder** (`stackshot/waits/ladder.py`, `ladder_*` in `service/ladder.py`, `[ladder] enabled`, off by default). The hand-off ladder (a reminder for a background agent, the project's builder, the cold call, the sender, the fleet's builder asked) and the stall ladder (the notice again, the cold call, the builder, the fleet's builder asked) were two orders on two records, and an item could climb both. With `[ladder] enabled = true` an item whose mover went quiet has one record, its entry in `<state>/stall.json` (its `via` says which audit brought it: `handoff` for a hand-off nobody took, `stall` for a pane with no turn running), and one order: (1) **ask**: the mover is sent the notice again (a hand-off's own notice for an untaken hand-off, the stall notice for a quiet pane; a front agent gets the History line alone); (2) **look**: `[ladder] look_minutes` (30) after the ask, and only then, the pane is looked at: with no turn running the notice goes again, with a turn running nothing is sent and the look comes when the turn ends (a background agent's pane is not looked at, see **Background movers** below); (3) **cold**: `[stall] minutes` (10) later the cold call names who takes it (it never asks the owner); (4) **builder**: `[stall] minutes` later, or at once when the cold call named no taker, the project's builder takes the item; with none able, ONE message asks the fleet's builder to recover the session (the project's -main agent for a front-only project, see the stall ladder above), the item stays with its mover and is not put to the owner. The two audits that bring an item stay apart: the hand-off tick (`handoff_tick`) brings an untaken hand-off (not taken in `[model] handoff_minutes`, a turn that ended with no write, a gone pane, two failed pushes: those last two start at the cold call, there being nothing to ask), the stall tick (`_stall_tick`) a quiet pane, and both take the rungs after the first here. An untaken hand-off to a session is the hand-off audit's alone (the stall tick does not start it) and the hand-off tick leaves an item already on the ladder, so one item never climbs two ladders at once. The sender rung is gone (an untaken hand-off is not sent back to the session that handed it over), and so is the reminder as a step of its own: a background agent is asked like any mover, so one whose turn ended with no write is now asked after the idle grace period rather than after the `handoff_minutes` clock, and the reminder's extra wait is gone. A write to the item by anyone but the mover, or the mover's own confirm (at most `stall.RESTARTS` times), restarts the episode but keeps the item on the ladder: the ask is not sent a second time, the look comes `look_minutes` after the last rung taken, and the hand-off tick does not bring the item again; the mover starting work on the item takes the hand-off and ends the ladder, as does a new mover, and the entry is for the hand-off it was made for (`ho_at`: a later hand-off of the item to the same mover starts a ladder of its own). The rungs after the ask are taken by the stall tick, so while the stall pass is paused (`[stall]` paused, or `[model] handoff` off) the ladder waits where it is and goes on when the pass runs again; the cold call is made at most once per item in 24 hours. With the flag off both ladders run as they did; turning it off in the middle of a ladder hands the item back to them, the stall ladder reading the ladder's steps in its own shorter table (`ladder.unwind`: a builder rung still to come stays reachable). **Background movers** (`ladder.action(background=, live=)`, `stall_tick` in `service/stall_tick.py`). A background agent's pane is nearly always busy or showing a background shell (a CI watch, a release), and that says nothing about one item, so with `[ladder] enabled` the rungs after the ask (the look, the cold call, the builder) of an item whose mover is a background agent wait on the clock alone, never on its pane, and a background shell no longer exempts a builder. The evidence that the mover is working on the item is the item's own step status: a status in progress on a step that opens with the mover's own name (another agent's stale status holds nothing), changed within 90 minutes (`silence.subagent_running`) holds the ladder where it is, and the rungs go on 90 minutes after the line was last changed. Three limits: only a background agent (a front agent, and a session no page lists as a background agent, keep the pane rule); one notice per background agent per stall pass (its other items wait for the next pass); and a background agent whose pane is live (the registry shows it, or the heartbeat holds it running; a heartbeat that is empty or unreadable is unknown, and counts as live) goes no further than the look on its own, since the cold call and the builder replace a mover that cannot answer and a live one can: they are taken only when its pane is not live (or the hand-off audit entered the item as gone: two failed pushes, no delivery, whatever the heartbeat shows), and a builder is never handed its own item (the last rung is then the one message to the fleet's builder). **A live mover's silence goes up instead** (`ladder.MAIN`, `ladder_main` (`service/ladder.py`)): `[stall] minutes` (10) after the look, a notice goes to the project's -main agent (`_main_agent`, a front agent): ONE per -main agent per pass, listing every item due for it (a lone item reads as a sentence), marked `[for <owner>]` on its first line like every message a front agent takes, saying each item has had no write from its background mover since the time of its last activity, asking it to decide whether the item needs a nudge or a different mover, and saying how to stop the repeats (write to the item, hold it or set its wait). It is no rung of its own: the entry stays where it is (so the cold call and the builder are still reachable if the pane stops being live), a History line says it, and the entry's `main_at` is its clock, so the same notice comes again only every 4 hours (`ladder.MAIN_EVERY`, a fixed interval) while the silence lasts, never once per pass; activity on the item ends it (the quiet entry's own rule), a fresh step status of the mover holds it (above), a front mover's item and a mover whose pane is not live get none, and a project with no -main agent (or whose -main agent is the mover) gets the History line alone, the rung taken. The ladder never lets an item whose mover is live and silent sit unseen for a day. The ask of a ladder a pane with no turn running brought (`via` = `stall`) still waits for that pane. **The dates pass's entry** (`[ladder] enabled`; the ladder's third way in, and the pane with no turn running is not one): the dates pass (an item past its own wake with no write since) sends its message to the mover, and for each fresh finding that reached someone (`audit_run.dates_pass(entered=)`, `ladder_enter_quiet` (`service/ladder.py`)) the item goes on the ladder with `via` = `silence` (the stored value keeps its name): that message is the ask, so the entry starts on the look, with its clock started when the message went and a History line ("asked for news"). The look comes `look_minutes` (30) later, and only if the mover's pane has no turn running (a turn running waits; a front agent gets the History line alone; a background agent's pane is not read, see **Background movers** below); the mover is told once more ("nothing written for N minutes", N from the item's last write; `ladder_quiet_look` (`service/ladder.py`)), then the cold call `[stall] minutes` after the look, then the project's builder, then ONE message to the fleet's builder, the item staying with its mover and off the owner's list, as above. The entry is for this quiet stretch alone: it ends when the item has activity (its `activity` clock moves past the entry's `act`) or its mover changes, so a bare confirm by the mover and a write that is no activity restart nothing (the stall pass's `RESTARTS` do not apply to it), and a leftover entry of the cold call's 24-hour bound is kept. A pane with no turn running does not start a ladder (`_stall_tick` only takes the rungs of an entry the hand-off audit or the dates pass made; an untaken hand-off is still the hand-off audit's). Suite: `tests/ladder_silence_scenario.py`.

**A merge is recorded on its item** (`stackshot/model/progress.py`, `service/merge_progress.py`'s `_merge_progress_tick`). There is no hand-up of an item that is not moving any more: nothing hands an alive item up to the project's -main agent for going four hours without a step marked, a state change or a merge. A mover that keeps writing lines but makes no progress (no step marked, no state change, no merge) is therefore no longer handed up after four hours: the hourly update rule and the busy-stretch tell look at real activity, and a mover's own line counts as activity, so a mover that writes a status line every hour is not told by either. The two rules that still tell -main about an item are a long busy stretch of the mover's pane (*A long busy stretch tells the right agent once*, below) and a live background mover's silence after the look (*A live mover's silence goes up instead*, above); neither takes the place of the old hand-up in that case. What stayed of the old clock is the list of what counts as the item having moved (`model/progress.py`: a step marked done or dropped, a state change, a pull request recorded as merged), which the last-activity record reads, and the merge pass below. **A merged pull request is recorded on the item it is tied to, whether or not it settles a step** (`stackshot/anchors/merge_log.py`, `stackshot/model/merge_tie.py`, `service/merge_progress.py`'s `_merge_progress_tick`, which rides on the minute anchor pass). The hub appends one line to `<state>/merges.jsonl` for every pull request it sees merge (`Hub.emit`, before any lane a notice takes, so the routine lines of the fleet's own repository and a direct anchor's are covered), from the read it already makes, with the item ids the pull request's body names as plain words (`board#N`, a temporary id, a legacy `gNN` id or an item link, read as a session's message is: code, quotes and glued ids are blanked): no GitHub read is added. The pass reads that file from a byte offset (`<state>/merge-progress.json`) and, on every pass, skips a malformed line (the offset moves past it: a line that is not JSON, or is nested too deep to parse, is dropped by `merge_log.read` without a log line; so is a line that parses but is not an object with a repository and a number (`{}`, `[1]`, a number of 0, an empty repository); a line that has both but is of the wrong shape (a repository that is not text or `owner/repo`, or longer than 140 characters; a number below 1, above a billion or too large to hold; a time that is not finite; the writers apply the same two caps, so a repository longer than 140 characters or a number above a billion in an anchor or a link writes no line at all, and the digit runs of the patterns that read them are bounded to match) is logged by the pass as its exception class, the first 80 characters of its message and a bounded look at it (at most 80 characters), never the whole line; a ref that is not a string is left out of its line, which is kept) and a merge older than six hours, so the backlog of a day of downtime records nothing and ties each merge to the open items it names: (a) an anchor scoped to the item names it (a project-wide anchor names no item, or every merge would move every item's clock), (b) the pull request's body names the item (in this public repository this rule cannot fire: a public pull request's body may not carry a board id, so the item-scoped anchor of (a) is the case that works), (c) the item's own words name it (its description, its steps, the status tag of each open step and the lines of its `next`: a session often writes "PR 136 released; PR 137 in review" on a tag before any step text says it), by its URL, or by its number (`#n`, `PR n`) when the item has no URL for it and the pull request is in this repository or one the item has a pull request anchored in. It stores the key in the item's `metadata.merged_seen` (the last 20) through a save of the server's own (activity kind `event`, a History line saying why), which is what the last-activity record and the activity clock take; a key the item holds is not saved again, and a closed item, one the board shows waiting or held and one in the owner's lane are left alone (they are not on this ladder, and a stray mention must not reset their quiet-time clock). A bare number ties only an item whose project page holds an anchor in that repository, or that has a pull request of it anchored to it (an item that meant another repository's number is still tied: a limit); a full pull request URL ties any item. Only merges the hub sees are logged: a pull request with no anchor, which the owner's GitHub account is not notified about either, is not seen. A pass whose offset is past the end of the file (replaced or shrunk) reads from the start, and an item that cannot be read or saved is logged and skipped, the offset still stored. `merged_seen` is a list of its own, not `released_told`: an entry there tells the mover and settles a step, and a merge that settles nothing must not stop the settle path from telling the mover later. A status line (`work`), a note, a reply, a message, a confirm, a new or reworded step and a description edit do not make the item moved: the last-activity record, the activity clock and the hourly audit line read them under their own rules. A save that is no one's write about the work (a migration, an audit, the server's own bookkeeping) counts only as a status or phase change (a wake, a close), so renaming a session in every item's mover moves nothing. A config file that still carries a `[ladder]` `main_hours` or `silence` line (the old hand-up's interval, and a switch the ladder no longer has) loads as it is: nothing reads either, and nothing warns about them; the lines can be deleted.

**The hand-off record follows the mover** (`handoff.follow`, `handoff_follow` in `stackshot/service/handoff.py`, called by the save (`stackshot/service/writes.py`) on every save). An item has one open hand-off record (`metadata.handoff`), and it never names someone but the item's effective mover: a session's write hands over through `handoff.apply` as before; any other save ends a record that names a mover the item left (it goes to `handoff_history` as "handed on, not taken", or "the item no longer has a mover"), and a save of the server's own that changes the mover to a session (a wake that makes the post-wake mover the mover, an event wake, the stall pass, a release of `after`) records the hand-off to the new mover, from the server, marked `no_clock`: **the 10-minute take clock still starts only on a session's hand-off**, never on a server-made record, and the timing of a woken mover stays with the stall pass, which leaves a busy pane alone. A taken record to the same name does not count as already naming the mover: a wake that hands the item back to a session that took it before makes a new record (the taken one goes to the history as "handed on"). The record is marked delivered only when a notice actually reaches the mover: a record to a front agent, one whose wake notice is held, and one whose notice goes to a session in needs other than the mover stay undelivered. The owner's answer, a script's save and a hand-back out of the owner's state end a stale record and make none; a record that carries a recovery request (the ladder's last rung) of an open item is left, unless a save of the server's own moves the item on to another session: that ends it as "handed on" and records the new mover (so the stall pass is not silent for it); the open record of a closed item is ended. Delivery is recorded on every notice path: the message tool, the router's push, the keeper's page-owed batch and the anchors prompt mark the open record of an item the text carries the notice link of to that session, and the message tool one the text cites (`handoff_told_text` in `stackshot/service/handoff.py`; a batch that only cites another item in a subject marks nothing for it), so a lost notice can be told from a fast take. Records the older code left are repaired by a pass in the server's start (`handoff_repair_pass` in `stackshot/service/handoff.py`, after the mover migrations and before the wake pass and any thread; idempotent, one log line with the count): it ends each open record that names someone but the mover and makes nothing new. `stackshot/tools/handoff_repair.py --store <copy of the store>` is the rehearsal (a dry run unless `--apply`); `--live` is a read-only dry run, and `--live --apply` is refused while the user unit `stackshot.service` is active.

**A hand-off is taken only by work started** (`handoff.started`, `handoff.touch`, called by the save (`stackshot/service/writes.py`) through `handoff.apply`). The mover's write takes its open hand-off only when the write shows work begun: a step marked done (the checklist's own mark), a step status (`update work={…}`) new or moved to `in progress` or `done`, or the item closed. An anchor scoped to the item added since the hand-off counts through `plan` as before. A note, a confirm, a reword of `next` or the description, a queue or wait line, a hold or wake, a dropped or new step and a timeline line do not, so they leave the 10-minute clock and its reminders running; the sentence of a note is never read, only the marks. The hand-off notices tell the mover so.

**A background agent that does not take a hand-off is reminded first** (with `[ladder] enabled` off only: on the one ladder there is no separate reminder, see above) (`handoff.plan`, `handoff.remind`, `handoff_exec` in `stackshot/service/handoff.py`). When a hand-off to a background agent is due and not taken (delivered and `[model] handoff_minutes` old; for such an agent a turn that ended with no write does not hurry it, the clock alone does), the first step is one reminder to that agent's own session, through the normal push: the item was handed over, no work on it has started, start its subagent alongside the current work. The recipient is checked fail closed (`handoff_reminder_target` in `stackshot/service/handoff.py`): the name must resolve to a live session that the role map lists with a background role and not retired, so a front agent, a page's name-line session, an unknown name, a keeper entry, or an unreadable role map gets no reminder and the ladder is what it was. The record gets `reminded_at`, its delivery is forgotten and the clock restarts from the reminder's own push result (delivered, or queued plus the inbox grace); a reminder whose push fails twice goes down the ladder. After a reminder only the clock counts (not the turn-end rule): when the item is still not taken after another `handoff_minutes`, section 5 goes on as before (the project's builder, the cold call, the sender, then the recovery request to the fleet's builder). Several reminders due in one pass for one agent go in one message. A new hand-off of the same item is a new record and is reminded again. An anchor scoped to the item and added at or after the hand-off counts as taken, for every mover (a pull request in flight is a build started; an older anchor says nothing about this hand-off): such an item is neither reminded nor moved on; the anchors are read once per pass and only for an item that would act. A `no_clock` record (one the server made) and a front agent stay without a clock.

**The last-activity record** (`stackshot/model/last_activity.py`, `stackshot/anchors/event_log.py`, `stackshot/service/writes.py`'s last-activity stamp, `service/event_activity.py`'s `_event_activity_tick`; `tests/last_activity_scenario.py`). The rule it prepares: no item an agent moves goes more than an hour without visible activity. Part A records it and shows it: the home page's On agent rows and the item page draw the time since it and what it was (see the row bullet in [board-ui.md](board-ui.md)). No flag guards it and no notice or clock changes: the `activity` clock is exactly as it was (there is no `progress` clock any more; `model/progress.py` only says what counts as the item having moved). Each open item can carry `metadata.last_activity = {"at": epoch seconds, "kind": ..., "what": "short words"}`, the newest visible activity and what it was. **One definition of activity**, in `last_activity.py`: a save that moved the item's progress (`progress.moved`, the same test: a step marked done or dropped, a state change, a pull request recorded as merged, the item created), and an event on a pull request tied to the item (a CI result, failed or passing on a new head, whatever the head before it was; a comment by a person, a review, a merge, a new head commit). Each is a signal of a named kind: `step_done`, `step_dropped`, `state_change`, `pr_merged`, `ci_result`, `review`, `comment`, `commit`, `audit` (a hourly audit line that verified something, `audit/hourly.py` `stamp_signal`, see *The hourly audit line*; the words are `audit verified` and the line's phrases) and `update` (a mover's own status write whose text differs from the previous status text; the words are that text; see *The hourly audit line*). **Not activity:** a status line that repeats the previous text or is written by anyone but the item's mover, a reply or a "no change" answer, a note, a message, a confirm, a new or reworded step, a description edit, and what the server writes about the item itself (a History line of the ladder or an audit pass, the ask, the step made for the owner): none moves the record. **Newest wins**: a signal replaces the record only when strictly later, a signal that is torn (no time, no words, an unknown kind, a time that is not a number: a bool or a string is none, whatever it spells) is skipped, a time ahead of the pass reads as the time of the pass, and a stored record dated after the pass is ignored (it would otherwise hide every later signal). **How a page reads it**: `read(item, now)`, `at` and `age_s` treat a stored record dated more than an hour ahead of the reader's clock (`SKEW_S`, the window an event's own time is allowed) as no record, never as "just now" (a clock that jumped is not a time that happened); one ahead by less is a skew of clocks and reads as just now. The band of an age is amber from 45 minutes up to and including an hour and red only past an hour (`band`: strictly more than `BAND_BAD_S`). **Saves** stamp it in `writes.save`, at the time of the save (a mover's new status text, kind `update`, is stamped there too: `last_activity.update_signals` finds it and `writes._stamp_last_activity` adds it when the writer is the item's mover; at the same time a step or state signal of the save wins over it). **Events on a tied pull request** come from the hub: `Hub.emit`, the funnel the merge log already uses, appends one line to `<state>/events.jsonl` for each kind of activity an event is (`{"ts", "repo", "n", "kind", "refs"}`; the merge log and its readers are unchanged, and a burst of types is a line for each kind). A comment or review whose every author is a bot (a login ending in `[bot]`, or an account the comment's own payload types as a bot, which costs no extra read) is left out; a CI event on a repository's notifications with no pull request is left out. `service/event_activity.py`'s `_event_activity_tick`, on the minute anchor pass beside the merge pass, reads the file from a byte offset (`<state>/event-activity.json`), skips a line that is malformed (logged in a bounded line), older than a day or stamped more than an hour ahead, and ties each line to open items with the same rules as a merge (`merge_tie` through `_merge_tied`: an anchor scoped to the item, the pull request's body naming it, the item's own words; a project-wide anchor ties nothing, and a closed, waiting or held item is left alone), except that only a merge ties through the body. Many lines for one item are one save, the newest of them. It saves an item only when the record changes, and only after reading the item again under the lock (one closed, held or begun to wait since the tie is left alone), as the server's own bookkeeping (activity kind `bookkeeping`, no History line), so the `activity` clock, `updated` and the board are unmoved. An item that cannot be read or saved is logged and skipped, the offset is stored, nothing raises out of the pass, and a read-only standby copy or a held board runs nothing. **Only a merge ties through the pull request's body** (the rule the merge log has always had). A comment, a review or a CI result ties only through an anchor scoped to the item or the item's own words, because in a public repository anyone can open a pull request whose body names an item and comment on it, and that must not stamp the item; a line of the log that carries board ids for any other kind has them dropped when it is read. A comment on a plain issue anchor is worded `comment on #n`, since the hub does not say whether the thread is a pull request. **Who counts** (one filter, `event_log.lines_for`, where an event becomes a line): in a public repository anyone can comment, and a fork's pull request runs CI without the repository's say, so an event that is not a merge is activity only when its source vouches for it. A comment or review counts only when its author's `author_association` in the payload (no extra read) is `OWNER`, `MEMBER` or `COLLABORATOR`; `CONTRIBUTOR`, `NONE`, `FIRST_TIMER`, `FIRST_TIME_CONTRIBUTOR`, `MANNEQUIN`, any other value and a missing one do not. A CI result counts only when the pull request's head repository is its base repository (`head.repo.full_name` equals `base.repo.full_name` in the pull request read the hub already makes), so a fork's branch, a deleted fork and a payload that does not say do not count. The receiver (`github.py`) sets `Event.vouched`, the kinds of the event it vouches for (a burst of comment and review is judged per kind; a thread of the repository's notifications vouches for a kind when any of its authors qualifies); the log writes no line for a comment, review or CI result that is not vouched for, whoever the item and whatever the tie. A merge is not filtered here: it keeps the merge log's rule and the body tie. The notice a session receives is not changed by any of this. **When it happened:** a line is written at the event's own time (`Event.ts`) when it can be read and lies within a day before and an hour after the hub's clock, so a backlog read after a restart or downtime stamps the time it happened at, not now; an event with no time, or one that cannot be read, is written at the hub's clock; an event older than a day or more than an hour ahead writes no line (the window the pass has always applied to a line it reads; a time far ahead is a torn clock). A naive time is read in the instance's timezone, as the hub writes its own. **Which time the receiver gives:** a comment or review read from a thread of the repository's notifications is stamped at the newest `created_at` or `submitted_at` among the items the repository's own side wrote (the vouched ones), not at the thread's `updated_at`, which a stranger's later comment in the same batch also moves (an owner-side comment at 05:44 and a stranger's at 07:42 stamp 05:44); a batch with no vouched item, and a merge, keep the thread's time. A CI result is stamped at the newest `completed_at` of the check runs it was read from (the moment the last one finished), when that lies inside the same window (a day before, an hour after the hub's clock); a result with no `completed_at`, or one outside the window, is stamped at the hub's clock as before, so a result seen after downtime is not stamped as now. The History's confirm test ignores `metadata.last_activity` (as it does `phase` and `waits_on`), so a confirm and the pass's stamp saved in one publish window still show the `confirmed` line. **A commit** (`commit on PR n`): GitHub sends no push notification, so the receiver finds it in the pull request read it already makes for every anchored pull request. It keeps the head sha it last saw per pull request, and when it last looked at the pull request, in its saved CI state; when the sha differs it logs a `pr_commit` event. Seen live (the last look was within ten minutes), the event is stamped at the time the hub saw it and no request is added: the push is what happened now, whenever the commit was made, so a commit made at 10:00 and pushed at 11:30 shows as just now, a force-push of an old commit does too, and a committer's wrong clock does not matter. Seen after the hub was away (the last look is older than ten minutes, or unknown, as after a restart or a stretch of downtime), the commit is read once (the only extra request, and only then) and stamped at its committer date, never later than now and never older than the event log's day-long window; a read that fails (the hourly cap, a refusal, a date that cannot be read) stamps the time seen instead, so the signal is not lost. A first sight of a pull request only keeps the sha, an unchanged sha and a 304 record nothing, and a pull request from a fork (or a deleted fork) is neither read nor recorded: only the repository's own branch counts, as for CI. Any new head counts, a merge of main pushed under the builder's account included, so a pull request that only takes in main can reset an idle agent's clock. A read that fails after a long outage (no committer date to use) stamps the time seen, which is later than the commit was made. A commit event is logged for this record and told to no session, on the direct lane too. The record keeps the newest, so a stamp older than it never moves it back. **The gaps:** Three limits are accepted: a pull request whose first read after a restart answers 304 has no `own_branch` mark (the payload that sets it is not sent), so its CI results are not vouched for until the payload changes; a merge line older than a day is dropped as last-activity (the window above applies to every kind); and a pull request from another repository of the same organization gets no CI credit, since only a head branch in the repository itself counts as the repository's own side. A review is seen only when the hub reads it: for a pull request with its own anchor the hub reads the issue comments, CI and the merge, and a repository's notification thread is skipped for it, so reviews arrive mostly for pull requests reached through a repository-root anchor. Comments made under the hub's own account are never emitted (the hub drops them upstream), so they are never seen here. No GitHub read is added for this; the audit's later "verified" line covers it by reading the pull request itself. The words of a signal are one line of at most 80 characters, control characters turned to spaces, whoever writes them. **A late anchor still counts a merge from the last day** (`anchorhub/github.py` `late_merge`): when the hub first reads an anchored pull request that merged within the last 24 hours (at most 120 s ahead of the hub's clock, which allows for GitHub's clock; further ahead is a torn time and writes nothing), it writes the merge line instead of seeding silently, so an anchor added after the merge still credits the item it is scoped to. The line goes to the event log and the merge log, both stamped at the time the pull request merged (not when the hub found it), so the last-activity record takes the merge from the last day while the merge pass, which skips a merge older than six hours, records only a recent one. The body's ids are not read on this path (a body can be edited long after the merge): the anchor's own scope is the tie. A pull request closed unmerged, still open or merged longer ago is a silent seed, a line that could not be written leaves the anchor unseeded so the next pass tries again (at most three tries, then the anchor is seeded without the line and a warning says so), writing only the log that lacks the line (a merge log write that succeeded is not repeated when the event log's failed), the sessions of the anchor get no notice for the line, and an item-scoped anchor added after the line was logged gets no credit for it (the passes tie a line once, when they read it).
**The backfill** (`stackshot/model/last_activity_pass.py`, `stackshot/tools/last_activity_backfill.py`, the ops `lastact` and `unlastact` of `POST /client/migrate`; `tests/last_activity_backfill_scenario.py`). An open item nobody has touched since the record shipped has none, so its On agent row has nothing to show. The tool fills `metadata.last_activity` for the open items that have no record that reads, from what is recorded about them, and writes that key and nothing else (no clock, mover, needs, state, step or History line, nobody told). **Where the time comes from:** the item's own History, the store's git versions of its file (the path alone: never `git log --follow`, whose copy detection takes the file of another, similar item for a rename), replayed oldest first through the function a save goes through (`last_activity.save_signals`, which asks `progress.moved`); whether a version was someone's write about the work is read from the item's own `activity` clock, which a real write moves and the server's bookkeeping leaves; the first version is the item being created; a version of the file on disk that git has not got yet is the last one. Then the hub's merge log and event log, tied to the item as the live pass ties them (`service/merge_progress.py`'s `_merge_tied`), each line at the time the hub saw it, a line stamped more than an hour ahead of the clock dropped as the live pass drops it. The record is the newest of them, newest wins. **The refused class:** an item whose History cannot be read (the store outside git, git not answering, a version missing from the repository or not JSON; an item file that git saw deleted and then added back is such an item, since no version of it stands at the deleting commit) or holds a version stamped more than an hour ahead of the clock is refused, named in the output with the reason, and left as it is; the time is not guessed. A record is never written dated after the clock (a time inside the skew is written as now). An item that already has a record that reads is left alone; a torn one, or one dated further ahead than the skew, counts as none and is replaced, its old value kept in the undo entry. **Modes**, as `tools/until_migrate.py` (whose run-directory lock, undo-file reading, unfinished-pass check and pruning it uses): the dry run is the default (the store copied into a private folder, its git read from the live store read only, the whole pass run on the copy twice, one block per item, the refused class and the totals); `--apply --sender <session>` asks the server for the plan (each item with the time and kind it would get; the apply writes nothing and says so ("the items to fill, the times they would get or the refused ones differ from the dry run in --plan", or "… changed while the plan was being read"; exit 1) when an item, a time, a kind or a refused item differs from the dry run's `--plan` file or from the plan read a moment before, a time that is just "now" excepted, unless `--allow-changed-plan` is passed; the time written is worked out once more under the item lock, and the undo file records what was written), prints the refused class, writes a backup of every touched file byte for byte and the undo file before the first write, then writes in batches under the item lock with a sha256 check (an item written meanwhile is `moved` and its write stands); `--undo <file> --sender <session>` puts back only a record that still is what the pass wrote (the key goes when it had none; a later write is `kept`), and a second undo does nothing. The route needs `[model] migration = true` and the sender in `[model] migration_senders`. **The hub's logs:** when the merge log or the event log cannot be read, or the events cannot be tied to the items (the anchors that tie them cannot be read included), an item would be filled from its History alone and a newer event left out; the dry run prints a warning in its summary and `--apply` refuses (nothing written) until they read. A bool, a numeric string, NaN or infinity as a stored time or clock is no time here, as in the record's own reader. Exit codes: 0 `--apply` wrote every planned item and none is left as it is, or there was nothing to fill and none is left as it is; the dry run finished and its second pass on the copy would change nothing (it exits 0 whether or not it lists items to fill or refused ones, so read its output); `--undo` put every entry back or found it as it should be. 1 a failure (the plan could not be made, a batch was refused or got no answer, an item could not be written, the plan differs from the one shown, the hub's logs or the anchors cannot be read, another run holds the run directory, the undo file cannot be used or an entry of it was refused, or the dry run could not make its copy or its second pass would still change something). 3 `--apply` only, not a failure: items are left as they are for a person to look at (refused, kept because their History holds no activity, written by someone else meanwhile, closed between the plan and the write), also when there was nothing to fill.

**The hourly audit line** (`stackshot/audit/hourly.py`, `audit_ticks._hourly_tick`, called from the ten-minute audit tick; `[audit] hourly_line`, on by default; it needs `[audit] enabled`, script mode). An item an agent moves is never to sit an hour with nothing on it. The mover writes the update, and the audit's line is owed after 45 minutes without activity, so it lands inside the hour; when it has nothing new to add, the audit checks that the item is moving and writes the line itself: one History line, `Audit 14:05: verified the mover's pane is in a turn, CI passing on PR 12` or `Audit 14:05: idle, nothing verified`, the time in the instance's zone. It is an entry of its own log, `metadata.hourly_audit.log`, kept apart from the ladder's `metadata.stall.log` so it neither crowds out the ladder's entries nor reads as a step of the stall pass (`get` prints the newest as `audit:`), with kind `audit`, `audit_idle` or `audit_unknown` (see *Unknown is not idle* below); the History shows it and a later part can read which items are idle. Nobody is messaged, a front agent included, and the save is the server's own bookkeeping: it does not move the activity clock, so the line cannot make the item look written. **A line that verified something is the item's last activity too** (`hourly.stamp` over `hourly.stamp_signal`, applied by `audit_ticks._hourly_tick` before the save): the item description promises the hourly update, and a verified line is that update, so it is stamped in `metadata.last_activity` (kind `audit`, the words `audit verified …`, the live phrases first, then the recorded ones that still fit in the 80 characters of one line) at the line's time, and the On agent row reads its time and words instead of "idle over 1 h" and an older event. Newest wins as for every signal: a real event recorded at the same time or later stays, and an older line never replaces a newer real one. The record never goes backwards for an audit line either: a stored record dated ahead of the line's time by less than `last_activity.SKEW_S` (a clock stepped back, an event the hub dated just ahead) stays, where the record's own rule alone would read it as not yet happened and replace it with the earlier time; one dated further ahead is no record and is replaced, as for every signal. A line that says `idle, nothing verified` is no update and stamps nothing (the item is marked idle for the hand-over below), and neither does a line that rests on recorded events alone (signal 3 below): the event is in the record already, at its own time. The audit's save is still the server's own bookkeeping and moves only `last_activity`, never the `activity` clock the hourly line and the idle hand-over read, so the stamp does not delay the next line or hide an idle item from the idle hand-over. **A mover's own status write is the hourly update too** (`last_activity.update_signals`, stamped by `writes._stamp_last_activity`): when the item's mover (the model's mover; a session's name, an alias and its id are one) writes the status line of its step (the update tool's `work`) with text different from that step's previous status text, case and spacing aside, the save stamps `metadata.last_activity` with kind `update` and the text as its words, at the save's time, through the same record and the same newest-wins rule as the audit's line, so the On agent row reads that time and text and its age restarts. No second clock: the hourly line still reads the `activity` clock, which every real write by the mover already moves, so an item whose mover wrote new text is not owed a line for another hour. The first status on a step that already existed counts, even when the session used that text on an earlier stage (there is no earlier text on this step). **Not an update:** the same text again (a "no change" reply), a status moved to another state with its words unchanged, a cleared one, a step reworded with a status its session already had, a write by anyone but the mover (a front agent relaying, another session, the owner's answer on the board, the audit's writer, the server's own save), a write filed as a message or an anchor event, and a save of a closed item. The mover test runs only when a save carries new status text, and a failure in it costs only the update, never the step, state or merge stamp of the same save. The audit's line is unchanged: it is still written when nothing new came, and a verified one still stamps `audit`; of the two, the later time is the record. The backfill (above) leaves an item that carries an audit record alone, as it does any item that has a record, and the audit's save is no signal in the History it replays. A line that rests on live states alone (signals 1 and 2) says so in its words, `Audit 14:05: verified the mover's pane is in a turn (live state only, nothing recorded on the item)`; one that rests on a recorded event does not.

*When.* An item is owed a line when it is open and on an agent as `silence.reading` reads it (a session moves it, the state is not the owner's, the board does not show it waiting), has had no activity for 45 minutes (`silence.clock`, the same clock: a bare confirm, a "no change" reply and the audit's own lines do not move it), and has no audit line lately (a line dated more than an hour ahead of the clock is a torn entry and is not counted): the next line is owed 45 minutes after the last for the first 24 hours of quiet (the first line is owed after the same 45 minutes without activity, so it lands inside the hour), then one every 6 hours, so a week of quiet is about fifty lines, not 168. A hold, a parked item and any stored wait (a dated wake, an item it waits after, a CI run, a relay, an outside party) are skipped, an untaken hand-off to a back agent too (the hand-off audit's), one to a front agent is not, and otherwise a front agent's item is treated like any other. A second pass within those 45 minutes writes nothing, and a clock that goes backwards only delays the next line. **Why 45 minutes and not an hour (`hourly.FAST_GAP`).** A verified line is the item's last activity, and the On agent row turns red ("idle over 1 h") strictly past an hour since it. The tick runs every ten minutes, in the first paced round after each tenth minute (`runner.TEN_PACE`, rounds a minute apart), so a line owed after an hour would land on the sixth tick, an hour plus the tick's jitter and a late round after the last one, and the row would read red for a minute or two some hours. A line owed after 45 minutes lands on the fifth tick, 50 minutes after the last on an exact grid and at most about 51 minutes with a round up to a minute late (a round that skips its tick altogether pushes it to about an hour, and the row can then flash), so the row of an item that keeps verifying never reads red between two lines (`tests/audit_hourly_scenario.py` section 18 reads the row at the worst landing time through `act_parts` and `band`). The cost is one line every 50 minutes in the first day (about 27 instead of 23). In the slow stretch the gap is 6 hours less five minutes of slack (a line is owed 5 hours 55 minutes after the last one, so jitter never pushes it a whole tick on); the row is red between those lines whatever the gap. **The first line is owed after the same 45 minutes (`hourly.EVERY`, the same figure as `hourly.FAST_GAP`).** It used to wait for a full hour without activity, so the row of an item whose last event was its real activity read red for up to one tick before the first line landed; owed after 45 minutes, it lands on the fifth tick after the last activity, 45 to 55 minutes on, inside the hour. A verified first line is the item's last activity as any other line is. What stays at an hour (`hourly.HOUR`): the window in which a tied pull request's event verifies an item, the age past which a log entry dated ahead of the clock is torn, and the idle hand-over below, which waits for a full hour without activity before it hands an item on, so an idle line written at 45 minutes hands nothing on sooner than it did.

*What is verified.* Recorded data only; nothing is read from GitHub. (1) The mover's pane is in a turn: the CLI's registry on the server's own box shows it `busy` (`handoff_status` in `stackshot/service/handoff.py`, the stall pass's read; a session that box does not run shows nothing, and a pane showing `shell` or `idle` is not a turn). A busy pane says the session works, not which item it works on, so it verifies an item only when that is the mover's one item on an agent (no other open item of the mover is on an agent as the board shows it, the `alone` parameter of `hourly.verified`, which `hourly.due` fills in); a mover with several items has none verified by its pane. (2) A subagent is running ON THIS ITEM (`stackshot/audit/subagent_tie.py`, `audit_ticks._mover_subagents`). A step status in progress is no proof: the mover wrote it, and one mover can carry it on several items while one subagent runs (a mover with three items each marked in progress and one subagent running had all three read "a subagent is running on it"). The audit reads the subagent itself, from the transcript Claude Code keeps on the server's box, in the roots `[said] transcripts` names (the same ones the owner's words are checked against): beside the session's transcript, `<session uuid>/subagents/agent-<id>.meta.json` (its description, and `finished: true` once it ended) and `agent-<id>.jsonl` (the brief the mover gave it is the first line). A subagent is running when it has no `finished` flag and its transcript was written within 90 minutes, and only for a mover whose pane is in a turn now, which the server reads from the registry row (`sessionId`, `status`). An unfinished subagent whose transcript is older than 90 minutes but no older than 6 hours (`subagent_tie.QUIET_CAP_S`) is listed as running but quiet: a builder waiting on a long CI or suite run writes nothing for a while. It ties like any other, and a quiet one tied to no item leaves the mover's untied items unknown; past 6 hours it is dropped (a pane that was recycled or killed leaves no flag, so a subagent stops counting after that), and a transcript dated more than five minutes ahead of the clock is dropped too. **A `finished` flag is not proof that a subagent is done.** Claude Code writes `finished: true` into the meta at the end of every turn of a subagent, also one that ends waiting for a background task of its own (a Bash in the background, a Monitor), and drops it only when that task's notice or a SendMessage wakes the subagent; a reviewer can end its turn a dozen times in ten hours while it works. A subagent flagged `finished` therefore still counts as running, with the same entry and the same `quiet` rule, when either (a) its own transcript holds a background Bash or Monitor with no end and was written within 90 minutes (`subagent_tie.PARKED_S`), and no notice of that task reached the session's transcript, or (b) the session's transcript holds a resume of it (a SendMessage result carrying `resumedAgentId`, `revivedAgentId` on Claude Code 2.1.323, as a top-level key of the `toolUseResult` of a user record: the same words quoted in a tool output or a message are none) dated no earlier than the meta's last write (its mtime, one second of slack): the flag is about to be dropped, or was not yet. A task starts only with a tool result that opens with the start text (`Command running in background with ID: …`, `Command was moved to the background (ID: …)`, the same after a timeout, `Monitor started (task …`): a transcript that another subagent printed or searched, and quotes the text, starts none. A task ends with a notice carrying a `<status>` (completed, failed, stopped), a Monitor's expiry or end event, or a TaskStop; a Monitor's per-event notice ends nothing. The end notice of a finished subagent's task is often written only to the session's transcript (a queue record, an attachment or a user message), so that transcript is searched for it too. A Monitor also ends when its start plus its lifetime (`expires in 10m`, `15m 30s`, `45s`, `timeout 900000ms`; one second of slack) is past and its transcript was not written since; a background Bash has no lifetime, so only the 90 minutes bound it. A subagent with no flag whose last row is `[Request interrupted by user]` (or `… for tool use]`) was stopped: it is not running, not even quiet, unless the session's transcript holds a resume of it dated no earlier than that last row (one second of slack). The session's transcript is read only for a finished or an interrupted subagent, once for each read of a mover's subagents and only its last 8 MB, and nothing is cached; a failure to read it, or the subagent's own transcript, reads as not parked, not resumed and no notice (never as unreadable). A subagent that ended for good with a task that never reported reads as parked for up to 90 minutes: the smaller error, since the audit then reads unknown, not idle. It is tied to an item when its description names the item, and only when the description names none of the mover's items does its brief decide (a brief that says "a follow-up of item X" must not tie the subagent to X when its description says what it works on), by the item (its shown id, whole: item 12 is not item 123) or a pull request anchored to it (`released_live.released_anchors` (`stackshot/service/released_live.py`): by its URL, as `owner/repo#n`, or `PR n` / `#n` in the repository the anchor is in; the same number in another repository, or another number, ties nothing: a text that gives the number's pull request by URL in another repository is that repository's, and a number written alone ties neither of two items of the mover anchored to the same number in two repositories, which only the URL or the `owner/repo#n` form tells apart). **Unknown is not idle.** With one subagent running and tied to one item, only that item reads verified for it, and the mover's other items read idle (the next paragraph hands them on) unless something else verifies them. But a real brief often names neither an item nor an anchored pull request (a build subagent starts before its pull request exists; "Build part D" names nothing). When the mover has a running subagent that is tied to none of its open items, the audit cannot tell which item it builds, so it does not call the mover's untied items idle: the line reads `Audit 14:05: a subagent of the mover is running, not tied to an item, nothing verified`, its log entry's kind is `audit_unknown` (a third kind beside `audit` and `audit_idle`, which `hourly.last_line` counts as a line for the cadence), it stamps nothing (the row stays as it is) and the hand-over below, which reads `audit_idle` alone, does not move the item. This was the smaller, safer choice: the alternative, reading every untied item idle, would hand an item to a second builder while the first subagent is still building it. When every running subagent is tied to some item of the mover's (including one on hold), an untied item is idle as built. Anything the audit cannot read is unknown the same way, never idle: a pane in a turn whose transcript the server's box does not hold or whose registry row names no session, a session that is registered on the server's box but is no interactive pane (a headless session) or whose registry status the server does not know, a subagents folder that cannot be listed, a subagent whose files cannot be read (listed as running with no words; a first line nested past the parser's depth, a `RecursionError`, reads as no brief), and a subagent view that raises (`Audit 14:05: the mover's subagents could not be read, nothing verified`). A mover with no registry row of a live process on this box is looked up in the fleet's heartbeat sessions index (by name or id): a session it holds running is on another machine, whose subagents this server cannot read, so its items read unknown, never idle (a back agent on another machine must not be handed on to a second builder while it works); a session the heartbeat marks gone or does not hold at all, in an index that was read whole, has no row anywhere and nothing is claimed for it: its items read idle, as before, which is what the orphan hand-over and the idle hand-over are right to act on. A heartbeat index that cannot be read reads unknown too, and so does one that is empty or partial (a machine's `sessions.json` that is absent or torn: `fleet.sessions_unreadable`; `fleet.read` gives {} for it, so an index built from it alone would otherwise say that every session of that machine is gone): no row in such an index is no proof that the session is gone. A registered pane that is idle or showing a shell has none running either (a subagent keeps its pane busy). The result of a failed read is kept for the pass, so the transcript lookup is not repeated for every item of the mover and again under the item lock. A front-agent test that raises reads as front, and so does a role map that cannot be read (the project registry reads {} when its file is unreadable; the hourly line asks `Env.is_front_or_unread`, `front_keeper(unread_front=True)` of `stackshot/service/telling.py`, where the other passes keep `is_front`, which reads that mover as no front agent): an unreadable registry leaves the item where it is, never reads its mover as a builder. Known limit, pinned by a test: only the mover's own items are candidates for the tie, so a description that names an item of another mover does not stop the brief from tying the subagent to one of this mover's items (a false verified, never a false idle); a description naming two of the mover's items ties it to both. A **front agent's** busy pane still verifies each of its items (the old phrase): its items are never handed on, and a stream of "idle, nothing verified" lines for a session the owner talks to would say nothing true. The 90-minute window and the match of a bare `#n` to a pull request of the item's own repository are as before. `silence.subagent_running` (the step status) is still what holds the stall ladder's rungs and the idle hand-over back; only the audit's line does not read it. (3) A pull request tied to the item had a CI result, a review, a comment by a person, a merge or a new head commit in the last hour (`hourly.PR_KINDS`), as `metadata.last_activity` holds it: the hub's receiver notices the new head and records it as a `commit`. When none holds, the line says idle and the item is only marked so (its log entry's kind, `hourly.idle_marked`); handing it on to a free builder is the next paragraph.

**Handing an idle item on** (`stackshot/audit/hand_idle.py`, `audit_ticks._hand_idle_tick`, run from the ten-minute audit tick right after the hourly line; `[audit] hand_idle`, on by default; it needs `[audit] hourly_line`). An hourly update is mandatory: with nothing verified the item is idle, and it goes to a free builder and the project's -main agent is told, never the owner. The pass reads the line the hourly audit left: an item is handed on when its newest line is `idle, nothing verified` (`hourly.idle_marked`) and not older than 6 hours 15 minutes (an older line means the hourly pass is off, or the item left the agent since), nothing has moved the item since that line and it has had no activity for a full hour (`hourly.HOUR`: the first line is owed after 45 minutes, so an idle line can be younger than an hour of silence) (`silence.clock`: a step done, a state change, the mover's own write, an anchor event or the owner's answer all count, a bare confirm does not), it is open and on an agent as the board shows it, not held, its hand-off if it has one was taken (an untaken hand-off is the hand-off audit's), and its mover is not a front agent (an item a front agent moves is the owner's work and stays). *Which builder.* The first free one of the item's own project's background agents, best first (the project's builder before the rest), and never a background agent of another project, however idle: a project's work is built, reviewed and released by its own builder, so an item handed to an unrelated project's builder would have to be handed back by hand. A builder is free when its pane is not in a turn on this box (`handoff_status` in `stackshot/service/handoff.py`, the read the stall pass and the hourly line use; a pane that box does not run reads as not in a turn) and it is the mover of no open item that is on an agent (an untaken hand-off to it counts: it is about to take that item; an item on hold or behind a wait does not); a name known to have no pane, or whose pane cannot be read, is not free, and the item's own mover is never picked. *The move* is the minute hand-off pass's own write (`handoff_exec` → `handoff_write_move`, the path of the audit's orphan hand-over): the builder heads `needs`, the stored mover follows, the hand-off record is made from the server (so the hand-off audit clocks it as any other) and the builder is told by the hand-off notice. One History line says why and names the mover it left, `handed to team-back: no activity for an hour, nothing verified (it was with home-peer)`, and `metadata.hand_idle` ({`handed_at`, `from`, `to`}) keeps the limits. The project's -main agent gets one message through the notice path the ladder uses for it (the front agent's mark on its first line, tag `stall`) that says what happened and asks nothing; no message goes to the owner, no row is made for him and no step is his. *No builder free.* Nothing moves; one History line says so and -main is told once per item per 24 hours (`hand_idle.none_at`); a project with no -main agent gets the History line alone. A project with no background agent of its own is this case too, and it is how such an item is surfaced: the item stays with its mover, -main is told in the same way (the mover's own work is never silently kept), and the long busy stretch rule below tells -main when the mover's pane stays busy for hours; no other project's builder is looked at. *Limits.* At most 3 items per pass (the next pass goes on with the rest), one per item per 24 hours; an item handed on once and idle again after 24 hours may be handed again, and a builder that took an item in a pass is no longer free for the next. A torn log entry or a torn `hand_idle` stamp (not a number, dated ahead of the clock) is no signal and raises nothing.

**The balancer** (`stackshot/audit/hand_idle.py` `balance_*`, `audit_ticks._balance_tick`; `[audit] balance`, on by default; `[audit] balance_minutes`, 10 by default and never under 1). It needs `[audit] enabled = true` and script mode and `[model] handoff` on, but neither `[audit] hand_idle` nor `[audit] hourly_line`. A builder does not wait an hour for an item that nobody has started. The balancer is its own minute tick, ahead of the hand-off tick, so a move at ten minutes comes before that tick's reminder to the mover (`[model] handoff_minutes`); with no target the hand-off ladder goes on as it always did. An item is moved when it is open, on an agent as the board shows it, not held, its mover is a builder and no front agent, and it waited `balance_minutes` (its hand-off, when its latest one names the mover, was delivered that long ago and `silence.clock` is that old) as either of two kinds. *Not started*: an untaken hand-off to a session (`handoff.awaiting_session`). *Queued*: the queue rule of `model/queued.py` read over `balance_minutes` instead of an hour (`queued.queue(..., window=)`): the mover has another item in hand with activity inside the window and this one has none; the board's own reading stays at an hour, and the balancer reads the queue by itself, so it works whether or not `[model] queued_behind` is on. *Builders only.* A builder is a background agent whose mandate says build, maintain, merge or engineer; an item whose mover is a reviewer or any other session is never balanced, and the candidates are builders alone, and only those of the item's own project (a mandate that says build, maintain, merge or engineer; another project's builder is never a target, because a project's work is built, reviewed and released by its own builder; with no other builder in the project the item stays where it is, silently), less a name with no pane, the item's own mover, every name in the hand-off record's `tried`, and a front agent. *Never an item the mover started*: its hand-off was taken (`taken_at`, in the latest record or in `handoff_history`), a step that opens with its name has a status in progress or done or is marked done, a subagent is running on the item (`silence.subagent_running`), an anchor is scoped to it, or a pull request event (CI result, review, comment, merge, commit) is its last activity. *Which builder.* The one with the fewest open items (the movers of the open items on an agent, `busy_movers`, names merged as one session, and the count follows each move of the pass); a pane in a turn only breaks a tie, an idle one first, never an exclusion. The move must improve the spread, the mover's count including the item: an untaken hand-off moves when `to == 0 or to + 1 < from` (a lone item goes to an empty builder), a queued item only when `to + 1 < from`. *The move* is the same write as the idle hand-over (`handoff_exec` → `handoff_write_move`): the builder heads `needs`, the hand-off record is made from the server and the builder is told by the hand-off notice, and one History line says why and names the mover it left. *The mover it left* is told once, by `tell_woken` with tag `balance` and not by the message tool (which would name it in `needs` again): `Disregard: <item> is now with <builder>. Drop it, stop any work or subagent on it, and write nothing to it. No reply is owed.`; several items of one mover go in one message, a front agent and a pane that is gone are never sent it, and only an item this pass moved is named. The notice is at-most-once: the save comes first, and a crash between the save and the send loses it. *Limits.* `metadata.balance` ({`at`, `from`, `to`, `count`}, apart from `metadata.hand_idle`, which the idle hand-over replaces whole) is written in the save of the move, before anything is sent; at most 3 items per pass, one move per item per 24 hours (an item the idle hand-over moved in the last 24 hours is left alone too; the idle hand-over does not read `metadata.balance`, so an idle line an hour after a balance move can move the item again, which is accepted), two in all: an item at the cap is left to the ladders and -main is told once (`capped_at`). A torn record (a count or time that is no number) is no signal. *No target.* With no usable candidate (the role map holds at least one builder other than the mover and every such builder is dead or gone) the item stays, one History line says so and -main is told once per item per 24 hours (`balance.none_at`), a message that asks nothing; the owner is told nothing. The pass looks again every minute, so a builder that comes back takes the item at once and its move ends the note. With no other builder at all (the mover is the only one), or when the pick is no improvement by the rules above (untaken: `to == 0 or to + 1 < from`; queued: `to + 1 < from`), the item stays and only a log line says so.

**A long busy stretch tells the right agent once** (`stackshot/audit/busy_tell.py`, `audit_ticks._busy_tell_tick`, run from the ten-minute audit tick after the idle hand-over; `[audit] busy_tell`, on by default; `[audit] busy_tell_hours`, 4 by default and never under 1; it needs `[audit] hourly_line`; `tests/audit_busy_tell_scenario.py`). The hourly line can go on for hours saying only that the mover's pane is in a turn, with nothing real happening on the item and nobody told: the idle hand-over is for an item the audit could verify nothing about, and this is for one it could verify only a busy pane about. A line that verified only that (`hourly.pane_only`; its log entry carries `"pane_only": true`) belongs to the stretch, but only when it follows the line before it (the last real activity for the first) within `busy_tell.EXTEND_GAP`, an hour plus the tick's slack (`hourly.HOUR + hourly.SLACK`, 65 minutes); a pane-only line after a longer gap (the slow cadence, a line about every 6 hours after a day of silence, or a stalled server) cannot vouch for the time between and starts a new stretch at its own time instead. **Design choice:** lines more than about an hour apart do not extend a stretch, because an event of the pull request 2 to 6 hours before such a line is invisible to the hourly check (it sees only the last hour), so a stretch of 4 hours is only ever built from lines about an hour apart, up to the tell itself: a background mover's stretch is told only while its newest line is no more than that same gap (`busy_tell.EXTEND_GAP`, 65 minutes) old; a mover silent for over a day with a busy pane is not told by this rule (a mover already told in the first day is not told again either). A line that verified anything else (a subagent, a pull request event of any kind, a new head commit included), nothing (idle) or could not tell (unknown) ends it. The stretch counts from the later of the item's last real activity (`silence.clock`: a step done or added, a state change, the owner's answer, a message, an event on an anchor, a write by the mover; the audit's own lines are none of these, so the pass never resets its own stretch) and the last line that was not pane-only, and needs at least two pane-only lines in it (`busy_tell.MIN_LINES`: one sample is not "busy for 4 hours"), the newest. At `busy_tell_hours` the item's project's -main agent is told **once**: the mover has looked busy for about that long with no other sign of progress on the item, and please look. An item whose newest line is idle is not told of: that is the idle hand-over's. **An item a front agent holds** (the mover is a front agent by the server's own test, as the hourly line reads it; its busy pane verifies its items and the idle hand-over never takes them) with no real activity for `busy_tell_hours` and an audit line written since, whatever the lines said, tells that front agent itself, once; its -main agent is not told about it. The message and the History line say how long it really was, in whole hours and never under `busy_tell_hours` (an item a front agent has held quiet for two days is told as about 48 hours, not as 4); with `busy_tell_hours` above about 5 the message names that threshold, not what the lines show, because the rolled eight-line log shows at most about 6 hours. The first pass after the rule is deployed tells every front agent that holds such an item (quiet for `busy_tell_hours`, an audit line written since its last activity and within the last 6 hours 15 minutes) once, however long it has been quiet, so a burst of messages is expected then: one message per agent, its items listed together, and no item twice. A project with no -main agent logs it (once an hour per item) and tells nobody; the pass looks again at the next tick. The owner is never told. *The message* is the idle hand-over's own form to a front agent: `[for <owner>]` on its first line, through `tell_woken` with the `stall` tag (a kind that asks the agent to act), one message per agent per pass, and one History line says who was told. *The once.* `metadata.busy_tell` ({`at`, `to`, `kind`, `since`}) is written in the save, before anything is sent (at most once: a crash between the save and the send loses the message), so it survives a restart; the item is told of again only when a new stretch starts after `at` (real activity moves the clock, a line that verified something else moves the start). A line dated ahead of now is not read, a `busy_tell` record dated more than an hour ahead of now is no record (the stretch is told again), and a front agent's item whose newest line is older than 6 hours 15 minutes is no news (a background mover's is held to the 65 minutes above). A recorded event newer than the stretch's start that no line has seen (the item's `last_activity`, any kind but the audit's own stamp: a CI result, a review, a comment, a commit, an update) holds the tell back, since the message says there was no pull request event; the next line verifies the event and ends the stretch only when the event is no more than an hour old when that line reads it (`hourly.HOUR`): when a skipped tick makes the gap between two lines 61 to 65 minutes the line is still pane-only, it stamps the audit over the event record, and the hold lifts with the stretch unbroken. The audit log keeps its last eight lines, so a stretch is judged by the lines it has. Once the log has rolled past the last real activity, its oldest line is counted from the activity (the gap before it is unknown), so a stretch that was told of is not read as a new one every time the window moves on; the message and the History line then measure that stretch only from the oldest line left (the lines cannot show more), so a stretch that went untold for a day is not told as one of a day. **This rule does not stand in for the older four-hour hand-up.** The ladder's hand-up of an alive item for going four hours with no step marked, no state change and no merge is gone. This rule tells -main (or the front agent that holds the item) of a mover whose pane looks busy for a long time with nothing else to show, and the ladder's live-mover rung (*A live mover's silence goes up instead*, above) tells it of a live background mover that writes nothing; a mover that writes a line every hour but makes no progress is told by neither.
