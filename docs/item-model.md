# The item model and the stored state

What this page covers: the alive and waiting model, the stored phase, retired inputs, the state checks, watchers, fleet-event waits, how a close keeps the description, and the mover that holds every power. Back to the [README](../README.md).

**A close keeps the description** (`stackshot/service/gates.py` `gate_close`, `update_unlocked` (`stackshot/service/update.py`), `stackshot/model/close_repair.py`, `stackshot/tools/restore_close_descriptions.py`). A close used to tell the closing session to rewrite the description to the end state, and nearly every close did, so the owner could not tell what a closed item had been about. Now the description stays exactly as it was, and how the item ended is its own field, `metadata.outcome_text`: `complete` (and `update` with `status=completed`) takes it as `outcome_text`, required, in the bullet form and length of a description (`[description]` limits; the forbidden tokens such as `Resolved:` apply to live descriptions only, since an end state may say what was resolved). `reason` stays the one-line, notice-facing text (at most `[close] reason_max`); `outcome` stays the kind. A description passed with a close by a caller that predates the field is accepted and stored as `outcome_text`, never over the description; both together are refused. An update that edits the description of an already closed item works as before; a reopen drops `outcome_text` with the other close fields. `get` shows an `outcome text:` line after `reason:`, search indexes it, and the item page of a closed item with an outcome text shows an Outcome block first in the main column, under the state line and above Background (an open item, or a closed one with no outcome text, shows none). A description passed with a close that equals the stored one (after strip) is ignored. Whose words are on a close (`_owner_words` in `stackshot/web/shared.py`, the For you row) are read from the outcome text and the reason, not from the description the close keeps (an item with no outcome text, or an open one, is still read from its description). The server's own closes (done check, terminal prompt, job gap, cold call) write their summary as `outcome_text` too; the cold call's answer key is `outcome_text` (the old `description` key is still read). On GitHub a close still closes the issue (completed or not planned) at once, in one PATCH and with no comment, and the issue body is the description the item keeps followed by an `## Outcome` section holding the outcome text (stored with ids already rewritten from `g<n>` to `board#<n>`, written as stored like the description); a reopen removes the section, and a close with no outcome text (stored before the field) has none. The body form number is not raised and nothing is backfilled: earlier closes already show their end state in the body, since it was their description. The repair's restored description and outcome text reach the issue as an ordinary paced change. **The repair** `stackshot/tools/restore_close_descriptions.py` puts back the descriptions that closes replaced in the last 14 days (`--days`): from the store's history it takes the description held just before the close, restores it, and moves the close-time text into `outcome_text`. It leaves an item closed before the window, one whose description is already the earlier one, one edited after the close, one with no earlier revision and one that already has an outcome text (counted as "has outcome text" in the dry run; its close's text would otherwise be lost); clocks and every other field stay. Dry run by default (`--store <copy>` for a copy of the board repository, `--live` for the live store, read only); `--live --apply` is refused unless `systemctl --user show -p ActiveState --value stackshot.service` says `inactive` or `failed` (so also while the unit is activating or deactivating, or when systemd cannot say), and `--store <copy> --apply` rehearses it. It is a tool and not a pass at server start because it runs once and the owner should see the dry run first; running it twice is safe.

- Ranks are retired, and `POST /client/rank` with them (the route answers the usual 404 for an unknown write). A builder starts every item handed to it at its next turn, and releases go out in merge-queue order. `update` still takes `rank` and `clear_rank` only to refuse them ("ranks are retired"), and a retired state input is refused the same way (below). At every server start `migrations._retire_rank_pass` removes `metadata.rank` from each open item that still stores it, whatever its value, and clears a stored state `queued` (a state that stood on the rank alone), so the item reads as derived from its fields (doing, for an item in a builder's hands). `updated`, `state_updated`, `confirmed` and every other field stay as they were; a closed item is not touched; nothing goes to GitHub; a store with nothing to clean writes nothing, so every start can run it. The save is quiet (no mover settled, no hand-off ended). The item's History says it from its revisions: `rank cleared (was N)` and `state cleared (was queued)`. A stored `queued` read anywhere else (an old revision, a stale copy) loads as `doing` (`states.LEGACY_STATES`).
- **The old item-state inputs are retired** (`stackshot/core/retired_inputs.py`, `_RetiredInputs` in `stackshot/web/middleware.py`, `service/mover_steps._state_apply`; `tests/retired_inputs_scenario.py`). An item stores alive or waiting directly (the item model), so `update` and `create` no longer take `state`, `clear_state`, `party`, `chase`, `end`, `proof` or `chase_note`: they are gone from the tools' signatures and descriptions, and a call that still passes one (a client's cached schema, an old script) is refused before the tool runs with one `ToolError` that names what to pass instead (`mover`, `hold` with `wake` and `wait_basis`, `after`, `wait_kind` with `wait_event`, `ask_by` and `post_wake_mover`, `needs` and `ask`; the word of a `state=<word>` is answered by what that word said), and nothing is written. An input a client sends empty (`""`, `false`, `null`) is no call and is left out. `POST /client/state` answers 400 with the same refusal and `stackshot/fleet/client.py post state` prints it and exits 1; `tools/state_from_fields.py` and `tools/move_waiting_doing.py`, the two one-time jobs that used the route, are removed. `step` and `supplies` stay as they were: a `step` stores the your-step state and `supplies` the blocked one, each refused without what its state needs (`states.problems`, with what to add). A step is withdrawn with `step="none"` (like `needs="none"`): the your-step state and his open step line go in that write and the mover goes back to `then`; it is refused on an item that stores no step. A `supplies` on an item stored in another state swaps it to blocked. **What stays stored and read:** an item an older write left a stored `state` word, `party`, `chase`, `end` or `proof` on keeps them (no write drops one, a close still does): the readers take them (`states.of`, `model.derive`, `watchers`, the item page and `get`); a write that touches a field a stored state stands on (`states.STANDS_ON`) so that the item can no longer stand in it drops the word and says so in the reply (`(stored state X dropped: …)`), since no call can move or clear a state any more. An item with no stored state is read from its fields (decision → your-call, external → outside, a hold → parked, an open `after` → blocked, else doing) and shows no state word: `get`, the brief and `stackshot/fleet/client.py get items` carry `state: <s>` (`state` and `state_fields`) only for an item that stores one, and the model line says alive or waiting and who moves it. **The retire pass** (`stackshot/model/retire_fields.py`, `retire_passes._retire_one`, `stackshot/tools/retire_fields_report.py`; `tests/retire_fields_scenario.py`) takes the stored state words and carry fields out of the open items: `party`, `chase` and `end` go to `wait_event`, `ask_by` and `wake` when those are empty (a verifying item's end day becomes a wake at 23:59 of that day, the end of it, as the state read it; a party the `wait_event` does not already name, and a chase day the `ask_by` does not start with, stay where they are, since a reader (the relay's text, the router's item list, the cold call) takes the `wait_event` or `ask_by` only when the `party` or `chase` is empty, and would show the other text once the field was dropped; on an item that stores a `wait_kind` the watchers read them, so its `party` stays and so does a `chase` with no `ask_by`), a verifying item's `proof` becomes the text of a `wait_basis` on its wake, `supplies` becomes a `- Needs: …` bullet at the end of the description (held, and left in `supplies`, when the description with it would pass 8 lines or 120 characters), `expected_by` and `expected_reason` are dropped; agent work in hand (the stored state doing with a session as mover: `waiting.doing_agent` reads it from the stored state alone), a your-step item, a step with no home and a proof outside a verifying item are held back and listed; `wait_kind` stays. The server refuses an item whose phase, kind of wait, mover or watched status would read differently. The script's dry run (the default) runs the whole pass on a copy of the store and prints the counts; `--apply --sender <you>` runs it through the live server (op `retire` of `POST /client/migrate`, behind `[model] migration`) after writing an undo file; `--undo <file> --sender <you>` puts the keys back (an item a later save changed is `kept`). No write stores a state word now except `step` and `supplies`; the pass is rerun to take those out.
  **Checks for the state rules** (`tests/state_checks_scenario.py`). The owner's step hidden under an agent's state (refused since an earlier change): a create or an update is refused, and writes nothing, when the item it would leave has a first line of `next` that opens with a who-takes-it opener (`<owner>:`, an alias such as `<alias>:`, `you:`, or `the owner to …` / `<alias> to …`; never `the owner's`, `OPS-X` or "the owner approved …") while its
  state, stored or derived, is doing, blocked or verifying (one detector, `states.next_names_owner`, serves the refusal and the note). The refusal names the fix: `step=…`, or `needs=decision` with an ask (a create has no step, so it takes `needs=decision` and an ask, or a first line for the session that takes the step). Only a write that sets `next`, `needs` or the step is judged, so the mover of a legacy item can fix it step by step; a write that sets none of those (a due date, a description) to an item already in that shape is allowed. `get`, the brief and that write's reply keep the note for such an item, `next names the owner but the state is <s>: pass step=… (or needs=decision with an ask)`, so legacy items stay visible. Closed items and the quiet states (your-step, your-call, outside, parked) are never refused or noted; the terminal prompt's own row is exempt on create and update (its script stores your-step right after the create). When the first line is another session's (next keeps each writer's lines at their place), the refusal names that writer and the exits: drop the step (`dropped=[its number]`), `clear_next=true`, or `step=…` if it is truly his step; it says to mark the step done only when his own words for it are recorded on the item (the audit's N4 flags a done mark on his step without them, and never a dropped one). Re-parking: a write that moves the wake of a parked or verifying item (or a verifying item's `end`) to a
  later day with nothing else changed but the wake, the end, the hold and the cap words (a changed `wait_basis` text is a real change; a pull-in or a time of day on the same day neither counts nor resets) is counted in `metadata.repark`, any other change resets it, and the third in a row is refused (the
  item goes to the owner as `needs: decision` with an ask) unless the owner's words stand behind it (a checked `said` entry, or his answer on the item since it last moved). A verifying
  item's `end` is at most 30 days out and stands as its wait like a wake (the watchers end the wait on that day): no separate wake, no idle nudge and no stale mark before it. Stale `next`: a write by a session that is neither the owner nor named by `next`, which changes needs, the stored state, hold, wake or after and not `next`,
  sets `metadata.next_stale {by, fields, at}`, shown as `(next may be stale: <who> changed <fields> <when>)` in `get` and the brief until a write passes `next`; a `next` that names a date
  that has passed (`Thu Mar 26th`, `Mar 26th`, `2099-03-26`; paths and file names are skipped, a bare day before a counting noun such as "May 5 items" is a count, a yearless date rolls into next year only when more than 90 days past) is marked the same way. A decision asked again: a write that puts `decision` back into needs
  within 60 minutes of the owner's last answer on the item is refused unless the ask line changed in the same write (an item already on his call is not put back, so a restated `needs=decision` on it passes) (a board decision keeps the ask it answered in its answer record).
  No item is hinted to store a state any more (`states.hint` and `pages.state_hints` are gone): neither the hook's board questions nor the items read carries `state_hint`.
  A refused board write must not go unseen inside a Code Mode script (an item can sit for days that way): every row of the items read carries `roles`, the asking session's live roles on the item
  (`mover`, `then`, `needs`), and the hook's board questions (the early one and the Stop one) say them beside each item (`board#N "…" (it comes to you after the owner (you are its then))`, `(named in its needs)`, `(you are still its mover)`).
  "You are still its mover" is only for an alive item the session moves while neither keeping it nor being named in its needs (the items read lists such an item too), the hand-back to someone else that failed
  after the needs were cleared; a keeper, or a builder named in needs, moves its item by default and reads only its keeper or needs role. A follow-up sentence is added only when a listed row says "still its mover":
  the role is the server's reading now, so a hand-back that still shows it was refused. The server also logs every refused tool call to stderr, one line, the reason clipped to 300 characters
  (`refused: update item=board#N sender=<session>: Refused: …`; the tool, the item id and the sender, then the tool's own refusal text, which can quote a short fragment of the call; never the call's other arguments).
- **The item model** (`stackshot/model/model.py`, step 1 of the redesign, the data layer: the write guards come with the next PR). An item is `dead` (closed), `alive` (someone in the perimeter
  is working: one mover) or `waiting` (nothing happens until something outside arrives: a time, an anchor's event, another item's close, or news only the owner relays). New optional
  fields in `metadata`, on `create` and `update` (the `update` tool also takes `clear_goal`, `clear_mover`, `clear_then`, `clear_wait`, and each field takes `none` to clear it): `goal` (the
  end-state, one sentence), `mover` (the owner, a session name or the project's background agent) and `then` (who takes it after the owner's answer or step; it stands only while the owner is the effective mover, whatever is stored), `wait_kind`
  (`time` | `anchor` | `item` | `relay`) with its input (a time is the item's date, stored as `until`, the one date every wait ends on (`wake`, `ask_by` and `hold` are accepted as old names of it until Wed Nov 25th 2026, and a bare date in a write that hands the item on is only that hand-off's backstop), an item its `after`; an anchor `wait_anchor` and `wait_event`, a wake being its backstop, and the anchor must be on the project's list first (`anchors`, scoped to the item or project-wide), else the write is refused; any new notice at the anchor that reaches the server and passes the project's keeper wakes the item, so an anchor wait fits something quiet apart from the awaited event and not a busy channel or DM, where a relay or time wait fits; a relay `wait_event`,
  the party or event, and `ask_by`, YYYY-MM-DD) and `post_wake_mover` (the old name of a waiting item's `mover`; while it is stored it still wins over a stored `mover` when read, but a write that sets a different `mover` on a waiting item drops it (a write that names `post_wake_mover=` and `mover=` together is stored as written), `clear_mover` and `clear_wait` drop it, and a write that sets a `mover` naming the same session changes nothing; stored items are not migrated yet, but every writer of a waiting item's picker (the wait-end fix, a decision's hand-over, `remember` and `restore_wait`) now stores it as `mover`). `clear_wait` and `clear_hold` end the wait and never the hand-over: the agent the item was handed to stays its mover, also when an older item stored it under `post_wake_mover`; the picker the item read as before the write (`model.stored_picker`) is promoted to `mover` in that write and the old key popped (`model.keep_picker`), whatever the shape: an old plain hold, a wait that goes on beside external, the old key beside a different stored `mover`; he as the picker goes with the wait; a hand-off in the same call (`needs`, `agent`) decides who moves, so nothing is kept then, and a `clear_hold` on a relay or event wait that holds no flag changes nothing (with `clear_wait` beside it the wait ends and the picker is kept). They are filing edits (no clock moves, no page is owed); a close drops the mover and the wait and keeps the goal.
  `model.derive(item, now)` reads them and today's state (your-call and your-step → alive with the owner as mover; doing → alive with the agent; outside, blocked, parked, verifying →
  waiting) and returns the state, the effective mover, `then`, the effective wait and its picker (`Model.picker`: on a waiting item what `model.stored_picker` reads, the one reader of it (`watchers.was_picker` for a `watch.was` snapshot): the stored `post_wake_mover` (the old name) if any, else the stored `mover` (the literal word none names nobody), else the default; the item's own `mover` stays empty while it waits), each marked stored (explicit) or defaulted (needs holds decision → the owner, else the first
  session in needs, else the project's builder, else its -main agent, never the item's creator; a relay's picker is the owner), and `conflicts` where fields cannot both stand (a `mover` and a different `post_wake_mover` on a waiting item: the post_wake_mover wins while both are stored, as an item stored that way before; a write that sets `mover` on a waiting item no longer leaves the two, since it drops the old key). `settle` (the stored mover against the state the item stands in) settles a waiting item that stood his only when called with `waiting=True`, which the update path alone passes (a write that did not name a mover); the on-save backstop and the once-per-start repair leave a waiting item's stored mover alone, because a stored mover that is he is where "he picks it up when the wait ends" is written. `get` and the brief show `goal: …` and one line,
  `model: alive · mover <who> (then <who>)` or `model: waiting on a time (wake …) · mover <who>` (`mover <owner> (then <who>)` when he picks it up), with `derived: mover, then` naming what is not stored. Every save records its writer on the item
  file: `written_by` (the session's name, the owner's for his board answer, or a script's label) and `written_by_id` (the session's id, or `board`), so each revision in the store's history says who wrote it. A server save with no writer (a wake, an idle mark, a done-check close) leaves both fields as they were: they name the last real writer.
- **The stored phase and the kind of its wait** (`metadata.phase`, `metadata.waits_on`, `model.stamp_values`, `stamp._phase_stamp`; `tests/phase_scenario.py`). An open item now also stores `phase`, `alive` or `waiting`: what the board shows it as, worked out by the reading it has always used (`model.view` of `model.derive`, so a held doing item, a wake that carries a `wait_basis` and a doing item whose open steps are all dated for a later day are `waiting`) and written by every save of an open item through the one save path (`writes.save`); a closed item stores none. A waiting item also stores `waits_on`, `time`, `anchor`, `item`, `relay` or `event`: the kind of the wait the board shows (`model.shown_pair`, worked out with the phase by `model.stamp_values`); an alive item stores none, and a close drops it. Both are what every reader takes the decision from: **the stored pair is the only source of whether an item is alive or waiting and of the kind of its wait** (`model.view`, `tests/stored_pair_scenario.py`). The lists, the item page, the wire `list` of `items?key=`, the `· the board lists it as waiting until …` tail of get's `model:` line and get's `named in next:` lines all go through `model.view`, which takes the phase and the kind from `metadata.phase` and `metadata.waits_on` and keeps `derive`'s details (the mover, the wake, the anchor, the post-wake mover, the basis text) wherever they fit it. There is no switch (`[model] read_stored` is gone), no check against the fields and no disagreement counter: where the fields say otherwise, the stored pair is what is shown, until the sweep restamps it (a minute at most). An open item that stores no usable pair (a new one not yet saved, a phase waiting with no kind, a value that is no phase) is shown as the writer would store it and counted in `model.UNSTAMPED` (`unstamped_reads` in `GET /audit/status`); the next save or sweep stores the pair. The writer is the one place that works the pair out from the fields (`model.view` with `check=False`, which `stamp._stamp_values` calls). The History comparison that recognises a bare confirm leaves the two keys out, as it leaves out `activity`. **The phase sweep keeps both true as the clock moves** (`stamp._phase_sweep`, `stamp._phase_tick`, the minute set's tick `phase_sweep` right after the anchor pass; `tests/phase_sweep_scenario.py`). A save restamps an item, but some things change what the board shows an item as without any write to it: a dated wait's wake coming within `[waiting] dated_wait_min_hours` of now, a wait_basis wake passing, midnight in the instance timezone bringing the day a dated step waits for, an `after` item closing for an item with no stored state, an anchor scoped to or taken off the project, a change of `[waiting] dated_wait_min_hours` or `[instance] timezone`. Once a minute, at the start (before the first publish) and after a config reload, the sweep works every open item's two values out again from its fields at the clock now, without the item lock, and compares them with what the item stores; only a difference goes to `_stamp_one`, which works the values out again under the lock, re-checks the file just before replacing it and writes the two keys and nothing else: no `updated`, no `written_by`, no activity or hand-off record, no For you row, no GitHub job, no notice and no History line. A session's write between the sweep's read and its replace is never overwritten (`moved`; the next minute stamps it), a closed item is left as it is, and a warm standby copy (`STACKSHOT_READ_ONLY`) neither sweeps nor writes. One publish at the end when it stamped something (a few times a day at most; most minutes write nothing). `GET /audit/status` carries a `phase_sweep` object: `runs`, `swept` (open items looked at in the last run), `stamped`, `moved`, `refused` and `disagreements` (stored pairs found different from the reading; since the start), `last_run`, `last_stamped` (epoch seconds, null until the first), `last_ms`, and `unstamped_reads` (`model.UNSTAMPED`, above). The display follows the stored pair, so the sweep is what moves it at a clock edge. **What stays on the fields on purpose:** `until`, the event, the post-wake mover and the basis text of a wait, the seven state words in get, the item page and the wire, the watched set (a stored `wait_kind`), the write guards, the hand-off, the router and the audit's filing rules, and the writer of the pair itself. `waits_on` is only a label: no update can set it, and the stored `wait_kind` is the field it always was (it is not added to an item that stores none, because a stored `wait_kind` hands the item to the watchers below). The proof is `tests/stored_pair_scenario.py`: on a store swept at the clock, every surface (the state word, the kind, the list word, the model line, get, the brief, the named-in-next lines, the wire fields, the home page, every item page, the projects page, `board.md` on both renderers, the brief's waiting-on-the-world text) is byte-equal to the same store read from the fields alone, at the clock now and at six later clocks (+30 minutes, +1 hour, +6 hours, the next midnight in the instance timezone, +3 days, +40 days), on a copy of the live store too when `PHASE_REPLAY_STORE` names one; a stored pair the fields no longer give decides until the sweep; and a reader that works the decision out from the fields, or takes the stored waiting with the fields' kind, fails it.
- **board.md and the brief say alive and waiting, not the seven states** (`Board.home_pairs`, `Board.phase_counts`, `home.wait_words` in `stackshot/web/render.py` and, kept in step, `stackshot/web/ui/render.py`; `tests/stored_pair_scenario.py`, `tests/verifying_apart_scenario.py`). Both count and list from the home page's own classification (`home.classify` over `model.view`, the same three lists with the same sorts), so board.md, the brief and the home page cannot disagree on a count. **board.md:** the head reads `_N open · A your move · B on agents · C waiting · machines: … · rendered by stackshot_`; the sections after the Machines, Anchor hub and Task board parts are **Your move** (with the provision line), **Waiting** and **On agents**, each item drawn in full as before; a waiting item's meta line adds `waiting on <kind>` in the model's words (`model.KIND_WORDS`: a time, an anchor event, another item's close, news only the owner relays, a fleet event); the Task board table's columns are `open · your move · on agents · waiting` (open holds every open item, and a parked item is marked `(on hold)` or `(after …)` in its cell). `agents` is the home page's On agent and Queued for release lists together, so `alive = your move + agents` and `open = alive + waiting`; a verifying item is a wait on its end date and counts under waiting, and nothing counts verifying apart or names an on-hold total any more. **The brief** (the lines a session reads at start): the first line is `Board: N open (A your move, B on agents, C waiting), D completed in 14d`, then up to five `  your move: …` and five `  waiting: … · on <kind>` lines (no state word on them), and the one counting line `  alive X (your move A, agents B) · waiting C` (the old `states:` line is gone). The `brief` tool's body finds the head of board.md up to its `## Your move` section. `get`, the item page, the wire and the `brief` tool's per-item blocks keep the seven state words until a later change retires them.
- **A mover busy on another item reads waiting, queued behind that item** (`stackshot/model/queued.py`, `silence.queued`, `Board.queue_map` in both renderers, `audit_ticks._queue_map`; `[model] queued_behind`, off by default; `tests/queued_behind_scenario.py`). A session that moves several open items works on one at a time, so the quiet ones were shown on an agent and chased as if nobody had them. The reading is derived when the board is read, never stored: no `phase`, no wait and no mover changes in any item, nothing is migrated, and switching the key off puts every item back at once. For each mover separately, the open items the board shows on an agent are the candidates; one candidate changes nothing. The item it is working on is the one with the newest visible activity (`metadata.last_activity`: a step, a state change, a commit, a review, CI or a merge on a tied pull request; a tie goes to the lower number), and it must have had activity within the hour itself. Each other candidate with no activity for more than an hour is read as `waiting` of the `item` kind, `after` the item in hand (`Wait.queued` is set, so a page says it as a queue): the home page lists it under Waiting with `Queued behind <item>` (a link), its mover still named, and the item page's Waits on row names the item in hand with `its mover is working on that item first`. board.md (the card's meta line) and the brief (the head's waiting lines) say `queued behind <item>` in its place, where a stored item wait reads `waiting on another item's close` (`home.wait_phrase`). An item with activity in the last hour stays on agent. It ends by itself, because the rule is read again every time: the mover moves a queued item (it now has the newest activity and is in hand), the item it waits behind closes, the item in hand goes an hour without activity (then nothing is queued, so the hourly audit line reaches them all), or the mover is left with one item. A front agent's items and the owner's are never queued (a front test that cannot answer, such as a role map that cannot be read, counts as front: nothing is queued on a guess, and only this rule reads it so; `telling.front_keeper(strict=True)`, `audit_run.Env.is_front_safe`); a held, a parked, a waiting or an owner's item is not a candidate and never counts as the item in hand. The counts, board.md and the brief follow the lists; `get` still prints the stored model. The hourly audit line, the idle hand-over and the stall pass read it as they read any waiting item (see *[The audit lines, the stall pass and the ladder](stall-and-ladder.md)*). `[model] queued_behind` is read at use; only a TOML `true` switches it on.
- **The stamp of items nobody has saved since** (`stamp._stamp_one`, the `stamp` and `unstamp` ops of the migration route, `stackshot/tools/stamp_phase.py`; `tests/stamp_scenario.py`). An open item that was last saved before the stored phase carries neither key; the stamp pass writes them. The route is the migration's (`[model] migration = true`, `migration_senders`, `migration_machines`, all of the operator's), with no `begin` and no board-wide pause: the server works each item's two values out when it writes, under the item's lock, from the fields as they stand, so a session's update takes its turn and nothing planned can be stale. It writes `phase` and `waits_on` and nothing else (no `updated`, no writer, no activity clock, no hand-off record, no For you row, no GitHub job; `wait_kind` untouched), re-reads the file just before replacing it and answers `moved` if another writer got there first, and refuses a closed item. `stackshot/tools/stamp_phase.py --dry-run --store <copy>` shows one row per open item (old display, stored before, shown now, stored after, whether the watchers own it before and after, `add` | `fix` | `same` | `edge`) with proof lines for the display, the watchers and the files outside the two keys, all 0, and writes nothing, the copy included; `--apply --sender <you>` asks the server for the plan, writes the undo file (fsynced) before the first write and stamps in batches; `--undo <file> --sender <you>` puts each item back where the stamp left it, or answers `kept` for one a later save restamped. A file a session saved after the stamp is told apart in the apply (printed as informational, never a failure; only a file the stamp itself changed outside the two keys fails the run), and an undo entry the run died on takes its keys from the server's pass record, not the planned ones. The same write is the phase sweep's (above), which runs it every minute for the items whose stored values the clock has left behind. Run as `uv run --no-project python stackshot/tools/stamp_phase.py …`.
- **The rewrite of stored waits as `until`** (`stackshot/waits/until_pass.py`, the `until` and `ununtil` ops of the migration route, `stackshot/tools/until_migrate.py`; `tests/until_migrate_scenario.py`, `tests/until_sweep_scenario.py`). An open item that stores its wait in the older fields (`wake`, `ask_by`, `hold` with `hold_set`) is rewritten as the one stored date, `until`, plus `wait_kind` where the fields imply one, as `update` would store it today (`until_write.fold`): a hold with a wake becomes the date alone (the flag goes; `hold_set`, who set the hold and when, **stays on the item**: `update` drops it with the hold, but the pass drops no record of a person, and `audit_run.wait_since` reads it as the start of the wait; the end of the wait clears it as it does the hold's stamp now, and `get` shows it as `hold: set by ...` on an item that waits on `until`), a date beside an `after` link with no kind becomes the kind `item`, a relay's ask-by day and an anchor, item or event wait's backstop become `until`. A bare date (no hold, no kind, no reason, no `after` link) is a hand-off's backstop or a wake stored before `until` and stays as it is; an item that stores an `until` beside an old date, or a reason or approval bound to another date (or to the same date with spaces around it: once the clean date is stored `basis_of` would no longer match it), or an old date with spaces inside it (a hand-edited store: the old readers took it for no date), is left and listed. The pass checks that the item reads the same before and after (phase, kind of wait, mover, held flag, the end date, and the model's `conflicts`: a conflict the item did not show before is a difference; the watchers may take over a wait the wake pass owned, never the reverse) and refuses an item that would not. **The conflict that shows after a rewrite:** `wait_kind=time on an item whose state is doing, which is alive`. A hold ends a stored work-in-hand state, so an item stored as `hold` + `wake` + `wait_kind=time` with no stored `state` word reads as parked (waiting) only because of the hold; once the pass removes the flag it reads as doing with an explicit kind, and the model lists the conflict (the wait still wins, so the phase, kind and mover are the same). The cause is in the pass's output, and the only ways round it each change something else (keep the hold flag beside `until`, drop the kind `time`, which hands the wait from the watchers to the old wake pass, or write the `state` word), so the pass refuses such an item and lists it; a person re-saves it with `update(until=...)` (the stored `state: parked` that holds wrote beside the kind keeps the reading clean, and those items migrate). The same conflict shows on any item `update` stores as `until` + `wait_kind=time` while its state reads as doing. On a relay or event wait `update hold=true` (with its day) stores no flag, because the wait is itself the park, but it ends a stored work-in-hand state as any hold does (the reply says so); the conflict is listed only for a relay or event wait that stores an alive state, so the hold clears it; a relay or event wait with no stored state lists none, even when its fields read as doing (needs naming only a session). **Dates the old code did not act on.** An `ask_by` the old watchers did not read was never acted on: they read it only for a wait they could end (a relay's ask-by day; the backstop of an item wait, or of an anchor or event wait that has its anchor or a valid event phrase), so an `ask_by` beside no kind, a time kind, an anchor wait with no anchor, or an event wait with a missing or unparseable phrase was read by nothing (whatever else the item stores: an `after` link, a hold kept by a pane recycle); an `ask_by` they did read is migrated and not listed. And a `wake` with no hold on a wait the watchers did not own (no kind, as beside an `after` link; an anchor wait with no anchor; an event wait with no valid phrase) only got a backstop notice from the old wake pass; as `until` the watchers act on both (on a wake the watchers also release the item: the mover changes and the link is dropped). A date of that kind that is already past is NOT migrated: the item is left as it is and listed as already due, to be re-saved with the date meant. A future one is migrated and listed as newly watched, with the day it wakes and how it was read before (never watched, or previously only a notice). A hold with a `wake` is not in this class: the old wake pass released it at the date, as the watchers do, with two rare shapes that differ, past or future wake alike, which are migrated and **listed** in the plan ("release differs", with the reason per item; they are part of the plan the apply compares, and they are not left over, so they do not change the exit code): (i) a hold with no kind, `needs` an owner's name and a `wake` (past or future alike): the old pass released it into the owner's lane with no new ask, the watchers give it an owner step and an ask ("Decide: ... whose wait ended") and tell no one; (ii) `needs` [A] with a different `post_wake_mover` B: the old release and its message went to A, the watchers hand it to B and rewrite `needs` as [B]. The pass itself wakes nothing and tells no one; the ticks after it act only on the newly watched future dates it lists. The watchers drop a front agent's `watch_reason` with the wake when the wait ends (`watchers.LIVE_DROP` and `DATE_DROP`, as the old wake pass did), so a reason given for one wake does not outlive it. It is the stamp pass's shape: the route is the migration's, each item is worked out and written under its own lock, nothing else in the file changes (no hand-off, notice, clock or session message, no item closed or woken), and each rewritten item gets one History line saying the stored wait was rewritten as `until` and that nothing else changed. `uv run --no-project python stackshot/tools/until_migrate.py` is the dry run: it runs the pass on a private copy of the store and prints, per item, the old and the new wait keys and the History line, then totals and whether a second pass would write anything (it never writes the live store); `--apply --sender <you>` asks the server for the plan, copies each touched item's file to `<run dir>/<pass id>/items/` (default run dir `~/.local/share/stackshot-runs/until-run`), writes the undo file (fsynced) before the first write, then rewrites in batches; `--undo <file> --sender <you>` puts the old wait keys back item by item, value for value (a key that returns lands last in the item's metadata, so the file is value-identical, not byte-identical, to what it was; the backup copies are byte for byte, but there is no tool that restores from them: they are for a person to read or copy back by hand), takes out the pass's own History line (the other lines of the log stay, and a line it pushed out of the eight-line log comes back), and answers `kept` for an item where a later save changed any of the six wait keys (`until`, `wait_kind`, `wake`, `ask_by`, `hold`, `hold_set`), even one the pass left alone; a later History line alone never makes it `kept`. A run that dies after the server wrote a batch is undone the same way: entries with no recorded result are taken from the server's pass record (`<state>/migration/<pass id>.json`), or from the planned entry, which holds no clock value; the next `--apply` writes those results into the earlier undo file, and names a file whose entries the record does not know (undoing such a file alone also reverts items a later `--apply` wrote: undo the later pass files first). One narrow rule resolves such an entry on its own: when its item is open and still holds the wait keys the entry planned as `before` (and not `after`), the server wrote nothing for it and the entry is recorded as `same`, so a file whose entries are all of that kind reads finished and may be pruned; an item that holds `after`, or anything else, leaves the entry unresolved. A pass file that was undone is marked and no longer named. A second run finds nothing to rewrite. `--apply` prints the newly watched and the already due lists before it writes, plans again right before the first write and stops (exit 1, nothing written) when those lists changed since, or differ from the dry run's `--json` file given with `--plan`, unless `--allow-changed-plan` is passed. Exit codes: 0 done, 1 a failure, 3 applied with items left over (refused, listed, already due, closed between the plan and the write, or a planned date that came due before the write: not a failure, a person has items to look at). Dates a person reads in the listings are in the rulebook's form (`Tue Nov 24th`); the JSON rows, the plan signature and the stored keys keep ISO dates, and the stamps in the undo file are Seoul time with the zone named (`Thu Nov 12th 15:30 KST`). One `--apply` or `--undo` runs at a time per run directory (an exclusive lock on `<run dir>/.lock`; a second one exits 1 and does nothing; an `--undo` reads its file first, so a path that is none, a file that is no undo file, one with an entry that is no object or lacks `item`, `before` and `after`, or one nested too deep to parse exits 1 with one line and creates nothing, and it takes the lock only for a file at `<run dir>/<pass id>/undo.json`). A batch the route refuses as a whole with a 4xx answer is recorded in the undo file (result `batch refused`; a refusal comes before any write), so the file is not named unfinished and an undo skips those entries. A batch that gets any other answer (no answer or a timeout, a 5xx) may have been written in part, so its entries keep no result: the pass counts it as failed (exit 1), the file is named unfinished by the next `--apply`, and an undo takes the entries from the server's pass record or puts back from the planned values, as for a run that died. Each `--apply` first removes the pass folders in the run directory that are older than 60 days, keeping the newest five (only folders named like a pass id and directly inside the run directory, never a link, never anything in or around the live store, and never one whose undo file is unfinished: that file is the only record of what the pass wrote). `--store` is for the dry run only: with `--apply` or `--undo` it is refused. An `--undo` answers `kept` for an item that closed since the pass (exit 0, listed apart from the ones a later save changed), and marks the file undone only when no entry is left unfinished (refused, written by someone else meanwhile, or a batch refused). The pass writes the History line into `stall` without touching its other keys; a `stall` that is not an object with a plain log is left as it is (no History line for that item) and the undo gives back the exact value. **Items the pass refuses** (such as a hold beside an open `after` item or a hold held by `needs` external: as `until` their reading would change) keep their old fields untouched and are listed by the dry run and the apply; they are still read as before, the next write that touches their wait stores them as `until`, and a person re-saves them with `update(until=...)` before `[model] wait_alias_until` (Wed Nov 25th 2026 as first set), when the old parameters wake, ask_by and hold stop being accepted in writes.
- **The waits' watchers** (`stackshot/waits/watchers.py`, `stackshot/service/watching.py`; `[model] watchers`, default true). They act only on an item that stores a `wait_kind`; every other item keeps today's wake pass, `after` release until the migration (`watchers.watches` is the gate those three read), so no item is moved by two mechanisms. When the wait ends the item turns alive with its post-wake mover (the hold, the wake, `after` and the wait's fields go, `mover` and `needs` name the mover, `woke` records what arrived and shows in `get` until a session writes), and the mover is told in one line (several items for one recipient in one pass are one message). A **time** wait ends at its wake (the wake pass). An **item** wait ends when the last `after` item closes (the close itself, and a catch-up in the wake pass); its backstop (`ask_by`, else the wake) passing first turns it with the note that the item is still open. An **anchor** wait ends when a notice for `wait_anchor` reaches the server (`anchor_release` in `stackshot/service/wakes.py`: the keeper passed or merged it, or nobody rules the project, or it is the fleet's own routine line that says merged or closed; the minute pass reads the routing log for the rest) and carries the notice's gist; its backstop turns it with "the anchor stayed silent". When the wait is set the reply says what the anchor watcher already recorded on that anchor since the item's last move and whether it watches the anchor for the project. A **relay** wait comes to the owner on its `ask_by` day with the ask `Decide: has <party>'s <event> arrived? · Options: arrived / not yet, ask again on <date> / drop` and three buttons: arrived → alive with the post-wake mover (`then`); not yet → the wait again on the date he writes in the box (a date or a phrase of the small table in `watchers.parse_date`, no model call; none readable: his note is kept as a comment, no date is set, and the item asks him back with three days to pick from, see *The answer box never refuses a note* in `docs/asks-and-answers.md`); drop → closed as not planned. A follow-up an older write logged (`metadata.chases`, shown as `chases: n`) on a relay or anchor wait still counts, though no call logs one now (`chase_note` is retired: the wait comes back on its `ask_by` day): with two on it, the wait's next end comes to the owner as `Decide: drop it? … · Options: drop / keep waiting until <date>` instead. A moved `ask_by` or wake starts the chases over. `[model] pause = true` holds all of it and today's wake pass with it; when it is false again the due ones fire in one pass. The brief lists the relay waits as "waiting on the world".
- **A wait on a fleet event** (`stackshot/waits/event_waits.py`, `stackshot/service/event_waits.py`; `tests/event_wait_scenario.py`, `tests/box_online_wait_scenario.py`). `wait_kind=event` with `wait_event` one of `pr_released <owner/repo#n>`, `pr_merged <owner/repo#n>`, `recycle [<machine>]`, `fleet_op <verb | any | many> [<machine>]`, `job_run <name>` or `box_online <machine>`, and a backstop day (`ask_by` or a wake) after now: the item comes back to its post-wake mover when the event arrives, or on the backstop if it never does, and the stall pass does not run for it meanwhile. The PR kinds and `box_online` are states the server reads for itself (a runner pass every minute, `evwait_tick`); the others are reported by the fleet tool (`stackshot/fleet/client.py event`). A wait for something already true is refused at the write: a PR already merged or live, and a `box_online` wait on a machine that is online now (its puller checked in within `[client] online_minutes`, `liveness.puller_online`), so an item is never woken by a state it was set on. `box_online <machine>` takes a machine the fleet knows (a machine in the `paths.fleet_names` table or with a record in the clients state, by hostname or fleet name); an unknown name is refused with the known ones. It turns the item on the first pass after the machine's puller checks in again, with a History line and one notice to the mover; a machine that never returns leaves the wait open until its backstop day, when the item comes back with "the event did not come". It replaces an item waiting on a date for an offline machine.
- **A machine anchor** (`stackshot/anchors/machine_anchor.py`, `machine_anchor_poll` in `stackshot/service/event_waits.py` and `service/wait_gates.py` `_machine_note`; `tests/machine_anchor_scenario.py`). The standing form of the same need, for an item that stays alive: the anchors tool takes `machine:<name>` beside the URLs (`anchors(project, add=["machine:laptop"], items=[<id>])`; the name is a machine the fleet knows by fleet name or hostname, in any case, and is stored under its fleet name; an unknown one is refused with the known ones), and the mover of each item the anchor counts for is told, once per check-in, when that machine's puller checks in again after being offline. The check-in is the machine's record in the clients state: `online_since`, which `clients.checkin` stamps exactly when an offline puller returns, compared with the mark kept in `state/machine-anchor.json` (set when the anchor is added, so a machine that is online then, or checked in before, tells nothing). The pass runs with the event waits' minute (`evwait_poll`). One message per mover and machine names the machine, each item with its link and the open step that names the machine (else its first open step); an item with several machines is told of each by name. Nothing turns or is saved on the item: a machine anchor is a notice, never a wait. Not told: an item with its own `box_online` wait on that machine (the wait tells it; a wait on another machine does not stop the notice for this one, the skip is per item and machine), an item the owner moves, or will move when its wait ends (a waiting item whose post-wake mover is the owner is never routed to its `then` or stored mover instead), a closed item (it also leaves the scopes). The marks file is read, changed and saved under one lock with the anchors tool's seeding, and each writer has its own temp file. Scope is the anchors tool's: `items` scopes the anchor to those items of the project (a project-wide one, no `items`, tells the movers of the project's open items whose open step names the machine, as a whole word). It lives in `<paths.store>/machine-anchors.json`, `{"<project key>": [{"machine", "items", "added", "by"}]}`, apart from `anchors.json` on purpose: the anchor watcher, the board pages, the model guards and a completion's keeper question read `anchors.json` and none of that fits a machine, so no page the owner reads shows it. The write side: a create or update that leaves an open step naming an offline machine (the fleet name or a hostname as a whole word; open steps only) while the item has no machine anchor for it and no `box_online` wait on it ends its reply with one `(note: …)` line naming the `anchors(…, add=["machine:<name>"], items=[<id>])` call, once per write, every such machine in the one line; it is a note, never a refusal.

- **A pure fact is corrected by the server, not refused** (`call_log.fixed`, `server._norm_id`, `parse_wake` in `stackshot/service/wakes.py`, `project_subject_prefix` in `stackshot/service/gates.py`). Three misses carry nothing the writer has to decide, so the server puts the field right, stores it, adds one line to the reply (`(fixed for you: …)`) and counts it in the call log: a bare item number (`645`) in the `item_id` of `get`, `confirm` and an `update` that does not close the item is read as `board#N` with that number (`complete`, an `update` with `status=completed`, `after` and `items` still refuse it: a close or a link is not undone by a resend); a wake given as a full ISO time (seconds, a fraction, `Z` or a UTC offset) is converted to that minute in the instance timezone; a subject on a create with no scope prefix gets the prefix of its project's scope when the instance has that prefix, else `[subject] fallback_prefix` (with neither, it is refused as before). A subject that already opens with a bracketed tag or a `word:` (`[Work] x`, `[work]x`, `work: x`) is not corrected: it is refused with the prefix list named, as before. A refused call stores nothing, so it corrects nothing; a writer who wants the field otherwise sends it again as wanted and the server leaves it alone. The History line is the change itself (the stored wake, the stored subject). What the server never corrects: closing an item, an ask, and anything on an item the owner moves.
- **A wait written only in words** (`model_guards.deferral_refs`, `unwaited_deferrals`, the `next_defers` guard; `tell_close_mentions` in `stackshot/service/telling.py` and `_next_names_lines` in `stackshot/web/tools/get.py`). An item's next deferred on another item in words with no `after`; that item closed and nothing woke the mover, while a front agent kept reporting it as waiting. Three fixes. *Refuse:* a next line that defers on another open item in words (once, after, when, until, till, before, as soon as, then a `board#N` in the same sentence within eight words, a comma between them breaking it unless the id is set off by brackets or commas; and a phrase of `[keywords.model_guards] defer_after_id` right after an id; a negation, a code span, a link target, a fenced block and a server note in parentheses are not read) is refused unless `after` names that item, with the fix `after=["board#N"]` and `ask_by=YYYY-MM-DD` (a wait needs its end), `supplies=` on an update; only the lines the write sets are judged (`defers_text`, like `windows_text`: a stored line is never rejudged, a close is never judged), a closed or unknown item is nothing to wait for, and the other flagged words (when, once, after, until alone) are not refused: the writer's reply and `get` carry a note, nothing is stored, and the filing pass lists them in its flags. *Tell:* on any close (`release_after` in `stackshot/service/wakes.py`: complete, update with status=completed, a done check, a dropped decision) the mover of every other open item whose next or description names the closed one hears one batched message (the closed item, outcome, reason, the first eight items that named it and a count; through the routing log where the router holds the project, as a wake does); the closer, the closed item and the items that had the closed one in `after` (their wake is their notice) are left out; an item the owner moves goes to the sessions its notices go to. *Show:* `get` (and the reply of a write) lists under `next:` a `named in next:` block, one line for each `board#N` it names (up to eight, itself left out) with the live state: `board#N: closed Sat Mar 28th 09:30 (done)`, `board#N: open, mover X`, `board#N: open, waiting after board#N`, `board#N: not found`. Suite: `tests/item_waits_scenario.py`. *Cleared wait:* the other half of the same gap. A write that clears a wait (`clear_after`, `clear_wait`, `after=none`, or an after list that drops an item) while an open next line still defers on what it cleared in words goes through, and its reply (`_stale_wait_notes` in `stackshot/service/update.py`) names each such line, `(note: next line N still waits on board#X, whose wait was just cleared: reword it)`, at most five and then a count, found with the same `deferral_refs` matcher; the lines are the writer's to fix in that turn. Suite: `tests/item_waits_scenario.py`.
- **The tools say mover** (`stackshot_create`, `stackshot_update`, `get`, `brief`, `message`, `stackshot/web/whatschanged.py`, step 4b). `owner` is no longer a parameter of create or update: create takes `sender` (the server stores it as the record's creator, still `metadata.owner`, which History shows as "created by") and `mover` / `then` say whose move it is. An `owner` passed in is accepted with a note naming `mover` up to and including `[model] owner_param_until` (read at each call; default `2099-03-03`, so moving it needs no release) and refused after. `get` leads with `mover:` and `then:`; History writes `mover: A → B`; board.md names the mover after the switchover. The notices and replies follow: who acts next is the mover (the notices say "its mover X is a front agent", "…, mover X: <subject>" on a wake line, "then X" for who takes it after the owner); (below) took the old creator role out; a stored key, a config name or a stderr log line keeps `owner`, and "the owner" still means the instance's owner. For 7 days after a release that changes a tool, the brief (the tool and the session-start brief) carries one line, `stackshot changed on <date>: <what>; see docs/design`, generated, not written (*[The tool-text gates](../CONTRIBUTING.md#the-tool-text-gates)* below): the server's start compares `tests/tool_text.snapshot.json` with the copy kept at the last start that changed it and appends the difference to `<paths.state>/tool_text.history.json`; the line goes by itself 7 days after its date.
- **The mover holds every power**: an item has a mover and nothing else that acts as an owner. The creator stays stored in `metadata.owner` (the key is kept, no data migration) and is only a History fact, "created by X". An item with no mover is moved by the project's builder (the background agent whose mandate builds; the first one listed, unless `[handoff.builder_by_page]` maps the page the item is filed on to another background agent of the project), else its -main agent, never by its creator: a start pass (`_mover_backfill_pass`) stores that mover once on every live open item that has none, and the model reads the same default for a new one. A close is told to the mover alone (never to `then` or the creator; the owner sees closes in Landed). A background agent may create items. An item is no longer refiled to its creator's project. The board and the recycle check use mover, needs and `then`, never the stored creator; an item the owner moves sits under its `then` agent, else in a "no agent" group. `then` defaults to the builder doing the work, not the front agent that relayed it: the background mover that hands the item to the owner, else the builder when it is the mover or named in `next` as the one building, else the model's default. The old role word is a retired term (`tests/retired_terms.toml`), so it cannot come back.

- **A wait on a list of waits** (`stackshot/waits/wait_list.py` and `wait_list_write.py`, `gate_waits` in `stackshot/service/gates.py`, the list reading in `stackshot/model/model.py`, `stackshot/waits/watchers.py`, `tests/wait_list_scenario.py`, `tests/wait_list_write_scenario.py`). An item can wait on 2 to 8 things at once. The stored shape is `metadata.waits`, a list of lines, each `{"kind": ..., ...}` with the fields of its kind (`time` `until`; `anchor` `anchor` and `event`; `item` `after`, one item id; `relay` `event`; `event` `event`), beside `metadata.wait_mode` (`all`: the item comes back when every line has arrived; `any`: when the first has) and `wait_kind = "list"`. The item's own `until` is the list's backstop day (the same format and the same rule for a wait of more than 7 days as an item or anchor wait), and `post_wake_mover` is who takes the item when the wait ends. The server adds `arrived = {"at": epoch, "what": text}` to a line when it arrives; nothing a caller writes sets it; a stored `at` that is not a finite time before year 10000 (`wait_list.ARRIVED_AT_MAX`) reads as no arrival, and a line's anchor, event text and item id keep only their first 300 characters (`wait_list.LINE_MAX`): that is a limit, not a cosmetic clip, since an anchor or an item id longer than that would no longer match the notice or the item it names, so anchor, event text and item ids in a list are limited to 300 characters and the write path refuses longer ones (a stored longer one is only clipped when it is read; an arrival's words are only clipped). `waits` and `wait_mode` are in the wait's field group, so every clear of a wait (its end, a close, `clear_wait`, a date alone) drops them with the rest. A list that does not hold (fewer than 2 or more than 8 lines, a kind outside the five, a line missing its fields, a mode that is neither, no backstop day) is ignored: the item reads as the single wait it would be without the list, the model says so in its notes, and a counter (`wait_list.MALFORMED`) counts each such read. `wait_kind=list` is no value a call passes (`check_fields` refuses it with the other five named): the server stores it when a `create` or `update` passes `waits` (how a list is written, and each refusal, is under *A list is written with `waits`* in `docs/waiting-and-doing.md`), and it never stores a list of one line (an edit that leaves one line stores the single wait that line is). While an update judges its write, the stored `until` stands as the old working field `wake`, so `wait_list.backstop` reads `until`, else `wake`. The phase stamp writes `waits_on = "list"` for such an item.
