# The board pages

What this page covers: how the board pages are drawn: search, the item page, the home lists, rows, cards, buttons, the side panel and the CI runners page. Back to the [README](../README.md).

**The CI runners page** (`stackshot/web/runners.py`, `GET /runners`, `GET /runners.json`, behind the board's sign-in). It opens with five count cards (Runners, Running, Idle, Disabled, Offline; the Offline card turns red above 0), then one row a machine in the Machines panel's order: its full name, its state (`on · 2 of 3 busy`, `disabling · 1 job finishing`, `disabled since 14:35`, `not reachable`) and a Disable or Enable button, beside the machine's runners (state, and the job a running one is on). The words are fixed: a runner turned off on purpose is **disabled**; **offline** is a runner GitHub lists as offline that nobody disabled, for 5 minutes or more (a fault, or a machine that cannot be reached); a runner offline for less than that (`runners.OFFLINE_GRACE_S`) is one restarting between two jobs, as a runner does between two jobs: it reads `restarting` (with the idle dot), is not red and counts as idle, in the side panel too. The time it has been offline is `off_since` on its row in the snapshot file `runners-snapshot.json` only (not in `/runners.json`), cleared when the runner is online again; it is carried only from a snapshot read at most 3 times the slowest rebuild interval ago (the largest of `[runners] cache_s`, `[runners] panel_refresh_s` and `[publish] every_minutes`, which sets the pace when nobody views the page: 30 minutes with the defaults, never less than the 5-minute grace), so a runner offline for good turns to a fault after 5 minutes whether or not the page is open, while a snapshot older than that (a page nobody opened for hours, a long restart) starts the clock again. The table is swapped every 30 s from `/runners.json`; the pages never wait on GitHub or ssh: they draw the last snapshot at once, with how old it is and whether a rebuild is running, and a viewer finding it older than `[runners] cache_s` starts the one background rebuild every viewer shares (the last snapshot is kept in `<paths.state>/runners-snapshot.json`, so a restart draws the table at once). A busy runner whose job GitHub has not listed yet, or no longer lists, reads `starting job…` or `finishing job…`; `job not found` is left for a mismatch that lasts over 3 minutes. **The button** (`POST /runners/switch`, form fields `box`, `act` = `off` or `on`, `token`) runs `bash <[runners] switch_script> off|on <box>` on the server (the switch script, which ssh's to the other machines), never through a shell string and under `switch_timeout_s`, one press at a time per machine. Disable lets a running job finish and then the machine takes no new job (it is not a hard stop); the answer, ok or the error in plain words, is shown above the table. The gates are the answer form's: refused with 503 on a read-only copy, 403 unless signed in to the board with a real address (an open board is refused too, as for /answer and /watch, and draws no button), from the board's own origin, with the page's token (an HMAC over the viewer and the machine); 413 above 4096 bytes; 400 for an action other than off or on, or a machine that is not one of the fleet's names or a `[runners] boxes` entry named in `[runners.ssh_hosts]` (spare-box, outside the sala fleet), before any command runs. No script configured = no buttons. The side panel's Runners card reads `disabled` for such a machine.

**Runners are optional** (`runners.enabled()`, `runners.unused()`). A board with no `[runners]` table, or one whose `repos` is empty, does not use the feature: nothing reads GitHub or ssh for it, no rebuild thread starts and no snapshot file is read back. `/runners` and `/runners.json` still answer, with one plain line ("This board does not use self-hosted CI runners.") in place of the cards and the table, and the side panel's Runners section reads "not used on this board". When `repos` is set and GitHub lists no self-hosted runner for them (the runners are retired), the page says so in one plain line ("GitHub lists no self-hosted CI runners for the repositories this board follows.") and the section reads "no self-hosted runners"; no red card, no empty table. A failed read is still shown as an error. With runners listed, the page is as described above.

- **The search** (`stackshot/web/search.py`, the box in `stackshot/web/ui/search.py`, `GET /search` in `stackshot/web/server.py`). One box in the header of every page of the board sends a plain GET to `/search?q=…`, behind the board's sign-in like the board, and opens the results in a new tab (the form carries `target="_blank" rel="noopener"`, so Enter and the button both do it, with no script), which leaves the page the search started from as it was; on the Search page itself the header box and the filters search in place, so tabs do not pile up (`ui/search.py` `box(q, in_place=True)`, passed by `page_header(search_page=True)`). An installed app window has no tabs, so the head script that sends a same-origin `target="_blank"` link to the window itself does the same for a same-origin GET form. The results page groups, in this order: **Items** (subject, goal, description, next lines and ask of every item, open or closed, found by its id as well), **History** (one entry per line of the item page's History, at most 600 characters), **Projects** (the Current state of every active project page, read from the pages checkout `[paths] brain`, never from gbrain) and **Sessions** (the names the board reads, linked to the fleet tool's view while the session has a live pane, as everywhere else). A result links the item or the page. Every word typed is a prefix match (`quok` finds Quokka; a run of Hangul or Kana syllables is one word, so a stem finds the same word with a particle glued on), all words must match, and a query under two characters finds nothing. No model call: SQLite FTS5 from the standard library (a `LIKE` scan over the same table where the SQLite build has none), in `<[paths] state>/search/index.db` (derived data: dropped and rebuilt on a schema change, in memory if the file cannot be written; a few MB for a store of several hundred items and pages). Each item file's modification time and size are stamped beside its rows; the server's one item save (`_save`) asks for the item to be re-indexed a moment later in the search thread, the results page syncs before it answers (the item's text only, so a write is never missed, a file edited by hand is picked up, and the page never waits on git; its History is the thread's), the stamp of an item holds the modification time of its issue's comment copy while the mirror is on (the History is then the issue's comments), and the thread (nice 10) also runs at start (the first build reads each item's History, in chunks, newest first, the database lock held only for the writes) and every five minutes. A pass never drops more than a tenth of the stamps (a Board that read part of the store), an item whose History came back empty is retried after ten minutes, and a damaged index file is dropped and built again. A deploy restarts `stackshot.service`; until the first build is done the results page says the index is still being built.
- **The search page of the board at the root is the fleet tool's search, in the board's rows** (`stackshot/web/ui/search.py`, `search.words` / `find` / `snippets` / `page_mtime`, `GET /search` in `stackshot/web/server.py`; `tests/ui_search_scenario.py`). The rule is that tool's: the query is lower-cased and split on white space, with "quoted text" kept as one unit, and every unit must appear as a plain case-insensitive substring somewhere in the same entry. There is no word or prefix logic (`redesign` finds `redesigned`, and a stem finds the same word with a particle glued on), a quoted phrase must appear contiguously as written, and there is no operator syntax. The page is one list, newest first, of all four kinds (a kind label on each row: Item, History, Project, Session; an item and its History rows carry the state tag), ordered by the time of the hit: an item's last change, a History entry's own time, a project page's file time, a session's last sight. Above it **When** (1 h, 6 h, 24 h, 3 days, 7 days, All, Dates with From and To in the board's zone), **Kind** (Items, History, Projects, Sessions) and **State** (Open, Closed; it filters items and their History and leaves projects and sessions alone), each box with the number it adds with the other filters as they stand. A search started from the box is the last 7 days (items live for weeks, so the fleet tool's 6 hours would hide most of them). 25 rows show first and `Show 25 more` (a link that adds 25 and lands on the first new row) goes on to 200, past which the summary says `cut at 200`. The whole search is in the address (`q`, `when`, `from`, `to`, `kind`, `state`, `n`, with `f=1` marking a submitted form so that an unticked box is off); the filters are one plain GET form whose chips are named submit buttons (`w` wins over the hidden `when`), and a small script submits it when a box or a date changes. A History row has no author on its who line: the author is a git read, which the results page never makes. A search that finds nothing says how many matches the window leaves out and which unticked boxes hold more.
- **The item page on the model** (`stackshot/web/itempage.py`, `Board.item_html` in `stackshot/web/render.py`). The goal is the title (the subject when there is none); one state line says the state in words (the state chip, `since <when> (<age>)` or the close's age, `by <session>` on a closed item, and `handed over, not yet taken` or `waits for recycle` when they apply; it names neither the mover nor the `then`: the sidebar's Mover row and Then row do, and a waiting item's wait block says what it waits on, `watched by <the scheduler | the server | the anchor module>`, `<until | ask by | backstop> <when>` and `then <mover>`; the line never names the project either: the sidebar's Project row does, in both layouts); there is no "Where it stands" section and no latest-change line beside it, the History says what changed). The ask, its buttons and the answer box show only while the item is alive with the owner as mover (an open item he does not move has the comment box in the same place, open, under the state line; the Comments fold keeps the list of comments only; the answer route is unchanged). Next shows every line, numbered, each `<mover>: <action>` (an unnamed line gets the item's mover); none is folded. A waiting item shows its wait and its chases. The sidebar opens with **Mover, Owner and Creator** (one group, in that order; the Owner row only when the item has a contact; the Mover row names the agent the item sits under, "no agent" when none, and is drawn once, never also in More details or on the line under the title) and goes on with project, then, priority, wake, anchors and the GitHub issue (and the For you control); today's other fields (agent at work, due, confirmed, work, after, observers) sit in a closed "More details" fold. The page is one markup in both layouts (the panel beside the item from 768px, stacked on a phone), so the order holds in both. The page runs: title and state line; Your step, the ask and its answer box, or the comment box; Next; Background; History; Comments. Background is the item's `description` (the field and the tool parameter keep their name), a fold (open): what the item is, where it lives, what done means, never steps. The write guard says so: on an item that is his to move (he is the stored mover, its state is your-step or your-call, stored or derived, or its needs hold his decision), a description write that adds a numbered line (`1.`, `2)`, also after a `- `) or a `! ` line outside a fenced block is refused, pointing at `step`; it is judged on what the write adds (a typo fixed beside an old line passes, as for commands), and a backticked command or a shell fence is refused on your-step with him as the mover as before. An agent's own items keep ordinary multi-step descriptions. History (one line per revision with its author, `written_by`) and Comments are folds, closed by default.
- **The board's pages are drawn by `ui/`** (`ui/`, the routes in `stackshot/web/server.py`). The home (`/`), an item page (`/items/<id>`), a project page, the Projects page (`/projects`), Closed, Search and Runners are drawn by `stackshot/web/ui/render.py`, `stackshot/web/ui/search.py` and `stackshot/web/ui/runners.py`; `stackshot/web/render.py`, `stackshot/web/search.py` and `stackshot/web/runners.py` at the top keep the data side (the markdown and the brief, the search index, the runners snapshot and switch). Every address a page writes (link, form action, redirect, script fetch, paging, search form, the runners refresh) goes through `ui.under()`, which adds the prefix `ui.PREFIX` (empty, so an address is the bare root address). **Shared at the root:** the write routes (answer, watch, Mark seen, Clear and Undo on Closed, the runners switch) are one handler each, change the one store and redirect back (a form's `back` is followed only when it names a page of the board); the JSON endpoints and files (`/answer-tokens`, `/audit/*`, `/receivers.json`, `/client/*`, `/ui/*`, `/routing/*`, `/prefs/panel-order`, `/landed/seen`, `/runners.json`, `/render-stamp`, icons, font, manifest) have one address each. Sign-in needs nothing new (the cookie has path `/`; a visitor sent to `/ui/login` comes back to the address asked). The home at `/` is drawn on request and kept for 30 s (dropped at once by a publish or a write from a page). `tests/board_pages_scenario.py` checks the pages, the writes and where they return, and the sign-in return.
- **A temporary probe page, `GET /probe/sala-link`** (`Board.probe_html` in `stackshot/web/ui/render.py`, behind the board's sign-in, `tests/sala_link_probe_scenario.py`). It writes one session link six ways (a plain link with and without `target="_blank"`, an Android `intent://` link in three forms, two script buttons) so a tap in the installed app on an Android phone shows which one opens the installed sala app instead of a browser tab; `?to=<address>` picks the target and is used only on the origin of `[client] session_view`. It changes no link on any other page, and it is removed, or its winning form is promoted into the session links, in the follow-up change.
- **The side panel's Projects section** (`projects-panel` in `stackshot/web/ui/render.py`, drawn by `Board.panel_blocks` like the Runners section, a fold with a grip, last by default) is the way to the Projects page: it replaced the lone "Projects" link that sat above the sections. One card per scope, in the Runners cards' look: the scope's name, its count of projects ("2 projects"; archived ones are counted, and the card's hover text gives the split, "1 active, 1 archived") and a link to that scope's group on the page, `/projects#grp-<name>` (the name lower-cased, anything but a letter or digit a dash; `Board.scope_anchor`; two scopes whose names come to the same slug keep distinct ids, the first the plain slug and a later one `-2`, `-3`…, the same on every draw). The scopes and the counts come from the same lists the Projects page draws (`Board.scopes`, `Board.project_keys`), so a new scope shows up here by itself; a scope with no project shows 0 and, having no group on the page, a link that lands at the top; the page's first row for a scope carries the id. A click on a link in the open phone drawer closes it only for a plain same-origin link with no target, so a link that opens a tab or leaves the board keeps the drawer. `tests/board_pages_scenario.py` and `tests/home_scenario.py` check it.
- **The order of the side panel's sections** (Machines, Runners, Anchor hub, Audit, Projects) is the signed-in person's own and is kept on the server, so a PC tab and a phone show the same (`stackshot/web/uiprefs.py`; `<state>/ui-prefs.json`, `{"users": {"<address>": {"panel_order": [...]}}}`, written whole to a temporary file, fsynced and swapped in with `os.replace`, under a lock; a file that does not parse is moved aside to `ui-prefs.json.bad-<epoch>` and the settings start empty). Each section's header has a grip: dragged with a pointer (mouse, touch, pen) an orange (accent) drop line shows where it lands; clicked, or focused and Enter / Space, it opens a menu (Move up, Move down, Move to top, Move to bottom; the moves that do not apply are disabled), the way for the keyboard and a phone. Each move is announced in a live region ("Runners moved to position 2 of 5") and saved at once with `POST /prefs/panel-order`, body `{"order": [...]}` or `{"reset": true}`: signed in (403 otherwise), from the board's own origin (403), a JSON body of at most 4 KB (415, 413, 400). Names the page does not have are ignored; the names sent (the sections the page shows) take the places they hold in the person's stored full order, so a section the page did not draw keeps its place; on reading, a section the stored order lacks is put back right after its default predecessor (first when none), so a release that adds or removes a section needs no migration; a settings file that cannot be read (not a missing or unparsable one) is never replaced by an empty one: a save answers 503 and the script says it was not saved; an order equal to the default is stored as no entry. The page is drawn in the default order (the home is one kept draw for everyone) and the order is put in on the way out for the signed-in person (`server._panel_ordered`, `ui.render.apply_panel_order`, each section wrapped in `<!--ps:id-->` markers), so the saved order is in the first paint and nothing moves on load. There is no reset button: the grips move every section, and moving them back is the way to the default order (the `{"reset": true}` body stays for a script). Every section's first block sits the same 8 px under its title, with the grip clear of it. `tests/panel_order_scenario.py` checks it; `tests/panel_order_check.py` is the manual browser check (1280 and 390 px, light and dark; `PANEL_ORDER_SHOTS=<dir>` keeps screenshots).
- **Whether the side panel is open** is the signed-in person's own too, kept on the server beside the section order (`stackshot/web/uiprefs.py`; the same `<state>/ui-prefs.json`, `{"users": {"<address>": {"panel_open": false}}}`), so it holds on every page, reload, browser and device. **Open is the default and is stored as no key**: only a person who closed the panel has `"panel_open": false`, opening it again removes the key (and a person left with no setting has no entry), and a value that is not `false` reads as open, so a file written before the key existed needs no migration. It applies on a wide screen (800 px and up): the pin beside the page. Under 800 px the panel is a drawer that starts closed whatever is stored, and opening or closing the drawer is never saved. Every page, the item page included (it no longer starts closed on its own), is drawn with the panel open (`<body class="panel-pin">`, the button `aria-expanded="true"` with the title "Hide summary panel"); the server turns that into the closed form for a person whose stored state is closed (`server._panel_ordered`, `ui.render.apply_panel_open`: a bare `<body>` and the button "false" with "Show summary panel"), on the way out like the section order, so the first paint is right on every page and nothing flashes, and the home's one kept draw still serves everyone. A click on the title bar's button on a wide screen pins or unpins the panel and saves it with `POST /prefs/panel-open`, body `{"open": true}` or `{"open": false}` (a real boolean, else 400), behind the order save's gates (`server._prefs_body`): signed in (403 otherwise), from the board's own origin (403), a JSON body of at most 4 KB (415, 413, 400); a settings file that cannot be read or written answers 503 and is left as it was. Opening a panel that is not stored closed writes nothing. The save leaves the home's kept draw alone (unlike the order save, the draw does not depend on the state). The script sends it with `keepalive`, so a click followed at once by a link is not lost. One save is in flight at a time (the last click wins) and a failed one is ignored (the panel is as the person left it on that page; a visitor not signed in gets 403 and the default, open, on the next page). The width crossing 800 px returns the panel to the state last chosen or drawn, not always to pinned. The in-place update swaps blocks by id and never touches the body, so it keeps the state. `tests/panel_open_scenario.py` checks it (the pages, the route, the store and the script, including a run of the script in node); `tests/phone_width_check.py` is the manual browser check.

- **The pages can read in a second language** (`stackshot/web/i18n.py` is the mechanism, `stackshot/web/i18n_catalog.py` the English text; `tests/locale_scenario.py` and `tests/locale_pages_scenario.py` (search, runners, the colour tool) and `tests/locale_audits_scenario.py` (the Audits, routing, Projects and Closed pages, For you, the sent notices, the said tags and the sessions list); `python3 tools/i18n_report.py` says how much of each page module is converted). What switches is the interface: labels, buttons, headings, state words, tooltips, dates and ages. What does not is item text (titles, descriptions, steps, history, asks) and the text of the tools, which stay as written. **English is the default and the only language the repository holds.** Every interface string has a dotted key by area (`state.*`, `panel.*`, `home.*`, `item.*`, `wait.*`, `answer.*`, `watch.*`, `more.*`, `link.*`, `search.*`, `runners.*`, `sessions.*`, `foryou.*`, `sent.*`, `said.*`, `routing.*`, `closed.*`, `projects.*`, `audit.*`, `page.*`, `js.*`, `chrome.*`, `date.*`, `age.*`) and its English text in code; a page asks `t(key, lang, **fields)`, and a page script asks `SST(key, {fields})` (English in the page head, the person's language put over it on the way out). A second language is one JSON file outside the repository: `[ui] locale_dir = "<folder>"` in the instance config (off by default; `stackshot.example.toml`) names a folder, and `<folder>/ko.json` is an object of key -> text, with the keys of the English catalog. The file is UTF-8 (a byte-order mark is fine), read again when it changes and checked when read: a key the catalog does not have is ignored, a value that is not text, that cannot be written out as UTF-8 (a lone surrogate) or that names a `{field}` the English text does not have falls back to the English text for that key, and one warning line per file goes to the server's log (never a page error, never a line per page). A missing folder, file or key is English for that string. A file with no usable key at all (an empty object, only unknown keys) counts as not loaded: no switch, and the pages stay English. The side panel's foot carries the **KO / EN switch**, drawn only when a second language has loaded (a board with no folder shows none) and only for a signed-in person, since the choice is saved per person (a visitor who is not signed in reads English and gets no switch); it is a pair of buttons (the pressed one is the language in use) and a keyboard reaches them like any button. The choice is the signed-in person's own, kept on the server beside the panel settings (`stackshot/web/uiprefs.py`: `"lang": "ko"` in `<state>/ui-prefs.json`; English is stored as no key; `POST /prefs/lang` with `{"lang": "en"}` or `{"lang": "ko"}`, behind the same gates as the other `/prefs/` saves), so it holds on every page, reload and device. A page is drawn in the person's language (the home keeps one draw per language) and `<html lang>` follows it. Dates and ages are templates in the catalog too (`date.full`, `date.day`, `date.ord.*`, `date.wd.*`, `date.mon.*`, `age.*`), so a language writes its own form from its file alone. Stages 1, 2, 3a and 4 convert the side panel, the home page, the item page (its areas `item.*`, `wait.*`, `answer.*`, `watch.*`, `more.*` and `link.*`), the rest of the board's pages module (`ui/render.py`: the rendered line as one template with the age wherever a language puts it, the History's whole-line templates with one key per kind of change, the due, command, session and mockup lines, the answer box's replies), Search, Runners, the colour tool and the small pages; the Audits, routing (a project's details), Projects and Closed pages, For you, the sent notices, the said tags and the sessions list follow in stage 3b. The Audits page's English words stay in `stackshot/audit/audit_overview.py` (its JSON at `/audit/status` and the card's tests read them); the page draws them through the catalog by looking each word up (`audit.desc.*`, `audit.pace.*`, `audit.mode.*`, `audit.source.*`, `panel.audit.group.*`), and `tests/locale_audits_scenario.py` fails when a word and its key drift apart. Left in English on purpose: the board's refusal lines for a POST (they have no request language), the brief text, the hold words, and the router's ruling words in the routing summary (the router's own vocabulary). `tools/i18n_report.py --list` names what is left.
- **The home's count cards are 60 px tall at every width** (`nav.hcards` / `a.hcard` in `stackshot/web/ui/render.py`): a label never wraps (`white-space:nowrap`, an ellipsis as the last resort), and where the full label does not fit the card it shows its short form, chosen by the width of the cards' column with a container query (`container:hcards/inline-size` on the nav, `@container hcards (max-width:680px)`), not by the window: with the side panel pinned the column is 288 px narrower than the window. Today only Queued for release has one ("Queued"; the rest of the label stays in `span.more`, clipped, so a screen reader still reads it all). Before, the wrapped label made the grid stretch every card to 80 px. `tests/ui_kit_scenario.py` checks the markup and the CSS; `tests/hcard_height_check.py` is the manual browser check (1280, 800 and 390 px, light and dark, panel open and closed, card heights by `getBoundingClientRect`; `HCARD_HEIGHT_SHOTS=<dir>` keeps screenshots).
- **The home's four lists are grouped by scope** (`Board.scope_groups`, `Board.scope_sections` and `Board.home_section` in `stackshot/web/ui/render.py`, with `stackshot/web/ui/groups.py`; `tests/home_groups_scenario.py`). The Closed page's New and Last 14 days sections draw the same subsections through the same two methods. Each of Your move, On agent, Queued for release and Waiting draws its rows in one subsection per scope, in [project_scopes] order (read through `projects.scopes()`, as the Closed page reads it), under the scope's name and its row count in the Closed page's `h3.iscope` heading (`<details class="fold sfold hscope" data-fold="home.your-move.home" open><summary><h3 class="iscope">home <span class="count">3</span></h3></summary><ul class="ir-rows">…`): a native `<details>`, the project page's list fold, so a tap on the heading folds the scope's rows. A subsection renders open, also inside a list that starts closed; each carries its own `data-fold` key (`home.<list>.<scope>`, `closed.new.<scope>`, `closed.completed.<scope>`) so the live swap on home carries a fold the viewer closed across a refresh, and nothing is remembered across a reload (home's fold script stores no state). A row's scope is `Board.landed_scope` of its project's board row (the project's mark or `derive_scope`; an item with no project is in the default scope), the reader the Closed page uses, not the older `proj_scope`. A scope with no rows in a list draws no subsection, and a list with no rows keeps its one empty line. Inside a subsection the list keeps its own sort (Your move and On agent oldest first, Waiting by end date); which lists start open, the lists' own counts, the count cards, board.md and the project pages (which draw `project_items`, not this) are unchanged. A row whose scope is not one of the configured scopes is not dropped: it sits in a last subsection under the scope's own name (several such, by name). The rows still hide the instance's bracketed subject tag (`[work] `, `[home] `) (`Board.bare`).
- **A row is a card with a colored left edge, and home and Closed name the project and its owner above the title** (`row` and the stylesheet in `stackshot/web/ui/kit.py`, `Board.home_row`, `Board.done_row`, `Board.landed_html`, `Board.project_line` and `Board.row_line` in `stackshot/web/ui/render.py`; `tests/ui_kit_scenario.py`, `tests/rows_background_scenario.py`, `tests/owner_on_rows_scenario.py`). Every list that draws the shared row (home's four lists, the Closed page, a project's items, Search) shows each item as its own card (the board's quiet border, 10px corners, a 12px gap between cards) with a 3px edge on its left in the list's color (`data-st` on the `<li>`): orange Your move, blue On agent, purple Queued for release, grey Waiting, green for a close on the Closed page's New section; Last 14 days, Search and a project page's closed items keep the plain edge. Home's rows and the Closed page's rows (New and Last 14 days) open with a small quiet line, `project · owner` (`.ir-proj`, drawn from `project_html` of `ui.row`): the item's top-level project as a link to its page (an item filed on a sub-page names the project that owns the sub-page, in name and link, never the sub-page; the project page's sub-page badge on the who line is unchanged), then the item's owner, the name the item page's side column shows as **Owner** (the item's contact, see *[An item's contact](projects.md)*), a link to the fleet tool's view of the session while it has a live pane and plain text otherwise (`Board.sess_html`, as every page draws a session). An item with no owner shows the project alone, and one with no project the owner alone. A project page's own rows (open and completed) show the owner alone on that line, the page saying the project; an item with neither has no line. The owner is resolved by the same function the item page uses: the server hands the board its `_contact_label` (`Board(..., contact_of=...)`), the board calls it once per item in a render (`Board.row_contact` keeps the answer for an item drawn twice, as on the Closed page) and for the rows the page draws only, with no network call; a board built without it (a tool, a test) reads the stored contact, as the side column does, and a resolver that fails leaves the row on the stored contact.
