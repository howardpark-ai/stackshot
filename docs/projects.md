# Projects: the record first

What this page covers: how a project is defined by its record, the project verbs and the table of commands, archived projects, and an item's contact. Back to the [README](../README.md).

A stackshot project is defined by its entry in `project-record.json` (section `projects`, `stackshot/projects/project_registry.py`), keyed by its permanent id (`prj_<8 hex>`): its name (the prefix of its agents' names), title, scope, status (`active` or `archived`), agents map with each agent's mandate line (front and background), hub, `page` (a pointer), `former_keys`, `former_names`, `former_agents`, and `made` / `retired` with who, when and how. **Every write to what a project is goes record-first** (`stackshot/projects/project_verbs.py`): one atomic change of the entry under the record's own lock, then a write of the page's mirror, which is three lines of the page's frontmatter and nothing else: `display-name:`, `agents:` and `status:`, computed from the record as it is when the write happens. The pane hooks, the page-maintenance jobs and the keeper lookups keep reading those page lines, which is why the mirror stays. A page edit made by hand to a mirrored line is not read (the entry wins) and the next mirror write puts the line back; a page that lists an agent the record lacks keeps its `agents:` block as it is, and only that block: the `display-name:` and `status:` lines are still written, and the answer says `mirror.state` is `failed`, naming the extra agents (the write would delete their lines for good). Clear it by listing each name with `agent-add`, which puts it in the record first; the next mirror then writes the block. `former_agents` is the other half of that guard: the names a retire or an agent rename has just taken off the entry, which the page may still list until a mirror has written it without them (a failed page write must not turn the name into a stranger the guard refuses); a mirror that leaves the page without a name drops it from `former_agents`, and a name listed again is dropped at once. A mirror that fails does not undo the change: the record is right, the answer says so, and the project's next change (or `mirror`) writes the page. Every answer of a verb carries `mirror` = `{state, key, note}` (`state` is `written`, `unchanged`, `would-write`, `none` for a project with no page of this instance's page store, `no-page`, `failed`, `exists` or `deferred`).

A project needs no page. Its `page` pointer is optional and may be a link to another knowledge base; page reminders, the page-first rule and the mirror apply only to a project whose pointer is a page in this instance's page store. A project with no entry yet (the migration has not reached it) gets one at its first verb, made from its page as the page store has it at that moment (not from the registry, which follows the pages checkout minutes late), with its pending agents folded in. That page is read **before** any lock is taken (`project_verbs.preread`; the server's `post project-agent` does it before `_PROJECT_LOCK`): a gbrain read can take a minute or two, and every record writer waits on the record's lock. Inside the lock a verb reads the record and nothing from the page store. If the pre-read fails, the answer carries a `warning` and the entry is made from the registry's copy of the page's lines; the mirror's guard keeps a line the registry did not know from being deleted.

**Sub-pages are never projects.** A key under another page (`projects/alpha/sub`) or a page with a `hub:` line is a sub-page: it gets no entry (the migration writes entries for top-level pages only), and `create` refuses it (400). Through a sub-page's key, `rename` and the agent verbs act on the top-level project that owns it; `archive`, `reopen` and `move-page` refuse it (400 naming the top-level page), because they act on the whole project; the id of a sub-page is refused by every verb. A project's page is one level (`projects/<slug>`): `create` and `move-page` refuse a key below another page.

`stackshot/tools/project.py` runs the verbs from a shell (`--dry-run` shows what would be written; `--json` the whole answer; `--by LABEL` names the actor):

| Command | What it does |
|---|---|
| `create NAME --scope S [--page KEY\|LINK] [--make-page] [--title T]` | a new project; with no `--page` it has no page and none is made |
| `rename PROJECT NEW_NAME` | the name changes, the id stays, the old name goes to `former_names`, pending agents under the old name are dropped |
| `move-page PROJECT NEW_KEY [--phase plan\|copy\|stub ...]` | runs `stackshot/projects/rename_page.py` (copy, then stub), then the record: the pointer is the new key, the old key a former key. A stub that refuses is a 502 saying the page was not stubbed; fix what it names and run `--phase stub`. A stub that was written for every page the plan listed but whose id move failed is not an error: the record is made right and the answer carries a `warning`; a stub that left a page under the old one unstubbed is a 502 too, with the same `--phase stub` retry (it skips the pages already stubbed). A page in a brain marked `shared` (the old key or the new one) is refused with 403 before any step runs, a dry run included |
| `archive PROJECT [--why W]` / `reopen PROJECT` | status `archived` (with `retired` = who, when, how, why) and back; the page's `status:` follows |
| `agent-add PROJECT NAME (--front\|--back) --mandate M` | the agent on the map, then the page's `agents:` block; the same agent again changes nothing, another mandate is a 409 (change a listed agent's line with `agent-mandate`) |
| `agent-mandate PROJECT NAME --mandate M` | the mandate line of an agent already on the map changed (its side, place and lister stay): the record first, then the page's `agents:` block, so the page cannot undo it and a second mirror write keeps it; an empty line is a 400, a name not on the map a 404 (`agent-add` first) |
| `agent-retire PROJECT NAME` / `agent-rename PROJECT OLD NEW` | the line off the map / renamed in place; the archive rule applies to a retire |
| `mirror PROJECT [--make-page]` | writes the three mirror lines again; answers state `retired` and writes nothing when the page is in a brain marked `shared`, or `[pages] copy_project_lines` is `false`. `--make-page` is independent of that switch: a page that is not there is made from the template on a brain not marked `shared` (state `written`, the template's lines only, no copy onto it), while a shared brain gets no page (state `retired`) (see [Second brains](second-brains.md#a-shared-brain)) |
| `adopt PAGE [--name N] [--scope S]` | makes a project from a top-level `type: project` page that has none: the page is read once (name from its `display-name:` line, the scope the registry derives, status, agents with the front and background split), the entry is written with `made` = who, when, `how: adopted` and the page's revision, its pending agents are folded in and the project is listed on purpose; from then on the page is only a copy the mirror writes. `--name` and `--scope` override what the page says. Refused: a link or a key outside the page dirs, a sub-page or a page with a `hub:` line (400, naming the page to adopt), a page that is not `type: project` (400), a page that does not exist (404), a page a project has or once had, and a name another project has (409) |
| `show PROJECT` | the entry and what the registry reads of it |
| `restore --list [--limit N]` | the last revisions of the record file in the store's history, newest first: the date, and what changed in the project count |
| `restore (--from-git REV \| --before DATE) [PROJECT] [--apply]` | puts the record, or one project of it, back as it was saved at a past revision. A dry run unless `--apply`; see *Restore a lost project* below |
| `restore --undo FILE [--apply]` | takes a restore back through the undo file it kept (a dry run unless `--apply`) |

**Restore a lost project.** The record is the one place a project's permanent id, its former keys and names, who made it and when, and its marks live, and the pages do not hold them: since the copy of the record onto the pages was retired (`[pages] copy_project_lines = false`, or a brain marked `shared`), the page lines are no longer a way to get a project back, and a page keeps no change made after that day. The way back is the record's own history. The server commits the store to its git repository within seconds of every change, so every past revision of `project-record.json` is in that history, and `restore` reads one of them (with read-only git commands: never a checkout, a reset or a pull in that repository) and writes it back through the same locked, atomic save the server uses.

1. **List the revisions.** `python3 stackshot/tools/project.py restore --list` prints the last 20 (`--limit N` for more), newest first, in the instance's timezone: `abc1234  Mon Nov 2nd 10:15 KST  3 projects (+1 -0 ~2), 5 ids (+0 -0)`. The numbers after the project count are the projects added, gone and changed since the revision before it. Pick the last revision from before the loss. (`--before "2026-11-08 12:00"` takes the last revision before a date, in place of a sha. A date is `YYYY-MM-DD` or `YYYY-MM-DD HH:MM[:SS]`, read in the instance's timezone, the one the list shows, unless it names a zone of its own (`Z`, `+0900` or `+09:00`, up to `+1400`); a date alone is its midnight; the years are 1970 to 2099. Anything else is refused, and a wall time that does not exist in the instance's zone (the hour a clock skips) is read as the moment after the gap.)
2. **Dry run.** `restore --from-git REV PROJECT` (PROJECT is an id, a page key, a bare slug, the name or a former name, as that revision knows it) says what would change: whether the project comes back or only its changed fields (the agents named, other fields as `old -> new`), the id rows and the mark that come with it. A restore that changes a project's status (it un-archives or retires it, or brings it back archived) says so on a line of its own (for the whole record, one line for each kind of change, naming the projects), and a changed order of the agents is shown (the first builder listed is the builder). Without PROJECT it is the whole file, and the answer names the projects made since that revision, which would be gone. Nothing is written until `--apply`.
3. **Apply.** The same command with `--apply`. It keeps the file as it was, with a small `undo.json`, in `~/.local/share/stackshot-runs/project-restore/<time>/` (`--run-dir DIR` for another folder), writes the record, and prints the undo command. It does not write any page lines: run `mirror PROJECT` afterwards if the page should show the restored name, agents and status.
4. **Undo.** `restore --undo <that undo.json>` is a dry run; add `--apply`. When nothing else has written to the record since, the file goes back byte for byte. When something has, a restore of one project takes back only its own entry, id rows and mark and leaves every other change; a restore of the whole record that has been written over since is refused, and the file as it was is named so you can look at it first.

One project comes back as its entry, its row of the id table, the rows of its page's sub-pages and former keys that the id table lacks, and its mark; the rest of the current record stays as it is. The restored entry replaces the current one if there is one, so agents added to it after that revision are not in it (the dry run lists them as `off`). **It restores the record as saved: a change made after that revision is not in it**, which is why you pick the revision just before the loss and read the dry run first. The pending agents table is not restored for one project (it holds agents waiting for a page line and is folded into entries by the verbs).

`restore` refuses, with nothing written and exit 1: a revision git does not know, or one with no record file; a record at that revision that does not read; a PROJECT the revision does not hold; an entry that would sit on the page key of a live project with another id, or take its name, or a page key (its page, a former key or its id row) that another live id already holds (archive, rename or move one of them first); a record that is being written (the lock stays held for 5 seconds); a store that is not in a git repository; and, for one project, a current record that does not read (restore the whole record then: the damaged file is kept for the undo). Wrong arguments are exit 2 with the usage.

The same verbs answer the client API: `stackshot/fleet/client.py post project --scope S (--key projects/slug | --name N [--page KEY\|LINK] [--make-page true\|false])`, `post project-agent`, `post project-agent-mandate` (the keeper or a front agent, by session id, as `post project-agent`), `post project-agent-rename` and `post project-agent-retire`. `stackshot/tools/migrate_project_record.py` (dry run by default) writes the entries of the top-level pages, folds the pending agents of active projects into them and clears the table; `--undo` removes only the entries that pass made.

**Items store the project's id.** An item holds `metadata.project_id`, the permanent id of the top-level project it belongs to, beside `metadata.project` (the page it is filed on: a copy of the project's own page key, or a sub-page's key as the item's plain detail link). `stackshot/model/item_project.py` is the one resolver: `key_of(meta)` reads the project's page through the id (a page that was moved or renamed, one of the project's `former_keys`, reads as the page now), `derive(key)` gives the id a key names (a sub-page or a page with a `hub:` line gives its project's), and the server reads an item through it when it loads one, so the board, the brief, the router's counts, the Projects list and the archive sweep follow a moved page with no write to the items. A save sets the id from the key (create, `update(project=)`, a re-file); `move-page`, `rename`, `archive` and `reopen` change the record only and the items follow. A save whose key names no project the record knows (a re-file to a registered page with no record entry) takes out the id the item carried, so the item reads as its new key and never as the project it left; an item that stores no id reads as stored too, so the pass below is what makes a moved page keep its items.

**An item's project is the top-level project; the page it is filed on is its detail link.** `item_project.project_of(meta)` is the page key of the top-level project that owns the page an item is filed on (`key_of` followed up through `derive`: a sub-page reads as the project that owns it, a page with a `hub:` line as the hub's project, a former key as the page now, a key that names no project as stored), with a stored `project_id` or without one, and `top_of(key)` is the same for a page key. It is a display and grouping reader and writes nothing. The readers that show an item's project use it: board.md's `- project:` line (the label is the top-level key, the link stays the mirror of the page the item is filed on), the item page's Project line, the search results' project label, and the `project:` line of `get`, `brief`, `create` and `update` (`item_project.line_of`: the top-level key, and `(filed on <sub-page>)` after it for an item on a sub-page, so the text keeps the detail link the markdown keeps as a link). The readers that need the page keep `key_of`, the page the item is filed on: page debts and the pages-owed nag, anchors scoped to a page, the keeper and agent lookups, the page-update gate, a page's own project page with its sub-page badge, the board row (`row_of` over the page, which already rolls a sub-page up to its project and keeps a `board_row: true` sub-page its own row: the items under that row show the top-level project on their `project:` line and link the sub-page, and the row heading above them names the sub-page; no live page sets it), the router's roots, move-page, rename and archive. The stored `project` and `project_id` are unchanged by it, so no migration and no write; `stackshot/tools/project_id_report.py` compares what `project_of` reads for every open item before and after the pass.

`stackshot/tools/project_id_report.py` stores the ids on the items already there (open and closed). Dry run by default: it copies the store to a private folder, runs the pass on the copy and compares what the board's markdown and brief, the server's brief and every open item's project key show before and after (it exits 1 when they differ). `--apply --sender <you>` runs it through the live server (`POST /client/migrate`, op `project_id`, the migration gate of `[model] migration`): it asks for the plan first, writes the undo file `<run-dir>/<pass id>/undo.json` before the first write, and writes only the one key in each file (no clock and no file time moves). `--undo FILE --sender <you>` takes the ids out again (op `unproject_id`; an item a later save changed is `kept`), and running either again is a no-op.

- **Archived projects** (`stackshot/projects/project_archive.py`, `stackshot/web/ui/groups.py`, `Board.projects_table` in `stackshot/web/ui/render.py`, `server._project_agent_retire` and `server._archive_tick`; `tests/archive_fold_view_scenario.py` and the 6f part of `tests/projects_picker_scenario.py`). The Projects page lists the projects whose page `status:` is one of `[project_scopes] retired_statuses` in a foldable **Archived** group after the active ones, drawn as home's scope subsections are (`groups.fold_block`: a native `<details class="fold sfold" data-fold="projects.archived">`, the heading with the count of archived projects, closed on load; inside it the projects are listed by scope, and the home fold script opens it for a link to a scope that has only archived projects). The project page's group of agents of an archived project says Archived too. **A project is archived when it has no agent and no open item.** The retire that sala already sends (`post project-agent-retire`) takes the agent off the project's agents map in the record and the page's block follows; the call then looks at the project, and when its agents map is empty, no agent is pending for it in the project record and none of the open items (its own, its sub-pages' and the pages that name it as their hub; on hold counts as open) is its, the project is archived: the record's status first (`retired` = who, when, how), then the page's `status:` line follows as a mirror write with a timeline line (the answer carries `archived` and `archive_note`). A page that cannot be written does not fail the retire: it is told in the note, and the record is archived all the same. An archive that cannot be made at all (the record cannot be written) puts the project on the wait list, so the sweep tries again. A project whose record has no `agents` field at all (never staffed) is never archived by a retire (not even by dropping its only pending agent); `stackshot/tools/archive_empty_projects.py` lists what the rule covers that nothing archived. With open items left the project goes on the wait list `<state>/archive-wait.json` and stays as it is; **the ten-minute archive sweep** (`archive_tick`, last of the ten-minute set) counts the open items of the waiting projects in one read and archives each whose items are gone, whether they were completed or handed to another project; a project that has an agent again, or is archived or gone, leaves the list without a write, and a second sweep over the same state does nothing. A retire answered "not listed" never archives, and a sweep never touches a project that is on no list. Sala sends nothing new: its existing retire call is the trigger.

- **Front-only projects** (`anchors.front_only`, `stackshot/anchors/anchors.py`; `tests/front_only_scenario.py`). A project is front-only when its `agents:` map lists no `background:` agent; there is no field to set, and adding a background agent to the map switches the project over. The map read is the page's own; a page with no map of its own (a sub-page) reads its hub's (`hub_of`: the nearest `hub:` line, else the top-level page). A page whose own map exists decides alone, so a sub-page that lists only front agents is front-only although its hub has a background agent. No map on the page or its hub, an unknown key and an empty key are front-only as well. A background agent counts whatever its mandate line says (the words "build", "maintain", "merge" or "engineer" the older builder tests look for play no part). Today three rules use it (the third, below, is the audit's): an answered step of a front-only project goes to the session its next open step names (else the item's contact), and one front agent may hand an item to another front agent of the same page through `mover=` (`stackshot/waits/builderless.py`); the audit sends a front-only project's unmoved findings and its unmoved digest to its -main agent instead of the global audit builder (`audit_run.Env.chase_of`, [audit](audit.md)). The other tests of "has a builder" (the router's builder pick, the hand-off and stall ladder) still read the background agents by their mandate words and move to this test one rule at a time. The older tests read the page, its top-level page and its member pages together, so this test differs from them in these shapes, which are the intended results: (a) a background agent whose mandate lacks the build words makes the project not front-only, where the mandate-word pickers (which these rules do not use) find no builder; (b) a sub-page with its own map of front agents under a hub that lists a background agent is front-only; (c) a sub-page with no map whose `hub:` line points at a page with no map, under a top-level page that lists a background agent, is front-only; (d) a hub whose own map lists front agents only is front-only although a member page that names it as its hub lists a background agent; and (e) a background agent that only the project record holds (its page line still owed) already makes the project not front-only. None of these shapes changes a project that exists on the running instance today, and the follow-up rule (the stall ladder's end) carries them.

- **An item's contact** (`stackshot/model/contact.py`, `service/contacts.py`, `stackshot/fleet/client.py backfill-contact [--apply]`, `stackshot/tools/backfill_contact.py`; `tests/contact_scenario.py`). The front agent (a user-facing agent) the person the board is for talks to about the item; the item page's side column leads with it as **Owner**, the session name linked to the fleet tool's view of it (`[client] session_view`), the label's hover text "the front agent to talk to about this item", and no row for an item with none. A **Creator** row sits under it (or first, with no contact) on every item, open or closed: whoever created the item, by the name the History's first line gives (`Board.creator_name`), a muted "unknown" when the item names none. Stored as `metadata.contact` (the session's permanent id where the fleet registry resolves it, so a rename changes nothing stored); `get` shows `contact:`, the client JSON rows (`item-facts`, the lists) carry `contact`. *Why not `owner`:* `owner` is a retired term (`tests/retired_terms.toml`; `metadata.owner` is still the stored creator, and the deprecated `owner` parameter of create and update is accepted until `[model] owner_param_until`), so a second meaning would mislead every old reader and session. *Who it is:* an item created by a front agent has that agent; a background agent's create names one of the project's front agents with `contact`, and the server refuses any other name, listing the project's front agents with their mandates and writing nothing; with no name it is the project's `-main` agent (`anchors.fallback_main`). Front and background are told apart by the project page's `agents:` map (`anchors.session_roles`, `contact.fronts`): an entry outside `background:` is front. `update` changes it with the same check, which also accepts the item's creator and its current contact while they are front agents (of any project): the front agent that made the item from talking with the person stays its contact wherever the item is filed, and can be set back to. A completed item keeps the one it had (reopen it first). *When it changes by itself:* the contact retires (the `project-agent-retire` endpoint) or is renamed (`project-agent-rename`): the items it was contact of fall to the project's `-main` agent, or follow the new name, and the endpoint's answer lists them as `contact_moved`; the item moves to another project: the contact stays if it is also a front agent there (a page rename keeps its agents) or is the item's creator (a front agent of any project), else it falls to the new project's `-main`; a stored contact that is no front agent any more reads as the project's `-main` agent until one of these writes it. It is a filing field (`_FILING_ONLY`): setting it moves no state clock, changes no mover, owes no page and sends no notice (a write through `update` still moves `updated`, as any write does; the backfill and the retire, rename and move passes are server writes that leave it). *The fill-in:* `stackshot/tools/backfill_contact.py` (dry run by default, on a copy of the store: the counts by rule and one line per item that would change; `--json`, `--store DIR`) and `stackshot/fleet/client.py backfill-contact [--apply]` (the running server writes, author `migration`, one filing write per item): an open item gets its creator when that was a front agent (`creator_front`), else its project's `-main` (`main`); a contact that is no front agent any more falls to the `-main` (`retired_contact`); one that has a live contact is left (`has_contact`), as is a project with no `-main` (`no_main`) and a closed item (`closed`). A second run writes nothing. There is no automatic pass at start.
