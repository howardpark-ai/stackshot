# Projects: the record first

What this page covers: how a project is defined by its record, the project verbs and the table of commands, archived projects, and an item's contact. Back to the [README](../README.md).

A stackshot project is defined by its entry in `project-record.json` (section `projects`, `stackshot/projects/project_registry.py`), keyed by its permanent id (`prj_<8 hex>`): its name (the prefix of its agents' names), title, scope, status (`active` or `archived`), agents map with each agent's mandate line (front and background), hub, `page` (a pointer), `former_keys`, `former_names`, `former_agents`, and `made` / `retired` with who, when and how. **Every write to what a project is goes record-first** (`stackshot/projects/project_verbs.py`): one atomic change of the entry under the record's own lock, then a write of the page's mirror (except `keeper`, which writes the record only), which is three lines of the page's frontmatter and nothing else: `display-name:`, `agents:` and `status:`, computed from the record as it is when the write happens. The pane hooks, the page-maintenance jobs and the keeper lookups keep reading those page lines, which is why the mirror stays. A page edit made by hand to a mirrored line is not read (the entry wins) and the next mirror write puts the line back; a page that lists an agent the record lacks keeps its `agents:` block as it is, and only that block: the `display-name:` and `status:` lines are still written, and the answer says `mirror.state` is `failed`, naming the extra agents (the write would delete their lines for good). Clear it by listing each name with `agent-add`, which puts it in the record first; the next mirror then writes the block. `former_agents` is the other half of that guard: the names a retire or an agent rename has just taken off the entry, which the page may still list until a mirror has written it without them (a failed page write must not turn the name into a stranger the guard refuses); a mirror that leaves the page without a name drops it from `former_agents`, and a name listed again is dropped at once. A mirror that fails does not undo the change: the record is right, the answer says so, and the project's next change (or `mirror`) writes the page. Every answer of a verb carries `mirror` = `{state, key, note}` (`state` is `written`, `unchanged`, `would-write`, `none` for a project with no page of this instance's page store, `no-page`, `failed`, `exists`, `deferred` or `skipped`, which is what `keeper` answers: it writes the record only and leaves the page's mirror alone).

**The record is read and written only on the server box.** `project.py` (every verb, a dry run and `show` included), `migrate_project_record.py`, `archive_empty_projects.py`, `keeper-mark`, `keeper-subpages` and `projects rename` are refused (exit 1) on a box whose config names another server host (`[release] deploy_ssh`, or `[server] box = false`): a copy of the record on that box can be far behind the live one, so a dry run would plan from old state and an `--apply` would write it over the live record. The refusal names the `ssh <host> '…'` line that runs the same call where the record is. `--store DIR`, a copy named on purpose, runs anywhere; a one-box install and the server host itself are not affected.

**An agent's surface.** An agent entry may carry `"surface": "slack"`: a front agent that answers messages sent to the Slack app, as opposed to a session of sala's list (no field, or `"sala"`, which is never stored, is a sala session and reads exactly as before). The record is the only place it lives: the page's `agents:` block lists a Slack agent as a front agent and has no surface line, and the mirror never writes one. A Slack agent is never the keeper, never a background agent (a mover) and never the `-main` agent: `agent-add` refuses it as the project's first agent (that agent is the keeper), with `--back`, or with a name ending `-main`; the `keeper` verb refuses it as a target; a page's `keeper:` line, a sub-page's `agent:` line or a `page_keepers` mark that names one is ignored as a name the record does not list is, and said in the row's `keeper_problems` and the registry check's `keeper-not-listed` debt; `agent-rename` refuses a rename to a `-main` name; a record that holds one of those, or a surface other than `sala` or `slack`, is refused by the reader in words. What reads it: the registry row carries `surface_agents` (the non-sala agents, name to surface); `anchors.front_agents` and `main_of`, the keeper's successor (`keeper.successor`), the router's recipients (`router.Context.agents`, `router_live._agents_of`), the hand-over list (`waits/successor.agents_of`), an item's contact (`contact.fronts`) and the audit's `-main` agent all skip a Slack agent and still find the project's other front agents; `roles.json` and `projects.json` carry `surface` on a Slack agent only, and its role stays `front`, so the gates that guard a front agent still treat it as one. Nothing is addressed to a Slack agent by the router, the audit or a stall notice. The `sessions` tool labels it `slack agent`, and `tools/project.py show` prints `slack` where it prints `front`. (`tests/agent_surface_scenario.py`)

**The keeper is a mark on one agent.** A project's keeper is the agent that keeps its pages current and hears the notices that fall to the project. It is a duty of one agent of the project, not a separate name. Three places can mark it (the third is a sub-page's own mark, below), and a project with no mark still has a keeper:

| Where | Form | Counts when |
|---|---|---|
| the project record | `"keeper": true` on one agent entry of the project's `agents` | always; at most one per entry, a second flag is ignored and reported as a problem line, never an error |
| the page | one optional flat frontmatter line `keeper: <agent name>`, beside `display-name:` (never inside the `agents:` map, so the map reads as it always did) | the name is an agent on that page's own `agents:` map; otherwise it is ignored and reported |
| the project record, for a sub-page | `"page_keepers": {"<sub-page key>": "<agent name>"}` on the entry of the project the sub-page sits under (the nearest page above it that has an entry, and only that entry: a mark held on an outer entry for a page under an adopted sub-project is ignored); an empty name says the page follows the keeper above it | the name is an agent that some project lists (its own map or another project's: a front agent of one project often keeps a working document in another); a key that is no page under the project, a name no project lists, a mark on an entry that is not the nearest above the page, or a page marked twice (the first rules) is ignored and reported on the project's row and, with the keeper debts on, as the registry-check debt `keeper-page-ignored`; never an error |

With no mark the keeper is derived by the rule the router already uses for a project's notices (`router_live.stand_in_of`, which `stand_in` is the live-page form of): the project's builder (the first background agent whose mandate says it builds), else its `-main` agent (`anchors.fallback_main`). Derivation reaches only a page that names nobody or lists agents itself. A page that lists no agent of its own or of its hub (a one-session page) has no derived keeper: the session its old fields name stays the keeper. So does a sub-page, or a hub-linked page, that has a `display-name:` line of its own and lists no agents of its own: its own line wins over the hub's builder (`legacy`). A retired project (its top-level page's `status:` is one of the scope settings' retired words: archived, done, closed and the rest) with no mark has no keeper at all: `keeper_agent` and `keeper_source` are empty strings, while its `session` stays as its old fields give it. The order that reads a page's keeper is `pages.keeper_of`: the page's `keeper:` line (role `mark`), then the record's flagged agent (laid over the page's row in `project_registry._overlay`; where both exist the record wins, as it does for every field), then the old keys (`display-name:`, `agent:`, `session:`) exactly as before. An unnamed sub-page inherits the keeper of the nearest page above it, a mark included.

What a registry row (`<store>/projects.json`) and a published record (`<state>/projects.json`) say about it:

- `keeper_agent` and `keeper_source`: the keeper agent and where it came from (a mark is read even on a retired project). `mark`: a mark names it. `derived`: no mark, and the project lists agents, so the builder, else the -main agent. `legacy`: no mark, and the old fields name it (a one-session page's `display-name:`, a sub-page's `agent:`). Both are empty strings for a page nothing keeps.
- With a mark, the row's `session` is the marked agent (its `role` is `mark`, or `inherited` on a sub-page under it) and the old value moves to `legacy_session` and `legacy_role`, so a reader that wants the project's name line reads those (`keeper.name_line`); the project's name, its agent-name prefix and its scope never come from the marked agent. A page nothing marks keeps every old field exactly as it was.
- In a published record, the marked agent's entry in `agents` carries `keeper: true`, and `keeper` is the marked agent. `keeper_problems` lists each mark that was ignored (only when there are some).
- A session keeps a page when it is the page's keeper by any of the three old or new rules: the mark, the old fields, an `agent:` line on a sub-page (`pages.keeper_pages`, `pages.keepers_any`).
- **A sub-page's own mark.** A sub-page an agent keeps as its own working document can be marked in the record instead of by its `agent:` line. The mark lives on the entry of the project above the page (`page_keepers`, see the table), because a sub-page has no entry of its own: it resolves to its project. The marked row keeps what it had (`session` is the marked agent, `role` stays `agent`, so the telling, the gates, the page debts and the notices read it as they read an `agent:` page, and the pages under it still do not inherit from it), gets `page_mark: true` and `keeper_source` `mark`, and the page's own line moves to `legacy_session` and `legacy_role`. Because the row looks the same to every reader, the keeper set before and after a mark that names the agent the page already named is the same (the fixture test in `tests/keeper_subpage_scenario.py` compares them). A mark the pass lays for a renamed session is the exception: the page's `agent:` line holds the old name, the mark names the new one, so the row's `session` becomes the new name, the readers ask the new name to keep the page from then on, and the old name stops reading it (for example, a session `old-x` renamed `new-x` that keeps 9 pages by their `agent:` lines keeps 0 under that name after the pass, and `new-x` keeps those 9). An empty name hands the page back to the keeper above it (role `inherited`, the old line kept as `legacy_session`): the keeper above it, the project's, gains the page, and a dead name's page follows the project's keeper by design. A mark is read on a retired project too, as the project's own mark is (the row says `mark` and its role stays `agent`); the registry check does not report a retired project's debts. The verbs carry the marks the way they carry the project's mark: `move-page` renames the keys, `agent-rename` renames the agent in every mark that names it, and `agent-retire` moves the marks of the leaver to the builder, else the -main agent, else removes them (the answer and its warning say which). A page with no mark is read from its `agent:` line as ever, so nothing about an unmarked sub-page changes. `page-keeper` (below) sets or hands back the mark of the pages named, on demand. `stackshot keeper-subpages [--apply]` (`stackshot/projects/keeper_subpages.py`) is the one-time pass that moves the sub-pages an `agent:` line keeps into the mark form: a dry run by default that prints one row per sub-page (the agent named, `mark`, `inherit` or `leave`, and why), `--apply` writes the record only, with an undo file in the `restore` format, and a second run changes nothing. It marks a page whose agent some project lists, hands back a page whose agent no project lists and no session runs under, and leaves a top-level page, a page under a project with no entry, a page under a project that lists no agent (a handed-back page would only follow an old form again), and a page whose agent is a running session no project lists (list it with `agent-add`, then run the pass again). When sala's list of running sessions cannot be read the pass makes no plan at all, a dry run included, and exits 1: a name nobody runs under cannot be told from an unknown one. Losses and gains are counted by what the readers of a page's agent answer (the row's session and role: `page_debt.page_agent`, `pilot_keeper`, `item_read`, the item keeper's first step), never by the names that keep a page including its old line, so a running session that would lose a page is named.

What a mark moves, and what it does not. The project's name, its agent-name prefix and its scope read the old name line (`keeper.name_line`), never the marked agent. The gates, the telling and the router read the mark first and fall back to the old fields:

- Notices for the project are addressed to the marked agent (`anchors.notice_name`), and the router's stand-in is the marked agent whether or not it is the builder (`router_live.stand_in`, `stand_in_of`, `telling.page_keeper`). A sub-page, or a page that falls to the project through its `hub:` line (`anchors.marked_for` reads the hub's mark for a page that lists no agents of its own), answers the same. The audit's page-debt fallback tells the marked agent first, then the builder, then the -main agent.
- The roles files (`session_roles`, `roles.json`) offer the name line of an unmarked page as a retired entry (it names the project, no session; sala skips it). The role `keeper` is still written for a name-line session: retired where the project lists a front agent or is finished, and unretired only for the one session of an active page that lists no agent (file_roles makes it front). It goes with the readers of the name line, not before: retiring that last kind of entry would take its front role from the session. The marked agent keeps its role, front or back, and carries `"keeper": true` (on its one entry, also when its best role is on another project than the one it keeps; the entry's `project` stays that best project, and `keeper_of` lists the pages that mark it, which the notices and the sessions tool name instead). A one-session project that lists its session as a front agent and marks it is a front agent in `roles.json` and in the gates alike, with no promotion; the sessions tool labels it `front agent and keeper of <project>`.
- `telling.front_keeper` keeps a marked front agent front (it is the keeper and tells nobody about its own), and tells the project's other front agents the marked agent, not the builder. `telling.keeper_words` says `the keeper of <project>` for it.
- The old fields are all still read where nothing is marked: a project with no mark answers exactly as before (`session`, `role`, the derived stand-in, the one-session promotion in `file_roles`).

**The keeper read gauge and counter** (`stackshot/projects/keeper_reads.py`; the state file `keeper-reads.json` in the service's state folder, `~/.local/state/stackshot/` by default; `stackshot keeper-reads [--json]` prints it). A removal of the old keeper forms (the page's own name line, an `agent:` line, `legacy_session` and `legacy_role`, the role `keeper`) is gated on two things, and the file holds both:

- **The gauge**: the number of registry rows whose `keeper_source` is `legacy` (only an old form names the keeper), with up to 50 of their page keys. `projects.sync` refreshes it each time it runs (the minute set's runner runs it about once a minute, the pause counted from the end of a round), and the file's write follows within a minute. The gauge carries a generation, a whole number that grows by one with every gauge written, an epoch, a random id the file gets from the moment it is created (a file made again after it was removed, or replaced after damage, has a new epoch, with a gauge or without one), and the time it was computed (never compared between publishers, so a clock that steps back or a file with a time far ahead cannot hold a gauge back from being written; the reader compares it with now: more than five minutes old, with no readable time, or ahead of the clock by more than five seconds is unknown). A publisher reads the file's (epoch, generation) BEFORE it computes its rows (`projects.sync` does so before it builds the registry), and its gauge is written only if the file still holds exactly that pair, which is checked again under the lock: a process that flushes late (it only recorded a read, or it is ending), a file removed or replaced since (also one that held no gauge when the publisher read it), and a publisher that was slow between reading and writing leave a newer gauge as it is. Inside one process the gauge step of `projects.sync` (the read of the file, the registry build and the hand-over of the gauge) is one at a time, so two syncs cannot share one reading and let the older rows win; a sync waits for the step for at most two seconds and goes on without a gauge past that (the next sync publishes it). A gauge that was refused is computed again from the registry as it is then and offered once more (a bounded retry of one, made outside the lock, with no sleep in it); a second refusal waits for the next sync. A gauge refused in a flush that could not compute the rows again (a timer or exit flush, a read flush that carries a pending gauge, a sync whose retry was refused too, a `sync(reg=...)`, which has no retry) leaves the file's gauge as it is and is recorded as `refused` in the file; the gauge left in the file was written by an earlier flush, which may be this process's own or another's. While it stands the gauge is unknown (nothing says whether the gauge in the file or the refused one is from the newer rows): `count_of` gives none, the report prints a `NOT RECORDING?` line (worded apart when the file holds no gauge because it was removed or replaced) and the status is 2, until the next gauge written clears it; a refused gauge that is computed again is written at once, and a process that recorded a refusal writes its next gauge at once too, so the unknown ends at the next sync and not a minute after it. The record is only as strong as the oldest writer in a deploy window (any flush of an older version, a heartbeat, a gauge or a read, drops it), and a `refused` value that is a string but not a time is printed as it is in the report (on one line, cut to 40 characters) and cleared by the next gauge, an empty string included (a record that is present counts, whatever its text), while one that is not a string is a damaged file. The stamp of no file never matches a file that exists, one a previous version wrote without an epoch included. `count_of` checks a document handed to it as it checks the file (its own values, not a JSON copy of them: a tuple, a set or a key that is not a string makes it unknown), and the report and the exit status read the clock once. That compare is what is guaranteed. What is not ruled out is one stale gauge: a process that computed its rows from an older registry and only then read the file can still publish them, and the next sync replaces that gauge within a minute. A refusal on record does not change this: a refusal leaves the epoch and generation as they are, so a publisher that read the file after the refusal but computed its rows before it can still write one stale gauge, which clears the refusal too, and the next sync replaces it. A later stage that removes the old forms does not trust the gauge alone: it recomputes the legacy rows from the live record when it removes, so a stale zero cannot pass it. A `sync(reg=...)` (a caller that built the registry itself) carries this weaker promise too: its reading of the file comes after the rows, and it gets no retry. A file from before the generation counts as generation 0, and a file with no epoch (one a previous version wrote) counts as epoch none and gets its epoch with its first gauge. Zero means every keeper is a mark or derived, and a zero gauge only counts as evidence after a gauge written by a process that started after the last deploy (a gauge from an older process was computed by older code). A gauge that has no `count` or no list of keys, lists more keys than it counts, or sits in a file with a number that is not finite anywhere (an `Infinity` or a `1e999` in an extra field included) is damaged: the file is kept as `.bad` and the gauge is unknown, never zero. `stackshot keeper-reads` then says `gauge unknown` and exits with status 2, which it also does when there is no file or no gauge yet. A gauge computed more than five minutes ago, or one with no readable time, or one dated ahead of the clock by more than the tolerance (a clock that was wrong when it was written, or stepped back since) is unknown in the same way, whatever the file's last write says (the heartbeat moves with any process's read, so it does not show that the gauge is current): the report prints a `NOT RECORDING?` line for it, says `gauge unknown`, and the status is 2. The option `--json` of `stackshot keeper-reads` is not the report: `--json` prints the file as it is and is not a gate: a stale or future-dated gauge shows there with its count, and only the report and the exit status say it is unknown. The compare by generation and epoch is only as strong as the oldest writer while an older version of the code still writes the same file (the window of a deploy): an older writer drops the epoch of a file that has no gauge yet, and a stale gauge can be accepted then. The gauge is the only figure that can say the old forms are not needed to name a keeper.
- **The sites**: a reader that answers a keeper question from an old form records itself, but only when that form decides the keeper of the row (the row's `keeper_source` is `legacy`: no mark on the row or its project). A mark that answers, with the old key read beside it, is never counted. Each time a gauge is written, the keys a site holds that are not rows of that gauge are dropped (a row that has since got a mark, or agents, leaves the sites with it, and a row that is legacy again is counted again by the next read: a process remembers a key only until the write that put it in the file, so another process's pruning cannot hide it), so right after a process writes a gauge its sites hold only rows of that gauge (a process whose gauge is older than the file's adds its keys without pruning, and the next gauge written prunes them), and when the gauge reaches zero every site has no key left; a site keeps its last read time and stays in the file, listed with 0 keys, until the file is reset by removing it. A site is the kind of read and the function that made it (`old form as the keeper <- router.<function>`), and counts each distinct row key once between two writes of a process, so a registry build that re-reads every row cannot hide a quiet week. The file keeps the last read time per site and up to 200 distinct keys. The sites: `anchors.name_line` (and `anchors.notice_name`, which reads it) and `anchors.session_hubs` (a page answered by its own old form, not by a mark), and the readers of the role `keeper` in `roles.json` (`telling.keeper_words`, `proofs`, `audit_checks`: a name-line session that is not retired, counted under its project's page key).

Not counted, and they stay until the readers are removed: `keeper.names_of` (a row's `legacy_session` exists only under a mark, so it is never what names the keeper), `pages.keeper_of` (it reads a page's own lines, and a mark lives in the project record, which it does not see), and `keeper.fields` with the page row built in `project_verbs` (they run on rows the record has not been laid over yet, so their answer is not the final one; the gauge counts the final rows). Not counted either, because they never ask who keeps a page: the readers of the name line for the project's name, its agent-name prefix and its scope (`keeper.name_line` and its callers in `projects.py`, `project_registry._overlay` and the name checks of `project_verbs`; the name line is the project's name there). `stackshot keeper-reads` prints both lists as `stays` and `until removed`.

What a quiet week says: the gauge at zero says no row's keeper depends on an old form, and that is the figure a removal gates on (a zero gauge only counts as evidence after a gauge written by a process that started after the last deploy, and an unknown gauge is never zero). A week with no read at an instrumented site says those readers were not asked for any row the gauge still counts. Because a site records only for a row the gauge counts, once the gauge is zero the sites are zero by construction: they add information only while the gauge is above zero, as which of its rows are actually asked about. A zero week does not cover the readers that are not counted (the four listed above, the readers of the name line, and every other reader of an old field), and it says nothing about an unmarked project that lists agents and keeps its name as `session` (its keeper is derived, so neither the gauge nor a site sees it). Which sites can reach zero: every one of them, and only through the gauge: a site goes quiet when its rows leave the gauge (each gets a mark, or lists agents so that its keeper is derived). A registry build with the roles files records nothing, as no reader there asks who keeps a page. The `agent:` sub-page rows are most of the gauge; a sub-page can carry a mark of its own (`page_keepers`, above), a marked sub-page is counted as `mark`, not `legacy`, and the legacy count falls by the number marked (`stackshot keeper-subpages` does that for the rows that exist).

How it is kept: in the process, and added to the file at most once a minute and when the process ends, by one atomic write (a temporary file named by the process and a counter, which only that writer removes, and a replace, with an fsync; a temporary file a killed writer left is swept by the next write, under the lock, once it is more than a minute old) under a lock on `keeper-reads.json.lock`. While the process runs the lock is taken without waiting: when another process holds it, this write is skipped and the counts stay in memory for the next one, so a read never waits on the file. A count that waits for its minute is written by a timer on a daemon thread when the minute is up (the minute is the monotonic clock's, so a wall clock that steps back delays no write), also when the process makes no other call (the timer is set again when its write is skipped or fails, and the process never waits for it at its end; one flush runs at a time in a process, and a timer flush that is writing when the process ends is waited for, within the same two seconds, by the write at the end). The write at the end of the process has no next one, so it waits for the lock, up to two seconds (a write holds it a few milliseconds), and only for a lock that is held: any other error ends the write at once. Processes that exit together lose no key; a holder that is stuck or stopped makes each exiting process wait the two seconds and then lose its counts, while a killed holder releases the lock at once. A write that fails (no state folder, a read-only standby, a full disk) is kept for the next try, leaves no temporary file behind and never changes an answer. The file's `flushed` time is its heartbeat, the last write that succeeded. `stackshot keeper-reads` prints a line starting `NOT RECORDING?` when the file is missing or unreadable, has no heartbeat, or was last written more than a day ago (a service that ran in that time has failed writes, and the counts below are old: that is not a week with no reads). A damaged file is replaced, the old one kept as `keeper-reads.json.bad` (one backup, the newest), and the report says so and when; a value of the wrong kind at any level (a site's `keys` that is a number, a gauge whose count or generation is a word, a negative number, a fraction, `NaN`, `Infinity` or a `1e999` anywhere, a gauge with no `count` or no list of keys), a file nested deeper than a counter file ever is, and one larger than 4 MiB are damage like any other. The report prints the gauge, each site with its last read in the instance's timezone and its distinct keys (most keys first), and the readers that stay; it writes nothing. Known limits: what a process had counted when it was killed (a stop signal runs no exit hook), or when the lock stayed held for more than two seconds at its exit, is lost, and a process that only reads leaves `keeper-reads.json` and `keeper-reads.json.lock` in its state folder.

Marks follow the pages below them. A sub-page whose own line names a keeper keeps it (and is not reclassified when its parent marks one: only a page that names nobody inherits), and an unnamed sub-page of a project that lists agents but has no `display-name:` takes a record's mark too (and gives it back when the mark goes). A page with its own `display-name:` and no agents keeps its own line as its keeper even when its hub marks one (`anchors.marked_for` and `keeper.fields` agree). Known limit: such a named satellite of a marked hub still gets the hub's builder as its router stand-in and its `page_keeper`, not the hub's mark; it only matters when no session of its own name is running. Known limit: a sub-page that has its own `display-name:` and lists its own agents still gets the top project's derived keeper in `keeper_agent`, as before the mark, which is also the agent the gates answer for it; its own agents are not read for the field. A retired project's mark is read, and its sub-pages follow it. A change of the record that touches only a project's status or hub reads the keeper of the pages under it again, also when the page mirror has not been written. A page's `keeper:` line that names an agent the record no longer lists is ignored, and `keeper_problems` says so.

A mark on a project with no page is not read (the mark lives on a page's row): the pageless view of the project carries a `keeper_problems` line saying so. Derived values are stored with the registry's rows: they are read again when the registry is rebuilt, when the record changes a page's own agents or mark, and for the pages that fall to a changed page through their `hub:` line; they are not read again when only the configuration changes or when the record changes the general page of a scope that a project with no builder and no -main agent falls to, until the next rebuild.

**What writes the mark.** Only the project verbs write it, in the record (the page's mirror writes three lines and the mark is none of them), in the same atomic change as the agents map. No migration and no job sets a mark: a project that has none keeps its derived keeper until someone marks one.

- `agent-add` marks the project's **first** agent (no agent listed, and no mark on the record or the page). A later agent is never marked, and a project that has a mark never gets a second one from `agent-add`. When the first agent takes the keeper's place over a session the old fields named (a project's `display-name:` session), the answer names that session and what it loses: its `roles.json` entry (each entry that moves is printed, as the `keeper` verb prints them), the notices addressed to it, and its permission to list agents or change mandate lines (the 403 names the marked agent). Known limit: the first agent is marked even when it is a background agent, so a project whose first agent is a builder has a builder as keeper and its talking session loses the standing.
- `agent-rename` of the marked agent makes the mark follow the new name. A mark that only the page's `keeper:` line holds is written into the record on that rename, because the record wins; the page's own line is for whoever edits the page to change, and the answer says so.
- `agent-retire` of the marked agent moves the mark to the project's builder, else its `-main` agent (the derivation rule above, read from the record's agents without the leaver), else clears it. The answer says which in `keeper` (`from`, `to`, and a `problem` line when nothing is left to take it, and the timeline line names it too). A mark is never left naming a retired agent. When nothing is left to take the mark and the project has a `display-name:`, the answer says that the name line is its keeper again (the old rule), not that the project has none. The three verbs leave the mark alone in a retired project (the agent list changes; the answer carries the `keeper` verb's refusal line).
- `keeper PROJECT AGENT [--apply]` moves the mark on purpose. It is a dry run unless `--apply`: it prints the old mark and where it came from (`mark`, or the derivation), the new mark, and every session whose `roles.json` entry would move (the same function the roles file is written from). `--apply` writes the record only (the page mirror is not run, so a mirrored line of the page that drifted from the record is left as it is; the answer's `mirror` says `skipped`) and keeps an undo file in the `restore` format (`~/.local/share/stackshot-runs/project-restore/<time>/undo.json`), printing `restore --undo FILE --apply`, which takes the change back. It refuses (404) an agent the record does not list, (409) a retired project and (400) a sub-page's key; it moves the one mark and never adds a second (a record that holds two flags, or a flag that is neither true nor false on another agent, comes out with one, also when the agent asked for is the mark already).
- `page-keeper PAGE [PAGE ...] (--agent AGENT | --hand-back) [--apply]` sets the own mark of sub-pages (see "A sub-page's own mark" above), the way `keeper` moves a project's: `page_keepers[<page>] = <agent>` on the record entry of the project the page sits under, for every page named, with the pages free to sit under different projects (each is held on the entry of its own). A dry run unless `--apply`: the answer says, per page, its keeper before and after (the agent and where it comes from: `mark`, `derived`, `legacy`), and every session whose `roles.json` entry would move. `--apply` writes the record only (no page is read or written; the answer's `mirror` says `skipped`) in one atomic change, and keeps an undo file in the `restore` format, printing `restore --undo FILE --apply`. The agent is one some project lists as a sala session, on the page's own project or another (the same rule the reader applies), matched without case and written as it is listed; `--hand-back` (an empty name) hands each page back to the keeper above it, and removes a mark of a page that has no `agent:` line to hand back. All the keys are read before anything is written, and one bad key refuses the whole call: (400) a project's own page (its mark moves with `keeper`), a page with a `display-name:` or a `keeper:` line of its own, a page reached only through a `hub:` line, or an agent that is not a sala session; (404) a key that is no page under a project, or an agent no project lists; (409) a retired project. The new record is read back before anything is written: when the registry would not answer, for any page, what the call asked (a mark it ignores, as when the page of the entry that holds the mark is not in the registry), the whole call is refused (400) naming the page and what the registry answers instead, and no undo file is made. The stored keys of an entry's marks are read as the registry reads them (a trailing slash or `.md` names the same page): the verb replaces every stored key of a page with one under the page's key, and `--hand-back` removes all of them. A page that has the mark asked for under its page key changes nothing, and a call that changes nothing writes no file and makes no entry for a project that has none. On the command line `--agent` takes a name: an empty one is refused (exit 2), and `--hand-back` is the way to hand pages back.
- `keeper-mark [--apply] [--accept-role-loss SESSION ...]` (`stackshot keeper-mark`, `stackshot/projects/keeper_mark.py`) is the one-time pass that puts the mark on every live project of the record. It marks the project's builder, else its `-main` agent, else its first front agent (the agent the derivation already named, so a project with a front agent keeps its stand-in and its item keeper); lists a one-session project's name-line session as its one front agent and marks it; never replaces a mark (the record's flag, or a page's own `keeper:` line); leaves archived projects alone; and clears an entry's `name` only when no agent of the project is it or starts with it and nothing hangs below the project that could use it. It writes the record only (never a page, whatever the page mirror setting). It is a dry run by default and writes nothing, not even an undo file; the summary says, per project, the agent marked and why and the name cleared, and then what moves for sessions: the `roles.json` entries that change, `sessions that lose a role: N` (a session that sala's `load_roles` counted as front or back and no longer does: a project that lists background agents only loses the front role its name-line session had), the running old name-line sessions that would show off the map, the projects whose gating class flips (a one-session project becomes a project with a front agent), the projects whose items or router passes go to another agent, and the marked agents that are not builders (a held notice reaches a front agent later than it reached a builder). `--apply` refuses while `N` is above 0 unless each such session is named with `--accept-role-loss`, keeps an undo file in the `restore` format (the whole file goes back byte for byte), and a second run changes nothing. The undo takes back the whole record file and is refused (409) once the record was written after the change; after a later write the way back is `restore --from-git REV --apply` (the printed hint says both). `--apply` plans again inside the record's lock and prints and returns that plan, the one it wrote; when it differs from the plan read just before the lock the output says so (`replanned` in `--json`), and so does a refusal that only the plan under the lock makes (a role loss another writer caused after the plan was read: the output shows that plan, says the record changed, and then the refusal). A one-session promotion happens once per name in a pass (a second project with the same name is skipped, and the names already listed on a project's page count too), and not for an entry whose agents map is empty or whose agents were all retired (its name is the project's name, not a session: the pass says to list the session by hand). A name is cleared only when nothing hangs below the project in the page registry either. A page's own session line on a sub-page is counted and never written (the session a promoted project lists is not counted).

- `keeper-subpages [--apply] [--run-dir DIR] [--by WHO] [--json]` (`stackshot keeper-subpages`, `stackshot/projects/keeper_subpages.py`) is the one-time pass described under "A sub-page's own mark" above. It reads the registry rows whose role is `agent` and whose keeper is `legacy`, prints a table (sub-page, agent named, action, where the agent is listed or why it is left), the legacy gauge before and after, the pages whose session or role differs, the names that gain or lose pages (with the pages each gains, and a line saying a handed-back page follows the keeper above it by design), and the running sessions that lose a page. Before it decides a page, the pass maps the name the `agent:` line holds through sala's rename log (`renamed_agents.renames_of`: the old name of a session sala renamed, to the name it has now; a chain of renames is followed to the newest name, and a loop in the log ends the chain). A name some project's map lists as it stands needs no mapping. When the newest name is an agent some project lists, the page is marked with the new name and the table says `renamed from <old name>: own map` (or the other project's map); the `agent:` line is not touched. When the newest name is on no map the page is left, and the row names both the old and the new name; a renamed session's page is never handed back (only a name that is neither on a map nor a rename source is a dead name). A page that moves from a session's old name to its new one is no loss for that session (the running-session loss count folds the old name into the new one), but the new name is listed among the names that gain pages, with the pages it is now the agent of, and the dry run says how many marks name a renamed session. When sala's rename log cannot be read, the pass refuses like it does for an unreadable list of sessions: no plan, exit 1, nothing written; so does a list of sessions where no row carries an `aliases` field at all (an old or stripped sala: nothing could then be told renamed), while an empty list is read as before. A dry run writes nothing at all and takes no lock; `--apply` plans again inside the record's lock, writes the record only (no page, no roles file) in one atomic write, keeps an undo file in the `restore` format, and a second run changes nothing.

Four keeper debts are named lines of the daily project registry check (`stackshot/tools/registry_report.py`, [audit](audit.md)), reported only with `[registry_audit] keeper_debts = true` (off by default: nobody is told of a mark's problem before marks are set on purpose): `keeper-not-listed` (a mark names an agent the record does not list), `keeper-two-marks` (two flags, or the record's flag and the page's `keeper:` line name different agents), `keeper-retired` (the mark names an agent the record says was retired) and `keeper-not-derived` (a live project that lists agents has no mark and no builder or `-main` agent to derive a keeper from). Each carries the `keeper` command that fixes it, except a stale `keeper:` line on a page, which no verb writes: its fix is to edit or remove the line.

A project's name stays what its agents' names start with, so a one-session project whose session does not start with the page's slug still reads (`projects._name_prefixes` takes the name line as written). A page with no name line takes the name from its front agents (`projects.agent_prefixes`): the `-main` agent's name without `-main` (`team-app-main` gives `team-app`), else the only front agent's whole name, and last the page's slug; `post project-agent` and `post project-agent-rename` accept all of these, so an agent already named after the slug stays a name of the project, and the want for a background agent offers the first.

A project needs no page. Its `page` pointer is optional and may be a link to another knowledge base; page reminders, the page-first rule and the mirror apply only to a project whose pointer is a page in this instance's page store. A project with no entry yet (the migration has not reached it) gets one at its first verb, made from its page as the page store has it at that moment (not from the registry, which follows the pages checkout minutes late), with its pending agents folded in. That page is read **before** any lock is taken (`project_verbs.preread`; the server's `post project-agent` does it before `_PROJECT_LOCK`): a gbrain read can take a minute or two, and every record writer waits on the record's lock. Inside the lock a verb reads the record and nothing from the page store. If the pre-read fails, the answer carries a `warning` and the entry is made from the registry's copy of the page's lines; the mirror's guard keeps a line the registry did not know from being deleted.

**Sub-pages are never projects.** A key under another page (`projects/alpha/sub`) or a page with a `hub:` line is a sub-page: it gets no entry (the migration writes entries for top-level pages only), and `create` refuses it (400). Through a sub-page's key, `rename` and the agent verbs act on the top-level project that owns it; `archive`, `reopen` and `move-page` refuse it (400 naming the top-level page), because they act on the whole project; the id of a sub-page is refused by every verb. A project's page is one level (`projects/<slug>`): `create` and `move-page` refuse a key below another page.

`stackshot/tools/project.py` runs the verbs from a shell (`--dry-run` shows what would be written; `--json` the whole answer; `--by LABEL` names the actor):

**Restore a lost project.** The record is the one place a project's permanent id, its former keys and names, who made it and when, and its marks live, and the pages do not hold them: since the copy of the record onto the pages was retired (`[pages] copy_project_lines = false`, or a brain marked `shared`), the page lines are no longer a way to get a project back, and a page keeps no change made after that day. The way back is the record's own history. The server commits the store to its git repository within seconds of every change, so every past revision of `project-record.json` is in that history, and `restore` reads one of them (with read-only git commands: never a checkout, a reset or a pull in that repository) and writes it back through the same locked, atomic save the server uses.

1. **List the revisions.** `python3 stackshot/tools/project.py restore --list` prints the last 20 (`--limit N` for more), newest first, in the instance's timezone: `abc1234  Mon Nov 2nd 10:15 KST  3 projects (+1 -0 ~2), 5 ids (+0 -0)`. The numbers after the project count are the projects added, gone and changed since the revision before it. Pick the last revision from before the loss. (`--before "2026-11-08 12:00"` takes the last revision before a date, in place of a sha. A date is `YYYY-MM-DD` or `YYYY-MM-DD HH:MM[:SS]`, read in the instance's timezone, the one the list shows, unless it names a zone of its own (`Z`, `+0900` or `+09:00`, up to `+1400`); a date alone is its midnight; the years are 1970 to 2099. Anything else is refused, and a wall time that does not exist in the instance's zone (the hour a clock skips) is read as the moment after the gap.)
2. **Dry run.** `restore --from-git REV PROJECT` (PROJECT is an id, a page key, a bare slug, the name or a former name, as that revision knows it) says what would change: whether the project comes back or only its changed fields (the agents named, other fields as `old -> new`), the id rows and the mark that come with it. A restore that changes a project's status (it un-archives or retires it, or brings it back archived) says so on a line of its own (for the whole record, one line for each kind of change, naming the projects), and a changed order of the agents is shown (the first builder listed is the builder). Without PROJECT it is the whole file, and the answer names the projects made since that revision, which would be gone. Nothing is written until `--apply`.
3. **Apply.** The same command with `--apply`. It keeps the file as it was, with a small `undo.json`, in `~/.local/share/stackshot-runs/project-restore/<time>/` (`--run-dir DIR` for another folder), writes the record, and prints the undo command. It does not write any page lines: run `mirror PROJECT` afterwards if the page should show the restored name, agents and status.
4. **Undo.** `restore --undo <that undo.json>` is a dry run; add `--apply`. When nothing else has written to the record since, the file goes back byte for byte. When something has, a restore of one project takes back only its own entry, id rows and mark and leaves every other change; a restore of the whole record that has been written over since is refused, and the file as it was is named so you can look at it first.

One project comes back as its entry, its row of the id table, the rows of its page's sub-pages and former keys that the id table lacks, and its mark; the rest of the current record stays as it is. The restored entry replaces the current one if there is one, so agents added to it after that revision are not in it (the dry run lists them as `off`). **It restores the record as saved: a change made after that revision is not in it**, which is why you pick the revision just before the loss and read the dry run first. The pending agents table is not restored for one project (it holds agents waiting for a page line and is folded into entries by the verbs).

`restore` refuses, with nothing written and exit 1: a revision git does not know, or one with no record file; a record at that revision that does not read; a PROJECT the revision does not hold; an entry that would sit on the page key of a live project with another id, or take its name, or a page key (its page, a former key or its id row) that another live id already holds (archive, rename or move one of them first); a record that is being written (the lock stays held for 5 seconds); a store that is not in a git repository; and, for one project, a current record that does not read (restore the whole record then: the damaged file is kept for the undo). Wrong arguments are exit 2 with the usage.

The same verbs answer the client API: `stackshot/fleet/client.py post project --scope S (--key projects/slug | --name N [--page KEY\|LINK] [--make-page true\|false])`, `post project-agent`, `post project-agent-mandate` (the keeper or a front agent, by session id, as `post project-agent`), `post project-agent-rename` and `post project-agent-retire`. `stackshot/fleet/client.py get agent-name <project> <name> [<name> ...]` (`GET /client/agent-name`, [the client contract](client-contract.md)) asks, before anything is registered, whether each name would be taken: the register's own name checks (`project_verbs.name_verdict`) as a read that writes nothing. `stackshot/tools/migrate_project_record.py` (dry run by default) writes the entries of the top-level pages, folds the pending agents of active projects into them and clears the table; `--undo` removes only the entries that pass made. For a page the call made, its note carries an offer of the ready `anchors` call for the project's repository releases and Slack channel ([the anchor offers](waiting-and-doing.md#anchor-offers)).

**Items store the project's id.** An item holds `metadata.project_id`, the permanent id of the top-level project it belongs to, beside `metadata.project` (the page it is filed on: a copy of the project's own page key, or a sub-page's key as the item's plain detail link). `stackshot/model/item_project.py` is the one resolver: `key_of(meta)` reads the project's page through the id (a page that was moved or renamed, one of the project's `former_keys`, reads as the page now), `derive(key)` gives the id a key names (a sub-page or a page with a `hub:` line gives its project's), and the server reads an item through it when it loads one, so the board, the brief, the router's counts, the Projects list and the archive sweep follow a moved page with no write to the items. A save sets the id from the key (create, `update(project=)`, a re-file); `move-page`, `rename`, `archive` and `reopen` change the record only and the items follow. A save whose key names no project the record knows (a re-file to a registered page with no record entry) takes out the id the item carried, so the item reads as its new key and never as the project it left; an item that stores no id reads as stored too, so the pass below is what makes a moved page keep its items.

**An item's project is the top-level project; the page it is filed on is its detail link.** `item_project.project_of(meta)` is the page key of the top-level project that owns the page an item is filed on (`key_of` followed up through `derive`: a sub-page reads as the project that owns it, a page with a `hub:` line as the hub's project, a former key as the page now, a key that names no project as stored), with a stored `project_id` or without one, and `top_of(key)` is the same for a page key. It is a display and grouping reader and writes nothing. The readers that show an item's project use it: board.md's `- project:` line (the label is the top-level key, the link stays the mirror of the page the item is filed on), the item page's Project line, the search results' project label, and the `project:` line of `get`, `brief`, `create` and `update` (`item_project.line_of`: the top-level key, and `(filed on <sub-page>)` after it for an item on a sub-page, so the text keeps the detail link the markdown keeps as a link). The readers that need the page keep `key_of`, the page the item is filed on: page debts and the pages-owed nag, anchors scoped to a page, the keeper and agent lookups, the page-update gate, a page's own project page with its sub-page badge, the board row (`row_of` over the page, which already rolls a sub-page up to its project and keeps a `board_row: true` sub-page its own row: the items under that row show the top-level project on their `project:` line and link the sub-page, and the row heading above them names the sub-page; no live page sets it), the router's roots, move-page, rename and archive. The stored `project` and `project_id` are unchanged by it, so no migration and no write; `stackshot/tools/project_id_report.py` compares what `project_of` reads for every open item before and after the pass.

`stackshot/tools/project_id_report.py` stores the ids on the items already there (open and closed). Dry run by default: it copies the store to a private folder, runs the pass on the copy and compares what the board's markdown and brief, the server's brief and every open item's project key show before and after (it exits 1 when they differ). `--apply --sender <you>` runs it through the live server (`POST /client/migrate`, op `project_id`, the migration gate of `[model] migration`): it asks for the plan first, writes the undo file `<run-dir>/<pass id>/undo.json` before the first write, and writes only the one key in each file (no clock and no file time moves). `--undo FILE --sender <you>` takes the ids out again (op `unproject_id`; an item a later save changed is `kept`), and running either again is a no-op.

- **Archived projects** (`stackshot/projects/project_archive.py`, `stackshot/web/ui/groups.py`, `Board.projects_table` in `stackshot/web/ui/render.py`, `service/projects.py`'s `_project_agent_retire` and `audit_ticks._archive_tick`; `tests/ui_guards_scenario.py` (its archive_fold_view part) and the 6f part of `tests/projects_picker_scenario.py`). The Projects page lists the projects whose page `status:` is one of `[project_scopes] retired_statuses` in a foldable **Archived** group after the active ones, drawn as home's scope subsections are (`groups.fold_block`: a native `<details class="fold sfold" data-fold="projects.archived">`, the heading with the count of archived projects, closed on load; inside it the projects are listed by scope, and the page's fold script opens it for a link to a scope that has only archived projects). The project page's group of agents of an archived project says Archived too. **A project is archived when it has no agent and no open item.** The retire that sala already sends (`post project-agent-retire`) takes the agent off the project's agents map in the record and the page's block follows; the call then looks at the project, and when its agents map is empty, no agent is pending for it in the project record and none of the open items (its own, its sub-pages' and the pages that name it as their hub; parked counts as open) is its, the project is archived: the record's status first (`retired` = who, when, how), then the page's `status:` line follows as a mirror write with a timeline line (the answer carries `archived` and `archive_note`). A page that cannot be written does not fail the retire: it is told in the note, and the record is archived all the same. An archive that cannot be made at all (the record cannot be written) puts the project on the wait list, so the sweep tries again. A project whose record has no `agents` field at all (never staffed) is never archived by a retire (not even by dropping its only pending agent), with one exception: a one-session project (a page with a `display-name:` line and no `agents:` map) whose own session, the name that line gives, is retired: that retire gives the record an empty agents map (the answer says "line removed" and its note names the project's own session; the page is written only by the archiving) and the project is then archived, or waits for its open items, as any project whose last agent left; `stackshot/tools/archive_empty_projects.py` lists what the rule covers that nothing archived. With open items left the project goes on the wait list `<state>/archive-wait.json` and stays as it is; **the ten-minute archive sweep** (`archive_tick`, last of the ten-minute set) counts the open items of the waiting projects in one read and archives each whose items are gone, whether they were completed or handed to another project; a project that has an agent again, or is archived or gone, leaves the list without a write, and a second sweep over the same state does nothing. A retire answered "not listed" never archives, and a sweep never touches a project that is on no list. Sala sends nothing new: its existing retire call is the trigger.

- **Front-only projects** (`anchors.front_only`, `stackshot/anchors/anchors.py`; `tests/front_only_scenario.py`). A project is front-only when it has no builder: `anchors.builder_of` finds no background agent of its hub whose mandate says "build", "maintain", "merge" or "engineer". It is the one test of "has a builder": the hand-off machinery's `handoff_builder` (`stackshot/service/handoff.py`) returns the same agent, and the front-mover gate substitutes it, with no other background agent as a fallback. There is no field to set; adding a builder to the map switches the project over. A project counts as having a builder when any page of its hub lists a background agent with those words, a sub-page's included (a name that is a front agent on any page is not one). A page reads the background agents of its hub (`hub_of`: the nearest `hub:` line, else the top-level page), also when it has a map of its own, so a sub-page that lists only front agents under a hub with a builder is not front-only, and a hub whose member page lists a builder is not either. No map on the page or its hub, an unknown key, an empty key and a project whose background agents have other mandates are front-only. A background agent that only the project record holds (its page line still owed) is no builder until the page lists it. A script's item-open call on a sub-page of front agents under a hub that has a builder is therefore no front-only fallback: it takes the mover from the sub-page's own background agents, finds none and is refused, as for a sub-page with no map of its own under that hub (the fallback to the -main agent is for a project whose page lists no background agent and has no builder). Today three rules use it (the third, below, is the audit's): an answered step of a front-only project goes to the session its next open step names (else the item's contact), and any live session some project page lists (a front or a background agent of this or another project) may hand an item of a front-only project to a live front agent of that project through `mover=`, which tells the front agent by a hand-off notice (`stackshot/waits/builderless.py` `handover_allowed`; the target must be listed on the item's own project page or a page above it, so the hand-over cannot point at an unrelated project's front agent; `then` and `post_wake_mover` (the old name of `mover`) take the same exception but tell nobody, because the owner's answer or the wake moves the item and no write of a session tells the target), and the front agent so handed the item is watched like a builder's, see [Hand-offs](handoffs.md) and [the stall pass and the ladder](stall-and-ladder.md); the audit sends a front-only project's unmoved findings and its unmoved digest to its -main agent instead of the global audit builder (`audit_run.Env.chase_of`, [audit](audit.md)). The router's own builder pick (`router_live.builder`) still reads the mandate words itself. A front-only project's refusals name the working path: a `mover`, `then` or `post_wake_mover` that is refused says which half failed and that a check goes to the page key with `For <peer>,` on the first line, and `needs` naming a front agent of the project says to set `mover=<peer>` or open its own item with `after=`.

- **A want for a background agent** (`stackshot/service/background_want.py`, `GET /client/background-wanted`, `[background_agent]`; `tests/background_want_scenario.py`). A message to a project that lists a front agent and no background agent has nobody to take it but that front agent, which a message that asks nothing of the person must not wake, so it is archived or held for the agent's next turn as before. With `[background_agent] enabled` on, such a message also records a want in `<state>/background-wanted.json`, keyed by the project's id (a page that is renamed keeps its want, which is looked up by the id), and the fleet tool may then create the agent ([fleet-tool](fleet-tool.md)) by a **background call** to `post project-agent` (a `--sender` label in `[project_agent] bg_senders` from a machine in `bg_machines`, else `form_machines`; `_bg_call` in `service/projects.py`, `background_want.open_state`): it lists a background agent only, and only while the project's want is open (switch on, want recorded and not served, no background agent yet), else a 403 that names the condition; it opens none of the form's other calls (the rename, retire, mandate and color routes read `form_senders` only; `tests/projects_picker_scenario.py`). Recording the want writes nothing to the project record and starts nothing; only the background call writes the agent to the record. The first message takes the old route; later messages reach the new agent by the one lookup the router and the message tool share. The want is recorded for every message to such a project, whatever the router rules it (its own call's archived, merged or dropped, a rule in code, an archive, a hold, an fyi, a pass that needs the person) and whatever the message tool's front gate does with a message to a front agent by name (a refusal included): the router makes the one call at the start of its action on the notice, the message tool before its gate. A want is recorded only for a message (never a board or anchor notice, the server's own line about an item, an audit or filing message (the audit's label or the audit agent's session, by name, by session id or to the project, and the server's own passes; the name must be exactly the audit's, a tag after it is ignored), a front agent's word to a peer or to its own project, the person's own message, or a message refused because its recipient is a retired session or one whose pane is gone; a `dropped` ruling still records it) to a project that is listed and not retired, is a top-level project (no sub-page, no `hub:` line), lists at least one front agent that is a session of the fleet (so the keeper mark never moves to the new agent), whose key, name prefix and front agent are plain names (a line of the answer is three words; the name prefix is the page's name line, else the `-main` front agent's name without `-main`, else the only front agent's whole name, else the page's slug), and has no background agent on its hub. It is set only when absent, under a lock (two requests make one want, in one process or two). `GET /client/background-wanted` computes the open wants fresh: a want whose project now lists a background agent drops out (and is marked served), one whose project turned ineligible is left out. A project that got an agent and lost it again wants one again only after `cooldown_minutes` (60 by default) counted from the want or from the agent's first showing, and only when a new message reaches it; at most `max_open` (3) wants are open at once. Every failure (an unwritable state directory, a state file that is damaged or nested too deep to read, a project that cannot be read) leaves the message as it was (a damaged file reads as no wants and the next want replaces it; one odd entry is skipped, never hiding the others), a read-only standby copy records and marks nothing and says nothing, and a switch that is off writes no file and answers an empty list.

- **What a front-only project has in place of a builder, for a script, the audit and a hand-back** (three more uses of the test beyond the three rules above, six in all). Three places that wrote "the builder is told, else nobody" now read `anchors.front_only` and use the project's front agents instead, and a fourth change is text only; a project that lists a background agent is unchanged in each. A script's `item-open` is filed under the project's `-main` agent as the item's mover (`fallback: true`, the item says so), as the job-gap route does ([client-contract](client-contract.md#an-item-a-script-opens-for-a-background-agent)). An alive item whose mover's session is gone goes to the closest live front agent, which is sent the one hand-off notice (tag `handoff`), and the History line says it is told ([audit](audit.md)). A hand-back by `needs` to a front mover tells that mover itself, marked `[for <owner>]` ([handoffs](handoffs.md)). The refusal of a front agent's unmarked message to a peer front agent also names the working form, a first line `For <peer>,` on a message to the project's page key (`stackshot/service/messaging.py`; the unmarked message stays refused). Tests: `tests/item_open_scenario.py`, `tests/successor_scenario.py`, `tests/front_quiet_scenario.py`, `tests/router_live_scenario.py`, `tests/pilot_scenario.py`.

- **One walk through a front-only project** (`tests/front_only_scenario.py`, its project part). - **An item's contact** (`stackshot/model/contact.py`, `service/contacts.py`, `stackshot/fleet/client.py backfill-contact [--apply]`, `stackshot/tools/backfill_contact.py`; `tests/contact_scenario.py`). The front agent (a user-facing agent) the person the board is for talks to about the item; the item page's side column leads with it as **Owner**, the session name linked to the fleet tool's view of it (`[client] session_view`), the label's hover text "the front agent to talk to about this item", and no row for an item with none. A **Creator** row sits under it (or first, with no contact) on every item, open or closed: whoever created the item, by the name the History's first line gives (`Board.creator_name`), a muted "unknown" when the item names none. Stored as `metadata.contact` (the session's permanent id where the fleet registry resolves it, so a rename changes nothing stored); `get` shows `contact:`, the client JSON rows (`item-facts`, the lists) carry `contact`. *Why not `owner`:* `owner` is a retired term (`tests/retired_terms.toml`; `metadata.owner` is still the stored creator, and the deprecated `owner` parameter of create and update is accepted until `[model] owner_param_until`), so a second meaning would mislead every old reader and session. *Who it is:* an item created by a front agent has that agent; a background agent's create names one of the project's front agents with `contact`, and the server refuses any other name, listing the project's front agents with their mandates and writing nothing; with no name it is the project's `-main` agent (`anchors.fallback_main`). Front and background are told apart by the project page's `agents:` map (`anchors.session_roles`, `contact.fronts`): an entry outside `background:` is front. `update` changes it with the same check, which also accepts the item's creator and its current contact while they are front agents (of any project): the front agent that made the item from talking with the person stays its contact wherever the item is filed, and can be set back to. A completed item keeps the one it had (reopen it first). *When it changes by itself:* the contact retires (the `project-agent-retire` endpoint) or is renamed (`project-agent-rename`): the items it was contact of fall to the project's `-main` agent, or follow the new name, and the endpoint's answer lists them as `contact_moved`; the item moves to another project: the contact stays if it is also a front agent there (a page rename keeps its agents) or is the item's creator (a front agent of any project), else it falls to the new project's `-main`; a stored contact that is no front agent any more reads as the project's `-main` agent until one of these writes it. It is a filing field (`_FILING_ONLY`): setting it moves no state clock, changes no mover, owes no page and sends no notice (a write through `update` still moves `updated`, as any write does; the backfill and the retire, rename and move passes are server writes that leave it). *The fill-in:* `stackshot/tools/backfill_contact.py` (dry run by default, on a copy of the store: the counts by rule and one line per item that would change; `--json`, `--store DIR`) and `stackshot/fleet/client.py backfill-contact [--apply]` (the running server writes, author `migration`, one filing write per item): an open item gets its creator when that was a front agent (`creator_front`), else its project's `-main` (`main`); a contact that is no front agent any more falls to the `-main` (`retired_contact`); one that has a live contact is left (`has_contact`), as is a project with no `-main` (`no_main`) and a closed item (`closed`). A second run writes nothing. There is no automatic pass at start.
