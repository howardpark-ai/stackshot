# The board, the publisher and the connector

What this page covers: the server and the publisher, the MCP connector, and every tool the connector offers. Back to the [README](../README.md).

**The board and the publisher.** `stackshot/web/server.py` is the only writer of the store (one JSON file per item, `<store>/<letter>/<n>.json`; its path and its file write are in `stackshot/core/store.py`, its readers of one item in `stackshot/web/store.py`) and the
only id allocator, and serves the rendered board at `/`. `stackshot/web/publish.py` renders the board
(`stackshot/web/render.py`: markdown and the one-line brief), commits the store to a git repository and pushes it, after every
write (debounced), on a timer and when the machine or session state changes. A publish that changes nothing commits
nothing.

**The connector.** The same server serves MCP at `/mcp`, behind Google OAuth (plus one optional machine token for a
Cloudflare MCP portal). Its tools:

| Tool | What it does |
|---|---|
| `brief` | The board at a glance: counts, the Machines panel, the receivers, the project index, then every open item in full. |
| `get` | Read one item by id; it shows `needs:` (whose move it is), `after:` (the items that must close first, each with its state), `observers:`; it leads with `mover:` and `then:`, shows `contact:` (the front agent the person talks to about the item; the item page's side column leads with it as "Owner"), and History says who created the item. |
| `create` | Create an item; `contact` names the front agent the person talks to about it (see **[An item's contact](projects.md)**); the gates refuse a bad subject, description, project, enum or date. `request_id` makes a retry safe. A thing the owner does himself is not `needs=decision` (his choice between options) but a your-step: a needs=decision ask that only confirms his own action is refused (see `update`). `needs` is a list: `decision`, `external` and session names (a background agent of any project, or the mover itself), several at once; the sessions named hear the item's wake, recycle and after notices (the page's keeper when none is named); `observers` hear a close or a reopen; `after` names the items that must close first (`agent=` is the older way to name one session). The mover, when it is a user-facing agent (a background agent is refused), is not messaged about its item's moves (a front agent's pane wakes only for what he has to do; a move to needs=decision included, since the board's Waiting on you (now Need your call (agents)) view is where the owner reads it): a close, a reopen or a naming by another session goes to the project's keeper (its builder, else its `-main` agent), which passes on what needs the owner; the owner's own answer or comment from the board or GitHub still reaches it. A close with the owner's own words on the item is the other exception: a `said` entry, or his name before a quote or a weekday in the description or the close's reason (a board answer alone does not count, answering a decision picks an option, it does not ask to hear of the close); it is then a row on his For you list (see **[The For you list](for-you-and-closed.md)**), not a message to the mover, whoever closed it (the router's `close-words` rule only rules a notice recorded before that as merged). A mover that is not a front agent hears a close, a reopen and its naming as before. `check` names the done check that closes the item once work handed to another session is done ([below](handoffs.md)); a create is never refused for a hand-off. A sender off the project's agents map gets a note at the end of the reply naming its -main agent (**[A session off its project's map](audit.md)**). |
| `update` | Change the fields passed; `contact` changes the item's contact; `sender` charges the page debt to the editor rather than the item's mover. A needs=decision item carries an ask line (`ask`: `Decide: … · Recommend: … · Stakes: … · By: …`, one line, at most 240 characters). One that asks for a pick between alternatives lists them (`options`: 2–6 entries `{label, line, recommended}`, exactly one recommended), shown on the item page, in the queue's tooltip and in board.md; an ask or description that names alternatives while none are listed is refused (keywords, a list "x, y or z" or "x vs y", and labeled choices in the Decide part such as "A or B" or "A (…) or B (…)"). A yes/no decision lists two options, `Approve` and `Decline` (the recommended one marked), so the owner gets one-click buttons: the page draws Approve and Decline only when they are listed. An open question (a Decide part that opens with what, which, how, who, whom, whose, when, where or why) lists its answers as options too, or is reworded as a yes/no (`Decide: whether to …`): with no options it is refused, since the page's Yes / No fallback cannot answer it. The same refusal holds for any decision with no options whose Recommend part is not a yes or a no (it names a person, a topic, a date), whatever words or language its Decide part is in: the choices go in as options, or the Decide part is a yes/no question with a Recommend of yes or no (the English yes/no words ship; `[keywords.ask_options] yes_no_words` adds the instance's own). The ask's Recommend part names the recommended option's label; when it does not, the reply carries a note and the write goes through. A needs=decision item whose description or `next` links a mockup (a `https://claude.ai/artifact/…` page, or a `https://<host>/mockup/<n>` page of the fleet tool's web UI, the host being `client.mockup_hosts`) while its ask does not is refused: put `[mockup](<that link>)` in the ask's Decide part, and the home row and the item page draw `Mockup ↗` beside the question (not twice when the ask's own link is already drawn there). A mockup link goes in the ask only: an option is a clickable card that selects or unselects, so an option whose label or line holds a markdown link or an `http(s)` URL is refused, on `create` and on `update`. A needs=decision item whose ask only confirms the owner's own action is refused, since his Yes would be read as consent and not as the step done: an ask that asks whether he has done it ("have you done X?", a bare "is it done?") with no alternative or judgement in it, or Yes/No, Approve/Decline or no options over a Decide part that names the action of one or more `<owner>:` lines of `next`. Use `step=<his action>` instead (on a create, create without `needs=decision` and set it by `update`), which the board ticks when he says it is done. A choice between options, an open question ("which", "should we", "or") and a judgement ("have you decided …") stay decisions; in doubt the write is accepted. `work` sets the status of the sender's first open step, one line per call (`{text, state}`: a few words, at most 40 characters; `in progress` is the default, `done` also ticks the step as `done` does, `remove: true` clears the status; a sender with no open step gets one made from the text), by the mover or a session named in `needs`: a step is a stage of the work, the status says where the session is in it and is replaced in place, so a night of writes is one line on the step, not one line each. The board row shows the statuses in progress as "engineer: migrating", the item page shows the status under its step in Next (the done steps fold behind one line, the newest stays), and History keeps one line per closed step with its status updates folded under it; the write owes no page and changes no needs. `next` replaces only the sender's own lines (every line of `next` remembers the session whose update wrote it, kept in `metadata.next_by`; `stackshot/model/nextlines.py`; a line stored before an earlier change is the creator's): `next="none"` removes only the sender's lines, `clear_next=true` wipes all. `done` and `dropped` mark steps of the next checklist (a 1-based position or the exact first line of an open step, any step whoever wrote it); a `next` or `next="none"` that drops one of the sender's own open steps without marking it is refused, and `clear_next=true` marks every line it wipes as dropped. `check` sets or clears (`"none"`) the item's done check; an update that hands the work to another session (a line of its `next` in the form `<session>: <action>`, naming a session other than the mover and the writer that is not already in `needs`) is refused unless the item carries a check (or, when none fits, a wake, a reminder; never a hold). `wake` (a date, or a date with a time) alone is a reminder, never a hold: the item stays in its lane, and at that moment the sessions its notices go to (the sessions in its `needs`, else its mover) are told once (one message per session per pass) and the wake is dropped; status, `needs`, `next` and the state clock do not change. Only `hold=true` parks an item, and with a `wake` it is released at that moment, as before; a hold and a wake stored before this change release the same way. The server records who set a hold and when (`metadata.hold_set`). `stackshot/fleet/client.py holds` (read only) lists the open items on hold that nothing holds now (no open `after` item, pane recycle, `needs=external` or item-scoped anchor; a stored reason is never trusted), with mover, wake, setter and time, for the item's mover to release one by one (`update clear_hold=true`); the board.md head, the `brief` tool's head and the session-start brief list the holds set in the last 24 hours and what holds each. No session text suggests parking an item on a date the session picked. `wait_reason` names what a step the mover waits on (its own wake, or a dated line of its own `next`) waits for: required with such a write, judged once by a model call that refuses when the step could be done now (`[wait_guard]`, [below](waiting-and-doing.md#a-wait-a-session-sets-on-its-own-item-names-its-blocker)). An item whose `needs` include `decision` is never shown on hold (the board, board.md, the item page, the brief, the staleness lines and the GitHub mirror ignore a stored flag on it); its next update drops the flag, keeps the wake as a reminder, and says so in the reply. A sender off the project's agents map gets a note at the end of the reply naming its -main agent (**[A session off its project's map](audit.md)**). |
| `confirm` | Mark an item still true: it reads fresh again. Sets its `confirmed` clock only: no page owed, nobody told. |
| `complete` | Mark an item completed (items are never deleted) and list anchors left with no open item. A close takes `outcome` (done, dropped or superseded), a one-line `reason`, and `outcome_text` (how it ended, as `- ` bullets, shown as the Outcome block above Background); the description stays as it was. |
| `said` (on `create`, `update` and `complete`) | The owner's own words on the item, under the Linux kernel's tags: `[{tag: Acked-by (his decision) \| Suggested-by (his idea or request) \| Reported-by (a problem he reported), quote: his sentences cut verbatim, msg: the uuid of his message, session: where he said it (default: the sender)}]`. The quote is checked against that message in the session's transcript on the server box (`[said] transcripts`); a readable transcript that fails (no such message, not his own, text a tool typed in, the quote not there) refuses the write, one the box cannot read stores the entry unchecked. Stored as `metadata.said`, appended; the issue comment ends with `Acked-by: <owner> <link>` (` (unchecked)` when so), never the quote, and is never bundled; the item page shows a tag on the History line with the words behind it. His questions are not posted: only conclusions go to the board. A message he sends while a session is working (a reply he got elsewhere, pasted in) is recorded in the transcript as an attachment entry of type `queued_command` with `attachment.origin.kind` human, inside the session's turn, not as a typed message, and is refused as his words; `{kind: acted, quote: a piece of its text verbatim, msg: the uuid of the attachment entry, session}` (no tag) records it instead: checked to be a `queued_command` attachment of human origin with the quote in its `attachment.prompt`, wherever it sits in the transcript (every other attachment type, a `queued_command` from a peer, a task notification or with no origin, and one whose text a tool typed in (the same marker, prefix and phrase test as his typed words), is refused), stored with the tag `Done-by` and `kind: acted`, and read only by the audit's N4, where a checked acted entry proves the owner's ticked steps on the item within 24 hours after its date, never where his words or his decision are needed. |
| `anchors` | List, add or remove a project's anchors, project-wide or scoped to some of its items (every URL in one `add` is scoped to every id in `items`). The page that holds an anchor keeps it (its keeper, its routing log and its receivers: its keeper, or on a page with no keeper its session and the movers of every open item it is scoped to, of any project), but an item reads the anchors scoped to it from every project's page, not only its own project's, each once (`stackshot/anchors/anchor_scope.py`, the one reader the server, the board pages, the briefings and the model guards share); a project-wide anchor counts for no item. `add` and `remove` also take `machine:<name>`, a machine of the fleet: the mover of each item in scope is told, once per check-in and naming the machine, each time that machine's puller checks in again after being offline (see *A machine anchor* in [item-model.md](item-model.md)). |
| `route` | A ruling on a notice delivered for a project: passed, merged, held or dropped, with a reason. The router rules the notices of every project itself; this overrules a ruling that was wrong. |
| `message` | Send a message to another session (a pane on any machine, or a cloud session), labelled as a teammate's request. A message to a front agent (a session the owner talks to) must carry `[for <owner>]` on its first line, and the mark is for what the owner has to do: a build hand-back, a result, a screenshot, "it's live" or an FYI goes to the project (`to=projects/<slug>`), where the router rules it and passes on what needs the agent. A marked message that says nothing is needed from him is refused too, by a short fixed list of phrases (`_NOT_FOR_OWNER` in `stackshot/web/server.py`: "nothing needed from <owner>", "nothing for <owner>", "no action needed", "no action for <owner>", "no decision needed", "nothing to decide", "FYI", "for your information", "for the record", "no reply needed"; whole words, any case, in the text after the mark); the refusal names the phrase and where the message goes instead. **A background agent's plain status report is written onto the item, not sent** (a front agent is woken by a message only when it has something to do or to tell him; `stackshot/waits/reports.py`, `server._builder_report`). A builder may message a front agent only to ask it something, tell it something it must know or give it something to do; a plain result goes on the item. The rule is turned around: a list of ask words always misses some, so only what clearly reads as a report is held back and everything else is delivered. A marked message from a background agent to a front agent (or a project message that opens `For <front agent>`) that names one to three board items as plain-word ids is saved as the server's note on each item (a History line from the sender, no field and no clock moves) and delivered to nobody only when `reports.report_doubt` finds nothing against it: every sentence, once the mark, the `For <agent>,` address and the ids (items, PRs, shas, numbers) are taken out, says done, live, merged, released, deployed, closed, opened, fixed, passes, green, recorded, written, pushed, landed, unchanged, "is up" or "no change"; it has no `?` anywhere (a URL's included), no fenced block and no prose in a code span (an id, sha, path or short command is fine); none of fail, broke, error, rolled back, cost, `$`, blocked, wait, await, pending, need, must, should, require, review, ready, approve, decide, confirm, please, ask, option, recommend or a word of `[keywords.reports] ask_words` (and a few more, `TROUBLE` in `stackshot/waits/reports.py`); it names no person or role to act (the owner or one of his aliases, you, your, owner, keeper, a front agent's name); and it states no plan (will, once, when, if, then, until, after …). The reply begins "Not delivered: written onto <item> as a History line from <sender>, because …". Anything not matched is delivered as before, and so is a message whose item has `decision` in its needs or names the target front agent in its needs, one that names no item or more than three, one from a session that is not a background agent, one to a background agent and any failure in the check. From a message to a project page, a sender off the project's agents map gets a note at the end of the reply naming its -main agent (**[A session off its project's map](audit.md)**). |
| `sessions` | The live sessions and machines, with each session's link, for a session that cannot see them itself. |
| `rules` | Serve the rulebook (`paths.rules`) every session is told to read at the start of a task. |
| `bump_versions` | Refresh the latest-version lookups and republish now. |

**A new tool or parameter** (`work` on `update`, say) reaches a running session's cached tool list only after about a day:
claude.ai keeps its own copy of a connector's tools, and a pane recycle does not refresh it. Until then a session calls the
new form through the MCP Portal's Code Mode, which reads the live schema: `portal_codemode_execute` with
`async () => codemode.stackshot_update({ item_id: "board#N", sender: "<your session>", work: { text: "migrating the ids", state: "in progress", agent: "my-engineer" } })`.
