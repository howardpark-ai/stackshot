# The board, the publisher and the connector

What this page covers: the server and the publisher, the MCP connector, and every tool the connector offers. Back to the [README](../README.md).

**The board and the publisher.** `stackshot/web/server.py` (the tools are in `stackshot/web/tools/`, registered by `stackshot/web/app.py`, which `stackshot/web/wiring.py` builds and wires together with the hook tables of the service areas, and the words they carry are plain text files in `stackshot/web/tools/text/`) is the only writer of the store (one JSON file per item, `<store>/<letter>/<n>.json`; its path and its file write are in `stackshot/core/store.py`, its readers of one item in `stackshot/service/store.py`, its one writer in `stackshot/service/writes.py`) and the
only id allocator, and serves the rendered board at `/`. `stackshot/web/publish.py` renders the board
(`stackshot/web/render.py`: markdown and the one-line brief), commits the store to a git repository and pushes it, after every
write (debounced), on a timer and when the machine or session state changes. A publish that changes nothing commits
nothing.

**Pages.** A brain adopted into a board writes its pages as markdown files under `pages/` of the board's repository and never commits them: the publisher
is the only committer and pusher of that repository. The board's own publish never commits anything under `pages/`, with `publish.pages` on or off (see
docs/configuration.md). With it on, `publish_pages(paths, author, email)` in `stackshot/web/publish.py`, called right after a write with the files that
write touched (relative to `pages/`), commits just those files (an edit, a new page or a removed one) in one commit, with the signed-in person or agent as
the git author and the board's own git identity as the committer (a name on the commit, not a signature), and pushes it. It returns true for a commit made
and false when every file named is as committed already. Everything it is given is checked before anything is staged: a path that is empty, has an empty,
`.`, `..` or `.git` part, holds a control character or is not UTF-8, is a folder or a symbolic link, runs through one or through a folder that is a git
repository of its own (`pages/` included), cannot be read, is left unmerged (a stash pop's conflict), or is neither on disk nor in the last commit is
refused, and so is a call of more than 1000 paths (or 64 KiB of them) and an author with no usable name. Each path is a file name, never a pattern. So are
a `[paths] repo` that is a folder inside its repository rather than its top, and a store clone whose index is locked (an `index.lock`: another git
command running, or one stopped that left it). The commit is built in an index of the call's own (`GIT_INDEX_FILE`, in a temporary folder removed at the
end: the last commit read into it, then the named files), never in the store clone's index, which every session on the host shares; a page whose entry
there is marked assume-unchanged is committed as it is on disk. That index is checked before the commit: nothing the caller did not name may go with it
(submodules included, whatever `.gitmodules` or `diff.ignoreSubmodules` hide), so a file that became a folder, or a folder that became a file, goes out
only when both sides are named (the new file and the old folder's files, or the old file and the new files in its place). The commit is `git commit
--only` of the named files: hooks and signing as for any commit, no automatic gc from it. Once it is made, the store clone's index is brought to it for the
named files only, so what a session staged there stays staged as it was; a call that would drop an entry a session staged (a new file in a folder that is
a named file now) is refused before the commit instead. The author's address is the one given, cleaned, else this process's `GIT_COMMITTER_EMAIL` (the
board's own), else `board@localhost`; never the clone's configured `user.email`. A commit that is not made (the switch off, a refusal, the clone in the
middle of a session's merge or rebase or on a detached HEAD, git refusing or failing a step) raises `CommitFailed`, the store clone's index exactly as it
was, so a failed page is never reported as unchanged and never goes out later under another writer's name; the same author tries again. Where that index
cannot be brought to a commit made (another git holds it at that moment), the call still returns true and says on stderr which files read as staged and
the `git reset -q --` that clears them. An interrupt (SIGINT in the main thread) waits for git, then raises `KeyboardInterrupt` saying whether the commit
was made; a second one stops git where it is. Once the commit is made, the push is tried at once; a commit that is not on the mirror after it (the push
refused or failed, or the fetch before it) is said on stderr, at most once an hour, and goes out with a later publish: the next one where the branch
tracks the mirror, else the next that commits. A real conflict with the mirror waits for a manual merge, as the board's own commits do. Call it under
`publish.pages_lock()` where another write could land on the same file first, so the write and its commit are one step. Each board has its own repository
and publishes only to it. A page file
edited by hand is committed only when a call names it, under that call's author. Where the store clone has no `user.name` or `user.email` of its own, the
board's merge with its mirror takes this process's committer (`GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`), else the last commit's committer: never a
page's author.

**The connector.** The same server serves MCP at `/mcp`, behind Google OAuth (plus one optional machine token for a
Cloudflare MCP portal). Its tools:

| Tool | What it does |
|---|---|
| `brief` | The board at a glance: counts, the Machines panel, the receivers, the project index, then every open item in full. |
| `get` | Read one item by id; it shows `needs:` (whose move it is), `after:` (the items that must close first, each with its state), `observers:`, `tell_him:`; it leads with `mover:` and `then:`, shows `contact:` (the front agent the person talks to about the item; the item page's side column leads with it as "Owner"), and History says who created the item. |
| `create` | Create an item; `contact` names the front agent the person talks to about it (see **[An item's contact](projects.md)**); the gates refuse a bad subject, description, project, enum or date. `request_id` makes a retry safe. A thing the owner does himself is not `needs=decision` (his choice between options) but a your-step: a needs=decision ask that only confirms his own action is refused (see `update`). `needs` is a list: `decision`, `external` and session names (a background agent of any project, or the mover itself), several at once; the sessions named hear the item's wake, recycle and after notices (the page's keeper when none is named); `observers` hear a close or a reopen; `after` names the items that must close first (`agent=` is the older way to name one session). The mover, when it is a user-facing agent (a background agent is refused), is not messaged about its item's moves (a front agent's pane wakes only for what he has to do; a move to needs=decision included, since the board's Waiting on you (now Need your call (agents)) view is where the owner reads it): a close, a reopen or a naming by another session goes to the project's keeper (its builder, else its `-main` agent), which passes on what needs the owner; the owner's own answer or comment from the board or GitHub still reaches it. A close with the owner's own words on the item is the other exception: a `said` entry, or his name before a quote or a weekday in the description or the close's reason (a board answer alone does not count, answering a decision picks an option, it does not ask to hear of the close); it is then a row on his For you list (see **[The For you list](for-you-and-closed.md)**), not a message to the mover, whoever closed it (the router's `close-words` rule only rules a notice recorded before that as merged). A mover that is not a front agent hears a close, a reopen and its naming as before. `check` names the done check that closes the item once work handed to another session is done ([below](handoffs.md)); a create is never refused for a hand-off. A sender off the project's agents map gets a note at the end of the reply naming its -main agent (**[A session off its project's map](audit.md)**). |
| `update` | Change the fields passed; `contact` changes the item's contact; `sender` charges the page debt to the editor rather than the item's mover. A needs=decision item carries an ask line (`ask`: `Decide: … · Recommend: … · Stakes: … · By: …`, one line, at most 240 characters). One that asks for a pick between alternatives lists them (`options`: 2–6 entries `{label, line, recommended}`, exactly one recommended), shown on the item page, in the queue's tooltip and in board.md; an ask or description that names alternatives while none are listed is refused (keywords, a list "x, y or z" or "x vs y", and labeled choices in the Decide part such as "A or B" or "A (…) or B (…)"). A yes/no decision lists two options, `Approve` and `Decline` (the recommended one marked), so the owner gets one-click buttons: the page draws Approve and Decline only when they are listed. An open question (a Decide part that opens with what, which, how, who, whom, whose, when, where or why) lists its answers as options too, or is reworded as a yes/no (`Decide: whether to …`): with no options it is refused, since the page's Yes / No fallback cannot answer it. The same refusal holds for any decision with no options whose Recommend part is not a yes or a no (it names a person, a topic, a date), whatever words or language its Decide part is in: the choices go in as options, or the Decide part is a yes/no question with a Recommend of yes or no (the English yes/no words ship; `[keywords.ask_options] yes_no_words` adds the instance's own). The ask's Recommend part names the recommended option's label; when it does not, the reply carries a note and the write goes through. A needs=decision item whose description or `next` links a mockup (a `https://claude.ai/artifact/…` page, or a `https://<host>/mockup/<n>` page of the fleet tool's web UI, the host being `client.mockup_hosts`) while its ask does not is refused: put `[mockup](<that link>)` in the ask's Decide part, and the home row and the item page draw `Mockup ↗` beside the question (not twice when the ask's own link is already drawn there). A mockup link goes in the ask only: an option is a clickable card that selects or unselects, so an option whose label or line holds a markdown link or an `http(s)` URL is refused, on `create` and on `update`. A needs=decision item whose ask only confirms the owner's own action is refused, since his Yes would be read as consent and not as the step done: an ask that asks whether he has done it ("have you done X?", a bare "is it done?") with no alternative or judgement in it, or Yes/No, Approve/Decline or no options over a Decide part that names the action of one or more `<owner>:` lines of `next`. Use `step=<his action>` instead (on a create, create without `needs=decision` and set it by `update`), which the board ticks when he says it is done. A choice between options, an open question ("which", "should we", "or") and a judgement ("have you decided …") stay decisions; in doubt the write is accepted. `work` sets the status of the sender's first open step, one line per call (`{text, state}`: a few words, at most 40 characters; `in progress` is the default, `done` also ticks the step as `done` does, `remove: true` clears the status; a sender with no open step gets one made from the text), by the mover or a session named in `needs`: a step is a stage of the work, the status says where the session is in it and is replaced in place, so a night of writes is one line on the step, not one line each. The board row shows the statuses in progress as "engineer: migrating", the item page shows the status under its step in Next (the done steps fold behind one line, the newest stays), and History keeps one line per closed step with its status updates folded under it; the write owes no page and changes no needs. `next` replaces only the sender's own lines (every line of `next` remembers the session whose update wrote it, kept in `metadata.next_by`; `stackshot/model/nextlines.py`; a line stored before an earlier change is the creator's): `next="none"` removes only the sender's lines, `clear_next=true` wipes all. `done` and `dropped` mark steps of the next checklist (a 1-based position or the exact first line of an open step, any step whoever wrote it); a `next` or `next="none"` that drops one of the sender's own open steps without marking it is refused, and `clear_next=true` marks every line it wipes as dropped. `check` sets or clears (`"none"`) the item's done check; an update that hands the work to another session (a line of its `next` in the form `<session>: <action>`, naming a session other than the mover and the writer that is not already in `needs`) is refused unless the item carries a check (or, when none fits, a date: `until`, which in a write that hands the item on is only the hand-off's backstop and no wait). A date with nothing beside it (an `until`) is a wait until it outside a hand-off: the item waits and the board lists it as waiting. In a write that hands the item on the item stays in its lane, and at the date the sessions its notices go to (the sessions in its `needs`, else its mover) are told once (one message per session per pass) and the date is dropped; status, `needs`, `next` and the state clock do not change. A park with a date (`until` with `wait_kind="time"` and a `wait_basis`) is stored as `until` and ends the same way: the item is released at the date. A park and a wake stored before `until` release at the date too, until the one-time pass (`stackshot/tools/until_migrate.py`) rewrites them as `until`. The server records who set a park and when (`metadata.hold_set`). `stackshot/fleet/client.py holds` (read only) lists the open parked items that nothing holds now (no open `after` item, pane recycle, `needs=external` or item-scoped anchor; a stored reason is never trusted), with mover, wake, setter and time, for the item's mover to release one by one (`update clear_hold=true`); the board.md head, the `brief` tool's head and the session-start brief list the parks set in the last 24 hours and what holds each. A session's own date on its own item is judged by the self-set wait guard: it carries `wait_reason` (below). `wait_reason` names what a step the mover waits on (its own wake, or a dated line of its own `next`) waits for: required with such a write, judged once by a model call that refuses when the step could be done now (`[wait_guard]`, [below](waiting-and-doing.md#a-wait-a-session-sets-on-its-own-item-names-its-blocker)). An item whose `needs` include `decision` is never shown parked (the board, board.md, the item page, the brief, the staleness lines and the GitHub mirror ignore a stored flag on it); its next update drops the flag, keeps its date (which parks nothing on his call), and says so in the reply. A sender off the project's agents map gets a note at the end of the reply naming its -main agent (**[A session off its project's map](audit.md)**). |
| `confirm` | Mark an item still true: it reads fresh again. Sets its `confirmed` clock only: no page owed, nobody told. |
| `complete` | Mark an item completed (items are never deleted) and list anchors left with no open item. A close takes `outcome` (done, dropped or superseded), a one-line `reason`, and `outcome_text` (how it ended, as `- ` bullets, shown as the Outcome block above Background); the description stays as it was. |
| `said` (on `create`, `update` and `complete`) | The owner's own words on the item, under the Linux kernel's tags: `[{tag: Acked-by (his decision) \| Suggested-by (his idea or request) \| Reported-by (a problem he reported), quote: his sentences cut verbatim, msg: the uuid of his message, session: where he said it (default: the sender)}]`. The quote is checked against that message in the session's transcript on the server box (`[said] transcripts`); a readable transcript that fails (no such message, not his own, text a tool typed in, the quote not there) refuses the write, one the box cannot read stores the entry unchecked. Stored as `metadata.said`, appended; the issue comment ends with `Acked-by: <owner> <link>` (` (unchecked)` when so), never the quote, and is never bundled; the item page shows a tag on the History line with the words behind it. His questions are not posted: only conclusions go to the board. A message he sends while a session is working (a reply he got elsewhere, pasted in) is recorded in the transcript as an attachment entry of type `queued_command` with `attachment.origin.kind` human, inside the session's turn, not as a typed message, and is refused as his words; `{kind: acted, quote: a piece of its text verbatim, msg: the uuid of the attachment entry, session}` (no tag) records it instead: checked to be a `queued_command` attachment of human origin with the quote in its `attachment.prompt`, wherever it sits in the transcript (every other attachment type, a `queued_command` from a peer, a task notification or with no origin, and one whose text a tool typed in (the same marker, prefix and phrase test as his typed words), is refused), stored with the tag `Done-by` and `kind: acted`, and read only by the audit's N4, where a checked acted entry proves the owner's ticked steps on the item within 24 hours after its date, never where his words or his decision are needed. |
| `anchors` | List, add or remove a project's anchors, project-wide or scoped to some of its items (every URL in one `add` is scoped to every id in `items`). The page that holds an anchor keeps it (its keeper, its routing log and its receivers: its keeper, or on a page with no keeper its session and the movers of every open item it is scoped to, of any project), but an item reads the anchors scoped to it from every project's page, not only its own project's, each once (`stackshot/anchors/anchor_scope.py`, the one reader the server, the board pages, the briefings and the model guards share); a project-wide anchor counts for no item. `add` and `remove` also take `machine:<name>`, a machine of the fleet: the mover of each item in scope is told, once per check-in and naming the machine, each time that machine's puller checks in again after being offline (see *A machine anchor* in [item-model.md](item-model.md)). |
| `route` | A ruling on a notice delivered for a project: passed, merged, archived or dropped, with a reason. The router rules the notices of every project itself; this overrules a ruling that was wrong. |
| `message` | Send a message to another session (a pane on any machine, or a cloud session), labelled as a teammate's request. A front agent (a session the person talks to) is given a turn only by what he has to do: a message to one carries `[for <owner>]` on its first line (except an fyi, below), and the mark is for what he has to do. The mark must point at something he has to do: a marked message names, as a plain-word id, an open item of his (`front_turn.his_items`: its needs hold `decision`, or the model reads its step as his, a park with him as the mover included) or one he asked that agent to tell him about (its `tell_him`, though a builder moves it), and one that names neither is held for the agent's next turn and starts none, the sender's reply saying to put his step on an item and name it by its plain id (it is refused instead when the hold is off; an item that cannot be read counts as none; his own message is exempt, a script's is tested like a session's). A marked message that names such an item starts a turn only while he is talking with that agent now or when he asked it, in his own words, to tell him about an item the message names (`stackshot/service/front_turn.py`: the agent is in that open item's `tell_him`, written by `update` with `said`); his own message always does; any other (an item named but no turn warranted), a script's included, starts no turn and is written onto each open item it names (one to three) as a History line from the sender, the reply saying the front agent reads it there (`messaging._written_unwoken`; the same words already written onto those items within a day are not written twice, so two senders' identical text is one line; a script gets status 200 with that reply). When no item can take it (none of those named is open or readable, more than three are named, the write fails) it is held for the agent's next turn and starts none, and only when the hold is off too is it refused, the refusal naming the background agent that works a named item (the message is kept in the message log). An unmarked message from a session (`_gate_front` in `stackshot/service/messaging.py`) goes one of five ways. **A background agent's hand-back is tested first, before (1):** a done, taken or no-action note from a background agent (a status report, `reports.is_report`, or one of the fixed phrases below) is never an answer to a question, whatever the front agent asked it before: when it names one to three open items none of which waits on his decision it is written onto them (as a plain status report is, below) and starts no turn, and otherwise it is held for the agent's next turn and starts none, the reply saying it is a note no item can carry (refused in one line only when the hold is off). A fixed phrase skips only the status words of that test: one with a question, an ask or a word of trouble beside it is no note. Only a message that is no such note goes on to (1). (1) An answer to a question the front agent itself wrote to the sender (the message log has a delivered row from it to the sender within a day that carries `"question": true`, `asked_by`: a front agent marks a question for the session it writes to with `question=true` on the `message` tool, and only a reply to such a message is an answer; a `?` in an unmarked message, quoted words or a URL included, makes none, and a row written before the mark existed has no field, so a reply to it takes the ordinary path, (2) to (5), for the day it would have counted; a question another agent of the project put to the sender is that agent's, and its answer is no answer for the front agent: it takes the ordinary rules below, (2) to (5)) is delivered, unmarked, while the person is in that conversation (his last message to that agent within `[presence] minutes`, 30 by default); outside it, it is written onto the item it names (one to three open items, none waiting on his decision, as a background agent's plain report is) or, naming none, held for the agent's next turn through the front gate. (2) A done, taken or no-action note from any other session (a plain status report, `reports.is_report`, or one of the fixed phrases below as the message's own statement), is held for the agent's next turn and starts none, the reply saying it is a note and how to have it written onto an item instead (refused in one line only when the hold is off). (3) A message from a front agent to a peer front agent (the channel between front agents), or from the project's background agent itself (the one address it would otherwise be sent to) or from a sibling background agent of the project (a message is never passed across from one background agent to another: it is held, not passed on), is held for the front agent's next turn and starts none; the sender's reply says so. (4) Any other message is passed to the project's background agent (`anchors.background_agent`, the one choice the router makes too: its builder, else the first by name order, a hub's for a component page with none), the reply beginning `Not for <owner>, so it went to <agent>` and saying the front agent did not get it and how to reach it (the mark and an open item of his); when that agent cannot take it, it is held for the front agent's next turn, and refused only when the hold is off too; when that agent is retired the message is not passed to it at all: it goes to the project's page, where the router rules it, the reply says the agent is retired and does not say it went to the agent, and the call log counts it as `held`. (5) A project with no background agent holds it for the front agent's next turn and starts none. The person's own unmarked message, and one with the mark or `needs: decision` away from its first line, is refused: the mark goes on the first line. An exception to all of it is a session's `fyi=true` message, which asks nothing and needs no mark: it is held for the front agent's next turn and starts none (a script's `fyi` there, through `client.py message --fyi` or `POST /client/message`, is held the same way; see [router](router.md)). A front agent that wants a peer front agent of its project sends it a message, or one to the project's page key whose first line is `For <peer>,` (the router's `for-agent` rule passes it to the agent the page lists): either way it is held for the peer's next turn and starts none (marked only for a need of the person, as in [router](router.md)). A marked message that says nothing is needed from him is a note too, by a short fixed list of phrases (`_NOT_FOR_OWNER` in `stackshot/service/messaging.py`: "nothing needed from <owner>", "nothing for <owner>", "no action needed", "no action for <owner>", "no decision needed", "nothing to decide", "FYI", "for your information", "for the record", "no reply needed"; whole words, any case, in the text after the mark, and only as the message's own statement: opening a sentence, a line or a list item (after a bullet, a number, an item id or markdown emphasis, with curly quotes read as plain ones), where it counts whatever follows it ("FYI the build is live" and "No action needed until Friday." are notes) unless a question mark comes right after it ("no action needed?" is asked); or a clause set off by a comma, semicolon, bracket or dash that ends there (the text ends, punctuation comes, or only a tail "from you", "from <owner>" or "on your part" follows), where a longer clause is no note ("merged, no action needed until Friday"); so a word used inside a request ("sent as an fyi so it waits"), a clause followed on or a phrase asked is no note and the message goes on to the item and turn tests, its reply saying so. A marked message that carries such a phrase and names an open item of his (`front_turn.his_items`: needs hold `decision`, or his step) is a real ask: it is delivered as a request whatever the phrase, the reply saying the phrase was left out. A real note, one that names no such item, is written onto the item it names when a background agent sends it and clearly only reports, else held for the front agent's next turn, the reply naming the phrase and telling the sender to name an open item of his or take the phrase out). Each message the relay handles where it once refused is a call that went through in the call log, with the kind of the refusal it replaced, `outcome: handled` and how (`passed-on`, `written-on-item`, `held`, `judged-on-items`), and the weekly refusal count shows it as handled, not refused ([audit](audit.md)). **A background agent's plain status report is written onto the item, not sent** (a front agent is woken by a message only when it has something to do or to tell him; `stackshot/waits/reports.py`, `messaging._builder_report`). A builder may message a front agent only to ask it something, tell it something it must know or give it something to do; a plain result goes on the item. The rule is turned around: a list of ask words always misses some, so only what clearly reads as a report is held back and everything else is delivered. A marked message from a background agent to a front agent (or a project message that opens `For <front agent>`) that names one to three board items as plain-word ids is saved as the server's note on each item (a History line from the sender, no field and no clock moves) and delivered to nobody only when `reports.report_doubt` finds nothing against it: every sentence, once the mark, the `For <agent>,` address and the ids (items, PRs, shas, numbers, and a bracket left holding only separators or "and", as "Taken (a1, PR 12 and PR 13)" leaves) are taken out, says done, live, merged, released, deployed, closed, opened, fixed, passes, green, recorded, written, pushed, landed, unchanged, complete, finished, removed, retired, "is up" or "no change" (one of them anywhere in the sentence: "Done (<sha>)", "the item is complete"; "taken" only as a sentence of its own, "Taken.", and "stopped" only in the passive, "the watch is stopped", since "the port is taken" and "the runner stopped" are trouble); a sentence that opens with yes or no ("yes, finished") is an answer, not a report, and goes on to rule (1); it has no `?` anywhere (a URL's included), no fenced block and no prose in a code span (an id, sha, path or short command is fine); none of fail, broke, error, rolled back, cost, `$`, blocked, wait, await, pending, need, must, should, require, review, ready, approve, decide, confirm, please, ask, option, recommend, not, n't, no longer, yet, still, never, nothing (but "nothing changed" is a status), no or none or zero before the thing ("no PR merged"; "no change", "no changes" and "no unit changed" are statuses, but not with a status word after them: "No changes were merged" says nothing happened), without, except, partly, partial, half, in use, red, only, "3 of 5", "3/5", minus, "other than", "apart from", "in part", mostly, "for now", omitted, skipped, "timed out", errored, aborted, unreachable, degraded, unmerged, abandoned, superseded (the check cuts the common clean bills out first, "no issues", "no conflicts", "no errors", "no failures", "no follow-ups", "no incidents", "no downtime", "no flakes", "nothing to report", "nothing left to do", "nothing else open", "nothing pending", "none pending", "without conflicts" and "closed without merging", so another word of trouble in the sentence still stops it: "Done, no errors, but nothing is live" is no report; "no regressions" stays trouble) or a word of `[keywords.reports] ask_words` (and a few more, `TROUBLE` in `stackshot/waits/reports.py`); it names no person or role to act (the owner or one of his aliases, you, your, owner, keeper, a front agent's name); and it states no plan (will, once, when, if, then, until, after …). The reply begins "Not delivered: written onto <item> as a History line from <sender>, because …". Anything not matched is delivered as before, and so is a message whose item has `decision` in its needs or names the target front agent in its needs, one that names no item or more than three, one from a session that is not a background agent, one to a background agent and any failure in the check. A `to` written as a page key another way than the registry has it (another case, `projects/` for the page's own directory, `-` for `/`: `projects/infra-gizmo` for the page `infra/gizmo`) is read as that page when exactly one registry key matches once case, a leading `projects/` and `-` against `/` are folded: the message goes there, the reply's last line says `<what was written> is <key>; sent there`, and the call log counts it as a correction (`page-key`), not a refusal. With none or two or more matches it is refused as before (`unknown-page-key`), the refusal listing the nearest keys (up to three). From a message to a project page, a sender off the project's agents map gets a note at the end of the reply naming its -main agent (**[A session off its project's map](audit.md)**). |
| `sessions` | The live sessions and machines, with each session's link, for a session that cannot see them itself. |
| `rules` | Serve the rulebook (`paths.rules`) every session is told to read at the start of a task. |
| `bump_versions` | Refresh the latest-version lookups and republish now. |

**A new tool or parameter** (`work` on `update`, say) reaches a running session's cached tool list only after about a day:
claude.ai keeps its own copy of a connector's tools, and a pane recycle does not refresh it. Until then a session calls the
new form through the MCP Portal's Code Mode, which reads the live schema: `portal_codemode_execute` with
`async () => codemode.stackshot_update({ item_id: "board#N", sender: "<your session>", work: { text: "migrating the ids", state: "in progress", agent: "my-engineer" } })`.
