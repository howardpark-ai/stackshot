# Drafts, steps and the Next checklist

What this page covers: the draft of a text the owner will send, the one-line step, the Next checklist and its write checks, step proofs and the hand-over of a finished step. Back to the [README](../README.md).

**A draft** (`stackshot/model/draft.py`). When the step the owner takes is to post, send or paste a text, the text itself is
on the item, not in a session's chat. `create` and `update` take `draft`: the text exactly as it is to be pasted, many lines, any language, stored as written in `metadata.draft` (only its line breaks are
made `\n` and the blank lines around it dropped; at most 20,000 characters, refused above). `update(clear_draft=true)` or `draft="none"` (`-`, `clear`) removes it; `draft=""` is the default and means
"not passed". A draft is a filing edit (no clock moves, no page is owed). `get` shows it as a `draft:` block, the brief only says it is there; the item page draws it inside the Your step block, inside the step that uses it (the last step that names text to post, send or paste, else the last without a command; left out when it is one of the commands the steps already show), under the label "Message to paste" ("Email text to paste" when the step speaks of an email; never "Draft") with a Copy button just beside it (the one the
command blocks use; where the browser refuses to copy, the text is selected for him); the text is in the page's own body font with its line breaks kept and escaped, not monospace (command blocks stay monospace). On an item that is
not in that block it is drawn in a block of its own. The home page's Your move row draws it the same way inside its step (under the question on an ask row), collapsed behind the same label, with the same Copy
beside the label, which copies without opening it. The GitHub mirror carries it in the issue body under `### Draft` (a fenced
code block) and says `draft set`, `draft edited` or `draft cleared` in the History. A close drops it, and so does his Send on the step (an empty box or with a note).
**The write guard** (`draft.problem`, `stackshot/service/gates.py` `gate_draft`): an `update` that leaves an item in state `your-step` with the owner as the mover (no stored mover, or his name), whose `step` names a text to post, send or
paste, is refused unless the item has a draft (stored, or in this write) or its step or description holds an `http(s)` link to a document that can carry the text (a doc, Drive, Notion or Slack link; a
GitHub issue, pull request or commit link, and a link to the board itself ([instance] `board_url`), do not count). A step names such a text when, outside backticks and links, it holds a word of `[keywords.draft]` (`stems` and `stem_patterns` anywhere in the step, `standalone_stems` as a whole word with at most one of the `particles` after it, and a phrase of `ignore_phrases`, such as a screen share, cut out first), or the whole word
post, send, paste, reply, draft, message, email, share, forward, submit (with their endings: posting, sent, replied, e-mail; "post-mortem", "postgres", an "error", "commit", "log" or "warning" message, "send me",
"send back", "reply here", "message me" (the answer to the session that asked), "share your screen", "going forward" and "submit the form" or "a PR" do not count). **The guard is a heuristic, not a complete
list**: a step that asks for a post in other words passes it, and a step that uses one of these words for something else is refused until it has a draft or a link. The refusal is one line that names `draft` and the link
alternative. The guard reads only a write that sets the state, the step, the mover or the draft, so an unrelated write to an old item is never held up; `[model] guards = false` skips it; a `create` cannot set a
state, so it only stores a draft (a text drafted before the step exists).

**The step is a one-line summary; the commands are in Next** (`stackshot/model/step_commands.py`).
The `step` of a your-step item is one line (at most 300 characters) that says what he does; what he runs is in the lines of
`next` that open with his name (`<owner>: In PowerShell run `ssh -t <host> 'uptime'` and read the output`), each command a backticked span with a space in it or a fenced block. The item page's Your step block shows only those lines, in full, as one numbered list, each said once (the line the server made from the summary, and a line that repeats an earlier one, are not drawn again), each command as a code block with a Copy
button under its line (the draft, if any, inside the step that uses it); the summary itself stays where space is short (the tab title, a Slack notice), and Next stays whole below, his lines included. An item with no line of his on the checklist draws the step field itself. Only the server's own line for the summary (recorded as `owner_step`) is skipped, never a separate step of his with the same words; a step field stored before the one-line rule keeps its numbered lines and commands in the block, each once, at their place among his lines; a line with nothing after his name takes the line under it as its step. A command that two of his steps both carry is drawn in each step's own box: each step says what it runs, so the repeat is intended. **The step guards** (`step_commands.problem`,
`stackshot/service/gates.py` `gate_step`) read an item a write leaves in your-step with the owner as the mover, in this order, and refuse in one line that names the field: (1) the description holds a shell command (a fenced block tagged sh, bash, shell, powershell, pwsh or console with one in it, or a backticked span that starts with a known command word or a path and has arguments: `COMMAND_WORDS`; words that are also English, such as make, go, find, sort, top, free, head and watch, count only with a flag, a path or another argument-shaped token after them, so a button label in backticks passes; a description write is judged only on the commands it adds or changes, a write that leaves the description alone against the stored one): the refusal says to put the command in a "<owner>:" line of next; (2) the step points elsewhere ("see the description", "see below", "refer to the description",
or a phrase of `[keywords.step_commands] pointer_patterns`; naming his Next line is no pointer); (3) a write that SETS the step and gives it a command (a backticked span that looks like a shell command, a `! ` line, a fenced block) is refused, and the refusal says to put the command in a "<owner>:" line of next and let the step say what he does. A step stored with a command before that rule keeps the older judgement on a write that leaves it alone (`step_commands.command_problem`): a command is bash for the host (`LINUX_ONLY`: sala, systemctl, sudo, python3 …, a `./` or `~/` path, `$(…)`, an `ls -la`) and not the ssh form `ssh -t <host> '<command>'` (a `~/` path alone is valid PowerShell; a cmdlet and the
cross-platform tools such as git, gh, uv, curl and tailscale pass), or it has no word that says where it runs: PowerShell, Windows, WSL or a name from `[keywords.step_commands] windows_words` (a Windows user's machine, the default for every shell command of his); "a terminal on the host" is no place.
A `! ` line (a command typed into a session's pane, also inline after a colon or a run cue such as "type ! cmd") is refused outright, in a step and in a "<owner>:" line of next, on create and update, whether or not the line asks him to run it: the fix is `In PowerShell:` with `ssh -t <host> '<command>'` (for another host `ssh <host> '<command>'`); "done!" and lines for other agents are not judged. That older check is the one the check on "<owner>:" lines of next reuses (my-engineer's build) and goes from the step when no your-step item holds a stored command. With `[steps] owner_shell = "sala-shell"` the owner runs his commands in sala's Shell (a terminal in the sala web UI that runs bash on `bash_host`; `shell_name` names its session in the text), and the place rules above change: a command is bash as typed there (`step_commands.command_problem`), or `ssh <host> '<command>'` for another machine, no line saying where it runs is asked for ("In sala's Shell:" is a place phrase like "In PowerShell:", never required), and a PowerShell or Windows-only command outside ssh (a cmdlet, `winget`, `ipconfig`, a drive path: `step_commands.windows_only`) is refused; a `! ` line is refused as before, with the Shell form in the refusal. The create and update texts and `stackshot/fleet/client.py`'s usage say so, with the paste hint (Shift+Insert, not Ctrl+V). With `"powershell"` nothing changes. Only a write that sets the state, step, mover, description or draft is judged; `[model] guards = false` skips it.

A command's box names the machine it runs on when `[steps] owner_shell` is set: "Runs on <machine>" (the ssh target of an `ssh` command, else `[steps] bash_host`), or "In PowerShell". An ssh command whose host cannot be read (a `$HOST` variable, for example) names no machine. With `sala-shell` and `[steps] shell_url` set, an "Open shell" link opens the owner's shell in a new tab. It goes on the first box of each numbered step that can carry it (one for the whole block when it is not a numbered list); a box that is a bare link or a `! ` line ahead of the command does not take it. The host is read only when the first command line starts with `ssh` itself. A box that has an ssh word (`ssh`, `slogin`, `autossh`, `mosh`, `plink`, `dbclient`) anywhere else in its text (`sudo ssh h`, `cmd && ssh h`, `bash -c 'ssh h'`, even `systemctl restart ssh`) shows no machine label, because the machine it logs in to cannot be told; so does a command that starts with a variable, an expansion or a word with a backslash in it (`$CMD x`, `s\sh h`). When an ssh command has a remote command, a chain or `-f` / `-N` and more command lines come after it (`ssh h id` then `ls`), those lines run locally, so no machine is named; a second ssh in the chain (`ssh a id | ssh b cat`) and an `-o HostName=` option name none either; a script inside an open quote or a heredoc belongs to the ssh command, and `ssh h` alone keeps its host, since the lines after it are typed into the session. In the installed web app a path on the same host opens in the same window, and a full address on another host opens a new tab. Stackshot holds no keys to any machine and has no shell of its own.

- **Next is a checklist** (`stackshot/model/steps.py`: the list retains all actions already taken or to be taken on the item, as a checkbox list, taken ones checked and slightly dimmed; open items start the list now, a dropped step stays, struck through). *Storage:* `metadata.next` stays what it was, the text of the open lines, so the brief, the notices, the home rows, the GitHub mirror, `get`, the write guards, the router and the search read it untouched. Beside it `metadata.steps` is the checklist, a list in the order the steps were written of `{text, status: open | done | dropped, by, at}` (a step is a line of next as `nextlines.split` groups it: a top-level line with the indented lines, notes and fenced blocks under it; each open step also knows its writer, `nextlines`' record). `next` is derived from it: the open steps joined; an update that writes `next` keeps the text exactly as written and the steps follow it. A write path that knows nothing of steps (a test, the migration, an old client) only changes `next`; `steps.view` lines the stored steps up with the text it finds (a step whose line is gone reads as dropped, with nobody and no time; a new line is an open step at the end). An item with no `steps` yet has the checklist its next lines give, all open: the list starts from now, with no backfill from History. *Writing:* `update(done=[…], dropped=[…])` marks steps, each entry a 1-based position in the checklist (done and dropped steps count) or the exact text of an open step's line; a marked step keeps its place and records who marked it and when. `done` and `dropped` mark any open step, whoever wrote it, and the marked line leaves `next` with its writer (`nextlines.prune`), except that `done` on one of the owner's steps (a line that opens with his name) while the item asks him is refused (only his answer ticks it). An update replaces only the sender's own lines of `next`, so only a sender's own open step can leave `next` unmarked: when the sender's `next` (or `next="none"`) no longer lists one of its own open steps and `done` and `dropped` do not name it, the update is refused, naming the step, its position and the call to retry with in one line (`done=[n]`, `dropped=[n]` or `reword={n: "<new text>"}`; the other writers' lines are not the sender's to answer for); `update(reword={n: "<new text>"})` gives an open step of the sender's own other words: a mapping from a step (a position, or the exact text of its first line; a JSON key is the position as a string) to its new text, the step keeping its number, its place and its open state, its line of `next` (`nextlines.reword`) and its `step_proof` following it, and `next` in the same call, when it is passed, listing the new text (else the line is changed for it); refused: a step that is done, dropped or not there, another session's step, the owner's, a step also in `done` or `dropped`, a new text of several steps or one another open step already reads, a new text that is the old one with words added (the rule below for a rewritten line holds for it) and a new text a line of `next` would be refused for; `clear_next=true` is a deliberate wipe: every line it removes becomes a dropped step, by the sender. A `next` that only adds or reorders open steps works as before (the open steps take the new order, in the places open steps held; new ones go at the end). `done` or `dropped` without a `next` leaves `next` as the open steps left. A step still listed in `next` while the same call marks it is refused; one written again after an earlier call marked it is a new step. Closing marks every step still open, by the closer (done when the outcome is done, dropped otherwise; marks passed with the close win for their steps; the server's own closes mark the same way) and keeps the checklist as the record (`get` lists it, the page shows it); reopening drops the steps an older close left open. The items closed before are marked by the server itself, once at every start before it serves (`_close_marks_pass`: done for outcome done, dropped otherwise, by "stackshot (backfill)" at the close time, no mirror write, idempotent, one log line); `stackshot/tools/close_marks_backfill.py` is its read-only report (dry run, `--json`, `--config <copy>/stackshot.toml`). A marks-only write counts as a change of `next` (it owes the page like one). *the owner's step made by the server (`stackshot/model/owner_steps.py`, `server._owner_steps_on_save`, `tests/owner_steps_scenario.py`):* when an item waits on him (needs decision with an ask, or state your-step), the server adds the open step `<owner>: <what to decide>` (the Decide part of the ask, or the step's one line; a text that already opens with his name, in any spelling `is_named` accepts, is not named twice, so the step reads the same written with the name or without it, and a session is never refused for it) to the checklist, written by the server so no session's `next` replaces it; a step already stored with his name twice still matches the one-name form (`steps.owner_key`) and is found by `done`, `dropped` and `reword` with the name, without it or written twice (`steps.resolve`, exact text first), and the item page shows it with his name once, so no stored data is migrated; a `<owner>:` line a session wrote that says the same as the ask or the step is adopted (recorded as the server's step, no second beside it), while a `<owner>:` line about something else (a session's "review PR 12") stays the session's own and the server's step is added beside it; a changed ask rewords it (the old dropped, the new added). His board answer ticks it as done by him at the answer's time, showing the option after an arrow (`<owner>: <decide> → <option label>`, or his quoted words cut at 60 characters); his Done on a your-step ticks it the same, and so does his note on a your-step (shown as `→ "<his words>"`; the lines a session wrote stay open); a second answer adds nothing. A session cannot tick it (an update whose `done` names it is refused while the item, as that update leaves it, still asks him; `done` together with a withdrawal in the same call is no refusal) but can withdraw what asks him (`clear_ask`, needs without decision, a state that no longer waits on him): the server drops its step with it. `dropped` on the step while the ask stands is undone: the server adds the step again. The two sources agree by a check on every save (the stored needs, ask, state and step still decide whether the item waits on him; the checklist is made to follow them), so an item that asked before this build gets its step on its next save. *the owner's step:* the item page's Your step block shows the summary line (`step`), then his own open Next lines (the steps whose first line opens with his name, or with none) in full, numbered, each command in a code block with a Copy button under its line (`step_commands` renders them); Next below stays whole, so it reads on its own. His Send with an empty box (or the old Done button) on a your-step item checks every open step of his, the ones the block shows, as done by him; a note ticks the server's step with his words and leaves the lines a session wrote open, and the session that takes the item marks them when it judges the step finished. *Reading:* `get` and the home page show the open steps (`next:`, the first open step first) and, once a step is done or dropped, `checklist:` with every step's position, status, who and when (the first line, clipped); an update's reply says `(step N done: …)`. History says `step done: …` and `step dropped: …` (the GitHub mirror's comment the same). The item page's Next fold draws the finished steps first, done and dropped together in the order they were marked, then the open steps in their planned order (`steps.drawn_order`; his decisions on the board, option picks and Approve/Decline/Yes/No/Done answers, are drawn among the finished rows by their time as `<owner>: picked <label> (<option line>)` rows of their own, `decided on the board · when`, with no position; drawing only: the stored steps, `next`, `get`'s positions and the positions `done` and `dropped` take keep the order the steps were written). It is a list of steps with CSS boxes (not form inputs), so it stays one column at phone width: open ones an empty box, done ones a checked box in the muted colour with `who · when` under the text, dropped ones struck through with `dropped · who · when`; each carries a visually hidden To do / Done / Dropped for a screen reader. A closed item shows its checklist too.

- **Next's write checks** (`stackshot/model/next_rules.py`, `server._gate_next`, `update_unlocked` (`stackshot/service/update.py`), `create_item` in `stackshot/service/create.py`, `_report_note`; one step is one action with one named actor; nothing leaves the list; an open item has an open step; a step is an action, never a status). Only a session's write through the `create` and `update` tools is judged (`server._SESSION_NEXT`, set by `_session_write()` around the tool bodies); the router, the wake and stall passes, the page-debt call, `stackshot/fleet/client.py post` (a question), the cold call, the terminal-prompt rows, an answer, the recycle write and every `server._update` or `create_item` call made by server code are not, and a line already stored is read as it was (a line naming no one still reads as the owner's in `steps.is_his`; no data is changed). *N1, refused:* a line of `next` whose first line opens with no `<name>:` (an optional list marker and bold marks, then up to three words and a colon: `steps.opener`) is refused with the line quoted and the fix `open the line with who takes it: <session>:, <owner>: or the outside party's name`; a sub-line (a bullet or number with no name) under a named step belongs to it and is fine, one with no step above it is counted, the words none, clear and `-` that remove lines are not lines, and the ask line a client without the `ask` parameter writes first is lifted before it is judged. *N3, refused:* an update that leaves an open step out of next unmarked (neither done=[n] nor dropped=[n]) and adds a step that is the old text plus words (the old text, its trailing punctuation aside, is a prefix of the new at a word boundary, or the new text equals the old once parentheticals are taken out and it has one the old lacks) is refused: mark the step done or keep it, write the next action as a new line, put the progress on the project page. A genuine rewording that is not a superset passes, and a step marked done is no reword (`next_rules.moves`, `growths`). *N6, refused:* a session's create that leaves no open step (no line of `next` and no step of the owner's that the server would make from the ask, `_model.stood_his`), and an update that removes an item's last open step while it stays open (`done` or `dropped` on the last step, `next=none`, `clear_next=true`) with none of the owner's, with the fix `add the next step … or close the item (complete)`. The update refusal applies only to a write that removes the last open step: an item that already has none is not refused for an unrelated write (held items and older items may legitimately have none), and a close is exempt. *N7, noted, never refused:* `_report_note` (the existing note, extended) names the line of a step that carries a commit id (7 to 40 hex digits holding a digit and a letter), a test count (`12 tests passed`, `all suites green`), a past-tense report (`merged`, `done at`, `live since`, `deployed` or `released` at the start of the line or right after `PR #N`; or a status word in the middle: `is`, `was`, `now`, `already`, `got` or `been` before `live`, `merged`, `deployed` or `released`, or `PR #N is merged`), or a stamp of when work began (`since 09:30`, `at work since`). A status word after once, when, until, after, before, if, unless, wait, check, verify, confirm, whether, that or so is a condition and stays quiet, `release PR #123` and `merge PR #12 after green CI` are actions and are not noted, and a line that opens with the owner's name is exempt. The write goes through and the reply carries the note (the first two lines it found). The text agents learn it from is `_NEXT_WORDS` (the create and update forms, the connector instructions, `tests/tool_text.snapshot.json`). *Part 3:* a label opener (`Status:`, `Note:`, `Result:`, `Done:` and the like, `model_guards.NOT_ACTORS`) is no actor and is refused with that said; a parenthetical role after the name (`my-x (builder):`) passes; `my-x:do` (no space after the colon) is refused with the spacing named (`model_guards.line_hint`); N3 refuses only when the old step leaves the list unmarked, so a step marked `dropped` may be replaced by a longer one; N6 on a held item says a parked item needs the step its wake leads to (`next_rules.NO_STEP_FIX_HELD`), and a hold written with that step passes. *The fill-in* (`stackshot/model/next_backfill.py`, `server._migrate_backfill`): a one-off that adds the done steps his past `decision` answers on open items would have left (`<owner>: <the Decide part of the ask> → <his option>`, done by him at the answer's time; an answer saved with no ask reads `answer the ask on the item`; a comment and a note on a step add nothing; an answer already on the checklist is not added again, so a second run adds nothing; a closed item is left as it is). It writes through the migration route (`POST /client/migrate`, a `backfill` write per item, the server recomputing from the item's own answers, `expect` and `expect_sig` checked, author `migration`), only while `[model] migration` is true. *The audit check* (`stackshot/tools/next_report.py`, `stackshot/audit/audit.py next-check [--line|--json]`): read only, lists the open items that break N1 to N7 as findings of the category `next rules` (id, project, mover, rule, detail); closed items are left alone. N3 is read only for a step that left `next` unmarked (a marked drop replaced by a longer step is allowed), N4 only for his steps a session ticked since part 1 went live (`next_report.PART1_LIVE`; earlier ticks are history), N6 is not counted again on an item that waits on him (N2 says it), and N2 and N5 read the real `after` links. Suites: `tests/next_backfill_scenario.py`, `tests/next_report_scenario.py`, `tests/next_rules_scenario.py`.

- **A step that names its proof is ticked by the server** (`stackshot/model/step_proof.py`, `server._proof_item`, `_sweep_proofs`, `_proof_tick`, `stackshot/fleet/client.py sweep-step-proof [--dry-run]`, `stackshot/tools/backfill_step_proof.py`; `tests/step_proof_scenario.py`, with `tests/released_scenario.py` for the release half). Two events, each one the server can see: `pr_merged` (the pull request is merged: this repository's merges the checkout holds, else GitHub's answer through the shared PR-state reader (`stackshot/github/pr_state.py`), the same read the done check uses) and `pr_released` (merged and live: its merge is in the last-good commit release.sh records and in the checkout's HEAD; this repository's pull requests, and those of a repository `[released.repos]` lists, live when their merge is an ancestor of that checkout's HEAD). A step names its proof two ways. *By its words:* `release PR #N`, `release #N`, `release <PR URL>` (also `release PR <PR URL>`), `merge PR #N`, `merge #N`, `merge <PR URL>`, optionally followed by one short parenthetical that names nothing to do (`(in its turn)`) and a closing full stop, with nothing else in the step but its session prefix, is a *pure* step and is ticked. Anything else is a *follow-up*: words after the phrase (`and verify`, `, restart x`, `- check prod`, `then ...`, `(after #M)`), words before it, or a second phrase (`release PR #5 after release PR #4`); the step is not ticked and its mover is told once that the event happened. A condition (`once #N is released`, `when PR #N is merged`, `after #N lands`, and a bare `after #N` on a step that says release, read as released) is never a proof: its mover is told once that it is met. A negated or undecided phrase (`do not yet release`, `cannot release`, `Do NOT, until Friday, release`, `don't merge`, `pre-release`, `decide whether to release`) and a step that only mentions a pull request (`review`, `verify #N is live`, `release notes for #N`) match nothing. A bare `#N` on an item with no anchor in that repository, and no URL, is not matched (it could be another repository's); a step names a `[released.repos]` repository's pull request by its URL (`release PR https://github.com/<owner>/<repo>/pull/<n>`), or by a bare `#N` on an item anchored to that pull request. A short name such as `sibling PR 31` is not read: the parser names a repository only by a URL, and a short name is ambiguous. *By the explicit form:* `step_proof=[{"step": <position or first line>, "proof": "pr_merged <owner>/<repo>#<n>" | "pr_released <owner>/<repo>#<n>" | "none"}]` on `create` and `update` (stored in `metadata.step_proof` under the step's key; the name is `step_proof` because `proof` is already the verifying-state parameter). An explicit proof ticks the step whatever its words say after it; it is refused for a step that is not open, for the owner's own step, and for a `pr_released` of the pull request of a repository that is neither this one nor in `[released.repos]`, and it goes away with the step (done, dropped, reworded, or a close). *What the server does when the event arrives:* it ticks the step (done, by the server, with the event as the reason; History says so); if no open step is left the item closes as a release has always closed one (outcome done, reason naming the pull request); otherwise its mover gets one notice that names the next open step. A pull request closed without a merge ticks nothing: the mover is told once that the step can never be ticked by it, and `get` marks the proof dead in its `step proof:` line. One GitHub cannot be read for ticks nothing and says nothing. Items on hold, waiting on a decision or on a session other than the mover are left alone; a step of another session ticks when its proof arrives; the owner's own step is never ticked by an event. An event seen twice ticks once and tells once (`released_told`). A dry run (`sweep-step-proof --dry-run`) judges each event on its own, so an item with two pending events lists both as ticked where the real pass ticks the first and closes on the second. *The first pass after a deploy:* the server's clock (`_proof_tick`, every 120 s) only logs on its first pass: it writes and tells nothing, logs what it would do and keeps it in `<state>/step-proof-dry.json`, and the passes after it act. `[step_proof] live = true` acts from the first pass, `live = false` never acts (a hand-run `sweep-step-proof` still does). The pass reads git only for the pull requests some open step waits on and keeps the answers by commit, and keeps a GitHub answer that can no longer change (merged, closed unmerged). *The fill-in:* `stackshot/tools/backfill_step_proof.py` (dry run by default; reads a copy of the store, makes no GitHub call unless `--github`, writes nothing) lists what the server would do for items written before this existed; `--apply` asks the running server to do it.

- **A finished step hands the item to the next session** (`stackshot/waits/handover.py`, `server._handover`, `_handover_by_hand` (`stackshot/service/update.py`), `gate_step_gap`, `step_proof.proof_gaps`, `audit_checks.check_step_handover`; `tests/step_handover_scenario.py`). A ticked step used to tell only the item's mover, so the session the next step names sat idle until somebody told it. Now, when a step is done (ticked by its proof, or marked `done=[n]` by hand) and the item stays open, the first open step decides: if it opens with another session, the item's mover becomes that session (needs follow, as in a hand-off made by the server) and it is told once, with the step's text. Several open steps are several sessions' turns: only the first is handed over, the later ones when the step before is done. Nothing moves when the next step is the owner's, a front agent's or a retired session's (the front-step rule moves a stuck front step), a name that is no session, or the mover's own; when the session is down or has no pane the item stays with its mover, who is told the step and why, once, and the record says `fallback` (the hand-over runs again only on a later done step; the audit names the session unreached after 30 minutes). An item on hold, waiting on a decision, or whose needs name another session is left alone, as a tick is; a write that names `mover`, `needs` or `agent` makes its own hand-off and this one does not run; a pass whose steps are all other pull requests' pure proofs is quiet. Idempotent by `metadata.handover` = {step hash, kind `moved` or `fallback`, to, at}. The dry run of a sweep does not preview a hand-over. *The write check:* a step whose own leading verb delivers a pull request (`release`, `merge`, `ship`, `deploy`, `land` on a PR number or URL; a step that reviews, verifies, waits for or checks one is no delivery) and has another session's step after it is refused on `create` and `update` when it is new in the write and has no proof (no `step_proof` and not a pure phrase), because without a proof its event ticks nothing and the next session is never handed the item. The refusal is one line: it says to split the step so `merge PR #n` stands alone (it then ticks itself), or, if the PR landing finishes the step, names the exact `step_proof=[{"step": n, "proof": "..."}]` to pass (a release of another repository's URL is given a `pr_merged` proof; for a bare `#n` it says what to pass for another repository's PR). A step that names no pull request is not judged, a script's write is not judged. The History shows the move as the plain `needs:` and `mover: A → B` lines and then `step hand-over: item moved from A to B`; a fallback shows `step hand-over: the next step is X's but that session isn't running; it stays with A` (both read from the item diff, `handover.fresh`). *The audit* (category `step-handover`, in the ten-minute filing pass) reports to the mover what slipped past both: the proof still missing, or the next session never reached after a done step; a front mover gets it through the page key, and it repeats only after a write to the item.
