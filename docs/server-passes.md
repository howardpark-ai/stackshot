# The minute runner and the filing passes

What this page covers: the minute set runner, the filing and dates pass, the front-step rule and its write check, the four facts the server files itself, and the wait-end rule. Back to the [README](../README.md).

**The minute set's runner** (`stackshot/core/runner.py`, the table in `stackshot/service/runner.py`). The clocks that end a wait and move work along run in one `Runner` (one thread, one lock), always started by `server._start_background`; they used to run in two threads of their own, a wake loop and a 20-second fleet watch, in no order the code stated. The runner runs them in this order, each in its own try so that one that raises is logged and recorded and never stops the next: (1) the events that end a wait: the watchers' pass (`wake_pass`), the anchor pass, the phase sweep (`_phase_tick`, [below](item-model.md)), the event waits (`evwait_tick`), the done check (`_check_tick`), the step proof (`_proof_tick`); (2) the balancer (`_balance_tick`, [`[audit] balance`](stall-and-ladder.md), off by default) and the hand-off tick; (3) the answers (`_answer_tick`); (4) the fleet's other clocks, after the wait-enders: the registry sync, the clients' tick, the pilot fallback, the stall pass, the hand-back, and the publish when the fleet files changed; (5) the ten-minute set, after the rest: the filing pass, the dates pass (the For you due dates, and a wake that has passed with no write since) and the wake catch-up. Each tick is a plain function (the wake passes, the event waits and the hand-off tick are those of `stackshot/service/wakes.py`, `stackshot/service/event_waits.py` and `stackshot/service/handoff.py`, the rest the server's), called as it is, and keeps its own interval gate (the done check once a minute, the stall pass `[stall] every_seconds`). **The pace is one minute, and `runner.PACE` is the runner's one knob:** the fleet's clocks are *paced*, one round every `runner.PACE` seconds (60), the pause counted from the end of the last paced round, so a clock with its own gate of a minute or more (the done check, the event waits, the step proof) is not slowed; the two wake passes are *event* ticks, run when the wake event `_update` sets, when the wait the runner computes ends (until the earliest wake, at most 60 s), and in every paced round, in front of the paced ticks, so the events that end a wait are settled before the done check, the step proof or the hand-off tick look at the board, whichever of the two clocks started the round; a wake still fires at its minute, except that the lock is held for the whole round: a wake that falls due while a round runs waits for it to end and can slip by the length of one round (a tick over 30 s is logged by name). The thread sleeps until the earlier of the two. The ten-minute set (`runner.TEN_PACE`, 600 s) is a third group: it runs in the first paced round after a start (so a restart never delays it), then in the first paced round after each tenth minute, right after the minute set in that round, on a schedule that does not slip when a round is late and does not run twice after a long gap; it stands still while the board is held, and a wake event alone never runs it. `GET /audit/status` carries `ten_pace_seconds` beside `pace_seconds`. The migration's hold on the board skips the same clocks as before (all but the registry sync and the clients' tick). **The runner is the only path:** there is no switch. A config file that still carries the retired `[runner] enabled` key starts as usual; the key is read by nothing, and `bin/stackshot doctor`, the server's start and a reload print one note saying it can go. The start logs `stackshot: minute set: runner …`, and `GET /audit/status` carries a `runner` object: `enabled` (always true), `mode` (always `runner`), `running`, `started`, `pace_seconds`, `rounds`, `last_round` and per clock `name`, `group`, `pace`, `runs`, `errors`, `skipped`, `last_run`, `last_ms`, `last_error` and `last_error_at` (epoch seconds; `last_error` is null until the first error and then stays, with its time, until the next error: a clean run does not clear it). **The wake catch-up and the runner's watchdog:** the timer publish (every `[publish] every_minutes`) no longer runs a wake pass of its own. The pass it ran moved into the runner's ten-minute set as the tick `wake_catchup`, which runs the watchers' pass without the due-wake gate of the minute tick (the watchers also end waits that `next_wake` does not count: an item wait whose `after` items all closed while nobody saw the close, with its ask-by days away), and publishes the board when it released something. The watchdog is a thread of its own (`watchdog_loop` in `stackshot/service/runner.py`, started with the runner by `runner.start()`, a look a minute, so a stuck publish never silences it): it asks `Runner.stalled()`, and when the last completed round is older than `runner.STALL_AFTER` (3 minutes; a blocking call inside a tick) it writes one stderr line and sends ONE message to the `[audit] builder` per stall, naming the tick the runner is in (`Runner.current`), with no board item and nothing for the owner; the next look that finds a round completed again re-arms it. The runner's times are the wall clock (`time.time`), as its status has always been, so a clock step could show or hide a stall for one look. Not in the runner: the 10-minute publish, the router, the GitHub mirror, the comments reader and the search index keep their own loops (the page-debt call is no loop of the server any more: the audit run's pages stage asks for it).

**The filing pass and the dates pass** (`stackshot/audit/audit_checks.py`, `audit_run.filing_pass`, `server._filing_tick` and `_dates_tick`; the filing pass also needs `[audit] enabled`). The daily audit's checks that need no judgment live in `stackshot/audit/audit_checks.py` as functions (`field_findings` and the per-item checks; the daily run in `stackshot/audit/audit_run.py` calls them and re-exports their names). The ten-minute set runs a subset on the open items: **filing**, where the item says one thing and the board another and the fix is the writer's, nothing about silence or time passing. It checks stuck-elsewhere (a next line that hands a step to a session the item's mover does not own, `audit_checks.check_stuck_elsewhere`), step-handover (a finished step that did not hand the item on, `audit_checks.check_step_handover`: a step that delivers a pull request has another session's step after it and no proof, or the last done step was marked by the mover or the server at least 30 minutes ago and the session the first open step names, a background session, was never handed the item, unless the item is on hold, waits on a decision or has needs that name another session, which the server leaves alone too (`handover.skip_reason`, one rule for both); the finding goes to the mover), the board report's filing kinds (arbitrary-hold and mislabeled-state, the board report's two kinds), ask-options (an open item's ask the page cannot be answered from, `audit_checks.check_ask_options`, read with the write gates' own matchers in `stackshot/model/ask_read.py`: a Yes / No (also options the page cannot read) under a Decide part that is an open question or names alternatives, an item that lists no options while its Recommend part is not a yes or a no (it names a person, a topic, a date, so the Yes / No the page draws cannot answer it; `ask_read.recommend_not_stance`, whatever language the Decide part is in), or a Recommend part that plainly does not match the options (it names no option by label, letter, place or a leading word only the recommended label has, or names another; an option after not, avoid, never, skip, except or instead of, or a word of `[keywords.ask_options]` `refusals`, or a label right before a word of `refusals_after`, is turned away; a label followed by a `particles` suffix still counts as named) or answers yes or no to an open Decide; in doubt nothing is found, and an ask that does not split into Decide and Recommend is not read; the fix asks the mover to rewrite the ask with options; no model call, no cap, quiet once the ask is rewritten), a next line that reads as a wait in words only (`wait_words`: the precise hits, such as "once board#N closes", are a finding; the broad words when, once, after and until alone are listed in the pass's flags and sent to no one, and a date-only wait left alive (`audit_checks.date_only_wait`, category `why-not-now`: a doing item whose wake is over the hour away and whose every open next line is its mover's and opens with the wake's own hour or day, so nothing is left to do before then and the board still lists it as doing; no model call and no cap, unlike the daily `why-not-now` on dated steps; the fix is the server's own: the pass parks the item and messages the mover once, see **The server files four facts itself**), and the wait-end rule (`stackshot/waits/wait_end.py`, category `wait-end` and `event-missing`, see **The wait-end rule**). A finding goes to the same recipient the daily run's findings go to, through the same `deliver_findings`, and is sent once while the item is not written to. The pass drops a finding from its own record at the end of a pass in which it no longer holds, and no daily record shields it any more (the daily run does not make these checks), so a finding that ends and comes back with its item unwritten (the role map briefly empty, a pane that changes, an anchor or an after-item that changes) is sent again. The pass's record `<state>/audit/filing.json` (written atomically; it is no run, so `audit.runs`, `last` and `status` do not read it) and the newest daily record are merged (`merged_sent`), which matters only for a send an earlier daily run made; an item written since the send is sent again. The daily run no longer makes these checks (stuck-elsewhere, arbitrary-hold, mislabeled-state): they are the filing pass's alone, so a finding reaches its mover once, and the daily run's summary, its `by_category`, the unmoved digest, the `[audit] threshold` count and the 20% share of flagged items count only the checks the run makes. Idle-on-agent stays with the daily run. The pass does nothing while a daily run is in progress. The filing pass sends its messages from the runner's one thread, so a large first-run backlog holds the other rounds (the wake round included) until it is sent. The **dates pass** does two looks every ten minutes, each in its own try (the first error is raised after both have run, so the runner records it): it opens the For you due-date look's gate, and it looks for **a wake that has passed with nobody acting** (`audit_checks.dates_findings`, `audit_run.dates_pass`, `server._dates_expected_tick`; it also needs `[audit] enabled`, script mode). An item's expected time is the one `stackshot/waits/waiting.py` derives from what the item carries: its wake (a dated wait's, a hold's wake included). The rule is the date half of the daily audit's stale check (`check_stale`, which now is only this date rule), with its exemptions kept: an item is found when it is an open item in the state doing whose wake has passed and which nobody has written since the wake; agent work in progress with no wake has no date to pass; a wake still ahead, a hold with no wake, an item on the owner or an outside party, behind an open item, or in a state that is itself a wait (parked, outside, blocked, your-call, your-step, verifying) is left alone; one the idle pass poked is no finding, as in the daily run. A finding is the `stale` finding the daily run used to send for this, word for word, goes to the same recipient through the same `deliver_findings` (headed `Dates check <time>`), and is sent once while the item is not written to; the pass's record `<state>/audit/dates.json` (written atomically beside `filing.json`; no run, `dry` sends and writes nothing) and the newest daily record are merged (`merged_sent`), so a send an earlier daily run made still holds while its record is the newest; a finding the pass drops from its own record and that comes back is sent again, as in the filing pass. The pass does nothing while a daily run is in progress (what falls due in that time is sent by the first pass after the run).  No state-check note is stored on an item any more: the next-line words that are not refused (a stored `model_flags` list, read by nothing but the writer's reply) are derived from the stored next when the writer's reply or `get` needs them (`_state_check_notes`, `audit_checks.wait_words`), and a write that sets the next drops a legacy `model_flags` entry. Suites: `tests/filing_scenario.py`, `tests/dates_scenario.py`, `tests/audit_run_scenario.py` (the pin of what the daily run still checks, and that each moved check is made by its ten-minute pass alone), `tests/runner_scenario.py`. **An unanswered finding is not forgotten** (`audit_run.split_sent`, `[audit] remind_hours`, default 6, 0 = once only as before): a finding of the filing or dates pass that its item has not answered (no write since) is sent again that long after its last send, worded as a later try (`second try, no answer`, the ordinal in words: the router drops a message that repeats an earlier one but for numbers and dates), until it has had three sends (a send after a write counts too: each finding record carries `tries`, kept while the finding stands and gone when it ends; a reminder or escalation that is not reached keeps the finding on its old send and tries, `audit_run.carry_unreached`, so the next pass retries that same send); at the next due time after that it goes once to the project's builder as unmoved (the daily run's unmoved flag, `chase the mover (job)`), to no one else, and by the project's page key (where the router rules it) when the builder is the mover or the finding's recipient, never to the session that did not answer. **Level 2:** when the finding still stands unanswered at the next due time after that send and its recipient was a builder (a background agent), it goes once more, to the project's `-main` agent, marked `[for <owner>]`: `<id> · nobody answered after N messages · <category> · <detail> · <mover> writes it, or says what holds it` (`audit_run.deliver_findings`; `split_sent` sets `escalate` to 1 for the builder, 2 for `-main`; an unreached send keeps its tries like any other). A finding whose first recipient was the page key or a front agent (a front agent's finding, a retired or outside mover's) went to the builder at level 1 and ends there, as does one whose builder is `-main` itself; a builder-moved item's finding goes to the page key at level 1 (never to the mover) and then to `-main`. Only a builder-level send made with the level kept (`lvl: 1` on the finding's record, read by `audit_run.levels_before`) is followed by level 2, so a finding already escalated before this level existed stays quiet and a release sends no burst. After level 2 it is quiet until the item is written. The dates pass has its own ladder entry and sends none of these. Suite: `tests/front_step_move_scenario.py` (8).

**The front-step rule** (`stackshot/audit/front_step.py`, `audit_run.front_step_pass`, the server's `_front_step_mark` and `_front_step_move`; part of the ten-minute filing pass, so it also needs `[audit] enabled`, script mode). A stuck-elsewhere finding about a front agent's step goes to the project's page key and is sent once (`audit_run.recipient`); the mover only relays it and the ladder gives a front agent a History line, so nothing changed the board and such a step could stay open for as long as the item did. The rule moves it. **Scope:** a stuck-elsewhere finding whose step opens with a front agent or a keeper (role `front` or `keeper` in the role map, `audit_run.FRONT_ROLES`) or a retired session, on an item whose mover is a session that is not retired. Not the owner's steps, not a background agent's (it gets the finding itself and can answer it), and not an item the owner moves or one with no session as mover (there is nobody to move the step to). **Clock:** the first pass that sees the finding for a step stores `metadata.stuck_since = {"step": <hash>, "mover": <the item's mover>, "at": <epoch>}` on the item (written only after the server has read the item again under its lock and found the finding still holding) (the hash is twelve hex digits of the step as the checklist compares it); it is the server's own bookkeeping, a save with no writer, so it moves no activity clock and writes no notice. A write to the item by anyone does not restart it, only a change of that step does: a pass that no longer sees the finding for the step (the step done, dropped or reworded, the opener changed, the item closed) drops the record, and a reworded step starts a clock of its own. A clock kept for another mover reads as none: when the item goes to a new mover while the front agent's step stays first, the clock starts afresh under the new mover, so it is not handed the step minutes after it took the item. **Threshold:** `[audit] front_step_move_hours`, default 3, a decimal reads, 0 = off (a pass with the setting at 0 only drops clocks it finds, so switching it on again starts clean). **Action:** when `now - at` reaches the threshold and the finding still holds, the server reads the item again under its lock, and moves nothing unless the item's mover is still the one the pass saw and the stuck-elsewhere finding still holds on the item as it is now (the same check, so an item handed to the opener, parked, held or put on a wait since the pass read it is left alone), and rewords the step so its first line opens with the mover (the list marker, bold marks, the rest of the line and the lines under it kept; a role in parentheses after the old name is dropped), through the pieces an `update(reword=…)` uses: `nextlines.reword` (the line is the mover's own from then on: `reword` takes a `new_writer`), `steps.apply` for the checklist, and the step's proof moved to the new text. Nothing moves when the item is closed, the first open step is another one, the new text would read like another open step, or the first line has no opener to replace. It writes one History line (`metadata.stall.log`, drawn as `stackshot: …`): `step moved from <opener> to <mover> after N hours open with the stuck-elsewhere finding unanswered (reword it back to undo): "<the step>"`, so the original opener is on record and a reword puts it back. The step's hash goes into `metadata.stuck_moved` (the last five), the clock is dropped, and the step moves **once**: worded back to the front agent it is a finding again, with no clock and no second move. **Messages:** the mover gets one plain message per moved step, `fyi` (it starts no turn for a background agent), from the filing pass; nobody else is told, not the front agent and not the page key, and a mover that is itself a front agent is not messaged at all (the History line is the record: a front agent hears of its item at two moments only). **The finding** of a step still waiting says so: its fix line reads `take the step, or reword it to <mover>; if it is still open then, it moves to <mover> at <time>` (the finding is not tool text; the time is the clock's start plus the threshold, in the instance zone; a finding whose clock could not be written, or whose move was refused, promises no time and keeps its plain fix line). With no roles at all (the role map is briefly empty now and then) the rule does nothing and drops no clock; without the item writers (`Env.step_mark`, `Env.step_move`: the command line) it does nothing; a dry run starts and moves nothing. The pass's record, `filing.json`, carries `front_steps` (`hours`, `started`, `moved`, `cleared`, `errors`, `messages`) when the rule did something. **After the move** the server leaves `metadata.stuck_landed = {step, mover, at}` (the reworded step's hash, the mover, the time; `gates._REPARK_QUIET`, no writer) and the hourly audit line and the idle hand-over count the mover's quiet time from it (`silence.clock`): the mover is given its time from the move, so a mover who does not act gets the audit line and, with nothing verified, the hand-over, and the stall pass has the item as before. A reword of the step, the mover's own activity or a new mover ends it. Decisions: a front mover is moved to but not messaged; the owner's own steps are left to the existing finding; the clock lives on the item rather than in a file of the pass, so it survives a restart and shows with the item. Suite: `tests/front_step_move_scenario.py`.

**The front-step write check** (`front_step.held`, `stackshot/service/gates.py` `gate_front_step`, called from `update_unlocked` (`stackshot/service/update.py`) and `create_item` (`stackshot/service/create.py`); one of the model's write guards, so `[model] guards = false` switches it off). The front-step rule repairs a step a front agent already holds; this check stops a new one at the write. A session's `create` or `update` is refused when it adds or rewords an open step (a line of `next`, a `reword`) whose opener is a front agent (role `front`, not retired) and the item's mover is another session: a front agent gets no work notice and its own wake or until dates (with no hold) on such an item are refused, so such a step can never fire. Judged: only a step not already open before the write (compared as the checklist compares steps, so a re-sent line, a rebullet or an unrelated write passes), and only a session's tool write (`SESSION_NEXT`), never the server's own writes, a script's sender or a done mark. Allowed: the front agent is the item's own mover, the opener is a background agent, the owner or an outside party, the item has no session as mover, or the mover is retired. A failing roles read lets the write through with one stderr line (`front-step gate: ... not judged`). The refusal reads `Refused: the step "<first line>" opens with <agent>, a user-facing agent of <project>: it gets no work notice and its own wakes are refused, so nothing would wake it for the step, and <mover> moves <item>.` followed by `Give the step to <mover> (open it with "<mover>:") or send <mover> a message asking for it.`, or, when the mover itself wrote the step, `Keep the step with <mover> and message <agent> for what only it can give.` **The monthly count:** `audit_run.front_step_count`, the first run of each calendar month (instance zone), puts `front_step_count` (`month`, `days`, `closed`, `by_other`, `open`, `ids`) on the run record and one line in the run's summary to the stackshot project: `front-held steps, last 30 days: X of Y closed by someone else · Z open step(s) the write check would refuse now (ids)`. `closed` is the steps opening with a front agent that were closed (done or dropped) in the last 30 days, `by_other` those closed by a session other than that agent (a server mark or an unsigned close is no session), `open` the open steps on open items the check would refuse now (`front_step.month_count`). Suites: `tests/front_step_refuse_scenario.py`, `tests/front_step_move_scenario.py` (level 2).

**The server files four facts itself** (`stackshot/waits/server_fixes.py`, `stackshot/service/gates.py` `fix_front_mover`, `_fix_loose_reason` (`stackshot/service/update.py`), `_date_only_wait`, `_wake_park`, `audit_run.wake_park_pass`, `model_guards.window_line`; `tests/server_fixes_scenario.py`, `tests/front_mover_scenario.py`). Where a write or an audit finding is wrong in a way the server can read from the item itself, the server takes the fix and the mover is told what it was, instead of being asked to make it. Four fixes: (1) **a wake that is the whole of a wait** is parked (on hold, `wait_basis` from the wake and the step's own words) by the write that sets it and by the ten-minute filing pass for one already stored, in place of the `why-not-now` finding for a date-only wait; the pass sends each mover one `fyi` message naming the items it parked and the way back, skips closed items, held items, items the owner moves, items that wait on a decision and items a front agent moves (the finding stands for those), makes the park as the server's own save (no writer: the item's author, its activity clock and a pending answer stay as they were), and only parks a window or date-only wait, never one that an event starts; (2) **a front agent named as `mover`, `then` or `post_wake_mover` by another session** gets the project's builder instead (before, the write was refused); a project with no builder still refuses; (3) **a hold with a wake and no wait reason** takes as its `wait_basis` the line of the item's own `next` (as the write leaves it), else its description, that says the work waits for the wake's own day (never for an item the owner moves or one in an owner state); (4) **a quoted or already-made pick** is no wait on the owner: a quoted span, and a phrase of the owner's name and a past verb ("Oliver decided the lane"), are blanked before the decision words are read (not when the words between the name and the verb negate or hold it open, as "has not yet decided", when a waiting word comes right before the name, as "until Oliver confirmed", or when the quoted span is his name alone), in `server._waits_on_owner` and in the board report's `mislabeled-state` kind. Each fix is bound to its token (the wake, or `field=value`), kept in `metadata.server_fixed` ({fix: [tokens], last 5}); the front-mover token also carries the sender and the time (`field=value|sender|epoch`) and lasts a day; the fix writes a History line (the stall log, as "stackshot: ..."), and the reply of the write says what was wrong. **A mover who disagrees resends the field**: `clear_hold=true` (a parked wake), the same front-agent value again from the same session within a day (a front mover), or a `wait_basis` of its own (a reason); the server then leaves that field alone (the parked wake's no is recorded in `metadata.fix_declined`), and a changed value is a new fact it may fix again. Never done by a fix: closing an item, writing an ask, changing an item the owner moves. Both keys are quiet (`gates._REPARK_QUIET`: a write that touches only them does not renew the item).

**The wait-end rule** (`stackshot/waits/wait_end.py`, `audit_checks.wait_end_gaps`, `audit_run.wait_end_pass`, `server._wait_end_fix` and `_wait_end_facts`, `server_fixes.WAIT_END`; `tests/wait_end_scenario.py`; part of the ten-minute filing pass, so it also needs `[audit] enabled`, script mode). An open item whose next line waits in words for something nothing tells the item has happened ("wait for board#N to close", "once owner/repo#7 is merged", "when hp-box is back online", "wait for the reply in <link>", a step `ship PR #7` with no proof) sat as work until somebody noticed. The write guards refuse a new line of that shape; the pass finds the older ones and the ones another session wrote. Only the mover's own open steps and the steps that name nobody are read (another session's step and the owner's are never read), and an item that is held, already waits, waits on a decision or is moved by the owner is never touched. Where the server can set the wait with certainty it does, as its own save (no writer), through the gates a write passes, with a History line, a record in `metadata.server_fixed` and one `fyi` message to the mover naming the items: `after` for one open item (the item's mover becomes its `post_wake_mover`), an event wait `pr_merged` or `pr_released` for one pull request (a repository `release.sh` does not release is waited on for its merge; a bare `#n` counts only when the item is anchored to that pull request), `box_online` for one machine of the fleet that is offline, an anchor wait for a link the anchors tool takes (the link is added as an anchor scoped to the item), a step proof for a pure wait step among other work or a step that is only `ship PR #n`, and a backstop day for a stored wait no watcher can end (the wake or `ask_by` it has, else now plus `[waiting] cap_days`). An item waits only wholly, so an item-level fix needs the line to be the item's only open step. Where it cannot (an "or", several items or pull requests, a bare `#n`, a machine it does not know or one that is online now, a step with other work in it) the mover gets one `wait-end` finding that names the line and says what to write. A wait for an event no event type reports (a scheduled job's run, an upstream release, a CI run or deploy finishing, a service coming back, and a stored `job_run` wait) is an `event-missing` finding to `[audit] builder`, sent once and never repeated or escalated. A mover who disagrees sends the wait back with `clear_after=true`, `clear_wait=true` or `step_proof="none"`; the line is recorded in `metadata.fix_declined` and left alone until its words change. A line the pass would fix is held back for `[audit] wait_end_settle_minutes` after the item's last write (a mover still working on its next), at most ten fixes a pass, nothing closed and no ask written. `[audit] wait_end` is `fix` (default), `ask` (the findings only) or `off`.
