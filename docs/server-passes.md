# The minute runner and the filing passes

What this page covers: the minute set runner (the wait-loop walk is its fleet clock, described in [Audits](audit.md)), the filing and dates pass, the front-step rule and its write check, the four facts the server files itself, and the wait-end rule. Back to the [README](../README.md).

**The minute set's runner** (`stackshot/core/runner.py`, the table in `stackshot/service/runner.py`). The clocks that end a wait and move work along run in one `Runner` (one thread, one lock), started by `stackshot minute` (`[runner] process = "unit"`, the default, [below](#the-runners-process)) or, with `[runner] process = "inline"`, by `server._start_background`; they used to run in two threads of their own, a wake loop and a 20-second fleet watch, in no order the code stated. The runner runs them in this order, each in its own try so that one that raises is logged and recorded and never stops the next: (1) the events that end a wait: the watchers' pass (`wake_pass`), the anchor pass, the phase sweep (`_phase_tick`, [below](item-model.md)), the event waits (`evwait_tick`), the done check (`check_tick`, `stackshot/service/checks.py`), the step proof (`proof_tick`, `stackshot/service/proofs.py`); (2) the balancer (`_balance_tick` in `stackshot/service/audit_ticks.py`, [`[audit] balance`](stall-and-ladder.md), off by default) and the hand-off tick; (3) the answers (`_answer_tick` in `stackshot/service/answer.py`); (4) the fleet's other clocks, after the wait-enders: the registry sync, the clients' tick and the inbox flag (`stackshot/service/fleet_events.py`), the pilot fallback, the stall pass, the hand-back, and the publish when the fleet files changed; (5) the ten-minute set, after the rest: the filing pass, the dates pass (the For you due dates, and a wake that has passed with no write since) and the wake catch-up. Each tick is a plain function (the wake passes, the event waits, the hand-off tick, the stall pass, the answers' tick and the clients' tick are those of `stackshot/service/wakes.py`, `stackshot/service/event_waits.py`, `stackshot/service/handoff.py`, `stackshot/service/stall_tick.py`, `stackshot/service/answer.py` and `stackshot/service/fleet_events.py`, the rest the server's), called as it is, and keeps its own interval gate (the done check once a minute, the stall pass `[stall] every_seconds`). Each tick runs inside a pass memo (`stackshot/core/passmemo.py`): what it works out once for all its items (every session's role, the fleet's session rows) is kept for the tick and dropped when it ends, stamped with the files it was read from so a file written in the middle of the pass is read at the next look; a file read often (a pane's registry row, a machine's session file) is parsed again only when its modification time, size or inode moved (`stackshot/core/filecache.py`); what is worked out from several files and settings (the project registry the readers see, the index of the fleet's session rows) is kept the same way, under the stamps of its files, and is built again when one of them is written, at once for a write by this process (`filecache.derived`). **The pace is one minute, and `runner.PACE` is the runner's one knob:** the fleet's clocks are *paced*, one round every `runner.PACE` seconds (60), the pause counted from the end of the last paced round, so a clock with its own gate of a minute or more (the done check, the event waits, the step proof) is not slowed; the two wake passes are *event* ticks, run when the wake event `_update` sets, when the wait the runner computes ends (until the earliest wake, at most 60 s), and in every paced round, in front of the paced ticks, so the events that end a wait are settled before the done check, the step proof or the hand-off tick look at the board, whichever of the two clocks started the round; a wake still fires at its minute, except that the lock is held for the whole round: a wake that falls due while a round runs waits for it to end and can slip by the length of one round (a tick over 30 s is logged by name). The thread sleeps until the earlier of the two. The ten-minute set (`runner.TEN_PACE`, 600 s) is a third group: it runs in the first paced round after a start (so a restart never delays it), then in the first paced round after each tenth minute, right after the minute set in that round, on a schedule that does not slip when a round is late and does not run twice after a long gap; it stands still while the board is held, and a wake event alone never runs it. `GET /audit/status` carries `ten_pace_seconds` beside `pace_seconds`. The migration's hold on the board skips the same clocks as before (all but the registry sync and the clients' tick). **The runner is the only path:** there is no switch. A config file that still carries the retired `[runner] enabled` key starts as usual; the key is read by nothing, and `bin/stackshot doctor`, the server's start and a reload print one note saying it can go. The start logs `stackshot: minute set: runner …`, and `GET /audit/status` carries a `runner` object: `enabled` (always true), `mode` (always `runner`), `running`, `started`, `pace_seconds`, `rounds`, `last_round` and per clock `name`, `group`, `pace`, `runs`, `errors`, `skipped`, `last_run`, `last_ms`, `last_error` and `last_error_at` (epoch seconds; `last_error` is null until the first error and then stays, with its time, until the next error: a clean run does not clear it). **The wake catch-up and the runner's watchdog:** the timer publish (every `[publish] every_minutes`) no longer runs a wake pass of its own. The pass it ran moved into the runner's ten-minute set as the tick `wake_catchup`, which runs the watchers' pass without the due-wake gate of the minute tick (the watchers also end waits that `next_wake` does not count: an item wait whose `after` items all closed while nobody saw the close, with its ask-by days away), and publishes the board when it released something. The watchdog is a thread of its own (`watchdog_loop` in `stackshot/service/runner.py`, started with the runner by `runner.start()`, a look a minute, so a stuck publish never silences it): it asks `Runner.stalled()`, and when the last completed round is older than `runner.STALL_AFTER` (3 minutes; a blocking call inside a tick) it writes one stderr line and sends ONE message to the `[audit] builder` per stall, naming the tick the runner is in (`Runner.current`), with no board item and nothing for the owner; the next look that finds a round completed again re-arms it. The runner's times are the wall clock (`time.time`), as its status has always been, so a clock step could show or hide a stall for one look. Not in the runner: the 10-minute publish, the router, the GitHub mirror, the comments reader and the search index keep their own loops (the page-debt call is no loop of the server any more: the audit run's pages stage asks for it).

**The runner's signal files** (`stackshot/core/runner_files.py`, `<paths.state>/minute/`; `tests/runner_signals_scenario.py`). What the runner shares with the server, when it is a thread of the server (`[runner] process = "inline"`), is in memory; at the default, `"unit"`, the runner is a process of its own. Four small files carry the same four things for a runner that runs in a process of its own, each written by the side that knows it and read by the side that needs it; the in-memory form stays the truth for the process that holds it (a process never reads back a file it wrote itself), so nothing observable changes while the runner is inline (a process that has the runner in its own memory reads none of them back). (1) **The wake file** `wake`: `service/runner.py` `wake()` (what `update`, a board answer and the migration's end call, in place of setting the event bare) sets the event and writes one line, `<time_ns> <pid> <count>`, by a temp file and an atomic replace. A runner whose wait is longer than a second sleeps in slices of `runner.SIGNAL_POLL` (1 s, the loop's own short granularity, so a wake from another process reaches a waiting runner within a second and a half at most, and one from its own process at once by the event) and ends the wait when the line differs from the one it took at its last round; the line is taken as a round starts, so one wake is one round. A read is one open of about 40 bytes, once a second while the runner waits. (2) **The hold file** `hold.json`: `watchers.hold` writes the migration pass's hold (the holder's pid, who began the pass, `since`, `until`) and `release` removes it; `holding()` and `holder()` also read the file of another process. A file holds only while its holder's pid is alive, `until` has not passed and `since` is less than `HOLD_CEILING_S` (an hour) ago, so a pass that crashed leaves a file that holds nothing (a dead pid at once; a reused pid for at most the ten minutes of `until`). With no file the look costs one stat; with one, two stats and a `kill(pid, 0)`, the parse kept under the file's stamp. (3) **The status file** `status.json`: the runner hands `Runner.snapshot()` (its status record, its pid, a heartbeat on its clock, the tick running now and the tick that ran last) to `beat` at the top of each loop iteration, at the start of each tick and at the end of each round, never inside a tick, one small atomic write each (about 25 a round). `runner.status()` (`GET /audit/status`) and `runner.watchdog()` read it when the process has no runner of its own: `status()` then carries `source: "file"`, `pid`, `heartbeat`, `current`, and `running` is true while that pid is alive and the heartbeat is no older than `runner.STALL_AFTER`; the watchdog tells the builder once, as for an in-process stall, when the heartbeat or the last completed round is older than `runner.STALL_AFTER` (a process that died stops its heartbeat, and the message says its process is gone). A look is one stat, and a parse when the file moved. (4) **The server's start** `server-start.json`: `_start_background` writes the server's pid and start before it starts the runner, and `fleet_events.flag_start()` (what the inbox flag's first-pass delay counts from) returns that start when it was written by another process that is still running, else `INBOX_FLAG_START`, so a runner that restarts alone does not wait out the delay again. Every reader takes a missing, empty, torn or oddly shaped file as nothing there and never raises; every writer's failure is one stderr line a minute and never the caller's; the read-only standby writes none of the four.

<a id="the-runners-process"></a>**The runner's process** (`stackshot/web/minute.py`, `stackshot minute`; `[runner] process` in [configuration](configuration.md); `tests/minute_scenario.py`). `[runner] process` is `"unit"` (the default, when it is not set: the server starts no runner thread and `stackshot minute` runs it) or `"inline"` (the runner is a thread of the server, as above: the choice for a host with no minute unit, and what every host ran before `"unit"` became the default); it is restart-only and read once at a start, by the server (`service/runner.py` `start()`) and by `stackshot minute`. Nothing observable changes at `"inline"` but the lock below. **The singleton lock:** exactly one process runs the runner, by a non-blocking flock on `<paths.state>/minute/runner.lock` (`runner_files.lock_take`), held for the life of the process that runs it; the kernel frees it when that process dies, and the file is only a name to lock on (the holder writes its pid into it for a message, and empties it when it lets go). An `"inline"` server takes it before it starts its runner thread. If another process holds it, the server starts no runner, writes one stderr line (`runner not started: lock held by pid N`), keeps serving and starts everything else, and `GET /audit/status` carries `runner.message`: `minute runner not running (lock held by pid N)`, naming the holder as of that read (a holder that is gone, or a lock that is free, is not named: the message then says the lock is free and this server takes it at its next look). While the setting is `"inline"` and no runner runs here for that reason, the watchdog's thread tries the lock again at each of its looks (every 60 s, `runner.WATCHDOG_EVERY`; no new thread): when it is had it starts the runner by the path the start uses, once, says `the runner lock is free now; this server took it and starts the runner` on stderr, and the message goes away; a "unit" server never retries; a lock file that cannot be had is said and the runner starts without the lock, as a store lock falls back to its thread lock. A `"unit"` server takes no lock and says so; `GET /audit/status` carries `minute runner not running (runs in its own process: [runner] process = "unit"; start `stackshot minute`)`, plus the pid and the age of the last heartbeat when a status file exists, while no live process beats it (`running` false), and the watchdog tells the `[audit] builder` once, as for a stalled runner, when no process has beaten the file for `runner.STALL_AFTER` after the server's own start (`no process has reported since this server started`). The read-only standby takes no lock and writes no file. **The process:** `stackshot minute` installs its SIGTERM, SIGINT and SIGHUP handlers first, then refuses with an exit code of its own (to stderr, one line) when no config is named outside the production checkout (2), the setting is `"inline"` (3), the instance is a read-only standby (4), the lock is held by another process (5) or the lock file could not be had (6); then it imports `stackshot.web.server` as a module (the three wiring steps run in the order `tests/phase_sweep_scenario.py` pins; nothing starts and none of the start-time passes runs: they stay in the server), waits until the server's `GET /healthz` answers `ok` (it answers only after the start-time passes, so the store is migrated before the first tick; one stderr line every 30 s while it waits; a stop signal ends the wait), builds the same `Runner` over the same table with the wake, hold and status files, and runs until stopped. It starts no router, search, mirror, publish or watchdog thread. SIGHUP re-reads the config as the server's reload does for what the runner reads (the config, the stall pause); the publish and the phase sweep of a reload stay the server's. SIGTERM or SIGINT stops the runner, waits up to `--stop-wait` seconds (30) for the round that is running, abandons a tick that is still running after that (every tick is meant to be run again), releases the lock and exits 0. Exit 0 and 1 are a stop and a failure (an option out of range, `--ready-poll` not above zero or `--stop-wait` below zero, is refused with exit 1 and one line); 2, 3 and 4 do not change by themselves, 5 and 6 can.

<a id="the-runners-default"></a>**The default is `"unit"`.** A config that does not set `[runner] process` gets the unit; a config that sets `"inline"` or `"unit"` is read exactly as before. **A host that deploys with `./deploy.sh`** needs nothing: the deploy that brings the default runs `./install.sh units` after the fast-forward, and that script reads the default and installs and enables `stackshot-minute.service`; the deploy then restarts the server (which starts no runner) and the unit right after it, and checks for the unit's heartbeat. **A host that does not** (no systemd user manager, or the checkout is updated and the server restarted by hand) runs no minute passes after the restart until it either runs `./install.sh units --start` or sets `[runner] process = "inline"` and restarts the server. The server does not guess for it and does not start a runner of its own while it waits for a unit: a runner started by the server only when nobody else runs one would take the lock a unit that starts a minute later needs, and the unit would then refuse and fail. What it does is say so: one stderr line at the start that names both fixes (`[runner] process is not set, so the default "unit" applies ...`), the same text under `runner.message` of `GET /audit/status` while no process beats the status file, and the watchdog's one message to the `[audit] builder` after `runner.STALL_AFTER` with no heartbeat (`no process has reported since this server started`). A value that is set and is neither `"inline"` nor `"unit"` still reads as `"inline"`: a misspelling never leaves a box with no runner. `stackshot doctor` follows the same reading: it lists `stackshot-minute.service` at the default and reports one that is not `active`. `stackshot.example.toml` carries `process = "unit"`, so a config written by `stackshot setup` states it.

<a id="the-runners-unit"></a>**The runner's unit** (`units/stackshot-minute.service.in`, `install.sh`, `deploy.sh`; `tests/install_scenario.py`, `tests/release_scenario.py`). `stackshot-minute.service` is a user unit that runs `stackshot minute` (the server's `uv run --project <checkout> --locked --extra server` command line, the same working directory and environment lines), and it exists only with `[runner] process = "unit"` (the default). **When it is installed:** `./install.sh units` renders and installs it (and `install.sh render` lists it) only when `[runner] process` is `"unit"` (the default, when it is not set) and the box is not a read-only standby (`STACKSHOT_READ_ONLY=1` in the environment of the script, or in the one the user manager gives `stackshot.service`: an `Environment=` line of a drop-in, or an `EnvironmentFile=` file, whose last `STACKSHOT_READ_ONLY=` line decides as in systemd); any other value reads as `"inline"`, as it does everywhere. At `"inline"`, set in the config, nothing about the other units changes and nothing is installed, enabled, started or restarted for it: the script says `stackshot-minute.service: skipped ([runner] process is not "unit")`; on a standby with `"unit"` a unit an earlier run installed is stopped, disabled and removed, and the script says it is a standby (a runner there would write the board). That removal is the whole of it, not only a skip: the standby switch is read from the environment once, at a start, so a runner that is already running cannot notice that its box became a standby, and the standby's drop-in reaches the server's own units only, not this one; `stackshot minute` exiting 4 covers a start, not a process that is up. The stop comes first (`disable --now`, else `stop` and `disable` apart) and the file is removed only once the unit is off; a unit that is still running after that keeps its file, `install.sh` prints what failed on stderr, installs the other units all the same and exits 1 at its end (a removed file would leave the process with nothing to stop it by). A failed state the unit leaves behind (a tripped start limit) is cleared with `reset-failed` after the removal, so nothing lingers as `not-found failed`. `./install.sh minute-off` does the same stop, disable and removal whatever the setting says. Promoting the box later is `./install.sh units`, which installs the unit again at `"unit"`. **How it runs:** it is ordered `After=stackshot.service` and tied to nothing (no `Requires=`, `Wants=` or `PartOf=`), so restarting the server neither stops it nor starts the server: the process waits for `GET /healthz` at its own start only. `Restart=on-failure` with `RestartSec=5` covers exit 1, 5 and 6; `RestartPreventExitStatus=2 3 4` keeps the three exits that cannot fix themselves down (the unit stays failed with that code). Exit 5, the runner's lock held by a server that still runs the runner inline, would otherwise be retried forever: `StartLimitBurst=8` starts in `StartLimitIntervalSec=300` (about a minute of tries at that pace, with room for slow starts under load; a crash that comes back only now and then never adds up to eight) stops it, and systemd reports the unit failed (`systemctl --user status stackshot-minute.service`; the server's `/audit/status` already says no runner runs); once it has tripped, a plain `systemctl --user restart` is refused ("Start request repeated too quickly") and only `systemctl --user reset-failed stackshot-minute.service` clears the count, so `install.sh` and `deploy.sh` run `reset-failed` before every start or restart of the unit (a deploy that ships the fix inside the window then recovers it). **Priority:** `Nice=10` and `CPUWeight=50` (the default weight is 100) put the runner's work behind the server's requests when the machine is busy (`CPUWeight=` is ignored where the cpu controller is not delegated to the user manager; `Nice=` still applies), which is the point of running it as its own process; there is no `MemoryMax=`, since a runner that shared the server's memory until now has no measured peak to cap safely and a hard cap would kill a round in progress. A stop is SIGTERM to the process (`KillMode=mixed`): it finishes the round that is running for up to `--stop-wait` (30) seconds and releases the lock, and `TimeoutStopSec=45` sits above that. **Reload:** `stackshot-reload.service` is unchanged and still reloads the server and the hub and names no minute unit; the unit says `ReloadPropagatedFrom=stackshot.service`, so systemd turns that reload into a reload of this unit while it is running (and does nothing while it is not), `ExecReload` sends SIGHUP, and the process re-reads the config as above. **Deploy:** `deploy.sh` restarts it right after the server, when its unit file is installed and a change touches what the server imports (the same files that restart `stackshot.service`, except the server's own unit and the reload watcher's), `install.sh`, `stackshot/web/minute.py` or the unit itself; the `--dry-run` plan lists it then, a rollback reads the same map from the older commit's own `deploy.sh`, and it is not in the plan, and not restarted, when the setting reads `"inline"` or the box is a standby (the deploy reads both, so a deploy that flips the setting back does not restart a unit `install.sh` is about to remove; a config it cannot read counts as `"unit"`). **Flipping back in a deploy:** the setting is restart-only, so a server started at `"unit"` has no runner of its own, and a deploy that flips the setting to `"inline"` removes the unit; a change that restarts nothing by its files (a docs-only one) would leave the box with no runner. `deploy.sh` therefore restarts the server in that same deploy whenever the unit is installed and the config reads `"inline"`, in the `--dry-run` plan and in the run alike, with a note that says why. **After the restart:** the unit is `Type=simple`, so a restart that succeeds and a `/healthz` that answers say nothing of the runner (it can fail at its own start, a lock held or an import error, after the server is up). For a unit this deploy restarted, `deploy.sh` waits after the health check and the republish, up to `DEPLOY_MINUTE_WAIT` seconds (90; 0 looks once), for the unit to be `active` and for a heartbeat in `<paths.state>/minute/status.json` (what the runner writes at the top of each round, read through `runner_files.status_read`) that comes from the unit's own process (the pid is the unit's `MainPID` or below it: `uv run` stays the parent of the runner) and is newer than the restart; a unit that is `failed` ends the wait at once. A runner that does not show is one `WARNING` line (the unit, its state, what was seen of the heartbeat, the wait, and `systemctl --user status` and `journalctl --user -u` to run) and the deploy still exits 0, like a failed republish: the server runs the new code by then, a nonzero exit would read to `release.sh` as "merged, not live" and pause its queue for a runner that is only slow to start, and the server's runner watchdog and `stackshot doctor` flag a runner that stays down. At `"inline"` nothing is restarted, so there is no check and no wait. **Rollback to a commit from before the unit:** that commit's own `deploy.sh`, which does the second step, knows nothing of the unit and would leave it running against the older code next to the older server's runner (two runners, one lock). When the unit is installed and the commit has no `units/stackshot-minute.service.in`, the first step therefore runs `./install.sh minute-off` before the reset and the hand-over, and stops with the checkout untouched when the unit cannot be stopped (the order stays: the unit is gone before the reset, so if the reset or the older `deploy.sh` then fails, the step prints a `WARNING` that the server may have no runner and what to run: `./install.sh units` when the checkout did not move, then `systemctl --user restart stackshot.service`); the older server's own runner (a thread, at the default) comes up with the restart its deploy makes, and the plan names this in a note and omits the unit. **Doctor:** at `[runner] process = "unit"`, `stackshot doctor` lists `stackshot-minute.service` with the other units and reports one that is not `active` (failed, inactive) as missing, with `./install.sh units --start`; at `"inline"`, or on a read-only standby (which has no such unit: `install.sh` removed it), it says nothing of it. A first install is not in a `--dry-run`'s plan (the plan reads the installed unit file, and none exists yet). **Switch to the unit:** set `[runner] process = "unit"`, then `./install.sh units --start` (it installs and enables the unit, restarts the server, which then takes no lock and starts no runner, and starts the unit after it). **Roll back:** set `[runner] process = "inline"` and restart: `./install.sh units` stops, disables and removes the unit and says that the server must be restarted, because it runs no runner until then, and `systemctl --user restart stackshot.service` starts the server's own runner (a server that finds the lock still held by the runner process that is stopping says so and takes it within a minute, as above); a unit that is only restarted with the setting at `"inline"` exits 3 and stays down.

**The filing pass and the dates pass** (`stackshot/audit/audit_checks.py`, `audit_run.filing_pass`, `_filing_tick` and `_dates_tick` in `stackshot/service/audit_ticks.py`; the filing pass also needs `[audit] enabled`). The daily audit's checks that need no judgment live in `stackshot/audit/audit_checks.py` as functions (`field_findings` and the per-item checks; the daily run in `stackshot/audit/audit_run.py` calls them and re-exports their names). The ten-minute set runs a subset on the open items: **filing**, where the item says one thing and the board another and the fix is the writer's, nothing about silence or time passing. It checks stuck-elsewhere (a next line that hands a step to a session the item's mover does not own, `audit_checks.check_stuck_elsewhere`), mover-no-session (an open item whose mover is a session name that no live or known session carries, so its wake notices wait in a queue nobody reads: a name or alias of any row of the session registry, a retired row included, and a name the fleet's own session files list are known, and a person, an outside party, a cloud session, an id, the instance's own name or no mover at all is no case; `audit_checks.check_mover_no_session`, names read once a pass by `audit_checks.session_names`, and a registry that holds no session or cannot be read finds nothing; the finding gives the mover and the item's last write and its fix says to set the mover to the project's -main agent from its page, else to name a live session; it goes to that front agent through the project's page key, or to the audit's main agent when none can be named, and only reports: nothing edits the item), step-handover (a finished step that did not hand the item on, `audit_checks.check_step_handover`: a step that delivers a pull request has another session's step after it and no proof, or the last done step was marked by the mover or the server at least 30 minutes ago and the session the first open step names, a background session, was never handed the item, unless the item is parked, waits on a decision or has needs that name another session, which the server leaves alone too (`handover.skip_reason`, one rule for both); the finding goes to the mover), the board report's filing kinds (arbitrary-hold and mislabeled-state, the board report's two kinds), ask-options (an open item's ask the page cannot be answered from, `audit_checks.check_ask_options`, read with the write gates' own matchers in `stackshot/model/ask_read.py`: a Yes / No (also options the page cannot read) under a Decide part that is an open question or names alternatives, an item that lists no options while its Recommend part is not a yes or a no (it names a person, a topic, a date, so the Yes / No the page draws cannot answer it; `ask_read.recommend_not_stance`, whatever language the Decide part is in), or a Recommend part that plainly does not match the options (it names no option by label, letter, place or a leading word only the recommended label has, or names another; an option after not, avoid, never, skip, except or instead of, or a word of `[keywords.ask_options]` `refusals`, or a label right before a word of `refusals_after`, is turned away; a label followed by a `particles` suffix still counts as named) or answers yes or no to an open Decide; in doubt nothing is found, and an ask that does not split into Decide and Recommend is not read; the fix asks the mover to rewrite the ask with options; no model call, no cap, quiet once the ask is rewritten), a next line that reads as a wait in words only (`wait_words`, which never reads the owner's step the server made from an ask or a step, the line `metadata.owner_step` records: "Decide: which address to give until Dec 6th" makes the line `<owner>: which address to give until Dec 6th`, his step on a question put to him and no wait a mover parks; a `<owner>:` line a session wrote is read like any other until the server's next settle of his step adopts it as his: the precise hits, such as "once board#N closes", are a finding; the broad words when, once, after and until alone are listed in the pass's flags and sent to no one, and a date-only wait left alive (`audit_checks.date_only_wait`, category `why-not-now`: a doing item whose wake is over the hour away and whose every open next line is its mover's and opens with the wake's own hour or day, so nothing is left to do before then and the board still lists it as doing; no model call and no cap, unlike the daily `why-not-now` on dated steps; the fix is the server's own: the pass parks the item and messages the mover once, see **The server files four facts itself**), and the wait-end rule (`stackshot/waits/wait_end.py`, category `wait-end` and `event-missing`, see **The wait-end rule**). A finding goes to the same recipient the daily run's findings go to, through the same `deliver_findings`, and is sent once while the item is not written to. The pass drops a finding from its own record at the end of a pass in which it no longer holds, and no daily record shields it any more (the daily run does not make these checks), so a finding that ends and comes back with its item unwritten (the role map briefly empty, a pane that changes, an anchor or an after-item that changes) is sent again. The pass's record `<state>/audit/filing.json` (written atomically; it is no run, so `audit.runs`, `last` and `status` do not read it) and the newest daily record are merged (`merged_sent`), which matters only for a send an earlier daily run made; an item written since the send is sent again. The daily run no longer makes these checks (stuck-elsewhere, arbitrary-hold, mislabeled-state): they are the filing pass's alone, so a finding reaches its mover once, and the daily run's summary, its `by_category`, the unmoved digest, the `[audit] threshold` count and the 20% share of flagged items count only the checks the run makes. Idle-on-agent stays with the daily run. The pass does nothing while a daily run is in progress. The filing pass sends its messages from the runner's one thread, so a large first-run backlog holds the other rounds (the wake round included) until it is sent. The **dates pass** does two looks every ten minutes, each in its own try (the first error is raised after both have run, so the runner records it): it opens the For you due-date look's gate, and it looks for **a wake that has passed with nobody acting** (`audit_checks.dates_findings`, `audit_run.dates_pass`, `audit_ticks._dates_expected_tick`; it also needs `[audit] enabled`, script mode). An item's expected time is the one `stackshot/waits/waiting.py` derives from what the item carries: its wake (a dated wait's, a park's wake included). The rule is the date half of the daily audit's stale check (`check_stale`, which now is only this date rule), with its exemptions kept: an item is found when it is an open item in the state doing whose wake has passed and which nobody has written since the wake; agent work in progress with no wake has no date to pass; a wake still ahead, a park with no wake, an item on the owner or an outside party, behind an open item, or in a state that is itself a wait (parked, outside, blocked, your-call, your-step, verifying) is left alone; one the idle pass poked is no finding, as in the daily run. A finding is the `stale` finding the daily run used to send for this, word for word, goes to the same recipient through the same `deliver_findings` (headed `Dates check <time>`), and is sent once while the item is not written to; the pass's record `<state>/audit/dates.json` (written atomically beside `filing.json`; no run, `dry` sends and writes nothing) and the newest daily record are merged (`merged_sent`), so a send an earlier daily run made still holds while its record is the newest; a finding the pass drops from its own record and that comes back is sent again, as in the filing pass. The pass does nothing while a daily run is in progress (what falls due in that time is sent by the first pass after the run).  No state-check note is stored on an item any more: the next-line words that are not refused (a stored `model_flags` list, read by nothing but the writer's reply) are derived from the stored next when the writer's reply or `get` needs them (`_state_check_notes`, `audit_checks.wait_words`), and a write that sets the next drops a legacy `model_flags` entry. Suites: `tests/filing_scenario.py`, `tests/dates_scenario.py`, `tests/audit_run_scenario.py` (the pin of what the daily run still checks, and that each moved check is made by its ten-minute pass alone), `tests/runner_scenario.py`. **An unanswered finding is not forgotten** (`audit_run.split_sent`, `[audit] remind_hours`, default 6, 0 = once only as before): (a finding about how an item is written, filed or waited on, on an item the owner moves, is the exception: it asks nothing of him, so it is sent once, never reminded or escalated, and held for a front agent instead of marked; `audit_run.once_only`, `audit_checks.NO_PERSON_NEED`, [audit](audit.md)) a finding of the filing or dates pass that its item has not answered (no write since) is sent again that long after its last send, worded as a later try (`second try, no answer`, the ordinal in words: the router drops a message that repeats an earlier one but for numbers and dates), until it has had three sends (a send after a write counts too: each finding record carries `tries`, kept while the finding stands and gone when it ends; a reminder or escalation that is not reached keeps the finding on its old send and tries, `audit_run.carry_unreached`, so the next pass retries that same send); at the next due time after that it goes once to the project's builder as unmoved (the daily run's unmoved flag, `chase the mover (job)`), to no one else, and by the project's page key (where the router rules it) when the builder is the mover or the finding's recipient, never to the session that did not answer. **Level 2:** when the finding still stands unanswered at the next due time after that send and its recipient was a builder (a background agent), it goes once more, to the project's `-main` agent, marked `[for <owner>]`: `<id> · nobody answered after N messages · <category> · <detail> · <mover> writes it, or says what holds it` (`audit_run.deliver_findings`; `split_sent` sets `escalate` to 1 for the builder, 2 for `-main`; an unreached send keeps its tries like any other). A finding whose first recipient was the page key or a front agent (a front agent's finding, a retired or outside mover's) went to the builder at level 1 and ends there, as does one whose builder is `-main` itself; a builder-moved item's finding goes to the page key at level 1 (never to the mover) and then to `-main`. Only a builder-level send made with the level kept (`lvl: 1` on the finding's record, read by `audit_run.levels_before`) is followed by level 2, so a finding already escalated before this level existed stays quiet and a release sends no burst. After level 2 it is quiet until the item is written. The dates pass has its own ladder entry and sends none of these. Suite: `tests/front_step_move_scenario.py` (8).

**The front-step rule** (`stackshot/audit/front_step.py`, `audit_run.front_step_pass`, `service/wait_gates.py`'s `_front_step_mark` and `_front_step_move`; part of the ten-minute filing pass, so it also needs `[audit] enabled`, script mode). A stuck-elsewhere finding about a front agent's step goes to the project's page key and is sent once (`audit_run.recipient`); the mover only relays it and the ladder gives a front agent a History line, so nothing changed the board and such a step could stay open for as long as the item did. The rule moves it. **Scope:** a stuck-elsewhere finding whose step opens with a front agent or a keeper (role `front` or `keeper` in the role map, `audit_run.FRONT_ROLES`) or a retired session, on an item whose mover is a session that is not retired. Not the owner's steps, not a background agent's (it gets the finding itself and can answer it), and not an item the owner moves or one with no session as mover (there is nobody to move the step to). A live front agent of the item's own project in a front-only project is covered like any front agent, unlike in the write check: the finding is about the item's first open step, so no open step is before it and the step hand-over (which follows a done step) cannot carry the item to it, whether the peer was down (`metadata.handover` a `fallback`) or the step before it was dropped. A peer step waiting behind an open step is never the first open step, so it is never seen here (`front_step.is_peer` serves the monthly count). **Clock:** the first pass that sees the finding for a step stores `metadata.stuck_since = {"step": <hash>, "mover": <the item's mover>, "at": <epoch>}` on the item (written only after the server has read the item again under its lock and found the finding still holding) (the hash is twelve hex digits of the step as the checklist compares it); it is the server's own bookkeeping, a save with no writer, so it moves no activity clock and writes no notice. A write to the item by anyone does not restart it, only a change of that step does: a pass that no longer sees the finding for the step (the step done, dropped or reworded, the opener changed, the item closed) drops the record, and a reworded step starts a clock of its own. A clock kept for another mover reads as none: when the item goes to a new mover while the front agent's step stays first, the clock starts afresh under the new mover, so it is not handed the step minutes after it took the item. **Threshold:** `[audit] front_step_move_hours`, default 3, a decimal reads, 0 = off (a pass with the setting at 0 only drops clocks it finds, so switching it on again starts clean). **Action:** when `now - at` reaches the threshold and the finding still holds, the server reads the item again under its lock, and moves nothing unless the item's mover is still the one the pass saw and the stuck-elsewhere finding still holds on the item as it is now (the same check, so an item handed to the opener, parked, held or put on a wait since the pass read it is left alone), and rewords the step so its first line opens with the mover (the list marker, bold marks, the rest of the line and the lines under it kept; a role in parentheses after the old name is dropped), through the pieces an `update(reword=…)` uses: `nextlines.reword` (the line is the mover's own from then on: `reword` takes a `new_writer`), `steps.apply` for the checklist, and the step's proof moved to the new text. Nothing moves when the item is closed, the first open step is another one, the new text would read like another open step, or the first line has no opener to replace. It writes one History line (`metadata.stall.log`, drawn as `stackshot: …`): `step moved from <opener> to <mover> after N hours open with the stuck-elsewhere finding unanswered (reword it back to undo): "<the step>"`, so the original opener is on record and a reword puts it back. The step's hash goes into `metadata.stuck_moved` (the last five), the clock is dropped, and the step moves **once**: worded back to the front agent it is a finding again, with no clock and no second move. **Messages:** the mover gets one plain message per moved step, `fyi` (it starts no turn for a background agent), from the filing pass; nobody else is told, not the front agent and not the page key, and a mover that is itself a front agent is not messaged at all (the History line is the record: a front agent hears of its item at two moments only). **The finding** of a step still waiting says so: its fix line reads `take the step, or reword it to <mover>; if it is still open then, it moves to <mover> at <time>` (the finding is not tool text; the time is the clock's start plus the threshold, in the instance zone; a finding whose clock could not be written, or whose move was refused, promises no time and keeps its plain fix line). With no roles at all (the role map is briefly empty now and then) the rule does nothing and drops no clock; without the item writers (`Env.step_mark`, `Env.step_move`: the command line) it does nothing; a dry run starts and moves nothing. The pass's record, `filing.json`, carries `front_steps` (`hours`, `started`, `moved`, `cleared`, `errors`, `messages`) when the rule did something. **After the move** the server leaves `metadata.stuck_landed = {step, mover, at}` (the reworded step's hash, the mover, the time; `gates._REPARK_QUIET`, no writer) and the hourly audit line and the idle hand-over count the mover's quiet time from it (`silence.clock`): the mover is given its time from the move, so a mover who does not act gets the audit line and, with nothing verified, the hand-over, and the stall pass has the item as before. A reword of the step, the mover's own activity or a new mover ends it. Decisions: a front mover is moved to but not messaged; the owner's own steps are left to the existing finding; the clock lives on the item rather than in a file of the pass, so it survives a restart and shows with the item. Suite: `tests/front_step_move_scenario.py`.

**The front-step write check** (`front_step.held`, `stackshot/service/gates.py` `gate_front_step`, called from `update_unlocked` (`stackshot/service/update.py`) and `create_item` (`stackshot/service/create.py`); one of the model's write guards, so `[model] guards = false` switches it off). The front-step rule repairs a step a front agent already holds; this check stops a new one at the write. A session's `create` or `update` is refused when it adds or rewords an open step (a line of `next`, a `reword`) whose opener is a front agent (role `front`, not retired) and the item's mover is another session: a front agent gets no work notice and its own wake or until dates (with no hold) on such an item are refused, so such a step can never fire. Judged: only a step not already open before the write (compared as the checklist compares steps, so a re-sent line, a rebullet or an unrelated write passes), and only a session's tool write (`SESSION_NEXT`), never the server's own writes, a script's sender or a done mark. Allowed: the front agent is the item's own mover, the opener is a background agent, the owner or an outside party, the item has no session as mover, the mover is retired, or the opener is a live front agent of the item's own project and that project is front-only (`anchors.front_only`: no builder; `handover.peer_opener`, the pair `mover=` allows): the step hand-over moves the item to that peer when the step before it is done (the same property a background agent's step has; any session may write it, and it is not the same as `mover=`, which hands the item over at once), so the step can fire. It passes only with an open step before it (`handover.open_before`): as the first open step nothing would ever move the item, so it is refused as before, with a tail that says to put an open step before it, hand the item over with `mover=<peer>` or ask with a `For <peer>,` message to the peer's project page. `front_only` is read only for a live front agent of the item's own project, and a read that fails there leaves the step refused. A front agent of another project, and every front agent of a project that has a background agent, are refused as before. A failing roles read lets the write through with one stderr line (`front-step gate: ... not judged`). The refusal reads `Refused: the step "<first line>" opens with <agent>, a user-facing agent of <project>: it gets no work notice and its own wakes are refused, so nothing would wake it for the step, and <mover> moves <item>.` followed by `Give the step to <mover> (open it with "<mover>:"), or ask <agent> with a message to <its project page> whose first line starts "For <agent>,".`, or, when the mover itself wrote the step, `Keep the step with <mover>, hand <agent> the item with mover=<agent> (only between front agents of one project that has no builder), or ask <agent> with a message to <its project page> whose first line starts "For <agent>,".` The tail names only paths that work: a plain message to a front agent is refused unless it carries the owner mark, while the `For <agent>,` first line to the page is passed to the agent by the router. **The monthly count:** `audit_run.front_step_count`, the first run of each calendar month (instance zone), puts `front_step_count` (`month`, `days`, `closed`, `by_other`, `open`, `ids`) on the run record and one line in the run's summary to the stackshot project: `front-held steps, last 30 days: X of Y closed by someone else · Z open step(s) the write check would refuse now (ids)`. `closed` is the steps opening with a front agent that were closed (done or dropped) in the last 30 days, `by_other` those closed by a session other than that agent (a server mark or an unsigned close is no session), `open` the open steps on open items the check would refuse now (`front_step.month_count`). Suites: `tests/front_step_refuse_scenario.py`, `tests/front_step_move_scenario.py` (level 2).

**The server files four facts itself** (`stackshot/waits/server_fixes.py`, `stackshot/service/gates.py` `fix_front_mover`, `_fix_loose_reason` (`stackshot/service/update.py`), `_date_only_wait` and `_wake_park` (`stackshot/service/wait_fixes.py`), `audit_run.wake_park_pass`, `model_guards.window_line`; `tests/server_fixes_scenario.py`, `tests/front_mover_scenario.py`). Where a write or an audit finding is wrong in a way the server can read from the item itself, the server takes the fix and the mover is told what it was, instead of being asked to make it. Four fixes: (1) **a wake that is the whole of a wait** is parked (parked, `wait_basis` from the wake and the step's own words) by the write that sets it and by the ten-minute filing pass for one already stored, in place of the `why-not-now` finding for a date-only wait; the pass sends each mover one `fyi` message naming the items it parked and the way back, skips closed items, parked items, items the owner moves, items that wait on a decision and items a front agent moves (the finding stands for those), makes the park as the server's own save (no writer: the item's author, its activity clock and a pending answer stay as they were), and only parks a window or date-only wait, never one that an event starts; (2) **a front agent named as `mover`, `then` or `post_wake_mover` (the old name of `mover`) by another session** gets the project's builder instead (before, the write was refused); a project with no builder still refuses, except a `mover`, `then` or `post_wake_mover` set to a live front agent of the item's own project when that project is front-only (`anchors.front_only`: no builder) by any live session some project page lists; a `mover`'s target is told by a hand-off notice, a `then` or `post_wake_mover` target by the owner's answer or the wake, and the reply says so; a live front agent of the item's project that sets one of them (or `agent`) to a sibling front agent with the owner's words in `said` keeps it as sent and the sibling is told (`docs/handoffs.md`); (3) **a park with a wake and no wait reason** takes as its `wait_basis` the line of the item's own `next` (as the write leaves it), else its description, that says the work waits for the wake's own day (never for an item the owner moves or one in an owner state); (4) **a quoted or already-made pick** is no wait on the owner: a quoted span, and a phrase of the owner's name and a past verb ("Oliver decided the lane"), are blanked before the decision words are read (not when the words between the name and the verb negate or hold it open, as "has not yet decided", when a waiting word comes right before the name, as "until Oliver confirmed", or when the quoted span is his name alone), in `stackshot/web/tools/notes.py` `_waits_on_owner` and in the board report's `mislabeled-state` kind. Each fix is bound to its token (the wake, or `field=value`), kept in `metadata.server_fixed` ({fix: [tokens], last 5}); the front-mover token also carries the sender and the time (`field=value|sender|epoch`) and lasts a day; the fix writes a History line (the stall log, as "stackshot: ..."), and the reply of the write says what was wrong. **A mover who disagrees resends the field**: `clear_hold=true` (a parked wake), the same front-agent value again from the same session within a day (a front mover), or a `wait_basis` of its own (a reason); the server then leaves that field alone (the parked wake's no is recorded in `metadata.fix_declined`; a send-back that the same writer makes on the same item within an hour of the fix, like a front agent named again or a wait reason replaced, is counted in the call log as a bounce-back for the weekly report: `call_log.bounces`, `call_log.undone`; a send-back from another writer, or an hour later, is not counted), and a changed value is a new fact it may fix again. Never done by a fix: closing an item, writing an ask, changing an item the owner moves. Both keys are quiet (`gates._REPARK_QUIET`: a write that touches only them does not renew the item).

**The wait-end rule** (`stackshot/waits/wait_end.py`, `audit_checks.wait_end_gaps`, `audit_run.wait_end_pass`, `stackshot/service/wait_fixes.py` `_wait_end_fix` and `_wait_end_facts`, `server_fixes.WAIT_END`; `tests/wait_end_scenario.py`; part of the ten-minute filing pass, so it also needs `[audit] enabled`, script mode). An open item whose next line waits in words for something nothing tells the item has happened ("wait for board#N to close", "once owner/repo#7 is merged", "when hp-box is back online", "wait for the reply in <link>", a step `ship PR #7` with no proof) sat as work until somebody noticed. The write guards refuse a new line of that shape; the pass finds the older ones and the ones another session wrote. Only the mover's own open steps and the steps that name nobody are read (another session's step and the owner's are never read), and an item that is held, already waits, waits on a decision or is moved by the owner is never touched. Where the server can set the wait with certainty it does, as its own save (no writer), through the gates a write passes, with a History line, a record in `metadata.server_fixed` and one `fyi` message to the mover naming the items: `after` for one open item (the item's mover becomes its picker, stored as `mover`), an event wait `pr_merged` or `pr_released` for one pull request (a repository `release.sh` does not release is waited on for its merge; a bare `#n` counts only when the item is anchored to that pull request), `box_online` for one machine of the fleet that is offline, an anchor wait for a link the anchors tool takes (the link is added as an anchor scoped to the item), a step proof for a pure wait step among other work or a step that is only `ship PR #n`, and a backstop day for a stored wait no watcher can end (the wake or `ask_by` it has, else now plus `[waiting] cap_days`). An item waits only wholly, so an item-level fix needs the line to be the item's only open step. Where it cannot (an "or", several items or pull requests, a bare `#n`, a machine it does not know or one that is online now, a step with other work in it) the mover gets one `wait-end` finding that names the line and says what to write. A wait for an event no event type reports (a scheduled job's run, an upstream release, a CI run or deploy finishing, a service coming back, and a stored `job_run` wait) is an `event-missing` finding to `[audit] builder`, sent once and never repeated or escalated. A mover who disagrees sends the wait back with `clear_after=true`, `clear_wait=true` or `step_proof="none"`; the line is recorded in `metadata.fix_declined` and left alone until its words change. A line the pass would fix is held back for `[audit] wait_end_settle_minutes` after the item's last write (a mover still working on its next), at most ten fixes a pass, nothing closed and no ask written. `[audit] wait_end` is `fix` (default), `ask` (the findings only) or `off`.

**Where the page-debt call, the migrations and the inbox flag live** (`stackshot/service/page_debt.py`, `stackshot/service/migrations.py`, `stackshot/service/fleet_events.py`; what they still reach in `web/server.py` comes through `stackshot/service/passes_hooks.py`). `page_debt_pass` is the pass `POST /client/page-debt` asks for (the route stays in the server). The start-up migrations (`migrate_needs`, `migrate_owner_mover`, `migrate_holds`) run once per start from `server._start_background`; the passes of `POST /client/migrate` (`migrate_write` and what it applies, behind `migration_gate`) are in the same file, and the start passes (the session ids, the retire ranks, the mover backfill, the close marks and the close description repair) are in the file too, and `_start_background` runs them in the order it always did. **Where the readers of an item, of a project's agents and of a pane live** (`stackshot/service/item_read.py`, `stackshot/service/agents.py`, `stackshot/service/contacts.py`, `stackshot/service/pane_recovery.py`, `stackshot/model/holders.py`). `item_read.py` reads items and the facts about one: the open items an `after` names (`_after_open`), the item as the model reads it (`_model_of`), the anchors scoped to it, what the board draws as parked (`_is_parked`, `_date_parked`) and the model's switches; the two rules of the board renderer it still needs (`is_held`, `needs_kind`) come through its one `Hooks` table, which leaves when those rules move under `model/`. `agents.py` names a project's -main agent and its builder and the sessions a hand-off could name; `contacts.py` is an item's contact (the readers, the write and what follows a retired or renamed agent); `pane_recovery.py` is pane liveness (`_pane_stuck`, `_session_down`, `_machine_unreachable`, `_STARTED`) and the recovery request of a quiet mover; `holders.py` holds the pure hold rules. `_update` is a thin wrapper of `update_item` in `service/update.py`, which the server and its hook tables call by name there. **Where the save steps and the owner's words live** (`stackshot/service/mover_steps.py`, `stackshot/service/owner_words.py`, `stackshot/model/holders.py`; what they still reach outside `service/` comes through `stackshot/service/save_hooks.py`). The steps run inside every save, through the write path's `Steps` table and the update's hook table: `mover_steps.py` holds the stored state a step or supplies sets or a write unseats (`_state_apply`), the default `then` of an item that goes to the owner (`_owner_then`, `_owner_then_default`), the mover settle (`_owner_state_mover` for an update, `_settle_mover_on_save` for every other save; its third result drops a `then` that the user is not the mover for, and `_then_stands` does the same for a write that names the mover), the owner's step on the checklist (`_owner_steps_on_save`), the state as the brief shows it (`_eff_state`), the notes a read carries (`_state_check_notes`), the chain of an item that closed as superseded (`_follow_superseded`), the wait graph's loop test (`_after_reaches`) and `project_ref`. **Where the naming of the working agent, the message relay and the page-debt fallback live** (`stackshot/service/agent_names.py`, `stackshot/service/messaging.py`, `stackshot/service/page_debt.py`; what they still reach outside `service/` comes through `stackshot/service/save_hooks.py` and `stackshot/service/passes_hooks.py`). `agent_names.py` links a background agent to the item it works on: a handover message names it on the open items the text names (`_name_on_handover`), and a write by a background agent not yet named in the item's needs names it first (`_name_on_write`, which hands the caller the function that stores the naming); `_auto_name` is the one save both use, `_never_named` the `[pilot] never_named` list, `_one_mover_clash` the test that a naming never leaves an item with a second mover, `_back_agent` the test that a session is a background agent, `_item_refs` the reader of the items a text names and `_router_delivered` the router's push told to the hand-off record. `messaging.py` is the message tool's relay: `_message` (the message tool, the client API's `message` route and the passes that send from inside the server call it), its refusals and labels (`_gate_front`, `_dead_recipient`, `_project_of_name`, `_project_takes`, `_pane_dead`, `_reachable`, `_msg_label`, `_CSE_ID`), the status report written onto an item instead of delivered (`_builder_report`, `REPORT_ITEMS_MAX`), the phrases that say nothing is needed from the owner (`_NOT_FOR_OWNER`, `_NOT_FOR_OWNER_RE`), the publisher's letter (`_pub_letter`) and the log file every message is written to, `MSG_LOG`, which has no other owner: a reader takes it there. `_pilot_fallback_tick` (the page-debt call's fallback: a writer's pilot debt moves to the project's keeper) is in `page_debt.py`, with the call it backs up. The message length cap is the one new hook of `save_hooks.py`, and the owed-page check `_owed_brain_skip` the one new hook of `passes_hooks.py`. A suite that replaces one of these functions sets it on the module that holds it, and `_message` reaches the naming through `agent_names`, so one stub there reaches both callers.

**The store locks** (`stackshot/core/xlock.py`). The lock around an item's read-change-save (`writes.ITEM_LOCK`) and the locks around the whole-file stores (the For you list, the Landed list, the held hand-back lines, the page-debt ledger, the pending answers, the machine anchors, the anchors file, the wake pass, the stall record) are each an `XLock`: a re-entrant thread lock with a flock on `<paths.state>/<name>.lock` behind it, so a second process that writes the same files (the minute passes, once they run in a process of their own) takes turns with the server instead of overwriting what it wrote. The lock file is only a name to lock on: a holder that dies leaves it behind and not the lock. When locks nest they are taken in one order: the wake pass, then the item lock, then the pending answers, then the For you list, the Landed list and the held hand-back lines; the page-debt ledger and the stall record after the item lock; the machine anchors alone; the anchors file (`anchors.LOCK`, the name `anchors`) after the item lock where both are held, outside the numbered order, and never across a publish: the anchors tool, an anchor wait and its undo, the anchor sweep (the server's and the minute passes') and the re-key's rewrite of the anchor scopes each hold it from the read of `anchors.json` to its save, so a sweep in `stackshot minute` cannot lose an anchor the server added meanwhile or bring back one it removed. Every writer that reads an item, changes it and saves it takes the item lock round those three steps (the passes read the item again under it, after their scan; the GitHub re-key of an id takes it round the file move, the map and the rewrite of every `after` list that named the old id), and a send is never made while a store lock is held: a notice, a delivery, a push, a subprocess or a network call is collected under the lock and sent after it lets go (the wake pass, the release after a close, the anchor release, the check pass, the answer that drops an item, the escalation pass of the answers, the hand-over, the proofs and release passes, which hand their notices to the pass that holds the item lock round its loop, and the page-debt settle, which reads the pages' git with no lock held and applies its verdicts to the ledger as it then stands). What still sends under the item lock is named: the update's own notices (its reply text depends on what they return, and a notice to a front agent reads git through the front gate), the answer's delivery to the sessions (its record of who was told is kept under the answers lock): a second process waits behind those, by design, and this change leaves them there. Notices collected under a lock are each tried on their own once it is let go: one that raises never keeps the ones after it from being sent, and the first error goes on up when all were tried (a failed loop keeps its own error, the notices' are stderr lines). The answer that drops an item releases the items that waited on it after both locks are let go even when its delivery or its bookkeeping raised, and the error goes on up. A pending answer whose escalation send raised is put back, so the next tick sends it; one that was sent is not. A step notice stands as told to its session (the record the release event reads) only once it was sent. The re-key finds a dependent item by its id under the item lock, so one that another re-key moved since the scan is rewritten where the map now has it, and the scan is repeated while an item file came or went during it. The re-key's rewrite of the anchor scopes (`anchors.json`) is under the anchors lock, not the item lock, and the allocation of a local id (a thread lock) is under neither. A lock file that cannot be had (the state dir not writable, a file made by another user, no descriptor left after a short retry) makes the hold a thread lock alone and says so on stderr at every such hold, at most once a minute for each lock. That is the production default, so the single-process server is never broken by a lock rule. `xlock.strict` is the other mode, and the one the tests run in (`tests/run-suite` sets `STACKSHOT_XLOCK_STRICT=1`; any of 1, true, yes or on in that variable turns it on, and it is off when the variable is absent): the hold raises `LockUnavailable` naming the file and the errno instead, because a hold that keeps nobody out is a lost update, and a lock taken while one that must come after it is held raises `LockOrderError`. Both are `RuntimeError`s, not `OSError`s, so a broad `except OSError` cannot swallow them. A second process may write the stores only when it runs with `STACKSHOT_XLOCK_STRICT=1` too. The lock file is opened after the thread lock is held (a thread that only waits holds no descriptor), is never inherited by a child process, and is closed on every way out of an acquire that is not a hold. A wait with no time limit blocks in the kernel's flock, so it is woken the moment the holder lets go (a poll starves behind a process that takes the lock again at once); only a timed wait polls. A waiter that has waited 30 seconds names the lock on stderr (a watchdog thread, which holds nothing), and again every 60 seconds. [`[locks] cross_process`](configuration.md) set to false makes every one a thread lock again. `stackshot standby-copy` ([standby-copy.md](standby-copy.md)) holds all of them at once while it copies the stores: a new store lock goes into its `LOCKS` list (`stackshot/tools/standby_copy.py`; `tests/standby_copy_scenario.py` fails on one it does not know).
