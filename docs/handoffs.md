# Hand-offs, the done check and front agents

What this page covers: what a front agent may watch, the done check that closes an item when its proof is met, the shared PR-state reader, and when a front agent hears of its item. Back to the [README](../README.md).

**A front agent does not watch handed-off work** (stackshot refuses a sender's wake or check on a handed-off item, and its text stops teaching it; the line in his rulebook: a front agent does not watch handed-off work itself, no wake, poll or background check it schedules). `update` refuses a **front agent** sender's reminder `wake` when, once the call's own `mover`, `needs`, state and hand-off lines are applied, the item is **alive** and moved by another session (its mover; a session named by a `<session>: <action>` line of the call's `next` counts too). The refusal names the rule: the result lands through stackshot when the mover closes the item or hands it back to the front agent (`_tell_owner_close`, `_tell_handback`). Not gated: a `hold=true` park with its wake (a waiting item's wake is the park's own timer, fired by the server), a done `check` (the server-run push the rule itself names; an engineer's choice against the issue's first wording, which said "wake or check"), `ask_by` (the server watches that date), the mover's own wake, a wake the item already carries (re-sending it sets nothing), and any wake by a background agent, the owner or a sender no project page lists (the test is the message tool's front-agent test, `anchors.session_roles()`). `watch_reason=<why no push reaches you>` (at least 15 characters) lets a real exception through: it is stored as `metadata.watch_reason` and shows as a `watch exception` line in the item's History. It belongs to the wake it was given for: it is dropped when a later call changes the wake without a reason, clears it or sets none, when the wake pass fires or drops the wake, when a done check closes or fails the item, and at the close. A wake already stored survives a later hand-off (deliberate: it fires once as a reminder to the keeper). The hand-off gate below does not ask a front agent for a wake or check.

**The done check**. An item whose mover handed its work to another session
used to stay open after the work was done: nothing triggered the mover's check-and-close step. Now an `update` that creates such
a hand-off (a line of its `next` in the form `<session>: <action>`, a list marker such as `- ` or `1. ` before the name at most,
naming a session other than the mover and the writer that a page or the fleet knows and that its `needs` does not already name;
a name anywhere else, inside a page slug, a `#s=<name>` link or a sentence that mentions the session, hands nothing over) must
leave the item with a `wake` (a reminder: the sessions its notices go to (the sessions in its `needs`, else its mover) are told once at the date, and the item stays active in its lane; a wake parks an item only with an explicit `hold=true`; a wake that carries a `wait_basis` names what the item waits for, and the board lists the item as waiting until that wake) or a done check,
`metadata.check`, one of a fixed list the server reads itself every minute, never a command: `pr_merged <owner>/<repo>#<n>`
(the pull request is merged: one GET through the mirror's GitHub client, at most one per PR every `[check] github_minutes`,
shared by the items that name it, backing off up to an hour while GitHub is down), `item_closed <id>` (that item is
completed), `lane <session> <lane>` (the fleet tool's lane record, `[client] lanes_file`, has the pane on that lane: its row,
else the default lane, as the tool reads them; refused while `lanes_file` is unset; `sala_lane`, its former name, is still taken and read) and `unit_active <unit>` (the systemd user unit is loaded and active on the server
box, one `systemctl --user show`). When a check passes the server closes the item itself, outcome `done` and the reason
`done check passed: <the check>`, as its own act: no page owed, no notice to the mover, the sessions in its needs or the
observers, so no session turn is spent; with the mirror on the issue gets the server's comment, and the items that waited on it
(`after`) are released and told as any close releases them. A check the server cannot read (GitHub down or refusing, a unit
systemd does not know, no lane data) never closes: it is logged once per error, shown by `get`, and tried again each pass. A
check alone is a filing edit (no page owed); `check="none"` clears it; a close clears it. A write that leaves an existing
hand-off as it was is not asked again, and an item in that state before this rule is never retro-refused. A write that only
names a session in `needs` is not gated: that session is asked about the item at each of its turn ends and told to close it or
hand it back. The pass keeps its own state in `<state>/checks.json`.

- **The shared PR-state reader** (`stackshot/github/pr_state.py`, `server._pr_merged`; `tests/pr_state_scenario.py`). One GET of a pull request per pace window, shared by the three callers that ask whether it is merged: the done check (`pr_merged`), the step proof and the event wait. The first caller to ask reads and the others take its record, so one PR costs one request however many items wait on it; the read is counted once in the GitHub ledger under the first reader's tag. Each caller still keeps the record in its own file. GitHub down or rate-limited backs off (doubling, at most an hour, or what GitHub asked for); a closed PR that was not merged carries `dead`. Locks are one per PR and are never dropped.

**A front agent mover hears of its item at two moments only** (so a front agent need not set a far wake and wait on a builder): when the item is **back with it alone**, and when it is **closed** by another session. A builder's step is never pushed to it: a session that takes itself out of `needs` while another session stays in it, or marks its work lines done, sends the owner nothing; that step is recorded where the server already records it: one line in the item's History (a comment on the GitHub mirror) and, for a state-changing write, the page debt against the writer (the project page's Current state or a timeline line, `stackshot/router/page_debt.py`). Nothing new is sent in its place.

**No automatic return or fallback goes to a front agent, and an item notice reaches one only while the owner is there**. Two rules; both leave what a session or the owner writes on purpose as written (an explicit mover, a `then`, the `message` tool, a `[for <owner>]` notice, his board answer relayed to the session it is for, a hand-off, a migration or recycle notice, a notice that names the recipient in `needs`).
**(1) Returns and fallbacks.** Every place stackshot hands an item back or picks a fallback mover by itself now asks the same question: is the target a front agent (`anchors.session_roles()`, role `front`: the test the message tool uses)? The places: the hand-off ladder's last step, the return to the sender or origin (`handoff.next_step`, `Env.is_front`); the cold call's pick (`server._handoff_agents` offers only `background:` agents, so the call cannot name a front agent); the mover a stepped answer of his lands on when his `then` names none; the mover an ended wait falls back to (`mod.wait.post_wake_mover`, the answer-watch fallbacks). A front agent there is replaced by the project's builder (`server._auto_mover`, which reads `_handoff_builder`). **A project with no builder** keeps the item with its current mover; in the hand-off ladder that is the recovery request to the fleet's builder (a front origin is no longer a place to return to), and in the two places that have no other holder for the item (his answer, an ended wait) the existing fallback stays, because refusing his answer would lose the item. On a stepped answer that stored no `then`, a project with no builder first looks for the session the item's next open step names (the first open step that opens with a session other than the owner), then the item's stored contact, and only then the project's keeper (`stackshot/waits/builderless.py`, `server._builderless_answer_to`; `tests/builderless_handover_scenario.py`). Only a live front agent of the item's project (a page above the item's page counts) is named that way, so a step line does no more than `mover=` would. In the same project a front agent may also set `mover=` to another front agent of the item's project (the front-mover rule would otherwise refuse it for lack of a builder); a project with no agents map (a one-session page) counts as builderless but lists no front agent, so neither rule finds a session there and the old fallback stands; the reply says so and the target is told by a hand-off notice. The derived default mover of the item model (`_fallback_mover`) is read, not changed. **The hand-back line** (`server._tell_handback`: a builder or another session leaves the item's needs naming its front agent mover alone) is no exception: stackshot does not hand the item to that front agent. The project's builder is told instead, reworded ("is back with <front agent>, a front agent, alone ... told to you, not to <front agent>"), after the usual `handback_hold_seconds` window (a close in it drops the line); when the builder wrote the hand-back itself, or the project lists none, nobody is told: the item's needs and History show it, and the routing log has a `held` line. The write's reply says which of these happened.
**(2) What a front agent hears about an item.** An item notice for a front agent (`server._tell_woken` → `_front_gate`; kinds `progress`, `close`, `stuck`, from the call site or the notice's tag) is delivered only when **the owner is there for that pane**: `<state>/prompts/<session id>` holds epoch seconds within `[presence] minutes` (30). Another repo's hook writes those files and stackshot only reads them; the session id comes from the CLI's registry (`~/.claude/sessions/<pid>.json`, the pane `server._handoff_pane_row` finds); a pane this box does not run, a missing or unreadable file, a stamp from the future or an old one is "not there". **And only when the agent touched the item in its current conversation**: a revision of the item since the registry's `startedAt` for the pane names the session as its writer (a pane whose registry row has no `startedAt` counts as not touched: the gate holds, like a missing presence stamp) (`written_by` or `written_by_id`, the same git revisions History shows; a relaunch, a resume or a recycle moves `startedAt`, so an earlier conversation's touch does not count). Then an ordinary progress notice is filed as an `fyi` line (`stackshot/waits/held.py`, it rides his next turn and starts none), and the close of the item or an item marked stuck is a normal notice. Every other case sends nothing and writes a routing-log line ruled `held` by `stackshot (auto)`, reason `held: front agent, <why> (<kind>)`. A pane whose hook has not fetched held lines (`held.can_fetch`) gets no fyi line either (logged as held): a new turn for a progress notice is not worth it. Notices that ask the mover to act are never gated (the tags `wake`, `watch`, `idle`, `wait`, `comment`, `answer`, `needs`, `stall`, hand-off, migration, recycle): held, the item would sit unmoved. **The board always reaches him; a front-agent turn is only ever extra.** Whenever one of these reaches a front pane, or is held, the same news is written to the board in the same pass: a progress notice leaves one History line (`metadata.front_quiet.log`, `stackshot/waits/quiet.py`; written by the server, no writer, no clock moved, nothing posted to the issue; "<agent> hears of it on his next turn" or "<agent> was not told (why)"; deduplicated, the newest 8 kept, open items only); a close is the item's own close revision in History; a stuck item is the `wait_failed` mark a failed wait writes, written before the notice. The sender hints the kind through `server._tell_kind` (a thread-local read by the gate), so `_tell_woken` keeps its signature; the gate's verdict (sent, filed as an fyi line, or held) is read back through `server._gate_result()`, so a writer's reply says a front agent "was told" only when the gate let the notice through, and otherwise says it was not told and that the board carries it. The owner-change notice's last resort (the router record could not be written) is a progress notice, gated like the rest. A failure of the gate itself sends the notice as before.
- *Back with you alone*: a session other than the mover leaves the item's `needs` naming the mover alone (`decision` still in `needs` is his, not a hand-back; `external` is ignored), when before the write `needs` named someone else beside it. One line, "is back with you alone", with the first line of `next`. **It is held for `[board] handback_hold_seconds` (default 180) before it is sent** (a hand-back followed by a close would wake the keeper twice): a close of the item inside the window (any close, saved through `_save`) drops it, so the keeper hears only the close line; a second hand-back of the same item inside the window replaces the held line and keeps the first due time; when the window ends the line is sent if the item is still open and its `needs` still name the keeper alone (an item that moved on is dropped, one that waits on his decision too). The held lines are the file `<state>/handback-held.json`, so a restart loses none; the fleet tick (every 20 s, every 60 s under the runner) sends what is due. The tick sends first and removes the line after (at least once: a crash between the two sends it again, never zero), and when the held line cannot be written the hand-back is sent at once. `0` sends at once, as before. When it is sent, on a project the router is live for it is recorded for the router and passed by its `hand-back` rule; if the record cannot be written, it is delivered at once with the mark. **For a front agent mover** the item is not handed back by stackshot: the line is reworded ("is back with <mover>, a front agent, alone ... told to you, not to <mover>") and goes to the project's builder instead, through `_tell_or_hold` (kind `changed`: it asks the builder nothing, so where the builder's hook fetches held lines it rides the builder's next turn and wakes it for nothing, else it is pushed as a message). Nobody is told, and the board and the routing log carry it, when the project lists no builder, when the builder wrote the hand-back itself, or when a held record from before this release has no writer id (`wid`): then the builder may have written it, so it is not told about its own write.
- *Closed*: one marked message (`[for <owner>]` first line, delivered with the server's own owner delivery, router live or not) when a session other than the mover closes the item (any close, with his words or not; the For you [row above](for-you-and-closed.md) stays as it is). The server's own close on a done check (a merged pull request) tells a front agent mover the same way, "closed by stackshot's done check".
Neither is sent when the mover wrote it, when the mover is not a session, when `[board] tell_owner` is off, or when the item is muted on the list; a close is also not sent when the mover already heard the write. A mover that is not a front agent hears a close and a `needs` change through its older notices.
