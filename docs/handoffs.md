# Hand-offs, the done check and front agents

What this page covers: what a front agent may watch, the done check that closes an item when its proof is met, the shared PR-state reader, and when a front agent hears of its item. Back to the [README](../README.md).

**A front agent does not watch handed-off work** (stackshot refuses a sender's wake or check on a handed-off item, and its text stops teaching it; the line in his rulebook: a front agent does not watch handed-off work itself, no wake, poll or background check it schedules). `update` refuses a **front agent** sender's own `until` date (with no park beside it) when, once the call's own `mover`, `needs`, state and hand-off lines are applied, the item is **alive** and moved by another session (its mover; a session named by a `<session>: <action>` line of the call's `next` counts too). The refusal names the rule: the result lands through stackshot when the mover closes the item or hands it back to the front agent (`tell_owner_close`, `tell_handback`). Not gated: a park with its date (`until` with `wait_kind="time"` and a `wait_basis`: a waiting item's date is the park's own timer, fired by the server), a done `check` (the server-run push the rule itself names; an engineer's choice against the issue's first wording, which said "wake or check"), a relay or event wait's `until` (the server watches that date), the mover's own date, a wake the item already carries (re-sending it sets nothing), and any wake by a background agent, the owner or a sender no project page lists (the test is the message tool's front-agent test, `anchors.session_roles()`). `watch_reason=<why no push reaches you>` (at least 15 characters) lets a real exception through: it is stored as `metadata.watch_reason` and shows as a `watch exception` line in the item's History. It belongs to the wake it was given for: it is dropped when a later call changes the wake without a reason, clears it or sets none, when the wake pass fires or drops the wake, when a done check closes or fails the item, and at the close. A wake already stored survives a later hand-off (deliberate: it fires once, as a notice to the keeper). The hand-off gate below does not ask a front agent for a wake or check.

**The done check**. An item whose mover handed its work to another session
used to stay open after the work was done: nothing triggered the mover's check-and-close step. Now an `update` that creates such
a hand-off (a line of its `next` in the form `<session>: <action>`, a list marker such as `- ` or `1. ` before the name at most,
naming a session other than the mover and the writer that a page or the fleet knows and that its `needs` does not already name;
a name anywhere else, inside a page slug, a `#s=<name>` link or a sentence that mentions the session, hands nothing over) must
leave the item with a date (`until`: in a write that hands the item on the date is the hand-off's backstop and no wait, so the item stays active in the new mover's lane and the sessions its notices go to (the sessions in its `needs`, else its mover) are told once at the date; the hand-off is read from the mover the write leaves, so a `mover` argument, a session named in `needs` and a hand-off line in `next` all count, and a date beside a `wait_kind`, a `wait_basis` or an `after` is the wait it names, not a backstop. The same date in a write that hands nothing on is a wait until it, and the board lists the item as waiting. A hand-off write on an item that a bare `until` had parked ends that wait: the date stays as the backstop, the item is active in the new mover's lane, and the reply says so) or a done check,
`metadata.check`, one of a fixed list the server reads itself every minute, never a command: `pr_merged <owner>/<repo>#<n>`
(the pull request is merged: one GET through the mirror's GitHub client, at most one per PR every `[check] github_minutes`,
shared by the items that name it, backing off up to an hour while GitHub is down), `item_closed <id>` (that item is
completed), `lane <session> <lane>` (the fleet tool's lane record, `[client] lanes_file`, has the pane on that lane: its row,
else the default lane, as the tool reads them; refused while `lanes_file` is unset; `sala_lane`, its former name, is still taken and read) and `unit_active <unit>` (the systemd user unit is loaded and active on the server
box, one `systemctl --user show`). When a check passes the server closes the item itself, outcome `done` and the reason
`done check passed: <the check>`, as its own act: no page owed, no notice to the mover, the sessions in its needs or the
observers, so no session turn is spent; with the mirror on the issue gets the server's comment, and the items that waited on it
(`after`) are released and told as any close releases them. A check the server cannot read (GitHub down or refusing, a unit
systemd does not know, no lane data) never closes: it is logged once per error, shown by `get`, and tried again each pass. A
check alone is a filing edit (no page owed); `check="none"` clears it; a close clears it. A write that leaves an existing
hand-off as it was is not asked again, and an item in that state before this rule is never retro-refused. A write that only
names a session in `needs` is not gated: that session is asked about the item at each of its turn ends and told to close it or
hand it back. The pass keeps its own state in `<state>/checks.json`.

- **The shared PR-state reader** (`stackshot/github/pr_state.py`, `checks.pr_merged` (`stackshot/service/checks.py`); `tests/pr_state_scenario.py`). One GET of a pull request per pace window, shared by the three callers that ask whether it is merged: the done check (`pr_merged`), the step proof and the event wait. The first caller to ask reads and the others take its record, so one PR costs one request however many items wait on it; the read is counted once in the GitHub ledger under the first reader's tag. Each caller still keeps the record in its own file. GitHub down or rate-limited backs off (doubling, at most an hour, or what GitHub asked for); a closed PR that was not merged carries `dead`. Locks are one per PR and are never dropped.

**A front agent mover hears of its item at two moments only** (so a front agent need not set a far wake and wait on a builder): when the item is **back with it alone**, and when it is **closed** by another session. A builder's step is never pushed to it: a session that takes itself out of `needs` while another session stays in it, or finishes its own step by a status done, sends the owner nothing; that step is recorded where the server already records it: one line in the item's History (a comment on the GitHub mirror) and, for a state-changing write, the page debt against the writer (the project page's Current state or a timeline line, `stackshot/router/page_debt.py`). Nothing new is sent in its place.

**No automatic return or fallback goes to a front agent, and an item notice reaches one only while the owner is there**. Two rules; both leave what a session or the owner writes on purpose as written (an explicit mover, a `then`, the `message` tool (an fyi to a front agent excepted: it rides the agent's next turn and starts none, see [router](router.md)), a `[for <owner>]` notice (the router's pass to a front agent is marked only for a real need of his, and a message to one starts a turn only when it names an open item of his, and any other pass goes to the project's background agent or is held for the agent's next turn, see [router](router.md)), his board answer relayed to the session it is for, a hand-off, a migration or recycle notice, a notice that names the recipient in `needs`).
**(1) Returns and fallbacks.** Every place stackshot hands an item back or picks a fallback mover by itself now asks the same question: is the target a front agent (`anchors.session_roles()`, role `front`: the test the message tool uses)? The places: the hand-off ladder's last step, the return to the sender or origin (`handoff.next_step`, `Env.is_front`); the cold call's pick (`handoff_agents` in `stackshot/service/handoff_cold.py` offers only `background:` agents, so the call cannot name a front agent); the mover a stepped answer of his lands on when his `then` names none; the mover an ended wait falls back to (`mod.wait.post_wake_mover`, the answer-watch fallbacks). A front agent there is replaced by the project's builder (`telling.auto_mover`, which reads `handoff_builder`). **A project with no builder** keeps the item with its current mover; in the hand-off ladder that is the recovery request, to the project's -main agent when the project is front-only (`anchors.front_only`, `_recovery_target` in `service/pane_recovery.py`) and to the fleet's builder otherwise (a front origin is no longer a place to return to), and in the two places that have no other holder for the item (his answer, an ended wait) the existing fallback stays, because refusing his answer would lose the item. On a stepped answer that stored no `then`, a project with no builder first looks for the session the item's next open step names (the first open step that opens with a session other than the owner), then the item's stored contact, and only then the project's keeper (`stackshot/waits/builderless.py`, `holders._builderless_answer_to`; `tests/builderless_handover_scenario.py`). Only a live front agent of the item's project (a page above the item's page counts) is named that way, so a step line does no more than `mover=` would. In such a front-only project any live session some project page lists (a front or a background agent, of this project or of another) may also set `mover=` to a live front agent of the item's project, whether or not it is on the sender's own page (the front-mover rule would otherwise refuse it for lack of a builder; `handover_allowed` in `stackshot/waits/builderless.py`); a project that has a background agent still substitutes its builder, and a retired target, a front agent of another project, and a sender no page lists are still refused; `then` and `post_wake_mover` are not part of it, since the owner's answer or the wake makes that move and no write of a session tells the target; a project with no agents map (a one-session page) counts as builderless but lists no front agent, so neither rule finds a session there and the old fallback stands; the reply says so and the target is told by a hand-off notice. A finished step does the same for such a peer: when the next open step opens with a live front agent of the item's own project in a front-only project, the step hand-over (`stackshot/waits/handover.py`, `handover.peer_opener`) moves the item to it and tells it with the hand-off notice (tag `handoff`, which the front gate exempts), so the write check accepts that step behind an open step. Any session may write it and the item moves when the step before it is done, the same property a background agent's step has; it is not the same as `mover=`, which hands the item over at once. Such a step hand-over is made by the server: it is not clocked as a peer hand-off and gets its one notice with no clock; only a hand-off by a listed session's own move (`mover=`) is clocked. **A hand-off to a front agent of a front-only project is then watched like a builder's** (`handoff_peer` in `stackshot/service/handoff.py`, the hand-off `front_handed_by_peer` reads, whichever listed session made it; a project that lists a background agent substitutes its builder, so no front agent is handed an item there and every front agent stays exempt from the take clock as before): the item is the new mover's, so the clock (`[model] handoff_minutes`) starts when the notice is delivered, one reminder goes to the new mover alone if no work has started by then (a step marked done, a step status in progress, a work line: the same proof as for a builder), and when it is still not taken the ladder's rungs apply, without the cold call (its `close` and `ask_owner` answers would take the item from a mover nobody asked), with the last one, the recovery request, going to the project's -main agent while the peer's pane is not busy (the reminder and the ask are `handoff` pushes, which the front-agent gate lets through, and no other channel to a front agent is added). The session that handed the item over is told nothing at any step: not when the clock runs out, not when the item is closed or handed back, and it is not asked when the item sits (the rule: once a session hands an item to a front agent of a front-only project, the item is that front agent's, and it is never returned to its hander). A turn that ends on the new mover's pane does not hurry the reminder (a front agent's turns end with every conversation it has), only the take minutes do. Not covered, and still unclocked as before: a hand-off to a front agent of another project, a hand-off the server made, and a hand-off to the project's -main agent itself (nothing above it could be asked, and the request would fall to the fleet's builder). The derived default mover of the item model (`fallback_mover`) is read, not changed. **The hand-back line** (`telling.tell_handback`: a builder or another session leaves the item's needs naming its front agent mover alone) is no exception: stackshot does not hand the item to that front agent. The project's builder is told instead, reworded ("is back with <front agent>, a front agent, alone ... told to you, not to <front agent>"), after the usual `handback_hold_seconds` window (a close in it drops the line); when the builder wrote the hand-back itself, or the project lists none, nobody is told: the item's needs and History show it, and the routing log has an `archived` line (nothing was filed for anyone's next turn). The write's reply says which of these happened.
**A front agent hands an item to a sibling front agent on the owner's words.** A live front agent of the item's project (a page above the item's page counts) may set `mover`, `then`, `post_wake_mover` or `agent` to another live front agent of that project when the same write carries the owner's words in `said`, whether or not the project has a builder (`gates.fix_front_mover`, `gates.gate_needs_session`, `gates.sibling_quote`, `builderless.front_siblings`; `tests/front_mover_scenario.py`). The words are checked as the wake cap checks them, by the same reading (`owner_words._owner_quote_on`: an `Acked-by` entry checked against a transcript, from a message no older than `[waiting] cap_days`); a board answer is not part of the write and counts for nothing here. The value then stays as sent, with a note saying so, and nothing is substituted or marked. The sibling is told: a `mover` or `agent` hand-off records the quoted words (`metadata.handoff.words`, set by `handoff.sibling_words` from the checked entries that very save added) and `telling.handoff_notify` sends the hand-off notice (tag `handoff`, which the front gate exempts, as for a front-only project's peer), which says who handed the item over and quotes the owner; the notice is not clocked, as for any front agent. A `then` or `post_wake_mover` target is told by the owner's answer or the wake, as before. With no words, or words the check refuses, the substitution (or, for `agent=`, the refusal) stands and its text ends with how to send them (`said=[Acked-by …]` quoting his words with the time); a background agent, another project's session, a target that is not a front agent of the item's project, and a session no page lists are judged as before, and the second identical send of a substituted value is still kept as sent, without a notice.

**A front agent that holds the item's open step keeps the item after his answer.** When the first open named step of the item (a step with a `<name>:` opener; his own lines are passed over for a Done, which still has them open) is the front agent's own (`telling.own_step`, with `past_his`), the builder is not put in its place: the owner's pick or Done leaves the front agent as the mover and the first session in `needs` (`answer_handover._builder_for_front` returns nothing for it, at the three places that ask: the decision's hand-over, the answer's delivery and the Done), and a pick's line is pushed to it as the holder, marked `[for <owner>]`, which starts its turn, instead of being held for its next turn. The bare hand-over line of a Done with no note is told with `named=True` (`answer._answer_deliver`), so when the next open named step is the front agent's own it is given a turn, as a wake is; when the next step is the builder's, or the item has none, the builder takes the item as before and a front agent's line stays a progress notice. The same holds when `needs` names no session at all (the decision alone, no stored `then`): the front agent that holds the first open named step, a front agent of a project with a live builder (`answer_handover._front_step_holder`), is made the mover by the pick or the Done instead of the model's default, the builder; and the write that raises the item stores no `then` that would undo it (`mover_steps._owner_then`: the builder is not stored for a line naming it in `next`, or for a front agent first in `needs`, when a front agent holds the first open named step). A step of the builder's, a front agent's step that comes after a builder's, and an item with no open named step are as above. The holder is a live front agent of the item's own project, read in any letter case (`telling.front_name`, `answer_handover._then_live`): a retired or offline one, or another project's front agent, leaves what the answer did before (the builder, or the model's default). **A hand-back is kept as sent.** A session's `mover`, `then` or `post_wake_mover` = a front agent is not swapped to the builder (`gates.handed_back`, in `gates.fix_front_mover`; update only) when all of these hold: the front agent holds the item's first open named step past the owner's lines as the item stands before the write (`telling.step_holder_at`, case-insensitive; a step line the same call adds never counts, and the front-agent step gate refuses such a line on an item another session moves) and the same call leaves that step open (it does not tick, drop or reword it, clear next or close the item: the notice reads the item after the write, so a hand-back that would reach nobody is the swap). The call's marks are read the way the update tool reads them (`gates.step_marks`: `steps.resolve` and `steps.resolve_reword` against the stored checklist), in every form it accepts: `done` and `dropped` as a position, the digits of one as text, a comma list, a JSON string or the exact text of an open step, `reword` by a position or a step's text, and a `work` status done, which finishes the sender's first open step or the one its `agent` names; a ref the tool cannot read is taken as marking the holder's step, so the call is the swap (a ref no step reads is refused by the write itself); the holder is a front agent of the item's own project (`telling.front_name`); the sender is the project's builder, or the item's mover when that mover is no front agent (a front agent that moves the item hands it to a sibling front agent only on the owner's words, as before); the front agent is live (a live or cloud session); and the item is a stored one (a create has none, so it is swapped as before). A `mover` hand-back is then told to the front agent as a turn (`telling.handoff_notify`, `own_move_kind` with `named` and `past_his`), saying which session handed it back, and the reply says so; the notice is for the write whose gate kept the value (`HO_STATE.handback`, set by `gates.fix_front_mover` and cleared by the update tool), so a value another session sends again after the swap (the mover's no) tells nobody, as on main; only a `mover` sets it (a `then` or `post_wake_mover` is told by the answer or the wake), and the update tool clears it at its start and in a `finally` around the whole call, so a write the later checks refuse leaves none behind; a `then` or `post_wake_mover` is told by the owner's answer or the wake. Any other case (a third session, the front agent's step after another's, no step, a front agent that is not live) is the swap with its stall line, as before. Known limits: after a hand-back the raise notice still says its mover (the builder) has been told when no `then` is stored, as the same text does on main; a loop between the builder and the front agent (builder hands it to the front agent, the front agent hands it back, and so on) needs an explicit call each time while the front agent's step stays open, nothing repeats it by itself; with two front agents in `needs` only the first is read; `_builder_for_front` (the first session in `needs`) checks no liveness of its own; a step line in another letter case holds the step, and the item goes to the front agent under the name the roles list it by, but a bare Done's line to it is read against its id by `own_step` and so rides as a progress notice; and an item whose stored `then` is the builder, with a front agent in `needs` that holds the first open named step, now has the answer pushed to that front agent as a plain push, without the `[for <owner>]` mark that starts a turn (the builder takes the item as before). `tests/answer_reach_scenario.py` sections 12 to 14, `tests/front_mover_scenario.py`.

**A message between sibling front agents on the owner's words.** A message a live front agent sends by name to another live front agent of its project, marked for the owner (`[for <owner>]` on its first line) when he is not talking with the addressee and has not asked it to tell him about the subject, is today written onto the item it names, where the addressee reads it, and starts no turn (the message tool, `messaging._gate_front`; held for the addressee's next turn when no item can take it) or passed to the item's builder or archived (the router, `router_live._front_turn_gate`). When the message carries a line `Acked-by: "<his sentences, verbatim>" (<time>, session <the session that heard him>)` and the quote passes the same words check as `said` on a write (`sibling_words.held_words`, which reads it through `gates.sibling_quote`: the wake cap's own reader), it is held for the addressee's next turn instead, a held line that starts no turn (the message tool at the one call in `_gate_front`, the router at the one in `_front_route`, hook `front_words`; `tests/front_hold_scenario.py`, section 8). Without such a line, with words the check refuses or that are older than the cap, from a background agent or another project's session, or to a background agent, nothing changes; and when he is talking with the addressee or has asked it to tell him about the subject, the message starts its turn as before (both the message tool and the router hold only where that turn is not warranted: `_front_warranted` in `router_live`, `_turn_warranted` in `messaging`, the same test). The two rules compose in this order: the item test comes first. A marked message must name an open item of his (`front_turn.his_items`) or one he asked the addressee to tell him about; one that names none is held for the addressee's next turn by that rule whoever sent it and whatever it quotes (a sibling's quote of his words included), the sender's reply saying to put his step on an item and name it by its plain id (when the sibling's quoted words are valid, to name the item handed over, an open item of his, by its plain id), and the router, which marks only a message that names such an item, holds it as a front agent's word to a peer when the sender is a front agent (a background agent's message that names none goes to the builder). Only a message that names an item of his reaches the warranted test, and the sibling's quoted words hold it there when no turn is warranted.
**What a front agent sends to a front agent can go to the background agent** (both off by default; `tests/front_reroute_scenario.py`). With `[front] to_background_senders` listing the sender, its message to a front agent never waits on that agent: it goes to the project's background agent, and is held for the front agent's next turn only when there is none or it cannot take it; its hand-off that names no open board item is told so in one line. With `[front] idle_peers_to_background` on, a front agent's unmarked message to a peer front agent the owner is not talking with goes to the peer's project's background agent instead of being held. Details: [Configuration: integrations](configuration-integrations.md).
**A result comes back to the front agent that handed the work over** (off by default: `[front] result_turn_agents`, see [Configuration: integrations](configuration-integrations.md); `messaging.handed_to`, `messaging.result_turn`, `messaging.router_result`; `tests/front_result_turn_scenario.py`). A front agent hands work to a session by writing to it (the `message` tool) or by making an item that session moves. For an agent the instance lists, the session's message back starts the agent's turn, marked or not, whether or not the owner is there, and is not held as a status report or written onto an item: the result is what the agent was waiting for. A session counts as handed work when (a) the agent wrote to it within `[front] result_turn_hours` (24 by default; any message that reached it, a question or not: the log row is the signal, as for an answer to a question) or (b) the message names an open item that the session moves now and that the agent itself handed it: the item's hand-off record (`metadata.handoff`, written by the real write that moved the item) names the agent as the sender and the session as the new mover, with no time limit until the item closes or is handed on (the record keeps the latest hand-off only). That the agent made the item or is its contact proves nothing: any session may name a front agent of the project as an item's contact or take an item over with update(mover=...), so neither counts as a hand-over by the agent. The `sender` of a message is a label the caller gives, not an authenticated identity: that limit is the relay's own and holds here too. It does not apply to an `fyi=true` message, a script, the owner, the audit, a peer front agent or the agent itself, and a message to the page key takes the same test when the router passes it to the listed agent (`router_live._front_result_turn`, the `front_result` hook). The line is delivered with the kind `exempt`, so the pane's digest of lines queued while it was busy never files it as an fyi. **The loop risk:** the agent's reply to the session is itself a hand-over, so the session's next result starts the agent again, whose reply starts the session. Three things stop it: one session starts at most `[front] result_turn_cap_per_hour` (6) turns in one agent in an hour (the message past the cap is handled as without the key, which holds it for the agent's next turn, where it rides along with that turn, and the server's log says so; the count is read from the last 800 KB of the message log, and when that does not reach back an hour, as after a flood of rows, the count is unknown and counts as past the cap, never as zero; the check and the log row are not one step, so two messages that arrive at the same moment can each pass it and the cap can be exceeded by a few; a hand-over row that has fallen out of those 800 KB is not found, so the message is not a turn), `fyi=true` on any message that needs no reply, and the case being listed per agent, never global. Not changed: the notice of an item's close or a stuck item (`telling.front_verdict`), the front agent mover's pickup, `tell_him`, and every rule above for an agent that is not listed, so a close still reaches a front agent only while the owner is there.

**(2) What a front agent hears about an item.** An item notice for a front agent (`telling.tell_woken` → `front_gate`; kinds `progress`, `close`, `stuck`, from the call site or the notice's tag) is delivered only when **the owner is there for that pane**: `<state>/prompts/<session id>` holds epoch seconds within `[presence] minutes` (30). Another repo's hook writes those files and stackshot only reads them; the session id comes from the CLI's registry (`~/.claude/sessions/<pid>.json`, the pane `handoff_pane_row` in `stackshot/service/handoff.py` finds); a pane this box does not run, a missing or unreadable file, a stamp from the future or an old one is "not there". **And only when the agent touched the item in its current conversation**: a revision of the item since the registry's `startedAt` for the pane names the session as its writer (a pane whose registry row has no `startedAt` counts as not touched: the gate holds, like a missing presence stamp) (`written_by` or `written_by_id`, the same git revisions History shows; a relaunch, a resume or a recycle moves `startedAt`, so an earlier conversation's touch does not count). Then an ordinary progress notice is filed as an `fyi` line (`stackshot/waits/held.py`, it rides his next turn and starts none), and the close of the item or an item marked stuck is a normal notice. Every other case sends nothing and writes a routing-log line by `stackshot (auto)`: ruled `held` (with `next_turn`, the kind) when the line was filed for the agent's next turn, `archived` when nothing was filed, reason `archived: front agent, <why> (<kind>)`. A pane whose hook has not fetched held lines (`held.can_fetch`) gets no fyi line either (logged as archived): a new turn for a progress notice is not worth it. Notices that ask the mover to act are not gated (the tags `wake`, `watch`, `idle`, `wait`, `comment`, `answer`, `needs`, `stall`, hand-off, migration, recycle): held, the item would sit unmoved. **Four of them are gated when nothing in them is for the owner:** a wake (`wakes.wake_tell`), a watcher's "is yours now" (`watching.watch_tell`), the line of his board answer that hands an item over when it carries none of his words (a Done with no note: the line that ends "It's yours now", `answer._answer_deliver`; a line with his pick or his note keeps its kind and starts a turn) and the ladder's or the recovery's request to a -main agent (`ladder.ladder_main_tell`, `pane_recovery._recovery_tell`) are told to a front agent as `progress` (`telling.tell_own_move`, the tag stays and names the sender) when no item they name waits on his decision (`needs` holds `decision`) or is his step (the board's reading of Your move, `foryou_events._owner_moves`; `telling.carries_for_owner`). They ride its next turn and start none, as any progress notice, and each item's board line keeps the news; a notice that names an item that holds something for him, one that cannot be read, a closed item and a background agent's notice keep their tag, and so does every notice with `[router] hold_notices = false`. A wake or request that names several items is a progress notice only when none of them holds something for him. **A wake that hands an item to a front agent whose own named step is the work starts its turn:** when the item's first open named step (a step with a `<name>:` opener; one without is skipped), or its ask, is addressed to that agent (`telling.own_step`), the wake and the watcher's "is yours now" are told as ever, not as `progress` (`tell_own_move(named=True)`, set by `wakes.wake_tell` and `watching.watch_tell`), whether or not the owner is at the pane; otherwise such an item, left with the agent after a wait ended, sat unread until its next turn. A step of another session, or a step with no name, leaves the notice progress, and the answer line's bare hand-over of a Done is given a turn on the same test (the next open named step is the agent's own, `answer._answer_deliver`); the ladder's and the recovery's requests keep the rule above. The notice carries no `[for <owner>]` mark: the item is not his. The "N queued earlier" digest of a pane that was away never files one of these either (see [puller and inbox](puller-and-inbox.md)): a digest with a line of one of these kinds is handed out as a turn, with or without his mark. The one stall-side exception is the idle hand-over's and the balancer's summaries to -main (tag `stall_summary`: an item left in place, one handed from one builder to another, a balancer cap): their text says nothing is asked and no reply is owed, so they are progress notices, filed as an `fyi` line or held like any other, and each item's board line carries that item's own line (`telling.tell_news`), never the whole summary; the busy-stretch notice and the quiet-mover notice keep the `stall` tag, since they ask the receiver to look or to write (the quiet-mover notice to a -main agent is told as a progress notice when the item holds nothing for the owner, above). Two more notices that ask nothing take the same route. A machine's check-in (`event_waits.machine_anchor_poll`, tag `watch`) for an item that is waiting (on a wake, on another item, on an outside party or on an event: `item_mover_model` reads it as not alive), has no step to take yet: for a front agent it goes out as a `progress` notice, one message for each item (so an item's board line carries only its own line, and the line is short enough to keep its link inside a held line), with its own wording (`machine_anchor.news_notice`: "Nothing is asked of you now"), apart from the message for the items that are their mover's to do now, which keeps the wording "the step that needs <machine> can go ahead" and stays a turn; a reading of the item that fails is unsure and is told as asking. A background agent's check-in is unchanged. With `[router] hold_notices = false` the queue wake below is delivered as before. A wake that only leaves a front agent's item after an open item (its place in the queue, `wakes._front_queue_row`) is filed as an `fyi` line of the held kind `queue`, as a background agent's is held (`hold_notice`); a wake that puts the item back in its lane, and a reminder, still ask and, where the item holds something for the owner, are delivered; where it holds nothing for him they are progress notices (above). Both leave the board line described below. What a notice asks is decided at its sender, from its text: the audit's findings, the page-agent and registry lines (fix the line or retire the name), the busy-stretch notice and a machine's check-in for an item that is its mover's to do now ask and stay as they are; "is yours now", a wake that ended a wait (except where the agent's own named step is the work, above), the answer line that hands an item over when it carries none of his words (a Done with no note) and the ladder's and the recovery's request to a -main agent ask only when the item holds something for the owner (above). A peer's message to a front agent that says FYI in its words but was sent without `fyi=true` is delivered (the sender's flag holds a notice, never its text, `tests/held_scenario.py` 6k8 and 6k9).
**The board always reaches him; a front-agent turn is only ever extra.** Whenever one of these reaches a front pane, or is held, the same news is written to the board in the same pass: a progress notice leaves one History line (`metadata.front_quiet.log`, `stackshot/waits/quiet.py`; written by the server, no writer, no clock moved, nothing posted to the issue; "<agent> hears of it on his next turn" or "<agent> was not told (why)"; deduplicated, the newest 8 kept, open items only); a close is the item's own close revision in History; a stuck item is the `wait_failed` mark a failed wait writes, written before the notice. The sender hints the kind through `telling.tell_kind` (a thread-local read by the gate), so `tell_woken` keeps its signature; the gate's verdict (sent, filed as an fyi line, or held) is read back through `telling.gate_result()`, so a writer's reply says a front agent "was told" only when the gate let the notice through, and otherwise says it was not told and that the board carries it. The owner-change notice's last resort (the router record could not be written) is a progress notice, gated like the rest. A failure of the gate itself sends the notice as before.
- *Back with you alone*: a session other than the mover leaves the item's `needs` naming the mover alone (`decision` still in `needs` is his, not a hand-back; `external` is ignored), when before the write `needs` named someone else beside it. One line, "is back with you alone", with the first line of `next`. **It is held for `[board] handback_hold_seconds` (default 180) before it is sent** (a hand-back followed by a close would wake the keeper twice): a close of the item inside the window (any close, saved through `writes.save`) drops it, so the keeper hears only the close line; a second hand-back of the same item inside the window replaces the held line and keeps the first due time; when the window ends the line is sent if the item is still open and its `needs` still name the keeper alone (an item that moved on is dropped, one that waits on his decision too). The held lines are the file `<state>/handback-held.json`, so a restart loses none; the fleet tick (every 20 s, every 60 s under the runner) sends what is due. The tick sends first and removes the line after (at least once: a crash between the two sends it again, never zero), and when the held line cannot be written the hand-back is sent at once. `0` sends at once, as before. When it is sent, on a project the router is live for it is recorded for the router and passed by its `hand-back` rule; if the record cannot be written, it is delivered at once with the mark. **For a front agent mover** the item is not handed back by stackshot: the line is reworded ("is back with <mover>, a front agent, alone ... told to you, not to <mover>") and goes to the project's builder instead, through `tell_or_hold` (kind `changed`: it asks the builder nothing, so where the builder's hook fetches held lines it rides the builder's next turn and wakes it for nothing, else it is pushed as a message). Nobody is told, and the board and the routing log carry it, when the project lists a background agent but no builder, when the builder wrote the hand-back itself, or when a held record from before this release has no writer id (`wid`): then the builder may have written it, so it is not told about its own write. A front-only project (no `background:` agent on its page) has no builder to tell instead, so its front agent mover is told itself, marked (this replaces "nobody is told ... the project lists none" in (1) above for such a project; the line is recorded for the router, whose hand-back rule passes it marked `[for <owner>]`, or pushed at once with the mark, and as a notice that asks the mover to act the presence gate of rule (2) does not hold it; `telling.tell_handback`, `telling.handback_send`; `tests/front_quiet_scenario.py`, `tests/router_live_scenario.py`).
- *Closed*: one message with no `[for <owner>]` mark (the owner has nothing to do on a close; it is delivered with the server's own owner delivery, router live or not, and the front gate reads its kind, not its first line) when a session other than the mover closes the item (any close, with his words or not; the For you [row above](for-you-and-closed.md) stays as it is). The server's own close on a done check (a merged pull request) tells a front agent mover the same way, "closed by stackshot's done check".
Neither is sent when the mover wrote it, when the mover is not a session, when `[board] tell_owner` is off, or when the item is muted on the list; a close is also not sent when the mover already heard the write. A mover that is not a front agent hears a close and a `needs` change through its older notices.
