# anchor-hub, the router and the page-debt call

What this page covers: the receivers that watch external things, the router that rules every notice, the page-debt call, and how a notice is held or answered. Back to the [README](../README.md).

**anchor-hub and its receivers.** `anchor-hub.py` (a user unit) materialises each project's anchors into the sessions
bound to them (the project's keeper, plus the movers of its open items in scope), debounces bursts into one notice and
a follow-up, and delivers through `push.py`. Each receiver is a module in `anchorhub/` with a `run(hub)` function:
`slack.py` (Socket Mode, a user token), `gworkspace.py` (Drive and Gmail, push channels with polling behind them),
`notion.py` (webhooks where the integration can see the page, polling where it cannot) and `github.py` (through the
`gh` CLI: issues, pull requests, CI, releases, notifications). A receiver with no credentials stays off. `routing.py`
logs every notice delivered for a project and its ruling (the router's).

**The router** (`router.py`, the judging; `router_live.py` below acts on it). It judges every notice held for any project page: first by a rule in code (a notice already ruled by `stackshot (auto)`; a notice about a page from a job named in `[router] page_senders`, held for the page pass; a wake notice for the mover of the item it is about, dropped; an anchor notice on the WATCH anchor `example-upstream/tool#123`, passed to `other-main` for the owner; an anchor notice on a GitHub pull request whose head branch starts with a background agent's name and a slash (`my-engineer/topic`; anchor-hub reads the head from the PR and the routing record keeps it as `head`, with the author as `author`) and that is not itself for the owner, passed to that builder (rule `anchor-builder`: a CI or PR notice on a builder's pull request is the builder's to act on, not a turn of the item's front keeper; an identical repeat within an hour is dropped); an anchor notice that reports a CI or check-run result (anchor-hub's event type `ci_failed`, `ci_passed` or `ci_activity`, which the routing record keeps as `etype`; a record without one is read by its sender `CI`) on any pull request, upstream ones included, and is not itself for the owner, passed to the project's builder (a sub-page's: its hub's) (rule `anchor-ci`: a PR's CI run only goes to the engineer and never produces a front turn; it follows `anchor-builder`, so a builder's own branch still goes by that rule, and it carries the item id when the anchor is scoped to exactly one open item; it applies also when the item waits on the owner's decision or he moves it, since a CI result is never his; an identical CI notice is dropped as a repeat only when the latest earlier CI notice on the anchor is the same within the hour (a failure, a pass and the same failure again are three notices); a project with no builder routes the notice as before); an anchor notice from an anchor that carries a `#mention=<text>` filter (rule `anchor-work`), passed to the agent the page's lead names for the work (the one agent of the project's agents map, front or background, other than its -main agent, that the page's lead paragraph, the text before its first `## ` heading, names; `pages.py` records those names in the registry as `lead_agents`, so no page is read per notice), without the thin call's judgment, also when the notice names the owner, an identical repeat within an hour dropped; it runs ahead of the `quiet` rule, and fires once the page registry is rebuilt with `lead_agents` (publish.py's pass; before that the notice is ruled as before); it is held as before when it is only an image, and goes on to the rules below when the anchor is also listed without a filter, is scoped to items (anchor-item), when the lead names no agent or several, or when the work agent sent it; an anchor notice on an anchor scoped to one open item, passed to that item's mover (rule `anchor-item`), except, since an earlier change (a front mover is woken only for what may need him), build-side news on a GitHub anchor when the mover is a front agent, by a whitelist of the event's type (the routing record's `etype`: every type of the notice is `comment`, `review`, `review_comment`, `pr_*` or `issue_*`, or the anchor is a repository's `@releases`; a notice with no type on another anchor, which is what the `@notifications` reasons review requested, mentioned you, assigned to you, a security alert, an invitation and on your thread are, and an unclassified or mixed burst, stays with the keeper): it goes to the item's mover when that is a background agent, else to a background agent its needs or first next line name, else to the project's builder, and the item id rides along; a front agent mover keeps the notice when the owner wrote it (his login as the sender, any of a burst's senders), when its text names him (`[for <owner>]`, `needs: decision`, a decision word, the owner or one of his aliases, or `@` his login), when the item waits on his decision or he is its mover (the model's derived mover), in a project with no builder, and for an anchor that is not GitHub's (an identical repeat within an hour is dropped for such a pass; anchor-hub's follow-up for a burst of events keeps the burst's event types joined with `+`, its senders joined with `, ` and, for any earlier text that names the owner, that text first in the gist and `other` added to the types, so a comment folded behind a CI result is not a CI notice); a message naming one open item, passed to whoever does the item's work: a background agent the item's needs name, else its mover when that is a background agent, else the project's builder (the background agent whose mandate says build, maintain, merge or engineer), else, when the message itself is for the owner (`[for <owner>]` or `needs: decision`), the front agent mover for the owner, else held for the digest when it only names the owner or a decision, else merged because the item carries it, and merged when the target is the sender itself (a project with no background agent passes to the mover as before); an exact repeat of an anchor notice, dropped; a message of the same sender whose text, with hashes, quoted commit subjects, digits, weekdays and months masked (at least 80 characters), equals an earlier message already ruled by the router within `max_age_hours`, dropped (a sync-check script); on a project page whose config marks Drive anchors as quiet (`[[router.quiet]]`, e.g. `projects/example-site`) a non-urgent Drive anchor notice, held for one digest after the quiet hour (also when it only names the owner or a decision; only `[for <owner>]` or `needs: decision` goes on to the call); a notice whose text is only a file marker such as `[files: image.png]`, held with the reason "image not read", never passed; a green `[release]` message from the project's own maintainer, a sender named `*-maintainer` that the page lists as an agent, merged as "log only: the maintainer's own release"), the rest of a project's unjudged notices together in one fresh `claude -p` call (Sonnet, no tools, a fixed rubric, the project's agents, its open items (at most ten, most recently changed first, a count of the rest: id, mover, the background agent that does the work when it is not the mover, the party it waits on, the title cut to 80 characters; a mover or worker that is no agent of the project's own list is not named, since the call may name no other; the rubric sends a notice that asks the item's agent for something to that agent, lets a mandate decide only a notice about no listed item, and leaves a notice that only reports activity on an item to the rules above) and its page's Current state, started from a login shell with the API variables unset, in the CLI's safe mode so no user hook runs) that returns a JSON ruling per notice (`id`, `ruling`, `target`, `reason`, `for_owner`, and an optional `note`: one line of at most 300 characters for the project page's timeline, kept on the ruling line as `note` for a notice nobody has to act on but that belongs on record). Each notice goes into the call with its full text, from the held stash when there is one, else the routing log's 300-character gist, at most 4000 characters. The owner's principle for the rubric: the fewer messages reach the front agents (the `-main` agent and the other top-level agents he talks to), the better. A front agent gets a notice live only when it asks that agent or the owner for an action or a decision; a notice that is unsure, off-topic or asks nothing is `held` for the project's daily digest to its `-main` agent; background agents get the operational notices as before. A failed or slow call, an answer that does not parse and a notice the answer leaves unruled are tried once more at the next tick (the notices stay unjudged; the tries are kept in `<state>/router/attempts.json`); the second failure, and a notice the answer passes to no agent of the project, go to the project's `-main` agent in the log, for the owner, with the reason. A notice's text is data: the call gets each notice between `<notice>` tags with its angle brackets written as entities, and its rulings are governed in code (`call_line`). Strong signals (the text carries `[for <owner>]` or `needs: decision`, the notice is an anchor notice of an item waiting on a decision, or the call itself marks `for_owner`) turn a drop, merge or hold into a pass to the item's mover (else `-main`) for the owner. Weak signals (the text only names the owner or one of his aliases, or says decision or a word of `[keywords.router] decision`) turn a drop or merge into `held`, "held for the digest: …", never into a pass to a front agent; a call's own `held` stays held. A pass to a front agent stands only with `for_owner` or in a project with no background agent, else it goes to the builder, else it is held for the digest ("held for the digest: …"); a pass to the notice's own sender is merged. The rules in code follow the same line: a message about one item and a quiet-hour notice reach a front agent only on a strong signal, and a weak one is held. Every call is one line in `<state>/router/calls.jsonl` (project, notice count, seconds, status, exit code, token figures and the CLI's own cost figure). `router.py` itself writes no routing log and delivers nothing: `router_live.py` applies its rulings (below).

**The page-debt call** (`page_debt.py`, step 3b). A session that changes a board item's state owes the item's project page an update; one still undone after `[page_rule] grace_minutes` moves to the project's keeper (`_pilot_fallback_tick`). With `[router] page_debt = true` the audit run's pages stage (the last stage of its model calls, under the same `[audit] max_minutes` limit) asks the server for a pass, once per audit run, so twice a day with the timer's two times (there is no thread of its own and no start hour of its own; a button press makes a pass too). The pass therefore needs `[audit] enabled = true` in script mode: with the audit off, or in agent mode (the audit agent, no script), no pass runs and the debts wait. The audit script is a separate process and the debt ledger and the page writes are the server's, so the stage calls `POST /client/page-debt` (`client.page_debt`) and the server makes the pass (`server._page_debt_pass`; the page is marked per run, so one run calls it once, and a pass stops beginning pages at the run's time limit and leaves the rest unmarked for the next run; a page whose call raises is counted and the pass goes on): for each page with moved, still unsettled debts, one fresh `claude -p` call (the router's runner: Sonnet, no tools, safe mode, the API variables unset, a timeout) is given the items (subject, description, next, needs, ask, outcome, the last `said` lines), the page's Current state and its last timeline lines, and answers with JSON: `{"edits": [{"old_text": ..., "new_text": ...}], "reason": ...}` (each `old_text` copied from the Current state, occurring exactly once there) or `{"cannot": ...}`. In **shadow** mode (`page_debt_shadow = true`, the default) it only logs: `<state>/router/page_debt.jsonl` gets the proposal and whether its edits would apply to the page as the pages checkout holds it, and nothing else changes; the 30-minute relay stays as it is, so the log can be set beside what the keeper wrote. In **live** mode (`page_debt_shadow = false`) the page is read with the gbrain CLI (`gbrain call get_page`, as `rename_page.py` does), the edits are applied to its Current state only and written with `gbrain put <key> --expected-revision <revision>`, read back, and the debts settled. A put that times out, or fails in a way that leaves it open whether the page was written, is not taken as a refusal: the page is read back first, and one that shows the edits counts as written and the debts are settled (`GbrainIO.put` returns `ok`, `refused` for an explicit error such as a stale revision, or `unknown` for a timeout). A `cannot`, an answer that does not parse, a call that fails or times out, an `old_text` that does not match exactly once, a refused put (the page changed since it was read), a read-back that does not show the edit and an unknown put whose read-back shows no edit all give the same result: the debts go in one message in the words of today's relay to the agent that keeps the page (the page's frontmatter `agent:`, when that session is live), else the project's `-main` agent, else its hub's or the scope's general `-main` agent (`anchors.fallback_main`), and are theirs from then on; nothing is dropped. The `[for <owner>]` mark opens the message only when the recipient is a front agent (the `-main` agent or another top-level `agents:` entry); a background agent gets the plain text. The notice is ruled `passed` to a page's agent or the `-main` agent by `stackshot (auto)`, so nobody is reminded of it. In live mode the 30-minute relay to the keeper is no longer sent: the debt is marked as moved and waits for the next audit run's call. Each call is also a line in `calls.jsonl` (`"kind": "page_debt"`; `router.py compare` leaves those out).

**The router acts on every project** (`router_live.py`). There is no switch: `[router] live`, `live_projects`, `shadow`, `tick_minutes` and `[pilot] projects` are ignored if a config still has them, and the rollback is a code revert. Every page of the registry is a project the router rules (`anchors.pilot_root`: its top-level page key). A notice is not delivered to a session by the place that receives it: that place (anchor-hub's `send`, the server's message to a project, the board relay `_pilot_relay` / `_pilot_relay_many`, the wake pass) asks `router_live.holds(project, recipient)`, and when it says yes the notice goes into the routing log as usual with `"live": true` and no recipient, its full text is kept in `<state>/router/held/<id>.json`, and nothing is pushed. A thread of the server (`router_live.loop`, every `[router] live_tick_seconds`, 60 by default) takes the unruled held notices and judges them with the router's code (`code_rule`, then one thin call per project, `call_project`), then acts: **passed** is pushed to the target (push.py, the pane inbox), with `[for <owner>]` on the first line whenever the target is a front agent, whatever `for_owner` says (a front pane takes a peer's message only with the mark; a delivery to a background agent is unmarked), and ruled with `routing.rule(id, "passed", to=target, by="stackshot (router)")`; **dropped**, **merged** and **held** are ruled and nothing is delivered (a held notice is the page pass's). After a ruling the server does what `route` does: a hold that waited on the notice's anchor is released on a passed or merged ruling (not on a dropped or held one), and the board is republished. A notice whose call failed or was left out stays held, undelivered, for one more try at the next tick (`attempts.json`); the second failure, or an exception, passes it to the project's `-main` agent with the mark and the reason, never dropped. **Which agents a page has.** A page lists its own front and background agents. A page that lists none is served as follows (`anchors.fallback_main`, `router_live.stand_in`): first its hub's agents (its `hub:` line; `router_live.agent_root`), then the `-main` agent of the scope's general page, configured under `[router]` as `general_<scope>`, one key per scope (none by default; an agent name, or a page key whose `-main` agent is used when the value has a "/"; a general page that lists no front agent but has a `display-name:` line is a one-session page, and its agent is that name-line session), falling back to the default scope's when that page does not exist. For such a page the call is given that one front agent and nobody else. A pass with no agent anywhere is `held` with the reason "no agent can take it", never dropped and never sent to a pane that is gone. A delivery that fails is tried again at each tick, three times, then goes to the `-main` agent. Every action is a line in `<state>/router/live.jsonl`. **Where a page's name-line session used to be written to, delivery goes to the stand-in** (`router_live.stand_in`, `server._stand_in_keeper`): the project's builder (a background agent whose mandate says build, maintain, merge or engineer), else its `-main` agent, else the hub's or the scope's general one. `_page_keeper`, `_keeper` (the item notices) and `_front_keeper` (a front agent mover's notices) answer the stand-in, and `_completion_anchor_prompt` tells it. The pages' `display-name:` lines name the project for the agent prefix and for `anchors.notice_name`, which falls back to the stand-in chain for a page without one; every name-line session of a page that lists user-facing agents is `retired` in `session_roles`. There is no unruled-notice reminder and no daily digest of automatic rulings (they chased a pane that is gone); the board's "waiting" flag and `python3 router_live.py status` show a notice the router has not ruled. The page-debt relay is held and ruled by the router too (the rubric sends a page debt to the agent that keeps the page, else the `-main` agent); with `page_debt` live the audit's page call takes it as before. **The daily digest of held notices.** A notice the router rules `held` (the page pass, a page's quiet hours, what the call is unsure of, an image it could not read) reaches no agent at once, and owes nothing: what is for the owner lives in stackshot's For you list, not in a front agent's turn. Once a day per project, from `[router] digest_hour` (default 9, the instance timezone; a server that was down then does it when it is back the same day), `digest_tick` (the live thread) writes one entry to `live.jsonl` (`kind: digest_logged`: project, group, count, ids and the digest's text, one line per notice with id, label, sender, time, gist and the router's reason) and counts the notices as digested (none is listed twice); an empty list writes nothing. The notices held by the code rule `page-pass` (the page sheets of the jobs `[router] page_senders` names) are their own group under the head "held for the page pass", logged the same way. A notice the router could not rule (see the cap below) is stackshot's own problem, so a digest with one is delivered: to the project's builder, unmarked, listing every row of the group; a project with no builder takes it to its `-main` agent, opening with `[for <owner>]`, since someone must see it. The held quiet-hour notices of `router.QUIET` and the `[[router.quiet]]` rows (a page such as `projects/example-site`, with its agent) go in the same pass to that agent instead, unmarked while it is a background agent. Each group has its own day mark and tries. `<state>/router/digest.json` records the day each group was done, the notices already digested (none is sent twice) and each project's last delivered digest; the routing log's `held` ruling is not touched. Each digest delivered is a line of `live.jsonl` (`kind: digest`, project, count, target, outcome). A push that fails is tried again at the next ticks, three times a day, and its notices wait for the next day. **A timeline note.** A ruling line from the call may carry `note` (one line, at most 300 characters). After the ruling is written the note goes to the project page's timeline, source `stackshot (router)`, dated today in the instance timezone, with the gbrain CLI the way `page_debt.GbrainIO` runs it (`gbrain call add_timeline_entry '{"slug", "date", "summary", "source", "detail", "request_id"}'`), once per notice (`noted: true` on the line). A gbrain failure is kept on the line (`note_error`) and never blocks the ruling. `[router] notes = false` ignores notes. **A cap on the re-judge loop.** A ruling that cannot be written to the routing log (`routing.rule` raised) is tried again at the next ticks, three times in all; the notice is then logged with status `stuck`, never judged again, and listed in the next digest as one that could not be ruled. `python3 router_live.py status` prints a line per project: the notices acted on in the last hour, the notices held since the last digest, the time of the last digest, the last error.

**A notice's ruling**: a message to a project is answered `held for the router — the router rules notice <id> …`, ending `get(item_id="<id>") shows its ruling`; when the sender is the mover of the one open item the text names, the router merges it (nothing to deliver), so the reply says `NOT PASSED ON: you move <item> yourself …` and a hand-on of a step is made by writing the item (`router.own_relay`, the same routing the router applies). No word for a builder or worker handing back on an item another session moves (routine), for a `For <agent>:` message or the audit agent's batch (other rules rule those first), or for a sender that is no session. The `get` tool takes that notice id as well as an item id (`client.py get notice <id>` is the same read for a script) and shows who sent it and when (in the instance timezone), the project, a one-line excerpt (120 characters at most), the router's ruling (passed to whom, merged, held or dropped) with its reason, rule (a rule in code, or the router's call) and the item it went onto, who ruled it and when; a repeat dropped by the rule in code names the notice it repeats; a notice not yet ruled says it is still held and when the router expects to rule it; an unknown id answers `no notice <id>`. The ruling is the routing log's (`routing.lookup`: each project's file searched as bytes, only the lines that carry the id parsed, the live log's `key` tried first, about 1 to 3 ms against 45 ms for reading every file); the rule and item come from `router/live.jsonl` (`router_live.trace`).

**A notice that asks nothing of a background agent is held for its next turn** (measured, such notices were a few percent of builder cost and up to half of them ended with nothing done). A background agent is an entry under `background:` in a page's agents map (`anchors.session_roles`, role `back`). A notice to one that asks nothing of it does not start a turn: it is held (`held.py`) and handed over with the agent's next turn, whatever causes that turn. The kinds (`held.KINDS`): `closed` (an item the agent moves or observes was completed with the outcome done by another session, `_tell_owner`, `_tell_observers`, `_tell_owner_change`; a background observer's close is held on purpose, like the owner's, since it asks nothing of the observer; a dropped or superseded item tells a builder to stop, so that close is delivered), `changed` (another session changed next, needs, check or after of an item the agent neither moves nor is named on), `queue` (a wake that leaves an item still after an open item, `_wake_tell`), `page-owed` (a page-update notice that owes the keeper nothing, such as the anchors notice of `_pilot_relay`, and the routing-log form the router passes; a notice that hands the debt to the keeper, "so it is yours as its keeper" or "the page update is yours as its keeper", is an ask and is delivered, and so is the page-debt fallback), `fyi` (a message marked `fyi=true`). Everything else wakes the agent as before: the audit's batch finding for an item's mover (see **The audit's findings** below), a notice that names it in needs, hands it an item (mover, hand-off), ends its wait, carries the owner's words (`[for <owner>]`, `needs: decision`, a `said` entry or a quote of his on the item, a `words` or `handback` mark), or asks something; so do a reopen, a reminder, a close that is not done, the page-debt fallback and any debt handed to the keeper, and any kind the code does not know. **Rollout gate:** a notice is held only for a session whose hook has fetched held lines (`held.mark_client`, recorded when the hook calls `/client/held`; `held.can_fetch`, valid 30 days). A machine on an old checkout, a cloud session and a session with no turn since the update get everything as before, so no line is stranded. **One decision point:** `held.decide(kind, is_background, text, owner_words, asks)`; the two places that ask it are `server._hold_notice` (the notices the server pushes itself: the senders call `_tell_or_hold(gid, owner, note, kind)`, or `_hold_notice` directly) and `router_live._hold_kind` (a pass of the router to a background agent: a notice recorded with `hold` (`routing.record(..., hold=…)`); an audit finding is never held there). A front agent is never affected. **The log:** a hold made by the server is a routing-log line ruled `held` by `stackshot (auto)`, reason `held: asks nothing (<kind>)`; a hold made by the router is the notice's own ruling `held`, by `stackshot (router)`, with the same reason (and `held_for`, `hold` on its `live.jsonl` line). **Where they live:** `<state>/held/<key>.jsonl`, one file per session (its permanent id when the registry resolves it, else its transcript id or name), one line each `{id, ts, kind, text, from, gid, nid}`: server-side state, so a pane's conversation cleared or recycled loses nothing and a restart of the server reloads it from the files. At most 100 lines a session (the oldest go) and none older than 7 days; every line dropped unread is a stderr line (`held: …`), and a file nothing has touched for 7 days (a retired session) is removed when anything is next held. **How they reach the turn:** `pages.py nag`, the `UserPromptSubmit` hook every `./stackshot client install` wires, asks the server (`POST /client/held`, the machine's token, `{uuid}`; the session must be one the server holds for that machine, as for `drain`, and its name is the server's record, never the request's; `client.py held_for`), prints the answer, which is the turn's context, and then acknowledges the ids it printed (a second `POST /client/held` with `{uuid, ack: [ids]}`, `client.py held_ack`). **At least once:** the server leases the lines it returns for 60 seconds and removes them only on the acknowledgement (`held.lease`, `held.ack`), so a line whose answer never arrived or whose hook died before printing is offered again; a duplicate is possible, a loss is not. Oldest first, one line each (time in the instance timezone, kind, text), at most 8 at a turn start and a last line `+N more, handed over at your next turn`. A session with nothing held gets an empty answer; the hook fails open. `[router] hold_notices = false` delivers everything as before. **The message tool's `fyi`:** `fyi=true` marks a message that asks nothing. To a background agent it is held (the reply begins `held for <agent>'s next turn`) and names the agent in no item's needs; to a project it is recorded with `hold: fyi`, and the router holds it when it passes it to a background agent; to a front agent it changes nothing (the front gate, the report check, the refusals); with `[for <owner>]` or `needs: decision` in it, or from the owner himself, it is an ordinary message. `client.py message … --fyi` and the `fyi` field of `POST /client/message` do the same for a script.
