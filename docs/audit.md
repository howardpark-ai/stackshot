# The daily board audit

What this page covers: the daily audit in script and agent mode, the Audits page, its checks (page agent lines, project registry, off-map sessions, board checks), the weekly refusal count and how findings reach their mover. Back to the [README](../README.md).

**The daily board audit.** With `[audit] enabled = true` the board is read once a day and what was found is reported
(`audit.py`, `audit_run.py`). `[audit] mode` says who reads it. **`"script"`** (the default) runs a script: the
field checks run in code with no model call (an ask missing, the next-line rules and the unmoved-flag escalation). Five checks that read item fields only are not made here but by the ten-minute passes, described below: stuck-elsewhere, the board checks' arbitrary-hold and mislabeled-state, an item whose own wake has passed, and an item on an agent that has had no activity for 45 minutes (the silence pass, which replaces the two silence rules this run had); a cheap heuristic then picks suspects for the judgment checks (a step already
done, wrong needs, an ask that no longer fits, a needless escalation, a project page newer than the item), and each suspect
gets exactly ONE `claude -p` call (the `[router]` command, run on the `[audit] lane` when that names one) with the fixed rubric in `audit_rubric.txt` as its system prompt,
answering `{finding, check, reason, fix}`. At most `[audit] max_calls` calls a run (default 40), one after the other, never
parallel; three failed calls in a row end the calls; an item judged is not judged again until it is written. Findings go to
the item's mover, one message per session, only when the mover is a background agent; a finding on an item a front agent, a retired session or an outside party moves goes to the project's page key
(`projects/<slug>`, unmarked), where the router hands it on, and never straight to a front agent. The marked paths are two: a finding on an item that is the owner's move goes to the project's -main agent
with `[for <owner>]` first, and a finding that went to a builder and stayed unanswered through its reminders and the builder-level send goes once more to -main, marked for its owner (the second level of the ten-minute passes' chain, below). A summary goes to `[audit] summary_to` (default `projects/example`, the stand-in page). A finding already sent for an item, with the item not written since, is not sent again (a write after the run read the item counts, one made while the run judged included, except those its own deliveries make: the record keeps `sending_from`, the time just before its first send; the record keeps it with its `sent` time, and the
summary counts it as not sent again); an item written since, or a finding that went away and came back, is sent anew. The unmoved digest (a finding of the earlier run whose item has had no write
since, chased to the project's builder) names an item once, in the first run that finds it unmoved; the record's `stuck` list and the summary keep naming it. A stuck-elsewhere finding (the ten-minute filing pass's; the first open step opens with someone other than the mover) reads a waiting
item against the session that takes it when the wait ends, so a parked, held or outside item whose step is that session's,
or the owner's while the wait is on him, is no finding, and neither is a session's step when the owner is the post-wake mover
(a session chases, then the owner acts). While a wait is on (a hold with its wake ahead or none, or any waiting item whose wait has not ended) nothing is stuck, whoever the first step names, and the owner's step dated for
after the item's wake is not the step in hand. On an alive item the owner moves, a session's first step is the one for after his answer or step, so it is no finding when that session is the item's `then` or the writer named no `then`; it still is beside a `then` that is another session. A message the tool refuses because its recipient is a front
agent goes to the project's page key unmarked, where the router hands it on; any other failure goes to the project's -main
agent. When a run finds `[audit] threshold` findings (default 5) of one check, or flags more than a fifth of
the open items, ONE message goes to `[audit] builder` naming the check and the item ids (the tightening review). The
shared "who moves this item, and is that session idle, for how long" lives in `mover_state.py` (the mover) and `liveness.py` (the pane), used by the stall pass, the audit and the
silence pass alike. `python audit.py run --dry-run` lists the suspects and makes no call, no
message and no record. **`"agent"`** is the earlier way and the rollback: an agent session (`[audit] agent`) reads the board and reports; the
server only cues it and reads what it wrote. A cue is one line pushed to the agent through `push.py`, as a wake notice goes.
Either way the run starts from `stackshot-audit.timer` every day at each time of `[audit] at` (one "HH:MM" or a list, such as `["05:00", "20:00"]`) in the instance timezone
(`audit.py cue scheduled`), or from the board's "Audit now" link, `POST /audit/now` (script mode starts the run detached and answers at once). The answer is
202 (started or cued), 409 (a run is in progress), 404 (the audit is off) or 503 (the run could not start, or in agent mode the agent is not live, with `push.py`'s answer);
every cue is logged to `<paths.state>/audit/cues.jsonl`. The board's side panel draws the audit in its Audit section as an "Audits" card: a shortlist of the audit groups, each with its number of audits and its findings in the last 24 hours (a dash, never a zero, for a group that keeps no findings log), the card's name a link to the Audits page, with the Audit now text link beside the name (a real button drawn as a link: accent text, underline on hover and keyboard focus, grey while a run is on, a 44 px tap area on a touch screen; the name row stays one line, as high as the other cards' name rows), and after it a "GitHub calls" card with the hour's writes and reads against their caps and the 60-minute window they were counted over. The Runners section above it is one line a machine, in the Machines panel's order, `busy/online` summed over the repos (a machine whose CI switch is off and has no job left reads `disabled`), linking to `/runners`. The run writes one record,
`<paths.state>/audit/run-<YYYY-MM-DD>-<HHMMSS>.json`, the start time in the instance timezone, so a second run the same day keeps the first one's record (readers take the newest; the plain `run-<YYYY-MM-DD>.json` the audit agent writes is read as before; the script adds `judged`, `calls`, `messages`, `idle_pass`, `mode` and, on a crash, `error`): `started`, `finished` (null while it runs; each an epoch number or an ISO-8601 string such as `2099-03-28T05:10+00:00`, and `GET /audit/status` gives them as epoch seconds), `items_read`, `findings`
(`{id, project, owner, category}` each), `by_session` and `by_category` (counts). An unfinished record two hours old or
more is a crashed run and holds no cue back. `GET /audit/status` gives the board its Audit card (the audit's state, and `card`, the shortlist's rows): enabled, the
agent, whether a run is in progress and since when, the last run in brief and the next scheduled one. Both routes sit
behind the board's own wall, like the board itself. A script run that dies leaves a finished record with `error` set and a line in `cues.jsonl`, never an open record that holds the next cue back; the detached run of the button
writes its output to `<paths.state>/audit/run.log`. A run is claimed under an exclusive lock (`cue.lock` in the same folder), so two cues at once get one 202 and one 409, and `audit.py run` (without `--dry-run`) is refused with a line and exit 1 while a run is in progress, when `[audit] enabled` is false or when the mode is
`"agent"`. `[audit] max_minutes` (default 100) stops the run from beginning new model calls late. **The orphan hand-over** (script mode, the run's first stage, before the board is read; `audit_run.orphan_stage` asks the server, `POST /client/orphan-handover`, which holds the item lock and the fleet's heartbeat; the pure half is `successor.py`) finds every open item whose mover (an alive item) or post-wake mover (a waiting one) is a session that is gone, the last agent of a retired project included, and hands it to the closest live agent. An item with a mover goes first to a live background agent of its project (the builder, then the others), because the minute pass sends a front agent no notice and never chases one; a front agent (the project's own, then the parent pages', the hub page's, last the scope's general `-main` agent, `[router] general_<scope>`) takes it only when no background agent is live, and then the History line says it is a front agent. A waiting item's post-wake mover keeps the closeness order (the project's `-main` first). A held item (`hold` set) waits on its wake and is not moved; a parked item whose post-wake mover is gone is. A name that is no session (the server's label, a script's) is never read as gone. The write is the minute hand-off pass's own (`server._handoff_write_move`: the new mover heads `needs`, an alive item gets the hand-off record, the new mover is told), and the item's History carries a line with the reason (`handed to X: Y is gone (...); closest live agent: ...`). An item the owner moves or waits on is never touched; an item with no live successor stays and is listed in the summary and on the record (`orphans.left`); a second call finds nothing left to do. `[audit] orphan_handover`: `"report"` (the default: the run lists what it would move and moves nothing), `"apply"` or `"off"`. To switch on the hand-over, set `orphan_handover = "apply"` under `[audit]` in the instance config and reload; `audit.py orphans --apply` moves only in that mode. At most 40 moves a run. The check stands still on a partial view of the fleet: an empty heartbeat; a mover on a machine whose `machine.json` cannot be read, or one with no row while a machine's session list is empty or unreadable, is not read as gone; and more orphans than 10, or than a quarter of the open items, is reported with the note that a partial view is likelier than that many gone sessions, and nothing is moved (`orphans.ceiling`). `--dry-run` lists what would move and writes nothing; `audit.py orphans [--apply]` makes the same call by hand. **The proof-waits stage** (script mode, `audit_run.proof_stage` over `audit_checks.proof_wait_findings`; code only, no model call, no write) runs after the judgment calls and before the pages stage. An item held open for a real event closes if the fix's tests passed and it is live; otherwise its mover is told to stage the event now (a downgrade, a probe, a dry run) and to close on the result. A candidate is an open waiting item (held, parked, or waiting on a time or a fleet event) that is an event wait for something the fleet can run on its own (`recycle`, `fleet_op`, `job_run`) or whose own words (the wait basis, the expected and watch reasons, next and the open steps) say it is kept open to see the fix happen for real; a wait on a pull request's merge or release is the release path's and no candidate, and neither is a line that names a pull request still to merge or be released. The fix counts as tested and live when the item carries a release notice (`metadata.released_told` holds a bare `owner/repo#n`: main's full run passed on that merge and the merge is in the live checkout; a merge-only or dead stamp is not one): the finding then says to close the item with that evidence, else to stage the event now (a job run, a downgrade, a probe, a dry run) and, if it cannot be staged, to write why as the wait's basis; a recycle or a fleet op needs the owner's go, and that is the basis when staging it needs his go. A wait that really cannot be staged keeps its basis named and is left alone, listed on the record's `proof_waits.left` with the basis: an outside party (needs external), news only the owner relays, an anchor event, another item's close, a real-world date (the wait basis) or the owner's recorded words for a date, a release still to come (an open step with its proof), a post-wake mover who is the owner or an outside party. The finding (category `proof-wait`) goes to the item's mover through the same `deliver_findings` with the same send stamps as every other finding (once per unchanged item; when no mover can be reached it falls back like the other findings), and the audit closes nothing. An item whose move is the owner's or an outside party's is left alone. At most `audit_checks.PROOF_MAX` (10) fresh findings are sent per run; the rest are counted in `proof_waits.capped`, named in the summary line and go out on the next run (findings sent before take no place). One item whose metadata cannot be read is skipped and counted (`proof_waits.skipped`). A stage that fails is a stage not made: the record's `proof_waits.failed` and the summary line say so and the run goes on. `audit.py run --dry-run` lists the findings and the items left alone. Suite: `tests/proof_waits_scenario.py`. **The pages stage** (script mode, `audit_run.pages_stage`) makes the page-debt call (see **The page-debt call**) once per run after the judgment calls, under the same limit; its counts are on the record's `pages` and in the summary line, and a failed page or a failed stage does not stop the run. **The pattern review** (script mode, `audit_run.pattern_stage` over `audit_checks.group_patterns`, `pick_patterns` and `parse_drafts`; `[audit] pattern_review`, `"shadow"` by default, `"off"` for nothing) is the last stage of each model run, after the pages stage and before the run's messages. Findings that repeat are a sign the flag is not the fix, so it reads every audit's findings since the review before it, groups the repeats by kind (the category; for `next rules` and `board checks` the rule or kind inside it), agent (the mover) and project, and makes ONE model call that drafts one guardrail for each pattern: a hook, a mod, a tool's text, a rulebook line, or a new audit or an edit to one (`audit_checks.PATTERN_BRIEF` is the system prompt; the call runs on the `[audit] lane` and `[audit] model` as the judgment calls do). **What it reads:** the findings log, `<paths.state>/audit/findings-log.jsonl`, one row a line (`at`, `source`, `id`, `kind`, `agent`, `project`, `detail`). Each audit pass (`write_pass_record`, shared by the filing, dates and silence passes) appends a finding the first time its record shows it, and again if it ended and came back; the run appends its own fresh findings after the review has read them. The window opens where the review before it finished reading (the previous record's `pattern_review.at`); when that review failed, was cut short or left patterns to the cap (it has no `at`), the window opens at the last review that did finish reading, found by walking the run records back, so nothing is lost however many such reviews follow one another (the dedupe keeps a pattern from being drafted twice); with no record it is the last 24 hours, with records but no finished review 48, and never more than 48. A log line that is no finding's appearance (wrong shape or type) is skipped. Appending to the log is one write on an append descriptor, so a batch of any size goes in whole beside another writer; the run's upkeep of the log (its own findings, the 14-day prune) does not depend on the review succeeding. Rows older than 14 days are dropped by the run. **A pattern** is at least 3 appearances on at least 2 different items (`PATTERN_MIN`, `PATTERN_MIN_ITEMS`); one item flagged over and over is its mover's business, not a pattern. **Dedupe:** a pattern (kind, agent and project) drafted in the last 7 days (`PATTERN_DEDUPE_DAYS`; the drafts are on the earlier records) is not drafted again; **cap:** at most `PATTERN_MAX` (5) patterns are asked about per run, the largest first, the rest wait for the next run. **Budget:** the call begins only inside `[audit] max_minutes` and takes one of the `[audit] max_calls` (the judgment calls keep `max_calls` minus one; a cap of 1 gives it to the judgment calls, a cap of 0 leaves none, and the record says so). **Shadow** (the default, and the only mode built): the drafts are only logged. The record's `pattern_review` holds `mode`, `at`, `since`, `read`, `groups`, `patterns`, `deduped`, `capped`, `called`, `failed`, `timed_out`, `note` and `drafts` (`key`, `kind`, `agent`, `project`, `count`, `items`, `guardrail`, `route`, `draft`, `why`, `at`); the summary line says how many patterns were found and drafted (`pattern review (shadow): 2 pattern(s) in 14 finding(s), 2 drafted (hook, rulebook)`), with one line under it per draft naming its guardrail, where it would go and its key (the text of a draft stays on the record); nothing is sent to any agent, no board item is opened, and nothing is edited. `route` says where a draft would go once the review goes live: `code` (a hook, a mod, a tool's text or an audit: a board item for `[audit] builder`), `rulebook` (a message to the session that holds the rulebook's rule command, never an edit), or `owner` (it changes what the owner sees or receives, or what a rule means: a board decision item with options and a recommendation). Going live needs a way to open board items from the audit script that does not exist (opening one is a server route), so it is a later change and a decision for the owner; until then the key has two values. The review never edits code, config, the rulebook or an audit, and writes no memory file. A stage that fails (a call that fails or whose answer cannot be read, an error in the stage) is recorded as failed (`failed`, `note`) and the run goes on; the audit's own writes (the log is no item write) are not activity. `audit.py run --dry-run` groups and picks from the log and says how many patterns it would ask about, with no call. Suite: `tests/pattern_review_scenario.py`. A finding whose message to its mover fails goes to the project's `-main` agent, noted on the record's `messages`. `install.sh units` installs and starts the timer only while the
audit is enabled, and disables and removes a timer it installed earlier once it is not.

**The Audits page** (`GET /audits`, `audit_overview.py`, `Board.audits_html`; `tests/audits_page_scenario.py`) shows what the audits do in one place: the three paces they run at (every minute, every 10 minutes, the scheduled runs), the audit groups (Silence, Filing, Wording, Dates, Proof and patterns, Pages and agents, Fleet and services, Text and rules) each a fold of its audits with their pace and mode, the findings of the last 24 hours (newest first, each linked to its item) and the recent runs, with the same Audit now button as the card's (one script, one `POST /audit/now`, the same refusals). It reads only what the audits already write: the findings log `<paths.state>/audit/findings-log.jsonl`, the run records and the runner's record. A group whose audits report to a machine or to CI keeps no findings log and shows a dash ("not logged" on the page), never a zero; with `[audit] pattern_review = "off"` no log is kept and no group has a count. It runs no audit and changes none.

**Two runs a day.** With two times in `[audit] at` each day has two records (`run-<date>-<HHMMSS>.json`; neither overwrites the other and no cue is refused for having run today; only a run in progress refuses one). `GET /audit/status` reports the newest record as `last` and the soonest time ahead as `next`.
A finding already sent is not sent again until its item is written, across runs as within one, so the second run sends what the first did not. The unmoved digest compares a run with the one before it (the last one that started at least six hours earlier, which the example's two scheduled runs, 06:00 and 18:00, 12 hours apart, always are), so an item flagged in the morning and still unwritten in the evening is chased then, once. The tightening history counts days, taking the newest record of each earlier day, so "3 days running" still means three days. A run that is not the first of its date names itself with its start time in its messages and summary (`Board audit 2030-01-15 18:00`; the first run of a date says only the date, so a once-a-day schedule shows only the date unless another run, a button press say, happened earlier that day). The threshold message and the page agent lines message are not deduplicated across runs: each goes out on every run that finds something, so twice a day, under headings that differ by the run's time (the threshold message is retired by the audit redesign plan). The project registry message (below) is deduplicated by date: an agent a delivered registry message of the date already told is sent nothing by a later run of that date, so it goes out once a day, and only with `[registry_audit] send = true`. The rulebook scan (`tools/rulebook_scan.py`, no model) is the unit's `ExecStartPost`, so it runs after each run and its page checks and not before, and the run never reads its result; a note already sent and still true is not sent again.

**The page agent lines check** (script mode only; `tools/page_agent_report.py`, `audit.py page-agents [--line|--json]`, run by `audit_run.py` after the item findings). Sessions get renamed and retired and a project page does not follow on its own, so a page can go on naming a session sala no longer knows. Each daily run lists those lines and sends them, one message per agent, to the agent that keeps the page: the page's own -main agent, else the top-level page's, the hub's and the scope's general one, the first of them that sala knows, else straight to the audit's -main agent (never through the router's fallback, `anchors.fallback_main`, which walks the same candidates without asking sala and can answer the very name that is gone; a message to a gone name queues silently). A front agent's message starts with `[for <owner>]`, the audit's -main agent's too. The message is not an fyi: it asks the agent to fix the line or retire the name. A name is a leftover when it is on an `agents:` map (user-facing or `background:`) or a sub-page's `agent:` line and is neither a live sala session nor an alias of one, or when a page's `display-name:` is no live session and no live session's own name starts with `<display-name>-` (an alias does not excuse a display-name: the old name of a session outliving its project's name is the case this catches). A page that is retired, done or moved is skipped, and so is a line that holds an id and no name. The live sessions are read by `anchors.sala_sessions` (the code behind `anchors.sala_live`); when sala's list cannot be read (no fleet store, no sala, a timeout, a failing call) or is empty, nothing is flagged and the run's summary says "page agent lines not checked (the reason)", never every name as stale. A list cut short but not empty is refused the same way: when 10 or more of the distinct names read are unknown and they are more than a quarter of all the distinct names read (`UNKNOWN_MIN`, `UNKNOWN_SHARE` in `tools/page_agent_report.py`), nothing is flagged and the note says the list looks partial (a real run flags a few names of a few hundred). An agent written on a page before its session is spawned is flagged until the spawn: the page is the one to hold back, or the line waits for the spawn. The lines are not item findings: they are kept on the run record under `page_agents` (`checked`, `note`, `sessions`, `pages`, `findings` of `{page, line, name, to}`), logged in `messages` with `kind: "page-agents"`, counted in the summary ("page agent lines N") and left out of `by_category` and the tightening review. They repeat each day until the line is fixed; a failed delivery is not retried before the next run. `python audit.py run --dry-run` prints them as `[page-agents]` lines and sends nothing. Suite: `tests/page_agent_report_scenario.py` (the check, its CLI and routing) and section 26 of `tests/audit_run_scenario.py` (the run).

**A project page with items and no agents** is the page agent lines check's third kind of line, and `rename_page.py` has the same check at a move. A page that is `type: project`, no sub-page (a key under another page of the registry, or a `hub:` line; a `parent:` line makes none) and not retired, done or moved, with open items (or items touched in the last 30 days) and no front agent on its `agents:` map, has items with no contact and no one to take its notices: the daily run sends `<page> · no agents map · N open items · <the fix>` (`no front agent` when the map lists background agents only) the way it sends the other lines, to the page's own -main agent, else the fallbacks, else the audit's -main agent, and repeats it each day until the map is added. A one-session page (a `display-name:` line and no agents map) is a page by design and is not flagged while that name line names a live sala session of its own prefix (a live session named so, or one that starts with `<name>-` and does not belong, by the longest project name it starts with, to another top-level page); a name that is, or starts with, the page's own slug is the page's own next to a shorter project (`foo-bar` beside `foo`); it is flagged when no live session answers to the name line, and also when its only session is named for another project (the name starts with that project's name, not the page's own: `<page> · other project's session · <session>`), however live that session is. The rule is one function, `projects.agent_gap`, used by both. `rename_page.py` makes its check only where the page registry is readable: with an empty or missing registry it prints one note and skips it (a would-be sub-page cannot be told from a project), and a page nested only by `parent:` still needs an agents map or `--no-agents-ok`. If the board items cannot be read the check says so on stderr and makes no such line. `rename_page.py plan|copy` print a WARN when the page at the new slug is such a project page, and `stub` refuses (FAIL, exit 1, nothing changed) until the destination page lists a front agent, its -main agent, or `--no-agents-ok` says the project has none on purpose; a move to a sub-page, a note, a retired project, a one-session page with a live session of its own or a page that lists a front agent is not touched. Suites: `tests/rename_scenario.py`, `tests/page_agent_report_scenario.py` and `tests/audit_run_scenario.py`.

**The project registry check** (script mode only; `tools/registry_report.py`, `audit.py registry [--line|--json]`, run by `audit_run.py` after the page agent lines). The project record is the project; the page it points at is a copy of three lines (`display-name:`, `agents:`, `status:`), and the two are written by different hands. The check lists what is wrong, each problem with the command that fixes it: a `type: project` page that is active and no project points at (`page with no project`, fix `tools/project.py adopt <page>`, with `--name` when the page's name line is missing, invalid or taken; a completed page, a note, a sub-page and a project's former page are not flagged); a project whose page is in neither the registry nor the page store (`project's page is gone`: the project is kept with its items and agents, only the pointer is flagged; an archived project's page is not, a page whose read failed is not, and nothing is flagged gone while the published page registry is empty); a page whose mirrored lines were edited or whose `agents:` lists an agent the record lacks (`page lines differ`, fix `mirror`; the same comparison the mirror makes, so a page listed is one the next mirror write changes); an agent of a project with no page of this store, or a pending agent, that sala does not know (`agent on no live session`, fix `agent-retire` or `agent-rename`; a mirrored agent of a project with a page is the page agent lines check's, not repeated, and a cut-short session list checks none); open items whose `project_id` is in neither the record's entries nor its id table (the id `item_project.derive` reads as no project) and open items on a key no project owns (re-file them, or adopt the page); two live (not archived) projects on one page. A `parent:` line is not checked: nothing in the registry reads it, so a line off the key tree is no error of the record. Every run puts the findings on its run record as `registry` (no item finding: they count in neither `by_category` nor the tightening). **Sending is off by default** (`[registry_audit] send = false`): turn it on with `send = true` in the instance's config, and then each project's -main agent (else the page agent lines' fallbacks) gets one message listing its problems, no fyi, kind `registry` in the run record, at most once a calendar day (a later run of the same date sends an agent nothing a delivered message of that date already told it; the next day it comes again until the problem is fixed). Nothing is sent when sala's session list cannot be read: the findings then have no recipient and the note says the agents were not checked. Read only. Not checked when the record has no projects (an instance that has not made its record would read every page as a page with no project), and a source it cannot read (sala, the page store, the items) skips only the checks that need it and says so. `--line` prints "Project registry: N problem(s) on M page(s)"; `--json` the whole report.

**A session off its project's map** (`anchors.off_map`, one rule for a write's note and the audit's line). A session is off the map of a project when no page of the project's hub lists it (`anchors.session_hubs`: the page, its parent page and the `hub:` page; `agents:` entries of both kinds, a `display-name:` or `agent:` line, under the name or an old name) and it is either listed on no page at all or named for the project (`<project>-<role>`: it belongs there and the map forgot it). A session listed on another project's map is a visitor and is left alone, and so are the owner, a `stackshot…` label (the server and the audit), a cloud session, a label no fleet view or session registry knows (a script) and, for the audit, a session sala no longer lists. *The note:* the reply of `create`, `update` and `message` to a project page (`to=projects/<slug>`) from such a session ends with a line `(note: <project> has no agents-map line for <session>. Its -main agent is <agent>: ask it to list you or to take this work.)`, the -main agent being the one `anchors.fallback_main` names (a page with no agents map falls to its hub's or the scope's general one), or `The project names no -main agent.` when none; a note, never a refusal, and a failure to make it leaves the reply as it was (`server._off_map_note`). *The finding:* the page agent lines check, which runs each day, carries a fourth kind of line, `<page> · session off the map · <session> (<n> items), … · <fix>`: for each active `type: project` page, the live sessions that created (`metadata.owner`), move (`metadata.mover`) or are the contact of an open item and are off its map, up to four named with their item counts and the rest counted (`page_agent_report.offmap`); the page is the one that holds the map (the hub's, for a page with a `hub:` line). It goes the way the other lines do, to the page's own -main agent, else the fallbacks, else the audit's -main agent, marked `[for <owner>]` on line 1 (`audit_run.page_agent_groups`, `par_target`, `compose`), and repeats each day until the page lists the session; it needs sala's session list as the other lines do (not read: no such line). Refusing a session for being off the map is not done here. Suites: `tests/off_map_scenario.py` (the rule, the notes, the moved page left with no agents map replayed from created items, the delivery) and `tests/audit_run_scenario.py`.

**The audit's findings reach their mover as a task** (decided on the item by the project's -main). The audit's batch to a project (router rule `audit-owners`, `router.audit_rule`) is split by item mover, one message per agent (`router_live._act_split`), each carrying the batch's opening lines, the agent's own findings whole (`router.audit_text`, never cut to one line) and the relay's closing paragraph. A finding asks its mover to act, so it is never held: a background mover (a builder) is woken at once with a normal notice, like a front one (marked for the owner as a pass to a front agent is), whatever `hold` the message carried, and it is never shown under "they asked nothing of you". An item with no mover, a mover who is no agent of the project, a closed item and the lines that are no finding go to the -main agent. The ruling's `to` (the "passed to" line) lists every recipient; an agent whose lines an earlier try held (a `live.jsonl` entry of `sent` ending `: held`, written before an earlier change) is named "(held)" there, so it does not look dropped. Before this, the lines for a builder were held as "asked nothing", and as one line made of the batch's opening and its findings cut to 260 characters, so the findings were lost.

- **The audit's board checks** (`tools/board_report.py`, `audit.py board-check [--line|--json]`; it challenges arbitrary on-hold descriptions and mis-labeled statuses; items on an agent that are not moving are the ten-minute silence pass's): read only, beside `next-check`; lists open items as findings of the category `board checks` (id, project, mover, kind, why), so the audit challenges each item's mover. Two kinds:

  - `arbitrary-hold`: an item on hold with nothing structural behind it (`render.hold_whys`, the function behind the briefing's "nothing holds it now": an open after item, a pane recycle, needs external, an anchor scoped to it; or a check, a party, a stored wait kind of item, anchor or relay, the owner's recorded words or name in the wait basis) and with next, steps, wait basis and expected reason naming no event (an item, a PR, a link, a wait word with an object, a thing that ends or resets): only a date or vague words.
  - `mislabeled-state`: the stored state differs from `states.derive` (your-step and verifying are stored only), the stored state lacks what it must carry (`states.problems`: your-call with no ask, outside with no external, blocked with no after), or the item is on hold while its words name the owner's decision (should be your-call) or an outside party (should be outside); that reading of the words is skipped for a hold already labeled outside (needs external or the stored state outside) or standing on his recorded words (`cap_ok`). A stored doing item that reads as another state is a mislabeled-state finding only, not also idle.
  The mover of a finding is the item's own (needs, post-wake mover, mover); an item that names none falls to the project's builder, else its `-main` agent, read from the project registry (`router_live.builder`, `anchors.fallback_main`) by `board_report.fallback_mover`, which the CLI installs as `waiting.FALLBACK_MOVER` the way the server does (without the server's last step, the page keeper). A project that names neither leaves the mover empty (printed `-`) and the idle check skipped.
  `--line` prints "Board checks: N item(s) · arbitrary-hold a · mislabeled-state b". Suite: `tests/board_report_scenario.py`.

- **The audit's page agent lines check** (`tools/page_agent_report.py`, `audit.py page-agents [--line|--json]`): read only, beside `board-check`; lists each name on a project page's agent lines that sala no longer knows, and each project page with items and no front agent, as `{page, line, name, to, fix}` (line is `agents line`, `agent line`, `display-name`, `no agents map`, `no front agent`, `other project's session` or `session off the map`; `to` is the agent the daily run tells). `--line` prints "Page agent lines: N line(s) on M page(s)" or "Page agent lines: not checked (the reason)"; `--json` the whole report (`checked`, `note`, `sessions`, `pages`, `findings`); `--sessions FILE` reads a saved copy of `sala sessions --json` instead of calling sala. The rules, the recipient and the run's use of it are under the daily board audit above. Suite: `tests/page_agent_report_scenario.py`.

- **The audit's project registry check** (`tools/registry_report.py`, `audit.py registry [--line|--json]`): read only, beside `page-agents`; lists what is wrong with the project record and the pages it points at, each as `{page, line, name, fix, project, to}` (line is `page with no project`, `project's page is gone`, `page lines differ`, `agent on no live session`, `item id names no project`, `open items on a key no project owns`, `or `two projects on one page`; `fix` names the `tools/project.py` command or the re-filing that mends it; `to` is the agent the daily run tells). `--line` prints "Project registry: N problem(s) on M page(s)"; `--json` the whole report (`checked`, `note`, `projects`, `pages`, `findings`); `--sessions FILE` reads a saved copy of `sala sessions --json`. Nothing is checked, and nothing said, when the record has no projects. The daily run sends the findings only with `[registry_audit] send = true`. The rules and the run's use of it are under the daily board audit above. Suites: `tests/registry_report_scenario.py`, `tests/project_adopt_scenario.py` (the `adopt` verb), `tests/audit_run_scenario.py` (the run's stage).

- **The weekly count of refused board writes** (`call_log.py`, `tools/refusal_report.py`, `audit.py refusals [--dry-run] [--force] [--week DATE]`, `_RefusalLog` in `server.py`; `tests/refusal_report_scenario.py`). The server keeps one line for every create, update, complete, confirm and message call, went through or refused, in `<paths.state>/calls/<YYYY-MM>.jsonl` (`{t, tool, ok}`; a refused call adds the item, the sender and the refusal's text clipped to 300 characters; the call's other arguments are never logged). After each finished Monday-to-Sunday week (instance timezone) the audit's unit (`ExecStartPost`, after the rulebook scan, so the first run after the week ends) sends one message that asks nothing, to `[refusal_report] to` (default `[audit] summary_to`): create and update calls refused of all and the share, the week before it, the kinds of refusal that make most of them (named kinds in `call_log.kind_of`, else the refusal's text with its ids and numbers folded), the sessions refused most, and what the server corrected instead. A week is sent once (`<paths.state>/refusal-report/sent.json`), a week with no records is not sent, and a log that starts after the week began says so. `[refusal_report] enabled = false` (the default) sends nothing; `--dry-run` prints the last full week anyway.

- **The open items' text** (`tools/open_item_text.py [--links] [--store DIR]`; `tests/open_item_text_scenario.py`): read only, no model, secret or network call; prints the description, next, steps and ask lines of every open item (held ones too), each prefixed by its id, or with `--links` the distinct `/mockup/<n>` links found in any string of an open item's JSON, sorted by number (a loose match on purpose: case-insensitive, a prefix such as `/mockup/120x` counts as `/mockup/120`, so a page is only ever kept longer). It fails closed: exit 0 when the store was read whole, 2 when the store folder (`--store` or `[paths] store`) is missing, 3 when an item file could not be read or parsed (the count goes to stderr, the links found are still printed).
