# Asks and answers on the board

What this page covers: the board sign-in, how a wrong ask leaves the owner, how the owner answers from an item page, the answer box and the History after a decision. Back to the [README](../README.md).

**The board's own sign-in** (`[auth] ui_open = false`; `ui_login` and `ui_callback` in `stackshot/web/server.py`, `_ui_guard` and `_ui_renewed` in `stackshot/web/signin.py`) lasts `[auth] ui_session_days` from the last visit. A visit is a GET that a browser opens as a page (`Sec-Fetch-Mode: navigate`, or no such header, as a tool sends): the signed session cookie is written again with the full days from now, once an hour of its days is used, so a machine in use stays signed in and one left alone longer than the days is asked again. A session that has run out, a forged one and one of an address no longer in `allowed_emails` are never renewed; a script's fetch (the open tab's polling) and the `/ui/` routes (sign-out) do not renew. The board signs in through this server's own OAuth as a client it registers for itself, and for that one client and its own callback `/ui/callback` the server goes from `/authorize` straight to Google with no Allow page: any other client (claude.ai, a connector, a client that registers itself with the board's callback) still gets it. The consent binding cookie is still set and still checked at the Google callback, and the code goes only to `/ui/callback`, which takes it from the browser that holds the signed flow cookie of a sign-in started at `/ui/login` (its `state`, and the PKCE verifier the code is exchanged with). A page's script (a request with `Sec-Fetch-Mode` other than `navigate`) that finds itself signed out gets a plain `401` from every guarded route and from `/ui/login`, never a redirect to the sign-in, so a tab that has lapsed starts no sign-in: the home's polling script stops at the first 401 and shows "Signed out — sign in again" (a link that opens the page, which signs in), the Runners page's script stops too. A person's browser opening a page without a session is redirected to the sign-in as before. A browser older than Safari 16.4 sends no `Sec-Fetch-Mode`, so its polling script is still redirected and follows it as before. A lapsed tab does not recover by itself when the person signs in in another tab: its "Signed out" link, or a reload, does.

**A wrong or moot ask leaves the owner's move** (`stackshot/model/ask_leaves.py`, `stackshot/model/note_read.py`; `server._ask_after_write`, `_ask_leave`; `tests/ask_leaves_scenario.py`). The limit on what the server does by itself reads: *Never by the server: closing an item, writing an ask, answering for the owner, altering his words.* The server may take off his move what its author calls wrong, in one plain sentence, and apply what he said; a board item the ask waits on being dropped only reminds the author. Four parts:

1. **A reminder.** A write to an item while an ask stands on it, by the session that wrote the ask, moves the item or created it, ends with one line: the ask stands for the owner, withdraw it now (`clear_ask=true`) if it is wrong or moot, with the owner's notes since the ask. For the ask's author the line also names a dropped dependency (part 3).
2. **The ask-time check.** A write that sets an ask shows the owner's comments and notes on the item since its last ask (or the last three days when it had none), so a note that already answers the question is seen before it is asked again.
3. **The server takes the ask off his move only on its author's own plain sentence; a dropped dependency only reminds the author.** (a) **The author's word** (`ask_leaves.author_says_wrong`): a write by the ask's author whose whole new text is exactly one sentence of the closed shape: "the ask is wrong", "this ask is moot", "my question is stale" ("the", "this" or "my" and "ask", or "this" or "my" and "question"; then "is" and wrong, moot, stale, void, obsolete, no longer needed or no longer valid, with "now" or "anymore" at most after it), with at most one list bullet ("- ") before it and a full stop after it. The new text is `ask_leaves.new_lines` over every text parameter of the call, all of it joined (`server._ASK_TEXT_PARAMS`: `subject`, `description`, `next`, `options`, `said`, `work`, `check`, `wait_basis`, `reason`, `expected_reason`, `step`, `supplies`, `goal`, `wait_event`, `draft`, `watch_reason`, `outcome_text`, `wait_reason`, `reword`, `owner_name`, `owner`, `agent`, `observers`, `step_proof`, `wait_anchor`, `post_wake_mover` and `then`; a mapping or a list gives each string inside it). It is read line by line against the lines the item already held in its stored texts (of a step, a work line or the wait basis only the `text`, never a status word such as "open" or "done"): a line that equals, whole, a line the item held is not new when re-sent with a later write, but a line that only appears inside a longer held line is new (an old "Status: migration is not yet done" holds no "Not yet"), and any other new line or sentence in any of those parameters (a hedge, "I disagree", "Not yet", "Maybe", "Keep it", a label such as "Note:", "Todo:" or "Pat's review:", a quote, a question, another language; in the description or in any other of those parameters) means no word. The parameters that are not read take a fixed word, a date, a link, an item id, a step number, or a session, a front agent or a page name (`status`, `priority`, `outcome`, `wait_kind`, `due`, `wake`, `expected_by`, `ask_by`, `needs`, `mover`, `contact`, `project`, `anchors`, `after`, `superseded_by`, `done`, `dropped`, `rank`), plus `item_id`, `sender`, the ask itself (`ask`, `clear_ask`: a write that sets one takes the ask-time check instead) and the on/off switches (`hold`, `recycle`, `clear_*`). A test sends a free-text hedge through the real update call, beside the author's sentence, for each of the parameters that take a string and requires that it is refused or not stored; a parameter that starts to store text fails it and moves to the read list. Another test keeps the two lists equal to the update tool's signature, so a parameter added later has to be placed in one of them. A write with no sender, or by a session that neither wrote the ask nor, with no record, moves the item, counts for nothing. Then the ask, its options and the owner's stored your-call go, `decision` leaves needs, the item goes back to its author, also when the owner is its stored mover and a `then` is stored (else as any answered decision leaves it), one History line says what and why, and the ask and options are kept in `metadata.ask_left` so that an answer he sends late (a stale option click, a note) is kept as a comment, not applied; a new ask or his answer to one drops `ask_left`, so a pick on an older ask then reads stale. The History line and the item page tell him; nobody is messaged on his behalf. The writer of the update is told in its reply, and the mover in a notice. `[ask] leaves = false` turns it off. The author is read from `metadata.ask_rec` ({by, at, text}), stamped on every save that changes the ask; an ask stored before the record has none, and then the item's mover and creator count as its author. (b) **A dropped dependency** (`ask_leaves.depends_on`, `dropped_deps`) removes nothing, because a gate is a precondition and a dropped gate often makes the ask more live, which only its author can tell. The reader names the item after/once/when/until/waiting for/depends on: an ask whose text has "after", "once", "when", "until" or "following" board#N followed by "lands", "is merged", "is released", "is live", "is done", "completes", "ships" or "is ready"; "waiting for" or "waiting on" board#N "to land", "merge", "finish" or "complete"; or "depends on" board#N "landing", "merging" or "finishing" (a list, "board#N and board#M", counts for each); a bare "after board#N", "blocked by" and a citation name none. When such an item was closed as dropped after the ask was written (`ask_rec.at`; a superseded item counts only when its replacement chain, followed to its end, ends in a dropped item), the reminder of the ask's author adds "board#N, which this ask waits on, was dropped on <date>; if the ask is moot withdraw it now (clear_ask=true), otherwise it stands", naming each such item once in the clause. The clause comes with each of his writes to the item for as long as the dependency stays dropped and the ask stands; the server keeps no state of it. An ask written after the drop is that item's fallout and an ask stored without a record has no time to compare, so neither is named. The item's stored `after` is the item's, not the ask's. No notice, no message, no History line and no removal: the ask stands on his move. This is narrower than the first design, which took such an ask off his move on the record alone; every shape of that rule went wrong on some phrasing ("sign the contract when board#N is released", "hire Pat once board#N is done"), so the author decides.
4. **The server applies what he said.** On his step, a note that is only "ran it" (or "done", "I did it"; "I ran it and will check tomorrow" ticks and holds nothing; the bare imperative "run it" ticks nothing) ticks the step as an empty Send does (`note_read.is_done`), and a note in which he says he will do it later, a first-person future with a time ("I'll do it tomorrow evening", "I will look at it next week", "I'm going to do it in 3 days", a date), puts the item on hold until then, with his words behind the wake (the park the answer path already makes: `_hold_set`, `_cap_ok_put`; `note_read.until`). The session that takes the item is told what was applied, in place of the usual "judge the note" line. A note that asks something, speaks of a past time, is negated ("not tomorrow", "can't do it tomorrow"), is a deadline ("by tomorrow evening", "need this by next week"), says "go ahead", is conditional, does the step now ("I'll do it now, then check tomorrow"), is no action of the step ("I'll let you know tomorrow", "I'll be traveling tomorrow") or says more than that is not read: it goes to the session to judge, as before.

**Answering from an item's page**. For a viewer signed in to the board (`[auth] ui_open = false`, the
server's own sign-in), an open item's page carries an answer box under its Ask: while it needs the owner's decision, one
button per stored option (the recommended one first; Approve and Decline only when the owner lists them as options; with three or more options the cards carry the letters A, B, C, and a label that repeats its own letter, as in `A Report`, `B Plan`, `C Fix`, is shown without it: `stackshot/model/option_labels.py` drops it on read, only when every label opens with its own place's letter in order, and changes nothing stored), or with
no options, Yes / No and the note box with its one Send; a stored your-step item gets the note box and one Send instead: Send with an empty box finishes the step, as Done did (recorded as
his answer "Done", the item goes to its then-mover), and Send with a note records `kind: step-reply` and hands the item to the then-mover with the note, which judges it (carry on if the note finishes the step; if it is a question or a request,
answer it or do it and hand the item back to him with a step; if it says he will do the step at a later time, put the item on hold with a wake at that time, `update(hold=true, wake=…, wait_reason=…)`, leave his step open and hand no new step back; the server reads the plain cases itself, see "The server applies what he said" above, and the then-mover's notice carries this instruction for a note it did not read). A page loaded before the release may still post `act=done` (as an empty Send) or `act=comment` (a comment only, the step stands). In the other cases the comment box is sent as his answer or as a comment. It is a plain form POST to `/items/<id>/answer`, refused without the sign-in, without the page's
token (an HMAC over his address and the item, keyed by `<secrets>/ui-session.key`) or from another origin. The page sends it
by script (a fetch that follows the 303, then `location.replace`), so the answer replaces the item page in history and Back
goes to where he came from; without script it is the plain POST and 303. Item and project pages are served `no-store` and
reload when restored from the back-forward cache (the board updates itself in place then). An answer is
stored in `metadata.answers`, takes `decision` out of needs (the sessions named stay) and clears the ask; a comment changes
neither. Each is pushed to the owner and to the sessions named in needs, and with the mirror on becomes the issue's comment
headed `[author: <owner> · board]`, a header only the server writes (a tool `sender` that names the owner is refused). A
decision that no session it went to has followed with a write within 30 min goes to the project's keeper once
(`<state>/answers.json`). There is no idle pass: a mover that goes quiet is the stall pass's and the hand-off ladder's ([below](stall-and-ladder.md)). A raise to the owner's call stored before the last rung
existed keeps its "Park until <day>" button, which the server still applies itself (the hold and its wake, a YYYY-MM-DD written in the box changes the day; `[idle] park_days` is only its
fallback). `[idle] hours` is still read, by `stackshot/waits/waiting.py`: it is the expected time of a plain on-agent item.

- **The answer box of the board** (`stackshot/web/ui/render.py` `_cards_html`, `_CARDS_CSS`, `_CARDS_JS`, `Board.answer_html`, `Board.home_ask`; `server._split_letter`; `tests/board_pages_scenario.py` section 2b). On an open decision the item page and each Your move row on the home draw **one card per option**, a radio input styled as a card (`name=choice`, so the form posts the field it always did and works with the script off), showing the option's label, the orange *recommended* badge on the recommended option and nothing else for it, and the option's **whole text** (the one-line cut and the per-option button are gone). A question with **three or more options letters its cards A, B, C** (in the order the owner stored the options, the order a session writes its ask in, so "Recommend: B" and the card lettered B agree; the recommended card keeps its badge wherever it sits) and the radio's value is `B · <label>`; two options (Approve and Decline, Yes and No) carry no letters and keep the recommended one first. The server takes the lettered value (`_split_letter`: the letter must be the label's stored place among three or more options, tried before a bare-label match, else the answer reads as stale): `metadata.answers[].choice` stays the bare label, the letter is kept beside it as `letter`, and History, the saved note and the notices read `B · <label>`. A picked card shows a filled circle, a 2 px accent border and a tint (one channel per meaning: recommendation is the badge only). An optional **Note** box sits below the cards and one **Send** is the only way to send; the page script greys it, with the hint "Pick an option or write a note" beside it, until a card is picked or the note has text, and a second tap on the picked card clears it (without the script Send is always on and the server answers "Nothing sent" to an empty form). A card picked with a note sends the option plus the note; a note alone is his answer as a note. The Ask block no longer lists the options while the box is drawn; for a viewer with no box (signed out) the list stays as the page's read-only copy. A decision with no stored options keeps its Yes and No (as cards); a comment-only box and a your-step box are unchanged.

- **History after a decision lists the options whole** (`stackshot/web/ui/render.py` `Board.item_log`, `Board.decision_made`). Where the decision left the needs, History shows "the options were:" and one short bullet per option, its label, the recommended mark and its whole sentence, with the one he picked marked "picked"; a note sent with no pick adds "no option was picked". The options come from the answer record (`metadata.answers[].options`, written by `server._answer` with the answer, so they outlive the options being cleared off the item), else from the version of the item before the decision; a record without either reads as it did. Next keeps its short "picked <label> (<sentence>)" line. The live refresh (`_LIVE_JS`) does not reload or swap a page whose answer form holds a picked card or a typed note, also when the new page's frame differs after a deploy (`tests/decision_pick_check.py`).
