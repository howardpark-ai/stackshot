# Asks and answers on the board

What this page covers: the board sign-in, how a wrong ask leaves the owner, how the owner answers from an item page, the answer box and the History after a decision. Back to the [README](../README.md).

**The board's own sign-in** (`[auth] ui_open = false`; `ui_login`, `ui_callback`, `_ui_guard` and `_ui_renewed` in `stackshot/web/auth/signin.py`) lasts `[auth] ui_session_days` from the last visit. A visit is a GET that a browser opens as a page (`Sec-Fetch-Mode: navigate`, or no such header, as a tool sends): the signed session cookie is written again with the full days from now, once an hour of its days is used, so a machine in use stays signed in and one left alone longer than the days is asked again. A session that has run out, a forged one and one of an address no longer in `allowed_emails` are never renewed; a script's fetch (the open tab's polling) and the `/ui/` routes (sign-out) do not renew. The board signs in through this server's own OAuth as a client it registers for itself, and for that one client and its own callback `/ui/callback` the server goes from `/authorize` straight to Google with no Allow page: any other client (claude.ai, a connector, a client that registers itself with the board's callback) still gets it. The consent binding cookie is still set and still checked at the Google callback, and the code goes only to `/ui/callback`, which takes it from the browser that holds the signed flow cookie of a sign-in started at `/ui/login` (its `state`, and the PKCE verifier the code is exchanged with). A page's script (a request with `Sec-Fetch-Mode` other than `navigate`) that finds itself signed out gets a plain `401` from every guarded route and from `/ui/login`, never a redirect to the sign-in, so a tab that has lapsed starts no sign-in: the home's polling script stops at the first 401 and shows "Signed out — sign in again" (a link that opens the page, which signs in), the Runners page's script stops too. A person's browser opening a page without a session is redirected to the sign-in as before. A browser older than Safari 16.4 sends no `Sec-Fetch-Mode`, so its polling script is still redirected and follows it as before. A lapsed tab does not recover by itself when the person signs in in another tab: its "Signed out" link, or a reload, does.

**A wrong or moot ask leaves the owner's move** (`stackshot/model/ask_leaves.py`, `stackshot/model/note_read.py`; `service/asks.py` `_ask_after_write`, `_ask_leave`; `tests/ask_leaves_scenario.py`). The limit on what the server does by itself reads: *Never by the server: closing an item, writing an ask, answering for the owner, altering his words.* The server may take off his move what its author calls wrong, in one plain sentence, and apply what he said; a board item the ask waits on being dropped only reminds the author. Four parts:

1. **A reminder.** A write to an item while an ask stands on it, by the session that wrote the ask, moves the item or created it, ends with one line: the ask stands for the owner, withdraw it now (`clear_ask=true`) if it is wrong or moot, with the owner's notes since the ask. For the ask's author the line also names a dropped dependency (part 3).
2. **The ask-time check.** A write that sets an ask shows the owner's comments and notes on the item since its last ask (or the last three days when it had none), so a note that already answers the question is seen before it is asked again.
3. **The server takes the ask off his move only on its author's own plain sentence; a dropped dependency only reminds the author.** (a) **The author's word** (`ask_leaves.author_says_wrong`): a write by the ask's author whose whole new text is exactly one sentence of the closed shape: "the ask is wrong", "this ask is moot", "my question is stale" ("the", "this" or "my" and "ask", or "this" or "my" and "question"; then "is" and wrong, moot, stale, void, obsolete, no longer needed or no longer valid, with "now" or "anymore" at most after it), with at most one list bullet ("- ") before it and a full stop after it. The new text is `ask_leaves.new_lines` over every text parameter of the call, all of it joined (`web/tools/update.py` `_ASK_TEXT_PARAMS`: `subject`, `description`, `next`, `options`, `said`, `work`, `check`, `wait_basis`, `reason`, `expected_reason`, `step`, `supplies`, `goal`, `wait_event`, `draft`, `watch_reason`, `outcome_text`, `wait_reason`, `reword`, `owner_name`, `owner`, `agent`, `observers`, `tell_him`, `step_proof`, `wait_anchor`, `waits` (the anchors, events and item ids of a list's lines), `post_wake_mover` and `then`; a mapping or a list gives each string inside it). It is read line by line against the lines the item already held in its stored texts (of a step, a step status or the wait basis only the `text`, never a status word such as "open" or "done"): a line that equals, whole, a line the item held is not new when re-sent with a later write, but a line that only appears inside a longer held line is new (an old "Status: migration is not yet done" holds no "Not yet"), and any other new line or sentence in any of those parameters (a hedge, "I disagree", "Not yet", "Maybe", "Keep it", a label such as "Note:", "Todo:" or "Pat's review:", a quote, a question, another language; in the description or in any other of those parameters) means no word. The parameters that are not read take a fixed word, a date, a link, an item id, a step number, or a session, a front agent or a page name (`status`, `priority`, `outcome`, `wait_kind`, `wait_mode`, `due`, `wake`, `until`, `expected_by`, `ask_by`, `needs`, `mover`, `contact`, `project`, `anchors`, `after`, `superseded_by`, `done`, `dropped`, `rank`), plus `item_id`, `sender`, the ask itself (`ask`, `clear_ask`: a write that sets one takes the ask-time check instead) and the on/off switches (`hold`, `recycle`, `clear_*`). A test sends a free-text hedge through the real update call, beside the author's sentence, for each of the parameters that take a string and requires that it is refused or not stored; a parameter that starts to store text fails it and moves to the read list. Another test keeps the two lists equal to the update tool's signature, so a parameter added later has to be placed in one of them. A write with no sender, or by a session that neither wrote the ask nor, with no record, moves the item, counts for nothing. Then the ask, its options and the owner's stored your-call go, `decision` leaves needs, the item goes back to its author, also when the owner is its stored mover and a `then` is stored (else as any answered decision leaves it), one History line says what and why, and the ask and options are kept in `metadata.ask_left` so that an answer he sends late (a stale option click, a note) is kept as a comment, not applied; a new ask or his answer to one drops `ask_left`, so a pick on an older ask then reads stale. The History line and the item page tell him; nobody is messaged on his behalf. The writer of the update is told in its reply, and the mover in a notice. `[ask] leaves = false` turns it off. The author is read from `metadata.ask_rec` ({by, at, text}), stamped on every save that changes the ask; an ask stored before the record has none, and then the item's mover and creator count as its author. (b) **A dropped dependency** (`ask_leaves.depends_on`, `dropped_deps`) removes nothing, because a gate is a precondition and a dropped gate often makes the ask more live, which only its author can tell. The reader names the item after/once/when/until/waiting for/depends on: an ask whose text has "after", "once", "when", "until" or "following" board#N followed by "lands", "is merged", "is released", "is live", "is done", "completes", "ships" or "is ready"; "waiting for" or "waiting on" board#N "to land", "merge", "finish" or "complete"; or "depends on" board#N "landing", "merging" or "finishing" (a list, "board#N and board#M", counts for each); a bare "after board#N", "blocked by" and a citation name none. When such an item was closed as dropped after the ask was written (`ask_rec.at`; a superseded item counts only when its replacement chain, followed to its end, ends in a dropped item), the reminder of the ask's author adds "board#N, which this ask waits on, was dropped on <date>; if the ask is moot withdraw it now (clear_ask=true), otherwise it stands", naming each such item once in the clause. The clause comes with each of his writes to the item for as long as the dependency stays dropped and the ask stands; the server keeps no state of it. An ask written after the drop is that item's fallout and an ask stored without a record has no time to compare, so neither is named. The item's stored `after` is the item's, not the ask's. No notice, no message, no History line and no removal: the ask stands on his move. This is narrower than the first design, which took such an ask off his move on the record alone; every shape of that rule went wrong on some phrasing ("sign the contract when board#N is released", "hire Pat once board#N is done"), so the author decides.
4. **The server applies what he said.** On his step, a note that is only "ran it" (or "done", "I did it"; "I ran it and will check tomorrow" ticks and holds nothing; the bare imperative "run it" ticks nothing) ticks the step as a Done does (`note_read.is_done`), and a note in which he says he will do it later, a first-person future with a time ("I'll do it tomorrow evening", "I will look at it next week", "I'm going to do it in 3 days", a date), parks the item until then, with his words behind the wake (the park the answer path already makes: `_hold_set`, `_cap_ok_put`; `note_read.until`). The session that takes the item is told what was applied, in place of the usual "judge the note" line. A note that asks something, speaks of a past time, is negated ("not tomorrow", "can't do it tomorrow"), is a deadline ("by tomorrow evening", "need this by next week"), says "go ahead", is conditional, does the step now ("I'll do it now, then check tomorrow"), is no action of the step ("I'll let you know tomorrow", "I'll be traveling tomorrow") or says more than that is not read: it goes to the session to judge, as before.

**Answering from an item's page**. For a viewer signed in to the board (`[auth] ui_open = false`, the
server's own sign-in), an open item's page carries an answer box under its Ask: while it needs the owner's decision, one
button per stored option (two options: the recommended one first, no letters; Approve and Decline only when the owner lists them as options; with three or more options the cards carry the letters A, B, C by place in the stored order, the recommended card keeping its badge wherever it sits; an item that links a mockup draws its options by name in the stored order, two included, with no letters; a new option label may not open with a lone letter, see below; a stored label that repeats its own letter, as in `A Report`, `B Plan`, `C Fix`, is shown without it: `stackshot/model/option_labels.py` drops it on read, only when every label opens with its own place's letter in order, and changes nothing stored), or with
no options, Yes / No and the note box with its one Send; a stored your-step item gets an optional note box ("Note (optional)") and two buttons instead: **Done** (the main one, `act=done`) finishes the step (recorded as
his answer "Done", the item goes to its then-mover; a note written in the box stays on that record and goes along, the then-mover's notice saying the step is done, with his note quoted), and **Send note** (`act=note`, greyed until the box has text, with the hint "Write a note to send it" on it; without the script it is enabled and a blank box answers `?sent=emptynote`, "write a note to send it", never "pick an option") records `kind: step-reply` and hands the item to the then-mover with the note, the step staying open, which judges it (carry on if the note finishes the step; if it is a question or a request,
answer it or do it and hand the item back to him with a step; if it says he will do the step at a later time, park the item until that time, `update(until=…, wait_kind="time", wait_basis=…)` (his words go in `said`), leave his step open and hand no new step back; the server reads the plain cases itself, see "The server applies what he said" above, and the then-mover's notice carries this instruction for a note it did not read). The notice after a Done says a note went along (`?sent=donenote`) when the box had one, and is the plain `done` notice without one. A page loaded before the two-button form may still post `act=send` (an empty box is a Done, a note a step-reply, as before) or `act=comment` (a comment only, the step stands); `act=done` and `act=comment` keep working as they did. In the other cases the comment box is sent as his answer or as a comment. It is a plain form POST to `/items/<id>/answer`, refused without the sign-in, without the page's
token (an HMAC over his address and the item, keyed by `<secrets>/ui-session.key`) or from another origin. The page sends it
by script (a fetch that follows the 303, then `location.replace`), so the answer replaces the item page in history and Back
goes to where he came from; without script it is the plain POST and 303. Item and project pages are served `no-store` and
reload when restored from the back-forward cache (the board updates itself in place then). An answer is
stored in `metadata.answers` (with `by`, the name of the person who sent it, from the address signed in, written when that person is not the first; an answer with no `by` reads as the first person, and the History, the tick on his step and the save's author use that person's name), takes `decision` out of needs (the sessions named stay) and clears the ask; a comment changes
neither. Each is pushed to the item's mover and to the sessions named in needs (and reaches the item's contact and the front agents he is talking to, as the first bullet below says; on a project with a builder, a front agent named in needs that neither moves the item nor takes it gets the line as a held line, as the bullet after the first one says), and with the mirror on becomes the issue's comment
headed `[author: <owner> · board]`, a header only the server writes (a tool `sender` that names the owner is refused). A
decision that no session it went to has followed with a write within 30 min goes to the project's keeper once
(`<state>/answers.json`). There is no idle pass: a mover that goes quiet is the stall pass's and the hand-off ladder's ([below](stall-and-ladder.md)). A raise to the owner's call stored before the last rung
existed keeps its "Park until <day>" button, which the server still applies itself (the park and its wake, a YYYY-MM-DD written in the box changes the day; `[idle] park_days` is only its
fallback). The older `[idle] hours` key is no longer read.

- **A decision is parked with him as the next mover, never as `needs: decision` plus the stored hold flag** (`model_guards.check`, the `decision_hold` guard; `stackshot/service/watching.py` `watch_ask`, `stackshot/waits/watchers.py` `turn_to_owner`; `tests/model_guards_scenario.py`, section 6d). An item on his call is on his move, and a park is not, so the pair is refused and the refusal names the way (the guard refuses only the stored hold flag beside `decision`; `needs=["decision"]` with `until` and `wait_kind="time"` is not refused by it, but the audit never reads an item whose needs hold `decision` as parked, so the way below is the one that returns the ask at the date): put the session that waits in `needs` (a doing item takes the same write), then `until=<date>`, `wait_kind="time"`, `wait_basis` and `mover=<him>`; no hold flag. `until` and `mover=<him>` without `wait_kind="time"` are refused as an item with him as mover and nothing for him to do (`owner_mover`), and that refusal names this form. The audit reads such an item as parked (`waiting.is_parked`: the stored flag, or a wait on one date alone, never one whose needs hold decision), so it keeps the ask without a `wrong-needs` or `ask-missing` finding. The ask and the options stay on the item as written (a write that takes `decision` out of `needs` leaves them), the item reads as waiting until the date, and when the date comes the wake sets `needs` back to `decision` with its ask, if it had one, and its options (an ask stored with no options is a yes/no and comes back as written; a stored ask that no longer parses gets the generic question with its two buttons instead). A park with no date is still refused. The park form is a time wait (`until` with `wait_kind="time"`) more than 7 days out with a `wait_basis`; a park of 7 days or less needs his words (`said`), and a `wait_basis` sent with such a date is dropped. A doing item parks the same way and its ask, if it had one, returns at the date. The retired parameters `hold` (beside a date), `wake` and `ask_by` are refused. His bare pick on the board while the item is parked finds a question that is not open: nothing is written (a pick with a note is kept as a comment on the item and the mover is told; the park stays).
- **His answer reaches the item's contact and the front agents he is talking to** (`service/answer.py` `_answer_deliver`, `_also_reached`, `_tell_aside`; `service/telling.py` `present_fronts`, `front_role`, `front_fyi`; `tests/answer_reach_scenario.py`). Beside the mover, the sessions named in needs and the then-mover, whose pushes are as above, the same line goes once to (a) the item's contact as the board reads it (`contacts._contact_of`: the stored contact while it is still a front agent, else the project's -main agent) and (b) every front agent whose pane he wrote in within the presence window (`telling.presence_here`, `[presence] minutes`, 30 by default; the one window, no second constant), whether or not the item names it. The line is the one the mover gets: a decision reads "answered", a comment, a note on his step and a Done read "commented on" or "did his step on". A front agent gets it as a held line through the front gate (`front_fyi`): it waits in the held store (`<state>/held`) and is handed over at the agent's next turn with the other held lines (oldest first, one line each, the store's own limits), it starts no turn and carries no mark. A front agent is never sent the plain push: where the gate cannot hold the line, nobody is told. That is the gate's own behavior for any such line, and this change adds no fallback of its own:
  - a front agent whose hook does not fetch held lines (a cloud session, an older checkout, an agent on a surface with no such hook, such as a Slack-surface front agent) is told nothing, and so is every front agent when `[router] hold_notices = false`; for those contacts the original gap stays, and the board's History line (below) is the record;
  - when the gate itself fails, or the roles cannot be read (the session is then taken for a front agent), nothing is sent either: the contact's History line says it was not told, and the routing log has the line.
  Only the item's contact leaves a History line on the item (`metadata.front_quiet`); a front agent of another project that he happens to be talking to keeps the routing-log line alone, so his History does not fill with other projects' agents. A contact that is a background agent gets the plain push the needs sessions get. A session that is both in needs (or the mover) and the contact, or the contact and also in conversation, is told once. A held line is cut at `held.LINE_MAX`: his words are cut and the item's link stays. The sessions told this way are not added to the pending answer (`<state>/answers.json`), so a write by the contact does not settle an answer the mover has not acted on. His comment written on the item's GitHub issue (the inbound mirror) keeps its own path, which reaches the mover and the needs only, not the contact.
- **After his answer the builder moves the item, not the front agent that filed or relayed it (unless that front agent holds the item's open step)** (`service/answer_handover.py` `_decision_hand_over`, `_builder_for_front`; `service/answer.py` `_answer`, `_answer_deliver`; `service/mover_steps.py` `_owner_then`; `tests/answer_scenario.py`, `tests/mover_writers_scenario.py`). When an item that waits for his decision, or for his step, stores no `then` and the first session in its needs is a front agent, a project that has a builder (a live background agent whose mandate builds, maintains, merges or engineers, the test a stored `then` passes: `_then_live`) hands the item to that builder at once: the builder is the mover and first in needs, `then` is cleared, and the front agent stays named in needs. A write that puts such an item on his move stores the builder as `then` at write time, and the reply's `(then <builder>: …)` note says so. The one exception is a front agent that is a live front agent of the item's project and holds the item's first open named step (the owner's own lines passed over, any letter case): it stays the mover, or becomes it when `needs` names no session, and is pushed the answer as the holder, so the write stores no `then` for it and the builder is not named (`answer_handover._front_step_holder`, `_builder_for_front`; `mover_steps._owner_then`; see [handoffs](handoffs.md)). The front agent's line is a held line (`_tell_aside`): it rides its next turn and starts none, and the answer is not on the pending record for it. A project with no builder (front-only) keeps today's path (the next open step's session, else the contact, with the front agent as the mover and the line pushed to it); so does a project whose builder cannot take the item (retired, unknown), and a `then` stored by a writer is left as written.
- **An update says when the item has moved under it** (`service/update.py` `_answered_since_note`; `service/telling.py` `touched_or_unknown`, `_writers_read`; `tests/answer_reach_scenario.py`). A write by a session to an item he answered (a pick, a comment, a Done or a note) that has not written to the item since his answer still applies; its reply (the `update` reply and the `complete` reply alike) carries one line, `(note: <his name> answered <item> on the board at <time>: <his words>. You have not written to the item since his answer, so what you hold of it may be out of date: read it again before you rely on it)`, with "commented on" in place of "answered" for anything but a decision and the time in the board's zone. The latest answer on the item is the one named. The server keeps no log of what a session read, so the signal is the session's own last write (`telling.touched_or_unknown`: the item's file and the store's git revisions since the answer, read before the write is saved). The line is left out, a missing line being better than a wrong one, for: a session the answer was handed to (the mover, the sessions in needs, the then-mover, and the contact and the front agents he was talking to when the line was actually filed or pushed to them; one the front gate could not file is not recorded and gets the line: their ids are kept on the answer's own record, `metadata.answers[].told`, written right after the delivery as a server save with no writer, so it holds for a decision, a comment, a Done and his comment on the item's GitHub issue (where the line says "on GitHub") alike, and whether the pending answer was settled by another session's write or dropped by the escalation); a session that wrote after his answer; an item he never answered; a write with no session behind it (the server's own, a script's); and whenever the history cannot be read in full. Known limits of the history: only the newest 60 revisions since the answer are read (more than that, no line); the store commits a burst of writes as one revision a few seconds after the first (`web/publish.py`), so a write that a later one overwrote inside that window is in no revision; a store outside git has no history at all, so only the last writer is known and no other session gets the line. Each answer costs one more server save, the one that records who it was handed to (a revision with no writer). The cost of the line is one item read and up to two git calls per update on an item that has ever been answered, inside the item lock (about 30 ms measured with 40 revisions); an item never answered costs nothing measurable.

- **A decision with no options is a yes/no** (`stackshot/model/decision_gates.py` `_gate_recommend_stance`, `stackshot/model/ask_read.py` `recommend_stance`, `recommend_not_stance`; `stackshot/audit/audit_checks.py` `check_ask_options`; `tests/decision_stance_scenario.py`, `tests/ask_options_audit_scenario.py`). With no options stored the item page draws Yes / No under the ask, so the ask must be a question those two answer. The open-question gate reads the Decide part for an English question word; a question in a noun phrase or another language passes it, and the page still drew Yes / No under "who joins and which topic". The write check reads the Recommend part instead, in any language: a needs=decision item with no options is refused (on a create, and on an update that sets the ask or the options or puts the item on his call, the writes the open-question gate already judges) unless its Recommend part opens with a yes or a no. The English words ship in `ask_read` (yes, no, yep, yeah, nope, ok, okay, agree, approve, accept, decline, reject, no-go, go ahead, go for it, go with it, hold off, hold on, and "go" or "hold" as the whole stance); an instance's own words go under `[keywords.ask_options] yes_no_words` (a `particles` suffix may follow one), so no other language's words are in this tree. A Recommend that names a person, a topic, a date or anything else is refused with the two ways out: put the choices as `options=[{label, line, recommended}]`, or make the Decide part a yes/no question with a Recommend of yes or no. Items with options, items that are no decision, a watcher's own ask and the question route are not read; an item already stored is not refused (only a write that sets the ask, the options or the decision). The audit's `ask-options` finding lists the open items on his move that sit in this state (no options, a Recommend that is no yes or no), so the ones written before the check are found; it goes the way the other `ask-options` findings go.
- **An option names who acts** (`stackshot/model/decision_gates.py` `_actor_note`, `_bare_pronoun`, `_OPT_PRONOUN_RX`; `tests/pilot_scenario.py`, the `actor:` checks). An option's label and its line (and the ask line) say who acts: a person or a session name, never "I", "you", "we" or "me" ("Flag, you approve" can be read as the session approving). Like the Recommend part that names no option (`_options_note`), it is a note at the end of the write's reply, never a refusal, and the write goes through. A label or line is flagged for a whole-word hit of I, I'm, I'll, I've, me, my, mine, myself, you, your, yours, yourself (and their contractions), and, in an option only, we, our, ours, ourselves, us, case aside; the ask line keeps the first list (no we, our, us) and its note always shows besides the option notes. The note is made only where the text is written: on a create, and on an update that sets the ask (the ask line is read) or the options (the options are read); a write that sets neither, and an item already stored, get none, and the audit does not read it. The note names the word and gives one example: "name who acts, e.g. <owner> unpublishes instead of I unpublish". One note per option (its label first, else its line), at most three. Words inside double quotes or backticks are a person's quoted words and are skipped; "usage", "mine-sweeper", "I/O", "i.e." and "US-EAST" are no hits, and an all-caps "US" is the abbreviation, not the pronoun, and a capital I that is a Roman numeral ("Phase I", "Type I", "Part I and II") is not the pronoun I. A word that opens right after a single quote, straight or curly, is skipped alike. English only. The tool text (the `options` and `ask` parameters and the shared item form) says the same.
- **A decision asks one question, and its answers are the options** (`stackshot/model/decision_gates.py` `_second_question`, `_SECOND_Q_RX`, `_gate_one_decision`; `tests/decision_ask_form_scenario.py`). A Decide part that joins a second question to the first ("approve the design, and say if a member may be read-only") is refused on a create and on an update that writes the ask, because the page draws one set of options (or a bare Yes / No) under both. Only the Decide part is read, with URLs, entities and quoted words masked. The rule is narrow on purpose, because a false refusal of a plain single decision costs more than a slip-through. A join counts only in these forms: a joiner (and, plus, then, but, also) with say or tell me / us followed by whether or if, or with decide, confirm, state, advise, specify, clarify or indicate followed by whether or if; `and`, `plus` or `as well as` before whether; `, and` or `, plus` before which, who or whom; `and, if so` and `and if so / yes / not / no` when the clause ends there (the end of the text, a `?`, `.` or `;`, or a question word after it); two question marks (each before whitespace or the end of the text, so `foo?.py` and `^a?b?` hold none) with a new question between them: a second question that opens with `or`, or is a bare list of options ("Use Postgres? Or SQLite?", "Merge the fix? Yes/No?"), is the first question's alternative and passes; a `;` followed by a space (the older rule). The text read is collapsed to single spaces and cut to its first 2,000 characters, and the curly-quote pattern is bounded, so the check takes linear time on any body. "Ship the login and signup pages", "whether A or B", "A and B together, or C", a bundled action ("retire the old queue and also move its jobs", "retire the old queue and also allow its jobs to drain", "merge the fix and also approve the follow-up PR"), a conditional ("merge now and, if the run is green, release tomorrow", "approve it and, if so, start Monday", "merge it now and if not, wait for CI", "ship the fix, and if it fails roll back") a message or a follow-up ("reply to Acme and say how long the fix takes", "email the customer and say what changed", "approve the spend and let me know when it lands", "ship it and tell me when it is done") and a later decision ("wait a day and then decide", "wait a day and then decide when to ship", "let the builder merge and confirm when it is live", "ship the fix and then state which version went out") pass: a comma after `if so` followed by anything but a question word is a condition on one decision, and "and also" before a verb is a bundled action, so neither is a rule. Known limits, left as they are: a second question put with an auxiliary verb and no join ("ship it, may a member read?"), an imperative that asks for another answer without whether or if ("and decide which lane", "and say which lane", "and let me know"), `and say whether` aimed at a third party ("reply to Acme and say whether the fix is live") is still read as a second question, "and also" before a verb that asks for another decision, the other design-like nouns (architecture, roadmap) and the other approving verbs ("agree to") are not read; two question marks stay refused when a new question sits between them ("ship it? may a member read?", "merge it? also should we rename the repo?"), and "??" or "? ?" is one emphasized question. The refusal names the two questions and says to ask the first now and put the other on its own item, or fold it into the options; the weekly refusal count files it under "an ask with a second question in its Decide part". An item already stored is not refused: only a write that sets the ask is read.
- **A decision on a design links it in the ask** (`stackshot/model/decision_gates.py` `_gate_design_link`, `_DESIGN_RX`, `_DESIGN_PART_RX`, `_LINK_RX`; `tests/decision_ask_form_scenario.py`). When the Decide part asks to approve or pick a design, plan, proposal, draft, spec, specification, migration (or decision, options, proposal, design, rollout, launch) package, RFC or options document (an approving verb such as approve, accept, adopt, sign off, pick, choose, select, decide on, go with, review or confirm, then a determiner and up to five modifiers before the noun, or "the six-part …"), the ask line itself must hold a markdown link or a bare http(s) URL. A link only in the description, a path on a machine or a summary does not count, because the owner opens the page from the question he answers. The matcher leaves out a noun that starts a compound (the noun followed by another plain word: "the design system rollout", "the design tokens update", "the spec change", "the spec sheet", "the proposal deadline", "the draft status"; only a preposition, conjunction, determiner, auxiliary or adverb after the noun, or nothing, leaves it a design: "the design in the link text", "the plan below"; a document-type word after design, plan, proposal, spec, specification, draft or rfc keeps it a design too: doc, document, page, file, text, notes, summary, outline, diagram, mockup, review, writeup, sketch, overview, section, update, version, revision, as in "the design doc", "the plan update", "the spec file", "the design review"), a plan that is a subscription or a payment (a service word before "plan": pro, max, free, team, enterprise, billing, api, paid, subscription, pricing, price, data, hosting, payment, support, storage, backup, phone, mobile, insurance, savings, retirement, service, cloud, monthly, annual, yearly, usage, credit, loan, ultra, team(s), starter, basic, standard, individual, personal, student, unlimited, prepaid, growth, developer, hobby, plus, flat-rate, metered, pay-as-you-go, cheap(er/est), premium, lite, a multiplier such as 20x; a plan followed by a colon and a list of options, "pick a plan: Pro or Max", or by "for the lane", "for this account", "for our team", "for each seat" or "for the machine" is a service plan too; it skips a plan only, so "the API design" and "the migration plan" still need a link), a software package (a bare "package" is no noun: "the package update", "the package for JSON parsing"; only a migration, decision, options, proposal, design, rollout or launch package is one), "package.json" and "package-lock", a draft of a thing ("draft PR", "draft pull request", "draft release", "draft email", "draft message"), "plan-A-only" (a hyphenated word is never the noun), "plan A", an ask that names no such thing ("restart the server tonight"), an item whose options name real alternatives (not Yes/No, not Approve/Decline), and a watcher's own ask. An ask already stored is skipped for an update of the priority, the description or next, but it is judged on an update of the options, on a resend of the same ask, and when the item is put on his call. A script's own question (the question route) is not read, because a script cannot add a link. The text read is cut and collapsed as above. Known limits, left as they are: "approve the API design plan" (a tier word before "plan" skips it), "approve the plan for the team" (read as a service plan), "the plan: Alpha or Beta" (a colon and a bare option list), the other design-like nouns and approving verbs, and an item stored before the rule keeps its ask. The refusal reads "Link the <noun> in the ask: a page <owner> can open, not a path on a machine or a summary" and shows the link shape; the ask is at most 240 characters, so a short link text (`[design](https://…)`) keeps room. The weekly refusal count files it under "an ask that approves a design or plan with no link in the ask".
- **A decision's link is a short decision page, never a long page the instance lists** (`stackshot/model/decision_gates.py` `_gate_ask_links`, `long_link_hit`, `long_link_refusal`, called by `_gate_ask` in `stackshot/service/asks.py` and `_gate_options` in `stackshot/service/wait_gates.py`, and on the ask a client with no `ask` parameter writes as the first line of `next`; `tests/ask_long_link_scenario.py`). The owner decides from the page the ask links, and a link to a long project or notes page cannot be read as a decision. The config key `[ask] refuse_link_prefixes` (default `[]`: nothing is refused; read at each write, so a reload is live; see [configuration](configuration.md)) lists URL prefixes of such pages. A create or an update that SETS an ask, or options, holding a link that starts with a listed prefix is refused; an ask or option already stored is never judged until a call rewrites it, and an update that sets neither is untouched. A link is a bare `http(s)` address or the address inside a `[words](url)` link. The scheme and the host match in any case, `http` and `https` alike, a default port is dropped, the path matches as written, a `/tree/` page and its `/blob/` form are one page, and a fragment is ignored; a prefix with no path means its host, and a prefix that does not end with `/` ends at a path segment (the prefix of one page does not take a page whose name only starts the same). The ask is judged before its shape, since the shape refusal would hand the link back in the corrected ask. The refusal says the link goes to a long page, not a decision page, and to link a short decision page made for this decision (an artifact, a document, or a mockup page from the web UI) with the decision, its choices and what is at stake on it; the long page stays on the project page. An option that holds such a link is refused with the same words (any other link in an option stays refused as before, and a mockup link goes in the ask).
- **A new option label never opens with a lone letter** (`stackshot/model/option_labels.py` `lone_letter_lead`, the gate `_gate_options` in `stackshot/service/wait_gates.py`; `tests/option_label_letter_scenario.py`). The board letters three or more options A, B, C by place in the stored order, so a label with a letter of its own ("B: strip", "A · Beta") can cross the board's: the same option would read as A on its card and B in its label. The write is refused (on a create, and on an update that passes `options`; options already stored are never re-read, and an update that passes none is never refused) when the label opens with a letter of either case, the articles A and I included, that is the whole label or is followed by `:`, `)`, a middle dot, a full stop, an em dash or a spaced hyphen or en dash, or is in parentheses; when it opens with one of the fourteen Hangul list syllables (ga, na, da, ra, ma, ba, sa, a, ja, cha, ka, ta, pa, ha) then one of the endings above, or in parentheses (any other one-syllable word, such as yes or no, is a word); after Option, Choice, Design, Mockup, Variant, Alt, Alternative, Version, Layout or Style, when a lone letter follows (a capital before any text, a lower-case letter only with the endings above, so "Design a strip" passes); and after Plan, when a letter is followed by one of the endings ("Plan B: x"; "Plan B" is a name). A letter then a plain word is a word, not a marker: "A one-line strip", "I think so", "B full panel", "X Corp", "V plan" and a letter then a Hangul word pass, spaced or not alike, and so do "X-ray", "A-frame", "U.S. plan" and "B2B". The refusal says the board letters the options by place in the list the session gives, and to name a mockup's designs by name. The cold call's rubric (`stackshot/model/cold_call.py`) tells its model a label carries no letter, since its options go through the same gate.

- **The answer box never refuses a note** (`service/answer.py` `_answer`, `service/answer_handover.py` `_keep_note`, `stackshot/waits/watchers.py` `parse_date`, `_relative_date`, `ask_back`; `tests/answer_scenario.py`, `tests/watchers_scenario.py`). What a person types in the box is not expected to be well formed, so the board interprets it or keeps it and asks back; it does not drop it. (1) A note he sends on a **closed** item, or with a pick that no longer fits the question (**stale**: the options or needs changed), is written on the item as his comment first (with the pick named in front when he sent one: "(the item is closed: <pick>)", "(late, the item no longer asks this: <pick>)"); a second send of the same thing within ten minutes (a double click, which for a pick with a note is first recorded as the decision) is a no-op (nothing is written and nobody is told again; only the first write is told to the mover, like any comment); the page says so for the first send and the repeat alike (`closednote`, `stalenote`). With **no note** nothing is written on either (`closed`, `stale`): a bare pick on a question that changed is not an answer to the new one. An empty box with no pick (`empty`), a step he has none of (`nostep`) and a text over 4000 characters (`toolong`) still write nothing, and so do the 403 and 413 checks of the route. (2) The date reader on a date button ("not yet, ask again on <date>", "keep waiting until <date>") reads, besides the dates it always read, a small table of relative phrases with no model call: a week, one week, another week, one more week, two weeks, a fortnight, N days, N weeks, a month, next month, N months, in a month, "a month from now", end of the week (the Friday), end of the month, after the weekend. The table is read **last**, only when no older reader (an explicit date, tomorrow, next week, in N days, a weekday) found a date, and only for a note that is mostly a date phrase: the phrase is the whole note, at its start, or right after a cue word (for, after, wait, give it, ask again, ask me, remind me, check back, park it, snooze it, again, until; "in a week" is a phrase like any other, not a cue); it is not part of a hyphenated word and not followed by ago, already, report, before or earlier; a bare "a day" or "one day" is an idiom, not a span; of two phrases the first in the text counts. A span counts from today; "more" and "another" count from the date the wait already ended on, when it is after today (and from today when that date has passed). (3) When no date can be read, the note is kept as his comment, **no date is set**, and the item stays his: its ask becomes `Decide: when should <what> come back? I kept your note (...) but could not read a date from it. Pick a day, or write a date in the box`, with the first question's own buttons again, which carry three days counted from today (a week, two weeks, a month; `Ask again on Tue Nov 17th`; the first question has them from the start, `watchers.date_options`, and no button of either is marked recommended); each day button stores its ISO day (`date` on the option) and a pick is read from that, never from the label, so a pick that comes after its day has passed is asked again with new days, not rolled to next year. A date typed in the box still wins. The page's notice for that answer is `askedback`.
- **The answer box of the board** (`stackshot/web/ui/render.py` `_cards_html`, `_CARDS_CSS`, `_CARDS_JS`, `Board.answer_html`, `Board.home_ask`; `stackshot/web/answers.py` `_split_letter`; `tests/board_pages_scenario.py` section 2b). On an open decision the item page and each Your move row on the home draw **one card per option**, a radio input styled as a card (`name=choice`, so the form posts the field it always did and works with the script off), showing the option's label, the orange *recommended* badge on the recommended option and nothing else for it, and the option's **whole text** (the one-line cut and the per-option button are gone). The server takes the lettered value (`_split_letter`: the letter must be the label's stored place among three or more options, tried before a bare-label match, else the answer reads as stale; on an item that links a mockup the letter is read but not recorded beside the name): `metadata.answers[].choice` stays the bare label, the letter is kept beside it as `letter`, and History, the saved note and the notices read `B · <label>`.
