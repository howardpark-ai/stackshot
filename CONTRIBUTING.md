# How stackshot is changed

`main` is production: the services on the server box run from a checkout of `main`, and `deploy.sh` there is how a merge
becomes live. Nobody commits to `main` directly; nobody works in the production checkout.

## The branch model

1. **A change starts on a branch in its own worktree**, named `<kind>/<short-topic>` (see *Commit and PR text* below):
   `git worktree add ../stackshot-<topic> -b <kind>/<short-topic>` (for example `fix/handoff-row-wrap`).
   Each agent of the project works in its own worktree, so two agents never share a working tree.
2. **Before the PR, run the suites that cover what you changed; CI runs the ones the change reaches, and main runs them all** (builders stop rerunning everything locally, to spare the host's CPU). Locally that is `tests/run-suite <name>` for each suite whose code your change touches, plus the suite that holds the check a change to behaviour comes with. On the PR, CI runs the suites the change reaches by the measured map (see *Suite selection* below; the job summary says which and why), and a PR merges only when it is green there; after the merge, main runs every suite. To run everything by hand when you want to (not a required step): `for f in tests/*_scenario.py; do t=${f#tests/}; tests/run-suite "${t%_scenario.py}"; done`.
   `tests/run-suite` runs a suite in the one shared test environment (see Dependencies), not a new one per worktree.
   **A change to the pages' markup or style also runs the manual phone-width check**, `tests/run-suite phone_width_check`
   (a browser: once per machine, `uvx playwright@1.63.0 install chromium`; CI's runner has none, so it is not in the loop): the board,
   a project page and an item page are the screen's width at 360 to 430 px with every fold open, in light and dark, and the root
   paints each theme's background.
   **A change to the item page's answer box** also runs `tests/run-suite answer_back_check` (the same browser): it starts
   the server in-process on a temporary config and checks that an answer replaces the page in history and Back lands on the board.
   **A change to the home page's answer forms** also runs `tests/run-suite home_step_send_check` (the same browser): it checks that a step row's Send is enabled with the box empty and after typing, and that a decision row's Send stays disabled until a card is picked or a note is typed. **A change to the answer forms or to the home page's live refresh** also runs `tests/run-suite decision_pick_check` (the same browser): a picked card always reaches the item with its note, across a refresh that passes between the pick and Send.
3. **Open a PR against `main`.** The description says what changes for whom (a session, the owner, a machine) and which unit a deploy restarts, in plain engineering terms (see *Commit and PR text* below). Anything a session creates on GitHub is anchored on the board in the same turn.
4. **The builder (`my-engineer`) reviews, merges and releases it** (one agent releases; with several builders, the others send it reviewed PRs to release). Before the merge a fresh Sonnet reviewer subagent reads the PR, the diff and this section's checks, and answers approve or findings; the builder fixes the findings or says why not, and merges only on an approve. A small change goes on CI alone, with no reviewer read. Then one command on the server box, `~/stackshot/release.sh <pr>`. It runs detached (a transient user unit) and goes through these steps. **Two merge queues**: `release.sh` can hand a PR to either of two. GitHub's merge queue is the default and is what the steps below describe. salamander's own merge queue (`salamander mq`, called the salamander merge queue here) is used when the host mergequeue file for this repo says `mode = "on"` and names this script's deploy lock (`deploy_lock = "<paths.state>/releases/deploy.lock"`; without it the release stops at `mq mode` before anything is merged, so the queue's merge push can never overlap a deploy). Mode off, mode shadow, no host file and a file that does not read all mean GitHub's queue (the log says which), and `release.sh` never edits the host file. The mode is read at the start of each release and each time the release queue starts something, so a change of the file applies to the next release. In mode on, one PR alone is released by the steps below with no call to `salamander mq` (it is merged at once by the plain merge call while the ruleset's queue is off, which is the setting mode on goes with; the ruleset's queue still decides when it is on), and two or more PRs go to the salamander queue as one group, `release.sh --group N N...` (at most 4; the unit `stackshot-release-<first PR>` runs `--run-group`): one `salamander mq add`, one `salamander mq wait` per PR, then one deploy of what the queue merged through the same deploy gate, deploy, session pick, report and main's run as below, with a `done:` line and a report for each merged PR. A PR the queue ejects or fails is reported as a failed release of its own and the others go out. A failure of the queue itself (an error, a pause, a block, no verdict within `RELEASE_MQ_WAIT_CAP`, 5 hours) drops the PRs still open from the queue and pauses the release queue; what the queue merged before is deployed all the same. A PR a group handed to the salamander queue has a marker in `<paths.state>/releases/mq-on/` that keeps a lone release from merging it (`FAILED at mq line`), in every mode: a host file changed to off mid-group does not take the PR out of the salamander queue, and the release queue does not start such a PR alone either. Mode on also refuses (`FAILED at mq mode`) while GitHub's own merge queue is on for `main`, so two queues never merge into it, and the release queue starts nothing while a group release it handed over is still running. **Checks**: it waits for the PR's checks (a failed check ends the release at `checks`). **Enqueue**: one GraphQL read decides how the PR goes in, `repository.mergeQueue(branch:"main")`. With the queue on, the PR goes into it with the mutation `enqueuePullRequest(pullRequestId, expectedHeadOid)`, pinned to the head the checks ran on, so a push after the checks cannot ride in; `gh pr merge` is not used then, because with a queue on it asks for auto-merge, which the repository does not allow ([cli/cli#13398](https://github.com/cli/cli/issues/13398)). The branch ruleset on `main` requires the merge queue: GitHub builds each entry on main's tip and on the entries ahead of it, runs the `suites` check on exactly that tree (the workflow's `merge_group` trigger) and merges it, so what lands on main is what was tested; a failing entry is removed and the entries behind it are rebuilt. With the ruleset active nothing pushes to `main` directly. The repository does not allow auto-merge, so the release waits for green checks before it asks. With the ruleset off (a rollback of the setting) there is no queue to read: the release runs `gh pr merge --merge --admin --match-head-commit <head>` (`--admin` because, with the bot-only ruleset active and main not excluded from it, a green PR reads BLOCKED and the plain call fails with "the base branch policy prohibits the merge"; GitHub still refuses a failing or pending PR with it), which merges at once, the log says the PR was merged without the queue, and the deploy waits for main's tests (below), because no merge-group run tested that merge. **Wait for the merge**: it reads `pullRequest { state mergeCommit { oid } mergeQueueEntry { state position } }` through GraphQL every 60 s (`RELEASE_POLL_QUEUE`) for up to 3 hours (`RELEASE_QUEUE_WAIT`), and the log says where the PR stands every 5 minutes. A PR that was in the queue and is gone without being merged (confirmed by a second read, then three more reads for MERGED, 10 s apart: a merged PR is never reported as removed) fails the release at `merge queue` before any deploy, with the reason GitHub gave (the timeline's `RemovedFromMergeQueueEvent` dated at or after the enqueue; an older event belongs to an earlier enqueue of the PR; GitHub's values `failed_checks`, `merge_conflict`, `manual` and `branch_protection_failure` are said in words, and `merged` is the merge itself, not a failure: the PR is read again until it shows merged). A refused enqueue (a red required check, a ref rule) fails the release at `merge` with GitHub's message, after the PR is read again; a queued release goes on with the others. **A rerun on a PR that is merged already** (an earlier release was killed, or gave up after the 3 hours, and GitHub merged the PR later) carries on from the merge: it reads the merge commit and goes to the deploy gate, the deploy, main's run, the last-good record and the report. Nothing says that merge came through the queue, so the gate is closed for it and the deploy waits for main's tests. The head branch is deleted best-effort once the PR is merged, after the open PRs based on it are retargeted to main. The CLI cannot take a PR out of the merge queue: to stop one, remove it on the PR's page. **Deploy gate**: GitHub's merge queue ran the suites its selection picked for the merge group on the tree it made (a `merge_group` run, which is not every suite), so the deploy goes ahead at once only when the queue made the merge and what lies between the live checkout and the merge is not known to be bad. A merge made by the plain merge call (the ruleset off), or found already merged by a rerun, closes the gate. Otherwise it needs (a) the live checkout to be an ancestor of the merge (`deploy.sh` fast-forwards), (b) a readable last-good commit to go back to (below) that is in the live history, and (c) no failed main run on any commit after the last good one, up to main's tip (a later member of the same merge group counts), read from GitHub's list of runs page after page until a run at or before the last good commit (an empty answer, a failed call, a list that never reaches it, or a run in the range cancelled after its job started is unknown and closes the gate; a run still pending is fine: back-to-back releases both deploy at once, and a failure of the first rolls both back). **Gate open**: `release.sh` runs `deploy.sh` on the merge commit, so a merge reaches the live site within a couple of minutes (install changed units, restart the services the change touched, check `/healthz`), flags the `--recycle` and reports once, and only then waits for the tests run on `main` that covers that commit (a PR runs only the suites its change reaches, main runs them all: see Suite selection; which run covers it: *Which run covers a merge*, below). A pass is a log line, `main's tests passed on <sha>`, and the commit becomes the last good one (`<paths.state>/releases/last-good`; the first time, the deployed `HEAD` when its run on main passed), after a check under the deploy lock that it is still in the live checkout (a rollback cannot land between the check and the record). **Gate closed** (a merge the queue did not make, a failed or unreadable run since the last good commit, as after a rollback, no readable last-good commit, a paused release queue, or a checkout that cannot fast-forward to the merge): the release waits for the run on main that covers the merge before it deploys, with the reason in the log, and deploys the newest commit containing the merge whose run passed; a run that fails stops it merged and not deployed. **Already live**: when the live checkout contains the merge (a later release deployed past it, or `deploy.sh` was run by hand) there is nothing to deploy; the report says so and main's run for the merge is watched as after a deploy. Just before `deploy.sh` runs (production changes at its fast-forward, and restarts and healthz take up to 180 s) a pending-verify record (commit, PR, time) goes under `<paths.state>/releases/pending-verify/`, its flock held by the running release and the record removed when the watch concludes; a release killed in between leaves it with the lock free, and **the next release to start reads that commit's main run first**: a pass is recorded, a failure rolls back and reports red for that PR as a live watch would, a run cancelled counts for nothing (*Which run covers a merge*, below), and one still going, or not found yet, or unreadable keeps the record and closes the gate until it is read (after two hours it is unknown: a red report). A rollback that never ran (the deploy lock not had) keeps its record. A failed deploy clears the record with its red report. Every external command runs without the lock file descriptors, so a child that outlives it holds no lock. A failure **rolls the deploy back**: `deploy.sh` with `DEPLOY_ROLLBACK=1 DEPLOY_TO=<last good>`, the only way `deploy.sh` goes backward. It is refused unless the deploy lock is held (by hand: `flock <paths.state>/releases/deploy.lock env DEPLOY_ROLLBACK=1 DEPLOY_TO=<sha> ./deploy.sh`), the checkout has no changed tracked file (staged or not) and no untracked file at a path the target tracks (an untracked file elsewhere, such as `.claude/`, is no matter), and is at a commit on `origin/main`, and the target is older and has a `deploy.sh` that knows the second step; it resets the checkout to the target and runs the target's own `deploy.sh`, so the good tree's units, restarts and health check do the work. The builder hears `FAILED at main's tests: rolled back to <sha>`, which names the merges the failing run covers when it covers several, the unit and timer files the rolled-back commits added (left installed: disable by hand if needed), whether a recycle had been flagged, and that **a rollback does not undo data or state changes the commits made**. Every other merge between the last good commit and the live checkout is taken out too, those deployed before the failing one (their runs still waiting) as well as those on top: each PR gets its own message ("rolled back with #A's failure; it is merged but not live; it goes live with the next release once main is fixed, or ./deploy.sh once main's tip run is green"), and its own run says "passed, but not live" when it ends (checked with git: the merge must be in the live checkout; a marker alone is not relied on, and such a run does not become the last good commit). A failed `deploy.sh` (healthz, say) is reported red and not rolled back: the rollback is for main's run failing. It rolls back only while the live checkout still contains the failing commit and no newer commit whose main run passed contains it; otherwise the report says it did not. `release.sh` ends every arm of its dispatch in an explicit `exit`, because a deploy replaces the file under the running script. A run that cannot be read in the time allowed (no covering run passed or failed; a cancelled run counts as none), is reported, not rolled back (check by hand). Main keeps the failing merge: fix forward or revert. It reports once to `projects/example` as a `[release]` message — green with the commit and what restarted, or red with the step that failed and the log. A green one is logged, not delivered: the server rules it merged as `stackshot (auto)`, comments on the items anchored to the PR, and leaves it on the project's routing page. A red one is delivered to `projects/example`, where the router rules it and passes the failure to the agent whose files it touches. `release.sh --status` shows a run; `deploy.sh --dry-run` shows what a deploy would restart.
   **A change no test can exercise merges at once, without `release.sh`**: docs, Markdown, comment-only lines, and a CI workflow's runner and concurrency settings. The builder runs the docs-merge script (the path in `[paths] docs_merge_script`) as `docs-merge.sh howardpark-ai/stackshot <pr>`, a dry run first (`--dry-run`). The script checks the diff line by line, pins the head commit and merges, or refuses with `REFUSED: <file>:<line>` lines and exit 3, which means "use `release.sh`". It merges without deploying: the production checkout picks the change up at the next release's fast-forward, and nothing a docs-only change touches is read by a running service. Every other change takes `release.sh`. **While the ruleset is active the script cannot do this**: it merges with `gh pr merge --delete-branch`, which GitHub refuses on a branch with the merge queue on, so `docs-merge.sh` has to change (it lives in the config repo, not here, and is not changed in this repository), and once the ruleset is active a docs PR goes through the merge queue like any other PR.
   **A branch behind main is not touched**: either merge queue builds each entry on main's tip, so a PR that is behind main needs no update, no catch-up rounds and no retest. One conflict is mended instead of failed: when two PRs both change tool text, merging main conflicts on `tests/tool_text.snapshot.json`, a generated file, and on nothing else (releases failed on it). When the first look at the PR says CONFLICTING, or GitHub removed the PR from the merge queue and the PR conflicts with main now, `release.sh` runs `tools/snapshot_regen.py`, which merges main into the PR head in a temporary worktree of its own (removed on every way out, locked with `flock` while it runs), and if the conflicted paths are exactly the snapshot takes main's copy, runs `python3 tools/tool_text.py update` and `check`, commits the merge and pushes it to the PR branch with a plain `git push` (never forced, so a branch its author pushed to meanwhile is refused), logs one line saying so, waits for the PR's tests on the new head (the `suites` check completed and successful on that very commit) and enqueues the PR again. It makes no GitHub API call: only git's own transport, after the `refs/pull/N/head` fetch it already does. At most `RELEASE_REGEN_MAX` (default 1) regeneration per release run. Any other conflicted path, a regeneration that fails, a push that is refused or a PR from a fork declines the mend and the release fails at `mergeable` (or `merge queue`) with the reason in the log. `release.sh --status <pr>` shows the log's tail, whose newest line says what is waited for.
   **Which run covers a merge** (after several PRs merged within minutes of each other and releases failed at their time limit): main's workflow runs one run at a time and cancels a queued run when a newer push arrives, so the run on a release's merge commit M can be cancelled while a later run, on a commit that contains M, is the one that tests it. Waiting for the run on main's tip meant waiting behind a long run, although a run on the merge or a later commit had passed. So M is covered by a main push run on M or on any later commit C that contains it (`git merge-base --is-ancestor M C`), and the runs are read oldest first, a cancelled one skipped, up to the first that has not passed: one still queued or going is waited for; the newest run that passed before it satisfies the release, which deploys to that run's commit (`DEPLOY_TO=<C>`); a run that failed ends the release as before, with this exception: when a run on M's own commit, or on a commit between M and the failing one, passed, the failure belongs to a later commit and the pass decides, so the release is judged by the oldest commit that failed, and the log says whose run decided. The 90-minute limit (`RELEASE_WAIT_MAIN`; a slow run on a loaded host could otherwise end a release) counts from when a covering run starts (in progress), not from the merge, and starts again for another run that starts; an outer cap of 3 hours from the merge (`RELEASE_CAP_MAIN`) keeps a release from waiting forever; the log line of a wait that gave up names both. The same rule serves the watch after a deploy: a cancelled run on its own merge no longer ends in `unknown` when a later run containing it passes; only cancelled runs and nothing else is `unknown` after the cap, and still never a rollback. **Step results**: GitHub fills in a job's step results some time after the run reports completed, and a release read main's run in that gap and failed a green run. A run that is completed and green whose `run every suite, measured` step has no conclusion yet is pending, read again at the next poll for `RELEASE_WAIT_STEPS` (600 s) at most; past it, a run whose own conclusion is success counts as green (the job succeeded, only GitHub's step list is missing): the log gets a `WARNING` line, the report goes to the keeper instead of green, and nothing is rolled back (a green main was once rolled back on this gap). A run that concluded failure, or whose suites step concluded anything but success, fails at once as before.
   **Two releases never deploy at the same time**: the deploy runs under an exclusive lock, `<paths.state>/releases/deploy.lock`, waited for up to 15 minutes (a release that cannot get it in that time fails at `deploy lock`: merged, not deployed; `./deploy.sh` by hand once it is free). The waits for GitHub (the PR's checks, the merge queue) happen before and outside the lock, so no release waits for another release's CI, only for a deploy that is running, which takes seconds to a few minutes (the health check alone waits up to 3 minutes). The lock is let go while the release waits for main's tests run (after a deploy, or before a gate-closed deploy) and taken again for the deploy or the rollback, so a release waiting on main never holds another one's deploy; it is released when `deploy.sh` returns. It is taken by `release.sh`; `deploy.sh` run by hand takes none. Every enqueue is pinned to the head the checks ran on (`expectedHeadOid`; `--match-head-commit` for the plain merge), so a push after the checks cannot ride in.
   **How a session runs it:** one plain `release.sh N` per command (it starts its own unit and returns at once). Wait for its log, `<state>/releases/pr-N.log`, for a line with ` done: ` or ` FAILED `, in a `run_in_background` shell with `timeout`. Never chain waiters that start the next release when the previous log says done: a failed step stops every later one with no report. Auto mode also refuses a loop of `release.sh` runs.
   **Several PRs go in the release queue**: GitHub's merge queue tests PRs together only when they reach it together, so `release.sh queue N [N...]` records the PR numbers in order in `<paths.state>/releases/queue` (a PR queued already keeps its place) and **starts every waiting PR's release at once**, as `release.sh N`, at most 4 running at a time (`START_MAX` in the script; a PR added while four run waits). `release.sh queue` first reads the PR's check rows and refuses a PR with a failing, cancelled or timed-out row (exit 1, each such row printed with its state and link, nothing queued), and a PR whose rows cannot be read; pending and skipped rows do not refuse, and there is no bypass. The releases enqueue their PRs in GitHub's merge queue together; the deploy lock serializes their deploys. A release started by the queue is marked in `<paths.state>/releases/queue.started` and stays in the queue file until it reaches *deployed* (the deploy and its report are done and it only waits on main's run); then it leaves the queue and the next waiting PRs start, up to the cap. A queued PR that fails before its merge (its checks fail, it conflicts, it is closed, GitHub removes it from the merge queue, a lock is not had) is reported exactly as such a failure is reported, and skipped: the queue goes on, and its red report says "skipped in the release queue". A failure after the merge of a release **the queue started** (main's run failing for it: merged and not deployed, or rolled back after a deploy; its deploy failing) **pauses the queue** (`<paths.state>/releases/queue.paused`, with the PR and the step): no new release starts, the rollback and the red report run as before and say the queue is paused, and `release.sh queue --resume` goes on once main is fixed. A plain `release.sh N` that fails writes no pause. The pause is written before the deploy lock is let go (a rollback writes it first thing, a failed deploy before it releases the lock), so a release waiting for that lock finds it when it gets the lock. A pause also stops a release the queue had started but not yet enqueued: after its checks pass and again before it enqueues, it fails at `queue paused` as a failure before the merge, with no hand-off, and stays first in the queue, so `--resume` releases it. A release the queue started that finds the queue paused when it takes the deploy lock (a rollback paused it while the release waited: a late member of the same merge group) does not deploy: the PR is merged, so it fails at `queue paused` as merged and not deployed and leaves the queue, and the next release's deploy carries it once main is fixed. A paused queue also closes the deploy gate of every release, so a release started by hand waits for main's tests. A PR already in GitHub's merge queue is not stopped (the CLI cannot remove it). The PRs a rollback took out with the failed one (releases deployed on top, or before it with their runs still waiting) are merged and stay on main, so they are not queued again (`release.sh N` on a merged PR carries on from the merge, which deploys nothing new once the rollback has taken them out): the red report and `queue.log` name them ("rolled back with it, merged and not live"), and the next release's deploy carries them once main is green (or `./deploy.sh` once main's tip run is green). A main run that cannot be read in time is not a failure and does not pause the queue. `release.sh queue --list` shows the queue in order with each PR running, waiting, or started but not running, and the pause; `release.sh queue --drop N` takes a PR out (a release already started is not stopped). A killed release is still in the queue file, so `queue --list` shows it and `queue --resume` starts it again (one already merged then carries on from the merge). A queued release picks what the sessions need from its PR's files, as any release does. **With the salamander merge queue on** (host file `mode = "on"`) the release queue starts one thing at a time and routes by count: one PR waiting is released alone (`release.sh N`), two or more (at most 4) go as one group (`release.sh --group`, the first PR marked in `queue.started`, the others not), and nothing else starts until that release is deployed, when the group's PRs leave the queue file and the next waiting ones start. `queue --drop` of a PR the salamander queue holds is refused and names the `salamander mq drop N` to run. With GitHub's queue, the default, it is as described above. Every change to the queue is made under flock on `queue.lock` and logged to `queue.log`. When GitHub says the PR's `mergeable` is UNKNOWN (it recomputes for a while after main moves), the release reads it again every 10 s for up to 3 minutes; only CONFLICTING, or UNKNOWN past that, fails it at `mergeable` (a CONFLICTING that is only the tool-text snapshot is mended first, as described above).
   `release.sh` picks what the running sessions need from the files the PR changed (the map is `session_need` in `release.sh`, the table [docs/session-reload.md](docs/session-reload.md)): nothing, a notice (`[fleet] notice_cmd`, when set) or a recycle, which only a file a session loads once at its start (the SessionStart hook) needs; then the open items anchored to the PR wait for a recycle. A recycle is never an item of its own; with no item anchored, the fleet tool is asked for one once the box is idle (`[fleet] recycle_when_idle`, when set). `release.sh <pr> --recycle` forces a recycle and `--no-recycle` forces nothing; `release.sh --pick <pr>` shows the pick first. A change to a tool or its parameters is a notice, not a recycle: claude.ai refreshes its cached tool list on its own within about a day, and until then a session closes or calls the new form through the MCP Portal's Code Mode.
5. **A minor fix** that restores intended behaviour with no design choice in it is the builder's to make, on a branch like any other change, the owning agent told, and a small one goes on CI alone. Anything with a design choice is the agent's PR.

## Branch names carry the builder

A branch is now named `<kind>/<short-topic>` (step 1 above, and *Commit and PR text* below), which carries no agent name; the rest of this section describes the routing by an agent-named prefix, which applies only to a branch that still has one. The router reads the head branch of a pull request that anchor-hub reports (a CI result,
a comment, a merge) and, when the prefix before the first slash is a background agent's name, passes the notice to that builder (router rule `anchor-builder`) and not to the item's
front mover. A branch named `<kind>/<short-topic>` is of any other shape here; a branch of any other shape (a person's, `main`, a subagent's
`worktree-agent-…`) routes as before, except that a CI result on any pull request, whoever's branch it is, goes to the project's builder too (router rule `anchor-ci`), never to a front agent. A builder's report on an item is written onto the item, not messaged to a front agent (the `message` tool; docs/board-and-connector.md, tool table);
a hand-back to a front agent mover is held three minutes and dropped when the item is closed in that time (docs/handoffs.md, *A front agent mover hears of its item at two moments only*).

## Commit and PR text

Commit messages, branch names, PR titles and PR bodies in this repository carry none of the instance owner's data: no board item ids, no owner or
colleague names, no machine names, no session or agent names, nothing about the one live instance. A change explains itself in plain
engineering terms: what it does, why, and what a reader of the diff needs to know. The link between a PR and a board item is kept outside git, on the board and in the
project's notes.

- **Branch names** are `<kind>/<short-topic>`, with `<kind>` one of `feat`, `fix`, `docs`, `ci`, `refactor`, `test`, `chore` (for example `fix/handoff-row-wrap`).
- **No attribution lines, no session links.** A commit message, a PR title and a PR body carry no `Co-Authored-By:` trailer (of any author, an AI assistant's included), no `Claude-Session:` trailer, no session URL (any claude.ai or claude.com URL that holds `session_`, and the claude.ai code-session path whatever its port, trailing dot, doubled slash or `%XX` spelling) and no "Generated with/by/using Claude" footer or link: any line that, once its markup, links, HTML tags and emoji are stripped, starts "Generated with", "Generated by" or "Generated using" and names Claude, plus "Generated with Claude Code" inside a longer line and the product's link (a sentence that only says something was generated with Claude, such as "Numbers generated with Claude 3 are not comparable", is not a footer and passes). A push to a public repository cannot be taken back, and GitHub keeps every pull request ref, so a line like that stays public for good; credit and context belong in the PR description in plain words. These are patterns of `tools/clean_text.py` of their own, so they hold with or without a deny list, and a line that hits is refused whole, with no exemption; the check names the kind of hit and the line number and does not repeat the line (the pull request's title and body are public anyway, and the workflow step's environment header prints them, so this keeps the check's own output short; it does not hide the text). A `Co-Authored-By:` trailer is read at the start of a line (after any quote or list mark: a bullet, `>`, `1.`, `1)`); prose that only names the trailer is not. The first line of a standard merge commit ("Merge branch 'main' into …", `git pull`'s "Merge branch '…' of … into …", "Merge pull request #N from …") is skipped for the deny list, but the branch names in it are checked like a branch name and the attribution patterns still read the whole subject; the owner and the URL in it are not read against the deny list. Only the commits a pull request adds are read in CI, so older commits on `main` that carry such lines are not rewritten and fail nothing. The one exception is a push that has to walk all history (see the hooks below): four commits already on `main` hold a `Co-Authored-By:` line from before this rule, and `ATTRIBUTION_EXEMPT_SHAS` in `tools/clean_text.py` names exactly those four by full sha, exempt from these attribution patterns only (the deny list and every other pattern still read them). No new commit can join that set.
- **CI enforces it** (`.github/workflows/clean-text.yml`, on every pull request, again when its title or body is edited): `tools/clean_text.py` reads the PR title, body, head branch and the message of every commit the PR adds
  to its base. It looks for board item ids (`board#N` anywhere in a word, so `_board#N` and `xboard#N` count and so does `dashboard#N`; `board-tmp-<name>#N`, the name made of letters, digits and hyphens) and links to a `https://<host>/items/<n>` path, for the attribution lines above, and for the words on a deny list. The deny list is the owner's data, so it is not in the
  repository: it is the repository secret `CLEAN_TEXT_DENY` (one case-insensitive Python regex per line), given to the one step that runs the script. It is a secret and not a variable because the runner prints a step's variables in the log and masks only secrets. Where there is no secret (empty, unset, or a pull request from a fork) only the generic patterns run, and the log says the deny list was not available. A failure prints the field, the line number and, for a board-id pattern, the offending line; an attribution hit prints its kind and line number only; a deny pattern is named by its line number in the secret (`deny pattern 3`) and neither it nor the line it hit is printed.
- **Text is refused before the push, not only after it** (a push to a public repository publishes what it carries; CI is the backstop). The tracked hooks in `.githooks/` do it: `commit-msg` refuses a commit whose message hits, and
  `pre-push` refuses a push whose branch name or new commit messages hit (for each pushed ref, the commits the remote being pushed to does not have yet; a branch delete is skipped). Only that remote counts: a commit that sits on another
  remote's tracking branch, a private one for instance, is not published by this push and is checked. A push by a URL is matched to the configured remote that has the URL; a URL no remote has, and a remote with no tracking branch yet, is checked against all history (more, not less; the four old commits named in `ATTRIBUTION_EXEMPT_SHAS` pass the attribution patterns there, as the first bullet above says, and nothing else does).
  `commit-msg` reads every line of the message, `#` lines included (`git commit -m` keeps them); it leaves out only what git itself writes into the editor template: everything below the scissors line of `commit -v`, and the
  `# On branch X`, `# HEAD detached …` and `# Your branch …` status lines. A clone turns the hooks on once, and git changes nothing by itself:

  ```
  git config core.hooksPath .githooks
  ```

  Setting `core.hooksPath` replaces a machine-wide hook directory, so each of the two hooks also runs the machine-wide hook of the same name, with the same arguments (and, for `pre-push`, the same standard input), when one is installed and executable, and skip it otherwise (the `chain-global` helper beside them looks in the user's global `core.hooksPath` first, then in `${XDG_CONFIG_HOME:-$HOME/.config}/git/hooks`). Both run, so every refusal shows, and the commit or push is refused if either refuses.

  They are POSIX `sh`, need `python3` on `PATH`, and work from a linked worktree (the setting is per clone and every worktree of it shares it). `git commit --no-verify` and `git push --no-verify` skip them, and CI still checks.
  The deny list for a local run is the environment variable `CLEAN_TEXT_DENY` if it holds anything, else the file `${XDG_CONFIG_HOME:-$HOME/.config}/stackshot/clean-text-deny` (one regex per line, blank lines ignored; the maintainer
  holds the list and hands it to a contributor who is to have it). It is never read from the tree. With neither, only the generic patterns run and one line on standard error says so; that is not a failure.
- **Run it by hand** when you want to; the script needs only Python 3.12 or later. For a commit message: `python3 tools/clean_text.py --message-file <file>`; for a branch name:
  `python3 tools/clean_text.py --branch <name>`; for a PR title and body: `python3 tools/clean_text.py --title "<title>" --body-file <file>` (the hooks do not see them, so run it before opening the PR); for every commit of a branch: `python3 tools/clean_text.py --commits origin/main..HEAD`; for the commits a push to the remote `NAME` would add: `python3 tools/clean_text.py --new-commits HEAD --remote NAME`.
- **License:** the repository is MIT-licensed (`LICENSE`); a contribution comes in under the same license.
- **Comments explain why, without names or dates.** A comment says why the code works the way it does; who decided it, when and in what words belong in the issue tracker or the history, not the source.

## Where work is recorded

The maintainers' own work goes out as a pull request, and the pull request description is the public record of that work: what

**The package has four layers, and `stackshot/web/server.py` is being split along them**: server code moves into new modules, a small change at a time, in this order: foundations, the write path, the surfaces, the passes, the domain moves, then the forwarding shims out (called the structure work below). Of the nine principles below, only the direction of imports (principle 1) is enforced today, by `tests/layers_scenario.py`; principles 2 to 9 describe where the structure work is going, and are marked as goals where today's code does not follow them. Every change that adds or moves code takes a step towards them and none away:

1. **Four layers, imports point down only.** Surface (`web/`: MCP tools, HTTP routes, pages), service (`service/`, not yet existing: the write path and the I/O half of every pass), domain (`model/`, `waits/`, `projects/`, `router/`, `anchors/`, `fleet/` and `github/`, which exist, and `notify/`, which does not exist yet) and core (`core/`: config, store, runner, clock). `audit/`, `tools/` and the command line (`cli.py`) sit outside the layers: they may import any layer, and nothing below the surface imports them (`web/` reads `audit/` today), apart from `paths.py`, which every layer may import. `tests/layers_scenario.py` checks the direction.
2. **The domain decides, the service writes.** A goal the structure work moves toward, not a fact today (domain modules import `core/`, where the store and the clock are, and `github/` does I/O). A domain module is pure: no store, no clock, no message, no import above it (`waits/handover.py`, `stall.py` and `ladder.py` already are). Reading the store, saving and telling sessions happen only in `service/`.
3. **One write path.** A goal the structure work moves toward, not a fact today (`service/` does not exist yet, and the transitional paragraph below documents a thread-local flag, `_SESSION_NEXT`). Every change to an item goes through `service/writes.py` (the lock, the save, the ids, the telling after); what a write must do differently is an explicit write context, not a thread-local flag.
4. **Thin surfaces.** A goal the structure work moves toward, not a fact today (`service/` does not exist yet, and rules still live in `web/`). A tool or a route parses its input, calls one service function and shapes the reply; no rule lives in `web/`.
5. **Tool text is text.** A goal the structure work moves toward, not a fact today (the tool descriptions are in `web/server.py`). Each tool's description lives in its own file beside the tool, apart from the code, so a wording change touches only text.
6. **A module is one area, named for what it holds.** `web/shared.py` and `web/common.py` are gone (their helpers live in `core/instance.py`, `model/`, `fleet/`, `projects/` and `web/publish.py`); the rest is a goal the structure work moves toward: no `shared`, `common` or `utils`; a helper used everywhere goes to the area that owns its idea (session identity to `fleet/`, item ids to `model/`).
7. **Size follows the repo's norm.** A module aims under about 800 lines; one over 1,000 is split by sub-area. This is a goal the structure work moves toward, not a fact today: several modules are over 1,000 lines, `web/server.py` and `web/ui/render.py` by far.
8. **Tests patch the owner.** This is the goal once the last change of the structure work is done (the one that removes the re-export blocks on `server`), not the rule today: a test then sets a name on the module that owns it, never on `server`, and no re-export block on `server` outlives the move that made it. Until then the transitional paragraph below governs: every moved name stays re-exported on `server`, and the suites stub the names where it says.
9. **`server.py` is the process entry only:** a goal the structure work moves toward, not a fact today (it is over 17,000 lines): check the config, build the app, start the background work, serve; under 400 lines.

A move is one target file (or one small group) per change, with no behavior change and the tool-text snapshot the same; the tests that patch the moved names are repointed to the owning module in the same change once principle 8 has taken over; until then the transitional paragraph below governs which module a suite sets a name on. `tests/layers_scenario.py` reads the package's imports with `ast` (no import is executed) and fails on an import from a lower layer to a higher one; `ALLOWED_TODAY` in that file lists the few that point the wrong way today, each with the work that removes it, and an entry is deleted as soon as its import is gone (the list only shrinks). `audit/` and `tools/` read the package and sit outside the layers.

## Page text: the string table, and no text in another language

**A word a person reads on a board page goes through the string table** (`stackshot/web/i18n.py`, with the English text in `stackshot/web/i18n_catalog.py`): a dotted key by area (`panel.*`, `home.*`, `state.*`, `js.*`, `item.*` and the item page's other areas) and its English `str.format` template, asked for with `t(key, **fields)` in Python and `SST(key, {fields})` in a page script. The tests use an ASCII test language instead, each value being the English text wrapped as `[x:...]`, so the mechanism is proved without any real translation. ## Scratch folders: a suite leaves nothing behind

A folder made with `tempfile.mkdtemp` and removed by one line at the very end of a suite is left in `/tmp` by a failing check, an
exception or an early exit, and folders left behind pile up in `/tmp`. Two things hold:

- **A suite makes its folders with `tests/_scratch.py`**: `import _scratch`, then `tmp = _scratch.mkdtemp(prefix="x-")`. They are removed,
  with whatever is in them, when the process ends: a pass, a failing check, an exception, `sys.exit`, `os._exit` (which the suites end
  with, and which skips `atexit`: the helper wraps it), SIGTERM and SIGHUP. Only the process that made a folder removes it, so a forked
  child's exit does not take its parent's away. `_scratch.track(path)` hands over a path made some other way (a folder the code under
  test names inside `tempfile.gettempdir()`). A suite never calls `tempfile.mkdtemp`, `mkstemp` or `NamedTemporaryFile` itself, and never
  names a `/tmp` path: it takes the folder from `tempfile`, which honours `$TMPDIR`. `tests/scratch_scenario.py` checks both.
- **`tests/run-suite` gives each run a `$TMPDIR` of its own** (`rs.XXXXXX` under the caller's `$TMPDIR`, short because a unix socket path
  is limited to 108 characters) and removes it when the suite ends, so what a subprocess or the code under test left goes too. uv keeps
  the caller's `$TMPDIR` (its one `uv-<hash>.lock` per project path stays there, and is the only thing a run leaves).

- **A running suite's folders hold a shared BSD lock** (`flock`, taken by `_scratch.mkdtemp` and `track` on each folder, and by `run-suite` on its `rs.*` folder). the host's age-based systemd-tmpfiles sweep clears old `/tmp` folders, which skips a locked folder and everything below it (tmpfiles.d(5)), so a long suite's folder is never taken while it runs. The lock drops by itself when the process ends or crashes, and a child process that outlives the suite does not keep it.

**To debug a suite, `KEEP_SCRATCH=1 tests/run-suite <name>`** leaves the folders and prints their paths (`scratch kept: …`); remove them yourself after.
To measure a suite: `d=$(mktemp -d); TMPDIR=$d tests/run-suite <name>; ls $d` shows only uv's lock file.
Run the suites with a `TMPDIR` outside any git repository (the default, `/tmp`, is): the `pilot` and `update` "not a git checkout" checks fail when the temp folder sits inside one.
A new suite is covered the same way, with nothing to register: it uses `_scratch`, and `tests/scratch_scenario.py` (a suite like the
others, so CI runs it when a change reaches it, and main always) fails on a suite that goes round it.

## Suite selection

A pull request (and a push to a release-queue branch, `queue/**`, and an entry of GitHub's merge queue, `merge_group`) runs only the suites its change reaches; a push to main runs every suite and measures them. `tests/suitemap.py`
does both (its docstring has the rules in full):

- **On main**, `measure` runs every suite under coverage.py (every Python process of a suite, subprocesses included) and, for
  the suites the push's change reaches and any not traced for a day, under strace (the files a suite opens, stats, runs or
  lists). The result, the map, goes to the Actions cache keyed by the commit. Then `audit` checks the choice the earlier map
  made for everything since its commit against the merged code's own measurement: a suite it should have run and did not
  fails that step by name, and so does a suite that failed on main after the PR skipped it, or a commit the audit cannot
  resolve (nothing was checked). **Main's measured run is split across six parallel jobs** (it was one long job on one runner while the
  other runners sat idle, and every release waits for it): the `shards` job of `tests.yml` makes the plan once (`tests/suitemap.py plan --of 6`: every suite in exactly one of six lists, the
  longest first into the list with the least measured time, by the map, else by a stable hash of the name, which is also what a cache miss in that job gives, for all six lists alike) and hands the six lists
  on as job outputs; the `measure` job is a matrix of 6 jobs on the labels the run used before, each measuring the list it is given and planning nothing (so a cache miss in one of them cannot make it
  double-run or skip a suite), and the `suites` job merges their maps (`tests/suitemap.py merge`), keeps and saves the map and audits as before. Its step `run every suite, measured`, the one
  `release.sh` reads, passes only when every shard passed and the merged map holds every suite exactly once, so `release.sh` and the CI-run poller read main's run as before;
  on a push to main the `suites` job runs on the light pool, since it only merges and audits. A pull request, a queue branch's push, a merge-queue entry and a manual run do not use the shards (a queue branch's `suites` job runs the selection, on the heavy pool). `tests/suitemap_scenario.py` checks
  that every suite is in exactly one list, that every shard reads the one plan, and that the matrix and `--of` agree with `SHARDS` in `tests/suitemap.py`. A suite that fails measured but passes on a plain rerun is a warning, not a failure: the map
  marks it `ok: false`, so every PR runs it until it measures clean, and `release.sh` names it in its report (which then goes
  to the keeper, not green), so a flaky suite stays in sight.
  **The plan splits by recorded times** (the longest-first fill that pytest-split calls `least_duration`; the times are the map main saves to the Actions cache on every push to main, not a durations file kept in the repository, which is where pytest-split keeps them: that map is already the always-fresh record of how long each suite took, so a second file could only drift from it), and no plan balances a suite longer than a sixth of the total.
  So a suite's own measured time stays short: `tests/_release_harness.py` starts `release.sh` and its stubs without the `COVERAGE_*` variables (`ENV0`), as `release` and `release_queue` once took three times their plain time loading coverage in thousands of stub starts.
- **A queue branch gets a pull request's run**: a push to a branch named `queue/**` (the salamander merge queue's entry branches, the queue `release.sh` uses when the host file says `mode = "on"`: main plus the PRs ahead of one in line plus that PR) runs `tests.yml` as GitHub's merge-queue convention has it,
  the checks a PR runs: no plan and no six measuring shards, the `suites` job alone, running the suites the change reaches by the newest map (the same selection step as a PR's; observed, not measured here: a PR's selected run takes some minutes on a PR retest after catching up, and a queue branch's full sharded run takes tens of minutes, as practice runs showed), and any failure of the selection runs every suite.
  The job keeps its name `suites`, the check the salamander queue (`mq`) reads on an entry's head and the one GitHub's ruleset requires, and its result is read by the commit (`salamander ci-runs howardpark-ai/stackshot --sha <sha>`). `.github/mergequeue.toml` says so with `suites = "select"`, and `tests/suitemap_scenario.py` fails when the file and the workflow disagree.
  What a queue run no longer gives is the measured map and the selection audit: only a push to main does those (it measures every suite in the shards, saves and publishes the map and audits the selection, unchanged). The risk is a selection that misses a suite, which a PR's run accepts as well, and main's full run after the merge catches it by name.
  The poller's window is the newest 30 runs of the repository, which queue pushes share with main's.
- **A GitHub merge-queue entry gets the same run** (`merge_group`). GitHub's merge queue is the default one `release.sh` uses. The repository's `merge_queue` ruleset on main turns it on (enforcement `active`; `disabled` is the way back, and `release.sh` then merges with the plain call), and `tests.yml` serves it: it triggers on `merge_group` (types `checks_requested`) so that the job `suites`, the check the ruleset requires, reports for an entry (a check that never reports makes the queue wait until it times out). An entry (branch `gh-readonly-queue/main/pr-<n>-<sha>`) runs exactly what a `queue/**` push runs: the selection, no plan, no shards, no measured map, no audit. The entry's branch is not in the `push` list (the `merge_group` event is the trigger; a push trigger too would run every entry twice). The event has no pull-request context, so the `tool-text` job skips on it, and the map's cache key uses the entry's `base_sha` where a PR uses its base commit (the restore falls back to the newest map). A run of an entry is never cancelled by another (the concurrency group holds the ref, and `cancel-in-progress` is true for a pull request only). `clean-text.yml` is left out: `suites` is the only check the queue requires, so it is not needed for an entry to merge; and it checks a pull request's title, body and branch name, which an entry does not have, along with the message of every commit the PR adds, which an entry does have, so it would need its own handling of its inputs. If it is ever made a required check of the queue, it needs a `merge_group` trigger and that handling. Our own queue (`queue/**`, `salamander mq`) is the other one `release.sh` can use, when the host file says `mode = "on"`; the two never share a run (a `queue/**` push is the salamander queue's, a `merge_group` entry is GitHub's), and neither is retired. `tests/suitemap_scenario.py` pins the workflow's shape for both events; GitHub's own behavior it cannot.
- **On a PR**, `select` reads the newest map and runs the suites whose measured functions or files the change reaches: a
  function body reaches the suites that ran it; a module-level binding (a constant, a def, a class, the docstring) the code
  that reads the name, followed across imports and through the bindings that use it, and the suites whose own file names it;
  a module-level statement with effects at import (an unknown decorator, a call) every suite that ran the file; a
  registered tool's header or description (`@mcp.tool`) its callers and whatever lists the tools. A comment or a file no suite
  touches reaches none. A change to the docstring alone of a module-level function with no decorator (or only a wrapping one, such as
  `functools.wraps`) is not a change of its body: it reaches the file's text readers, the suites whose own file names the function and the
  suites that ran code reading a docstring (`__doc__`, `getdoc`), not every suite that ran the function. A decorated function's docstring (an
  `@mcp.tool`'s is the description a session reads), a method's, a class's, a docstring changed together with its function's code, one that
  shares a line with other code and any file that calls `globals()` are selected as before. The rule's limit: a suite that fetches a function
  by a variable name and then reads its docstring is not selected by it. The tripwire in `tests/suitemap_scenario.py` selects nothing; it only
  makes a new use of the common docstring-reading and docstring-registering forms fail that scenario until its author has looked at it and
  pinned it on the allow list (forms with no use here, such as `vars(fn)["__doc__"]`, `attrgetter` or an `eval` string, are not scanned).
  An edit that only ADDS names to the imports of a file binds only the added names (`from typing import Any` to `from typing import Any, Iterable` no longer
  reaches the readers of `Any`, nor does a line rewritten with the same names, parenthesised or split). Any other import edit binds every name on the
  changed line, as before: a name removed (the importer may fail with a NameError at import), renamed, taken from another module, imported twice, swapped
  with another import of the same name or moved below other code. An import the file gains that may not resolve takes the file whole: a name added to an import from one of our modules that the module does not bind (a bare annotation, a name only under `if TYPE_CHECKING:` and a deleted name are no binding), a star import, a relative import to nothing of ours, a name a stdlib module has neither as an attribute nor as a submodule (`from typing import Annoted`), a top-level package that is neither the stdlib's nor installed, a stdlib module this platform does not have (`import msvcrt` on Linux), and a stdlib module that does something when imported (`antigravity`, `tkinter`) or any `__main__` below a package (`import unittest.__main__`), which are never imported to look. A bare `import X` is only looked up (`importlib.util.find_spec`), never run. A name from an installed package cannot be looked up and keeps the narrowing. In a file with `from __future__ import annotations`,
  a name used only in an annotation is no read when the annotation is on a parameter or the return of a def with no decorator (or only a wrapping one:
  `property`, `staticmethod`, `classmethod`, `lru_cache`, `cache`, `cached_property`, `contextmanager`, `asynccontextmanager`, `abstractmethod`, `overload`) whose name is only ever called
  anywhere in the checkout (a script with a python or `uv run` shebang counts; so does a use under another name, `from m import f as h`, followed across
  files), or on a local variable inside a function. The import statement keeps its own dependency, though: a name taken from another of
  our modules and used only in such an annotation still reaches the suites that run the importing file when that module's name changes (the import fails).
  These count as before: a def whose name is used as a value anywhere (passed on,
  assigned, decorated with, read as an attribute without calling, or a string), an annotation of a class body (a dataclass or model field), of a
  module-level variable or of a def with another decorator (`@mcp.tool` evaluates them), a default value, a decorator, the parameters of a class's
  `__init__`, `__call__`, `__new__` and `__post_init__` while the class is used as a value (`inspect.signature(Cls)`, a base class, `isinstance`) or one of those method names is (`get_type_hints(C(1).__init__)`, `getattr(C(1), "__init__")`), and every annotation in a file
  without postponed annotations. Turning postponed annotations on or off takes the file whole. The class-name escape (a method name of those read as a value) is ON for good in this repository: `stackshot/cli.py` (line 1007) and `tests/package_layout_scenario.py` (line 156) read `argparse.ArgumentParser.__init__` as a value, so the class-keyed names (26 distinct names, in 20 files) always count as reads, which errs toward more suites. The limit, as for docstrings: a function fetched by a
  variable name and handed to `typing.get_type_hints` or a registry is not seen; the annotation tripwire in `tests/suitemap_scenario.py` pins the
  number of uses of those forms (`get_type_hints`, `__annotations__`, `__annotate__`, `eval_str`, `wraps`, …) per file, so a new use fails that scenario until it is
  looked at. `SUITEMAP_IMPORT_RULE=I1` and `SUITEMAP_ANNOTATION_RULE=N1` give the old selection, plus these two always-wider differences: turning postponed annotations on or off takes the file whole, and a read of a name that a try/except fallback or a second line imports twice reads every source of it. `tests/suitemap.py`'s docstring (*Imports and annotations*) has the rules in full.
  A route (`@mcp.custom_route`) is none of tool, resource or prompt: it binds its own key, so its header or body reaches its callers and the suites that read the routes or serve the app (an attribute read of `http_app`, `routes`, `streamable_http_app`, `sse_app`, `_additional_http_routes`, `_get_additional_http_routes`, `run_async` or `run_http_async`, which also match a tool edit), and not the suites that only list the tools (`list_tools`, `get_tools`). A suite that names the route's function, one that reads the file as text, a function that builds or serves the app (it reaches the suites that ran it), and any wildcard reader of the module (`getattr(mod, name)` with a name that is not a literal, `vars`, `dir`, `inspect.getmembers`, a module loaded by a path), is selected as before; a function decorated with both a tool and a route binds both. `SUITEMAP_ROUTE_RULE=R1` gives the old selection (a route binds the key every tool binds); any other value but R2 is an error. `tests/suitemap.py`'s docstring (*Route registrations*) has the rule and its limits.
  An edit of a literal class attribute (`_SENT = {...}` in the body of a plain class) binds the attribute and not the class: it reaches the suites that read `.name` (an attribute access, a string that names it, a format-string token or a dotted token in a string of any length) and those that read attributes by a name they compute (`getattr(obj, name)`, `vars`, `dir`, `.__dict__` of another object), not every suite that ran another method of the class. A decorated class, one with bases, `__slots__`, `__getattr__` and the like, an attribute the class body reads bare (`B = A + 1`), an annotated or non-literal value stay whole-class. `SUITEMAP_CLASS_RULE=C1` binds the whole class for every edit in its body, as every edit did before C2 (it does not look for the plain `.name` readers in other modules that C2 adds); any other value but C2 is an error. A dynamic reader is matched under every name the file gives it (`from builtins import getattr as ga`, `g = getattr`, `pm = mock.patch.multiple`), and a classmethod's or a free `self.__dict__` is a dynamic read. Known limits: an alias made by a parameter, a call result or a container is not followed, a stdlib function that sets an attribute by a name it gets as data (`parser.parse_args([], namespace=Cfg())` with a `--K` option) shows no name of ours to match, `vars(self)` in a method of a metaclass (its `self` is a class) is taken for an instance's, and `mock.patch.object(Cls, name)` with a variable name is not matched; all are under-selection, kept because no static rule over the checkout finds them. The docstring (*Class attributes*) has the rule and its limits.
  A new file (added, or a rename's new path) reaches the suites that listed its directory; in a
  directory no measured suite lists, every suite, since code may look it up by a name nobody tried before (the checkout and
  `tests/` are listed by every suite: the import machinery lists the directories on `sys.path`). No map, a change to the harness (`.github/`, `tests/run-suite`, `pyproject.toml`, `uv.lock`,
  `tests/suitemap.py`) or a suite with no clean measurement: those run (all, for the first three).
- **The example config is read by what a change does to it** (`stackshot.example.toml`). Nearly every suite starts from its text as the base of its own temp config, so a plain file rule ran about 188 of the 196 suites on any edit of it. Those fixture suites read it through the tracked link `tests/example_base.toml` (`_instance.base_toml()`); the suites that check, patch or run code on the file itself (the direct readers) keep the real path, and the map tells the two apart by the path each opened. `select` compares the file at the map's commit and at the target as text. The direct readers alone are chosen only when every changed line, on both sides, is a whole blank line or a whole comment-only line of plain prose (letters, spaces and `. , ; : ! ? ( ) ' -`) that names no setting: no word of it is a table or key name of the example or of the constants in `tests/_instance.py` (`SETTINGS`, `KEYWORDS`, `FLAG_SETTINGS`, `TABLES`, `PINNED_TABLES`) (a short name such as `git`, `ssh` or `cap` counts: a name is matched as a whole word, and inside a longer word from four letters), the lines from the header of `[audit]` or `[anchor_hub]` to its first key are as they were, and no change is at, or directly after, the first line of the file (`stackshot/cli.py` anchors on that line for the configs it writes; the test is wider than the line on purpose, the safe side). Anything else selects the fixture readers too: a trailing comment or whitespace on a code line, a value, a key, table, inline table or array-of-tables row added, removed or moved, an uncommented sample, a comment with `=`, `[`, a quote, a digit or an underscore. Whether a fixture suite breaks depends on where a line lands and on text a suite patches, and no narrower rule held up against the edits reviewers tried, so none is attempted. The suitemap scenario runs `apply()` and fails when it changes a name the constants do not list (it holds for a `_set` or an append written in `apply()`; a name dropped from a constant and from `apply()` together is not caught). A text that does not parse selects every suite; a change to the link itself selects every suite. `SUITEMAP_EXAMPLE_RULE=A1` in the selection step's environment leaves no cheap case: every change to the example, a comment included, selects the fixture readers too (any other value is an error). A new suite that only needs the base config reads `_instance.base_toml()`; one that checks or patches the example's own text reads the real path. Until main's next measured run records the link for the fixture suites, the map lists the real path for them and the old selection (every reader) holds. `tests/suitemap.py`'s docstring (*The example config*) has the rule in full.
- **A release is checked by main.** A PR's checks cover only its suites, so main's full run is the check of every suite. GitHub's merge queue tests the merge group with the same selection (not every suite), then `release.sh` deploys the merge it made and the main run that covers it comes after:
  a pass is recorded as the last good commit, a failure rolls the deploy back to it (see step 4 above). When the deploy gate is closed (a merge the queue did not make, a failed or unreadable run since the last good commit, no readable last-good commit, a paused release queue, a checkout that cannot fast-forward), `release.sh` waits for the run that covers
  its merge (step 4, *Which run covers a merge*) before deploying, and deploys only when it passes (merged and not deployed when it does not: fix forward). Every deploy goes to one commit (`DEPLOY_TO=<sha> ./deploy.sh`), the newest one containing the merge whose run passed, never to a
  tip with no passing run: a merge another release lands meanwhile is deployed by that release.
- **A new suite** is a new `tests/<name>_scenario.py`: CI finds it by name, nothing else to edit, and runs it on the PR that adds it. (`tests/locale_scenario.py` is the one for the string table: the loader's fallbacks, the date and age forms, the per-person language, the switch, `<html lang>`, and the home page and side panel in English and in the ASCII test language; `tests/locale_pages_scenario.py` does the same for the search page, the runners page and the colour tool.)
- **A PR that retires a feature deletes the feature's tests in the same PR.** The suites, and the check lines inside a shared suite, that only exercised the retired behaviour go with it, not in a later cleanup: a test for a feature that no longer exists keeps running on every PR that reaches it and keeps its fixtures alive. If a suite still tests something the PR keeps, only the retired part's checks go. `tools/test_trim_report.py` (next section) shows the size of the suites over time, so a retirement that left its tests behind shows as test lines that did not fall.
- **A fixture never names a real box** when a suite compares it with the box it runs on (`socket.gethostname()`): CI's hosts
  differ from your own, so a fixture that named one box as the remote machine fails on the host that is that box. The remote machine is `far-host`.
- **Fixtures use invented names**: no real person, company, host or session name, in a fixture, a test comment or an expected string. `Acme`, `Pat`, `you@example.com`, `far-host` and `my-engineer` are the stand-ins; the clean-text job reads only the PR's text (its title, body, branch name and commit messages), not the files, so review is what catches a real name in a fixture.
- **An id match in a test is whole-word**: a test that looks for the id `ab-12` must not pass on `ab-123`. Match it with a boundary after it (`re.search(r"ab-12\b", text)`, or compare the whole token), never `"ab-12" in text`.
- **When the selection looks wrong**, the job summary lists each changed file with its reason. `tests/suitemap_scenario.py` checks
  the rules on a throwaway repository; a rule change comes with a check there.

## The weekly test-suite report

`python3 tools/test_trim_report.py`, run weekly from a checkout, is how the size of the suites is watched; it is read-only, standard library only, and cleans nothing up. It prints the number of suites, the test lines (the lines of `tests/*_scenario.py` that start with `check(`, `ck(`, `assert` or `self.assert`), the serial minutes (the suites' plain times added up) and the slowest 8 suites with their minutes, then what changed since the previous run: suites added and deleted by name, test lines added and deleted. The times are the suite map's (`suites.<name>.seconds`, see *Suite selection*; no second store): `--fetch` for main's newest `suitemap` artifact (taken before `--map`), else `--map FILE`, else `.suitemap/map.json` in the checkout; a time that is negative or not a finite number is ignored with a note; with none readable the minutes are `n/a` and the report says why. The previous run's record is one JSON file per repository, `${XDG_STATE_HOME:-~/.local/state}/stackshot/test-trim/<repo>.json`, replaced atomically (a previous record that cannot be used, damaged or from another repository, is started over from with a one-line note); `--dry-run` writes nothing and `--json` prints the record.

The thresholds are four keys in a small TOML file, `${XDG_CONFIG_HOME:-~/.config}/stackshot/test-trim.toml` (or `--config FILE`): `max_suites`, `max_serial_minutes`, `max_suite_minutes` (the slowest single suite) and `max_test_line_growth` (test lines gained since the previous run, scaled down to a week when the gap is longer). Keys at the top apply to every repository and a table named after the repository overrides them; a mistyped key is not used and gets a `warning: unknown key` line on stderr, and a value that is not a number of at least 0 (a boolean, nan) is exit 2. The shipped defaults are placeholders that never trigger; the real values are set from the measured medians. When a value is above its limit the report ends with a `TRIGGER: <which>` line per threshold and the same lines go into the state file; the exit status is still 0 and the tool opens nothing itself. A trigger is what opens a cleanup item, and the cleanup (a deep scan for duplicate or obsolete suites) is a separate pass, not part of the report. Exit status 1 means the state folder or file cannot be written, 2 a usage, config or checkout problem. `tests/run-suite test_trim_report` tests it on a fake repository.

## The tool-text gates

The owner's rule: **a tool's text changes in the same release as the tool.** What a session learns a stackshot tool from (its name, its parameters, its
description, the fixed labels of the lines it returns) is kept in one committed file, `tests/tool_text.snapshot.json`, and four gates keep a PR from changing
the tool and leaving the text behind. The first three are deterministic checks that CI runs; the fourth is a read by the builder's reviewer subagent before the merge. **No model call runs in a PR check**, and no CI job signs in to AWS.

1. **The snapshot** (`tests/run-suite tool_text`). The suite fails when the live registry differs from the snapshot, prints a readable diff (the words that
   changed, parameters added, removed or changed, labels gone or new) and the one command that refreshes it: **`python3 tools/tool_text.py update`**
   (it re-runs itself in the tests' uv environment), then commit the file with the change. `tool_text.py check` shows the same diff, `dump` prints the text.
   The labels (`mover:`, `then:`, `state:` …) are read from the source of the output helpers by an AST scan, a list kept in one place,
   `HELPERS` in `tools/tool_text.py`: a new function that builds a line a tool returns goes in that list in the same PR.
2. **The retired-terms lint** (`tests/run-suite retired_terms`; `tools/retired_terms.py` with `tests/retired_terms.toml`). Words the owner retired (`owner` → mover, `keeper of record` → mover or `created by`, `steward` → the router and the keepers) fail the build wherever text a session reads carries them: the string literals of the code, the
   hook texts, the tools' snapshot. A hit names the file, the line, the term and what to say. A legitimate use (the instance's owner, a stored key, the deprecated
   parameter's note) is an `allow` phrase in the toml with its reason beside it. The format is in the toml's header; sala copies the checker and writes its own list.
3. **The touched-tool check** (the `tool-text` job of `tests.yml`, pull requests only: `tools/tool_text.py touched --base <sha> --head <sha> --body-file <f>`).
   When a tool function (`@mcp.tool`) or an output helper has a changed body between the PR's fork point and its head, and the snapshot is unchanged, the job
   fails. A change that really leaves every sentence and label as it was (a refactor, a fix inside) says so in the PR body with one line,
   `tool-text: unchanged: <why no session reads a difference>`, and the job is re-run (it reads the body when it runs).
4. **The reviewer's read, before the merge** (no CI job; `tools/text_check.py`). The touched-tool check sees that a body changed, not whether the words still say what the code now
   does, and a script cannot judge that. So before merging a PR that changes **a tool's parameters or text, a help text, or a skill or rulebook line that names a command**
   (the changes that make an agent learn a command wrongly), the fresh reviewer subagent of item 4 in *The branch model* reads that text and checks it against the change: for a tool, the description,
   each parameter and the labels of the returned lines in `tests/tool_text.snapshot.json` against the diff; for a CLI, its help and the usage a wrong call prints; for a skill or a rulebook line,
   the line against the command it names. A mismatch is a finding, and the builder fixes the text and refreshes the snapshot (`python3 tools/tool_text.py update`) or says why the text is still true. **Small changes are skipped**:
   comments, docs, a one-line config change, a refactor that leaves every sentence and label as it was (the PR body's `tool-text: unchanged: <why>` line of gate 3 says so).
   To gather what the reviewer reads for a PR, run **`python3 tools/text_check.py pack --base <sha> --head <sha>`** by hand (or `--base origin/main --head <branch>`): it prints the tools the change reaches, the functions
   with a changed body, whether the PR changed the snapshot, the reached tools' text from the snapshot at the head and the diff of the watched files (hunks of the changed functions first), or one
   `nothing to read: <why>` line. The script uses the standard library only, calls no model, needs no AWS credentials, and **no workflow runs it**; `tests/run-suite text_pack` tests it. There is no switch, no repository variable and no
   PR-body escape line for this read: the reviewer's finding is answered in the PR.

**`python3 tools/tool_text.py check` alone does not catch every tool-text rule.** `tests/waiting_scenario.py` also bans a regex (ladder, stuck list, "step N of", grace) in the `get` and `brief` descriptions and requires some phrases there.
A change to a tool's text therefore also runs `tests/run-suite waiting`, plus the suites the change reaches. `select` prints `all` or a list of suite names, and `run` with no names runs nothing, so pass one to the other, as `tests.yml` does:
`sel=$(uv run --locked --only-group tests python tests/suitemap.py select --map .suitemap/map.json --to HEAD)`, then (if `all`, use `suitemap.py list` instead)
`uv run --locked --only-group tests python tests/suitemap.py run -T 600 $sel`.
`.suitemap/map.json` is gitignored and CI restores it from the Actions cache; with no map, `select` prints `all`.

**The brief's what-changed line is generated from the snapshot.** The server's start (`whatschanged.record`) compares the snapshot of its checkout with the copy kept
at the last start that changed it, `<paths.state>/tool_text.released.json`; a difference is appended, dated that day with a generated summary (tools added or
removed, parameters added, removed, renamed or changed, description and label changes by tool), to `<paths.state>/tool_text.history.json`. A deploy restarts the
server whenever a tool changed, so the start is the mark of a release, and no `deploy.sh` or `release.sh` step and no hand edit is involved. For 7 days after its
date the brief carries `stackshot changed on <date>: <summary>; see docs/design`. `tool_text.py summary` shows the line a change will
produce.

## Where CI runs: GitHub's hosted runners

Every job of the two workflows (`tests.yml`, `clean-text.yml`) runs on GitHub's hosted runners (`ubuntu-latest`). No repository variable is needed for that.

- **A trial from a branch**: `gh workflow run tests.yml --ref <branch>`. `tests.yml` also takes `-f suites="pilot release"` (names, space-separated) for a manual run of those suites, plainly; with no names it runs every suite, plainly, without the suite map.
  `clean-text.yml` on a manual run checks the branch's commits against `main`.
- **What a hosted runner gets.** `astral-sh/setup-uv` (every job runs it, with the Python the job needs: uv fetches the interpreter, so no `setup-python`), and the suites build their own fixtures with `git -c user.name=…` and a temp `HOME`, so no git identity or home folder is set up.
  The one install is `strace` (`apt-get`), only for the push to `main` that measures the suites (without it the suite map has no file half and every PR would run every suite). That step is gated on `runner.environment == 'github-hosted'`, true exactly where a job runs on a hosted runner.
  The time limits allow for a small runner: a suite 900 s, the whole job 180 min, the measured run's suite 3,600 s.
- **Minutes.** The standard hosted runners cost a public repository no minutes. A private copy (a fork or a mirror) uses its account's included minutes: a plain run of every suite takes about 15 minutes of the `suites` job and `clean-text` a minute (each job is rounded up to the minute),
  and a push to `main` measures every suite (strace and coverage, several times the plain time, in 6 shard jobs, each with its own setup minute or two) and costs the most. Check the allowance before enabling Actions on a private copy.
- **No CI job calls a model or signs in to AWS.** The earlier model check (a `tool-text-model` job that signed in through GitHub's OIDC token to an IAM role and called Bedrock) is gone; the repository variables and the secret it read
  (`TOOL_TEXT_MODEL_CHECK`, `TOOL_TEXT_AWS_REGION`, `TOOL_TEXT_MODEL`, `TOOL_TEXT_AWS_ROLE`) are read by no workflow now and are removed from the repository settings separately. No job asks for `id-token: write`.

## When the stall pass misfires

The stall pass (`stackshot/waits/stall.py`, docs/stall-and-ladder.md "The stall pass") moves an item on when its mover's pane has no turn running. When it takes a wrong step on an item, an agent does three things and never a fourth:

1. **Undo the step on the item** with `update` (the `get` tool says the same, and `update` points to it): set `mover` and `next` back after a hand-off (`cold`, `builder`); `status=open` with a new `next` after a close; nothing after a recovery request (the message to the fleet's builder cannot be unsent and the item was left with its mover). The `stall:` line stays in History as the record. A notice already sent (`resend`) cannot be unsent and needs nothing.
2. **Fix the cause through a normal PR** to stackshot (this file's branch model), handed to `my-engineer`: a wrong step is `not_due`, `action` or the registry signal reading the item wrong.
3. **If wrong steps reach the owner before the fix lands, ask him for a pause that ends by itself.** He answers on a board item, and `[stall] pause_item` names it.

**An agent never switches the pass off.** The server honors `enabled = false` or `paused_until` only when `pause_item` names a board item that carries the owner's own answer approving a pause (the chosen option or his comment says "pause"; an unrelated answer of his does not count) from the 4 hours before the server first saw the setting, and no pause lasts longer than 24 hours; a pause answered only after its cap has passed starts when the answer is honored, with one journal line saying so; any other setting is refused with one journal line (and doctor shows it).

## GitHub's hourly call budget

Everything on the host that uses `gh` or the server's `ghsync.token()` spends one shared hourly API budget that polling can exhaust: when GitHub answers
"API rate limit exceeded", ghsync queues its writes. Releases waiting on one main run that each polled `gh run list` and `gh run view` every few seconds were the main way to spend it. What a change here must keep to:

- **A wait polls slowly and shares.** release.sh's main wait looks every `RELEASE_POLL_MAIN` (60 s) and reuses a read another release made in the last `RELEASE_GH_TTL` (45 s) from `<state>/releases/gh-cache`. A new wait on a GitHub state does the same, or uses a conditional request.
- **A wait asks sala's CI-run poller first**: `salamander ci-runs howardpark-ai/stackshot --sha <sha> --max-age 120` reads a file the poller keeps, no GitHub call. Fresh and the commit's run still queued or in progress: keep waiting with no call. Completed, not listed (a 30-run window: a missing sha proves nothing), exit 3/4/5 or no `salamander`: the GitHub read, which alone decides pass or fail. release.sh does this in both its CI waits (`ci_going`: the PR's checks and main's run); its wait for the merge queue reads GraphQL every `RELEASE_POLL_QUEUE` (60 s) and shares nothing, since the merge group's runs are not main's push runs.
- **A read repeated on a timer sends its ETag** (`GitHub.request(..., etag=True)`, `runners._get`): a 304 is not counted. anchor-hub's polls already do, and it keeps its ETags across a restart (a read position that does not, spends the hour's cap on every start).
- **A 403 or 429 is a wait for the reset, not a retry.** ghsync probes `GET /rate_limit` (it costs no call) and resumes when 50 calls are left.
- **A session waiting on a CI run uses `gh run watch <id> --interval 60`**: the default interval is 3 s, thousands of calls an hour for one watch.
- The newest X-RateLimit headers any ghsync or runners call saw are in `<state>/github/ratelimit.json`.

## Where the instance lives

The code carries no instance: `stackshot.example.toml` holds the defaults, and an instance's own `stackshot.toml` lives
with its data (the owner's, kept in his config repo), found through `$STACKSHOT_CONFIG` or
`~/.config/stackshot/stackshot.toml` (see `stackshot/core/config.py`). Secrets are under `<paths.secrets>`, never in either repo. Units
are rendered from `units/*.in` by `install.sh` for whatever checkout path and user runs them.

On the server box, `~/.config/stackshot/stackshot.toml` is the live instance. A `stackshot/web/server.py` run outside the production checkout
(`~/stackshot`, `PRODUCTION_CHECKOUT` in stackshot/web/server.py) without `$STACKSHOT_CONFIG` is refused before it reads the store; run it only
with a temporary config (as the scenarios do). A start binds its port before anything else, so a second server on a port already
held exits without touching the store.

## The merge queue's replay cases

`salamander mq` (the salamander merge queue, which `release.sh` uses when the host file says `mode = "on"`) is tested by replaying a set of past pull requests whose outcome the old release path already decided, on a practice base. `tools/mq_replay.py build-cases` makes the cases: it reads the release logs (`${STACKSHOT_LOGDIR:-~/.local/state/stackshot/releases}/pr-*.log`) and git history (read only: it never checks out, switches, pushes or fetches into the checkout it is given; fetch `origin` first) and writes `tests/mq_replay/cases.json`, which is checked in so the cases outlive the logs. Stdlib only, no lock file.

- **The cases** are the table `SELECTION` at the top of the tool (`[pr, attempt]` pairs); the data of each is regenerated from the logs and git, never typed in. A merged PR's base is `M^1` and its head the head the old path merged, with release.sh's `Merge branch 'main' into` commits peeled off; a refused attempt's base is main's first-parent tip before the `FAILED` line's time, its head the attempt's `(head <sha>)`; a group's base is the tip the old path first saw. Only a base that contains the commit that made `queue/**` run the workflow can run CI.
- **Every sha is checked**: one that main's history holds is read there, any other is fetched by itself from the remote into a scratch repository. A case with a sha it cannot get (or a refusal the queue has no equivalent for) is dropped, printed and recorded under `dropped`.
- **`python3 tools/mq_replay.py build-cases --check`** verifies `cases.json` against git without writing (shas present, the merge-tree of head and base is what the file says, a merged PR that merges clean has `M`'s tree); `--allow-missing` for a checkout that lacks a refused attempt's head, `--verify fetch` to get it from the remote. `--check` validates shas and trees, not how a base was derived: the group and refusal base rules are applied only when the cases are built.
- **A refused PR whose checks are left out** (case c13: CI is to decide) has no `expected_reason`; its `expect` field says what the replay should see (the PR fails on its own and the chain drops it, the other PRs pass). `--repo-owner LOGIN` (default: read from a github.com remote) is the repository's own owner: the file records an `owner` only for a head branch of a fork, and the build stops when no owner can be derived.
- `tests/mq_replay_scenario.py` runs the tool on a throwaway git world and fixture logs in the real shapes (no network), and checks the shape of the checked-in file.

### Running the replay: `run`, `report`, `clean`

`tools/mq_replay.py run` (code in `tools/mq_replay_run.py`, stdlib only) replays the cases on practice branches through the real `salamander mq` in shadow mode and compares each verdict with what the old release path decided.

- **Per case**: it pushes `practice/<run>/<case>` at the case's recorded base sha, writes `replay.json` (schema version 1: `ci`, the repository's `.github/mergequeue.toml` rules with `base` and `queue_prefix` pointing at the practice names, each PR's recorded head, branch and checks; a PR with no `owner` gets the repository's owner, derived from a github.com remote or `--slug`, and the run fails clearly if neither gives one) and a host config (`mode = "shadow"`, the remote, a clone, the replay path) into a folder of its own, and runs `salamander mq add` and `mq wait` with `XDG_STATE_HOME` and `XDG_CONFIG_HOME` set to that folder. The real queue's state folder is never given to a case; only the CI-run poller's folder is linked in, so waiting costs no GitHub call. The case's `XDG_CONFIG_HOME` would hide the box's `gh` login (it lives in `hosts.yml` under the real config folder) and git's XDG config from the queue's driver, so `<case config>/gh` and `<case config>/git` are symlinks to the real folders (`GH_CONFIG_DIR` honoured); cleanup removes the links as links and never reaches into what they point to. Without a `gh` config folder and a token the run says so at the start of each case.
- **Profiles**: `--profile build` (the default) runs every case with `ci = skip` (the entries are built, not pushed; `mq wait` exits 4); `--profile full` runs the cases that need a CI verdict (a merged PR, a group) with `ci = real`. `--cases c01,c05` picks cases, `--concurrency N` (default 2) sets how many run at once, `--keep` keeps each case's folder and clone (the practice branches are deleted all the same).
- **Match rules**: a merged PR must be `mq wait` exit 3 (exit 4 under `ci = skip`), and where the case records a merge tree, the group's tree must equal it (a conflict mended by the rules' `on_conflict` hook included; a `head_mode = "queue"` case is replayed at its queue-time head); a refused PR must be exit 1 with the same check names, or "conflicts with main" with the same files; a PR the case expects to fail alone (its `expect` field starts with `fails alone`) must be named failed on its own, dropped by the chain with the entries behind it rebuilt on the one ahead, while the case's other PRs pass. A mismatch row says which side to look at: CI, the queue, or the old path or the fixture.
- **Idle gate**: no case starts while a `stackshot-release-*.service` unit is active, the release queue file (`queue` in the folder `python3 stackshot/core/config.py state releases` names, as `release.sh` reads it; `--logdir` overrides) is not empty, or a real merge-queue group is in any phase but `done` (`salamander mq status --json`; a status call that fails shuts the gate). It is read again before every case. When a release appears mid-run the run stops starting cases, cancels its own in-flight CI runs with `gh run cancel`, drops its PRs, waits for the case's driver to leave, cancels again by looking up the runs of the case's own `queue/practice/<run>/<case>/*` branches (a driver that was still building can push its group after the first cancel; GitHub lists a run a few seconds after its push, so when nothing is found the look is repeated once after `--settle` seconds, default 5; a run that still starts later runs against a deleted branch and is harmless), marks the case interrupted, cleans up and exits 75; `run --resume <id>` runs only the cases not done.
- **Guards and cleanup**: every ref the tool pushes or deletes must match `refs/heads/(queue/)?practice/...` (anything else is refused before git is called, and a delete with one bad ref deletes none); main, the PR branches and the real queue's state are never touched. Deletion is `git push --delete`, never the REST API. In a `finally` (pass, failure, SIGTERM) each case's `queue/practice/<run>/<case>/*` and `practice/<run>/<case>` refs, leftover groups, folders and clone are removed. A driver that does not leave after its PRs are dropped is stopped through its unit name, never killed by process name.
- **Stop signals**: `systemctl --user stop` and Ctrl-C reach the waiting `salamander mq wait` child together with the tool, so a wait ended by a signal is never a verdict: the case is interrupted (no row, resumable) and its CI runs are cancelled.
- **Detached**: `run --detach` starts the same run as the transient user unit `stackshot-mq-replay-<run>` (`systemd-run --user`, `TimeoutStopSec=300` so a SIGTERM's cleanup is not cut short; `GH_CONFIG_DIR` is forwarded into the unit when set, a token never is) and returns; plain `run` stays in the foreground. A run holds a lock, so two runs of one id cannot overlap. Exit codes: 0 all rows match, 1 a mismatch or an error row, 75 interrupted by the gate, 143 SIGTERM.
- **Report**: the table (case, PRs, head to base, the old path's outcome, the queue's verdict with its exit code and CI run link, match, note) is written to `${XDG_STATE_HOME:-~/.local/state}/stackshot/mq-replay/<run>/report.md` and printed; `report [--run ID]` prints it again (newest run by default).
- **Clean**: `clean --run ID` or `clean --older-than 1d` deletes a run's practice refs from the remote and its folders and stops that run's leftover driver units (`mq-<owner>__<repo>-<run>-<case>`, by exact name: the cases come from the run's `run.json` and from its refs, because a run id may hold `-` and a name prefix would also match another run's units; `--slug` names the repository when the remote is not a github.com url). `--dry-run` lists them. A run that still holds its lock is left alone whole, branches and units included, whatever its age (`--run` on it exits 1); a ref whose run age is unknown, and anything outside `practice/` and `queue/practice/`, are left alone too.
- `tests/mq_replay_run_scenario.py` (`tests/run-suite mq_replay_run`) runs all of it against a local bare repository with a fake `salamander`, `gh`, `systemctl` and `systemd-run` on `PATH`: matches, a forced mismatch, a conflict ejection, a failing PR dropped alone with its mate passing, isolation (a decoy queue state folder byte-identical, main unchanged, only practice refs added and removed), the gate at the start and mid-run with `--resume`, cleanup after a normal run, a failing case and SIGTERM, and the ref guard. No test reaches GitHub; the first real run is made by hand.
