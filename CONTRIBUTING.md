# How stackshot is changed

`main` is production: the services on the server box run from a checkout of `main`, and `deploy.sh` there is how a merge
becomes live. Nobody commits to `main` directly; nobody works in the production checkout.

## The branch model

1. **A change starts on a branch in its own worktree**, named `<kind>/<short-topic>` (see *Commit and PR text* below):
   `git worktree add ../stackshot-<topic> -b <kind>/<short-topic>` (for example `fix/handoff-row-wrap`).
   Each agent of the project works in its own worktree, so two agents never share a working tree.
2. **Before the PR, run the suites that cover what you changed; CI runs the ones the change reaches, and main runs them all** (builders stop rerunning everything locally, to spare the host's CPU). Locally that is `tests/run-suite <name>` for each suite whose code your change touches, plus the suite that holds the check a change to behaviour comes with. On the PR, CI runs the suites the change reaches by the measured map (see *Suite selection* below; the job summary says which and why), and a PR merges only when it is green there; after the merge, main runs every suite. To run everything by hand when you want to (not a required step): `for f in tests/*_scenario.py; do t=${f#tests/}; tests/run-suite "${t%_scenario.py}"; done`.
   `tests/run-suite` runs a suite in the one shared test environment (see Dependencies), not a new one per worktree.
   **A change to the pages' markup or style also runs the manual phone-width check**, `tests/run-suite phone_width_check`
   (a browser: once per machine, `uvx playwright@1.63.0 install chromium`; CI's runner has none, so it is not in the loop): the board,
   a project page and an item page are the screen's width at 360 to 430 px with every fold open, in light and dark, and the root
   paints each theme's background.
   **A change to the item page's answer box** also runs `tests/run-suite answer_back_check` (the same browser): it starts
   the server in-process on a temporary config and checks that an answer replaces the page in history and Back lands on the board.
   **A change to the home page's answer forms** also runs `tests/run-suite home_step_send_check` (the same browser): it checks that a step row's Send is enabled with the box empty and after typing, and that a decision row's Send stays disabled until a card is picked or a note is typed. **A change to the answer forms or to the home page's live refresh** also runs `tests/run-suite decision_pick_check` (the same browser): a picked card always reaches the item with its note, across a refresh that passes between the pick and Send.
3. **Open a PR against `main`.** The description says what changes for whom (a session, the owner, a machine) and which unit a deploy restarts, in plain engineering terms (see *Commit and PR text* below). Anything a session creates on GitHub is anchored on the board in the same turn.
4. **The builder (`my-engineer`) reviews, merges and releases it** (one agent releases; with several builders, the others send it reviewed PRs to release). Before the merge a fresh Sonnet reviewer subagent reads the PR, the diff and this section's checks, and answers approve or findings; the builder fixes the findings or says why not, and merges only on an approve. A small change goes on CI alone, with no reviewer read. Then one command on the server box, `~/stackshot/release.sh <pr>`. It runs detached (a transient user unit): waits for the PR's checks, then merges and deploys in one of two ways (**a merge deploys at once when the PR's run passed on a branch up to date with main**). *Up to date* means main's tip is in the history of the PR head the checks ran on (`git merge-base --is-ancestor`, after fetching both; GitHub's `mergeStateStatus` says BEHIND only when the branch rule "require branches to be up to date" is on, so it is not used), which makes the merge the very tree the checks ran on. A PR that is behind main is not sent to the old path: `release.sh` brings it up to date first (<owner>: main's full run never blocks a release; see *A branch behind main* below). The old path is for what the fast path cannot vouch for. It also needs (a) the live checkout to be at main's tip, so that everything on main is deployed already and nothing merged and still waiting on its run (an old-path release) or just rolled back rides along (behind main's tip only by commits that the docs-merge script (`[paths] docs_merge_script`) accepts without CI, docs and comments and runner settings, counts as at the tip, because a release never deploys them and the checkout stays behind after each one; the allow-list is read out of that script, `DOCS_MERGE_SCRIPT` names it, and an unreadable script fails closed to the old path; each commit's diff is read unquoted with fixed prefixes, and the checker's own summary line must say `files=N refused=0` with N the number of `diff --git` headers, so a quoted non-ASCII header or a checker that does not know the subcommand is never read as docs-only), (b) no failed main run on any commit after the last good one, read from GitHub's list of runs page after page until a run at or before the last good commit (an empty answer, a failed call, a list that never reaches it, or a run in the range cancelled after its job started is unknown: the old path) (a run still pending is fine: back-to-back releases both go fast, and a failure of the first rolls both back), and a readable last-good commit to go back to (below). **Up to date, and (a) and (b) hold:** `release.sh` merges and runs `deploy.sh` on the merge commit at once, so a merge reaches the live site within a couple of minutes (install changed units, restart the services the change touched, check `/healthz`), flags the `--recycle` and reports once, and only then waits for the tests run on `main` that covers that commit (a PR runs only the suites its change reaches, main runs them all: see Suite selection; which run covers it: *Which run covers a merge*, below). A pass is a log line, `main's tests passed on <sha>`, and the commit becomes the last good one (`<paths.state>/releases/last-good`; the first time, the deployed `HEAD` when its run on main passed), after a check under the deploy lock that it is still in the live checkout (a rollback cannot land between the check and the record). Just before `deploy.sh` runs on a fast deploy (production changes at its fast-forward, and restarts and healthz take up to 180 s) a pending-verify record (commit, PR, time) goes under `<paths.state>/releases/pending-verify/`, its flock held by the running release and the record removed when the watch concludes; a release killed in between leaves it with the lock free, and **the next release to start reads that commit's main run first**: a pass is recorded, a failure rolls back and reports red for that PR as a live watch would, a run cancelled counts for nothing (*Which run covers a merge*, below), and one still going, or not found yet, or unreadable keeps the record and refuses the fast path until it is read (after two hours it is unknown: a red report). A rollback that never ran (the deploy lock not had) keeps its record. A failed deploy clears the record with its red report. Every external command runs without the lock file descriptors, so a child that outlives it holds no lock. A failure **rolls the deploy back**: `deploy.sh` with `DEPLOY_ROLLBACK=1 DEPLOY_TO=<last good>`, the only way `deploy.sh` goes backward. It is refused unless the deploy lock is held (by hand: `flock <paths.state>/releases/deploy.lock env DEPLOY_ROLLBACK=1 DEPLOY_TO=<sha> ./deploy.sh`), the checkout has no changed tracked file (staged or not) and no untracked file at a path the target tracks (an untracked file elsewhere, such as `.claude/`, is no matter), and is at a commit on `origin/main`, and the target is older and has a `deploy.sh` that knows the second step; it resets the checkout to the target and runs the target's own `deploy.sh`, so the good tree's units, restarts and health check do the work. The builder hears `FAILED at main's tests: rolled back to <sha>`, which names the merges the failing run covers when it covers several, the unit and timer files the rolled-back commits added (left installed: disable by hand if needed), whether a recycle had been flagged, and that **a rollback does not undo data or state changes the commits made**. Every other merge between the last good commit and the live checkout is taken out too, those deployed before the failing one (their runs still waiting) as well as those on top: each PR gets its own message ("rolled back with #A's failure; it is merged but not live; it goes live with the next release once main is fixed, or ./deploy.sh once main's tip run is green"), and its own run says "passed, but not live" when it ends (checked with git: the merge must be in the live checkout; a marker alone is not relied on, and such a run does not become the last good commit). A failed `deploy.sh` on the fast path (healthz, say) is reported red and not rolled back, as on the old path: the rollback is for main's run failing. It rolls back only while the live checkout still contains the failing commit and no newer commit whose main run passed contains it; otherwise the report says it did not. `release.sh` ends every arm of its dispatch in an explicit `exit`, because a deploy replaces the file under the running script. A run that cannot be read in the time allowed (no covering run passed or failed; a cancelled run counts as none), is reported, not rolled back (check by hand). Main keeps the failing merge: fix forward or revert. **Otherwise** (not up to date, (a) or (b) failing, no readable last-good commit, or main moved between the check and the merge): the old path, with the reason in the log: merge, wait for the tests run on `main` that covers the merge (*Which run covers a merge*, below; that run failing stops the release merged and not deployed), then `deploy.sh` to the commit main's tests passed on. It reports once to `projects/example` as a `[release]` message — green with the commit and what restarted, or red with the step that failed and the log. A green one is logged, not delivered: the server rules it merged as `stackshot (auto)`, comments on the items anchored to the PR, and leaves it on the project's routing page. A red one is delivered to `projects/example`, where the router rules it and passes the failure to the agent whose files it touches. `release.sh --status` shows a run; `deploy.sh --dry-run` shows what a deploy would restart.
   **A change no test can exercise merges at once, without `release.sh`**: docs, Markdown, comment-only lines, and a CI workflow's runner and concurrency settings. The builder runs the docs-merge script (the path in `[paths] docs_merge_script`) as `docs-merge.sh howardpark-ai/stackshot <pr>`, a dry run first (`--dry-run`). The script checks the diff line by line, pins the head commit and merges, or refuses with `REFUSED: <file>:<line>` lines and exit 3, which means "use `release.sh`". It merges without deploying: the production checkout picks the change up at the next release's fast-forward, and nothing a docs-only change touches is read by a running service. Every other change takes `release.sh`.
   **A branch behind main** (main's full run never blocks a release): before, a PR behind main took the old path and waited for main's full run, so in a burst of PRs only the first was fast. Now, when the PR's checks have passed and main's tip is not in its head's history, `release.sh` updates the branch (`gh pr update-branch`: main is merged into it, no rebase and no force push), waits for the PR's own tests on the new head (up to 50 minutes, polled every 20 s, the same cap as the first wait; a failed or cancelled check fails at once, whichever it is, and a pass needs the `suites` check to be completed and successful in GitHub's check-runs of that very commit, so a pass still read from the old head is pending), and merges (pinned to that tested head) and deploys at the merge on the fast path; main's full run follows the deploy and rolls it back on a failure, as before. If main moved while it waited (another merge), it updates again and waits again, 3 rounds at most (`RELEASE_UPDATE_ROUNDS`), then takes the old path with the reason in its log. Releases that both need an update take turns, under `<paths.state>/releases/update.lock` (waited for up to 3 rounds x (50 + 3 min) + 15 min = 174 minutes by default, `UPDATE_LOCK_WAIT`; past that the release fails at `update lock` before anything is merged), taken before the deploy lock and let go when the merge is made, so they do not keep invalidating each other's update and the next one updates on top of the merge while the first deploys. When it has the lock a release reads the PR again: a closed PR fails it, a head pushed meanwhile has its tests waited for, and a branch that is up to date by then is not updated. A PR that is up to date from the start takes no update lock (it does not wait behind another release's CI), so its merge can still land on main during a round; the updating release then takes another round or, after 3, the old path, which is safe. An `update-branch` that errors (a conflict with main) fails the release at `update-branch`, and tests that fail on the new head fail it at `pr tests`: neither falls back to the old path. One conflict is mended instead of failed: when two PRs both change tool text, merging main conflicts on `tests/tool_text.snapshot.json`, a generated file, and on nothing else (releases failed on it). `release.sh` then runs `tools/snapshot_regen.py`, which merges main into the PR head in a temporary worktree of its own (removed on every way out, locked with `flock` while it runs), and if the conflicted paths are exactly the snapshot takes main's copy, runs `python3 tools/tool_text.py update` and `check`, commits the merge and pushes it to the PR branch with a plain `git push` (never forced, so a branch its author pushed to meanwhile is refused), logs one line saying so, and goes back to waiting for the PR's tests on the new head (inside the same update round, under the update lock it already holds). It makes no GitHub API call: only git's own transport, after the `refs/pull/N/head` fetch it already does. At most `RELEASE_REGEN_MAX` (default 2) regenerations per release run. Any other conflicted path, a regeneration that fails, a push that is refused or a PR from a fork declines the mend and the release fails at `update-branch` (or `mergeable`) with the same message as before. `release.sh --status <pr>` shows the log's tail, whose newest line says what is waited for (a "waiting for the PR's tests" line every 5 minutes).
   **No retest when nothing could differ**: the catch-up above costs a full retest, and for most PRs it cannot find anything the first run did not. Before it updates a branch, `release.sh` asks `tools/retest_skip.py` (`skip_retest`): the PR's changed files (merge base to head) and the files main's new commits changed (merge base to main's tip) are read against the suite map that main's measured run publishes as the artifact `suitemap` of `tests.yml` (for each suite, the Python files it ran, the files it opened, statted, ran or looked for, and the directories it listed). It skips the retest only when no suite reads both a file the PR changed and a file main's new commits changed, no file is changed by both sides, and every changed file is known to the map (read by a suite, or in the map's commit tree). The map's read sets are those of the map's commit, so a dependency a change adds is invisible to it, and the rules are strict about that: files changed between the map's commit and main's tip count as main's side too, and a diff on either side that adds or changes an import or `from` line, a call that loads, runs or reads a file (`importlib`, `__import__`, `subprocess`, `exec`, `open`, `read_text` and the like), a listing, glob, existence or stat call (`os.listdir`, `glob`, `iterdir`, `exists`, `stat` ...), or a string that looks like a repository path (a file name, anything with a slash, any string with `*` or `?`, a name at the repository's root), in any Python file (or a line that sources or names a file in a shell script), retests. A map that is missing, unreadable, older than 2 days, of a commit that is not in main's history, published by a run of another commit than its own, without file measurement or with a suite that has no clean measurement (one that failed only when measured keeps its earlier clean measurement as a carry, which counts unless older than 2 days or of a commit outside main's history, and the drift is counted from the carry's commit); an unknown file (new since the map); a Python file the helper cannot parse; or, on either side, a change to what the workflow checks outside the suites (the always-retest list: `.github/`, `release.sh`, `deploy.sh`, `tests/run-suite`, `tests/pyproject.toml`, `tests/uv.lock`, `tests/suitemap.py`, `tools/retest_skip.py`, any `*.lock` file, the `# /// script` block of any Python file, `tools/tool_text.py`, `tests/tool_text.snapshot.json`, `tools/clean_text.py` (what the tool-text job reads besides, `server.py` and the tool functions, needs no entry: a change that matters there also changes the snapshot, which always retests)): retests, exactly as in *A branch behind main*, with the reason in the log (`retest needed for the PR head …: <why>`). When it skips, there is no `update-branch`, no update lock and no wait: `release.sh` merges the PR head its checks passed on (pinned, as always) and, under the same conditions as for an up-to-date PR (the live checkout at main's tip, no failed run since the last good commit), deploys at the merge. The decision is made again under the deploy lock on main's tip as it is then; if it no longer holds, or main's tip is not exactly the merge of the tip checked and the head, the old path takes the merge (main's run first). The log line (`retest skipped for the PR head …`) and the green report (`was NOT retested: its last green checks stand …`) name both file sets. A merge made this way is not entered in the ride-along ledger, since its tree is not the one the checks ran on. Main's full run after the deploy checks every suite and rolls the deploy back on a failure, as for any fast deploy. The map is downloaded once per artifact (`<paths.state>/releases/suitemap/`, the older copies removed); `RELEASE_SKIP_DISJOINT=0` turns the skip off and `RELEASE_SUITEMAP=<file>` reads a map from a file.
   **Ride-along** (main's full run never blocks a release): the fast path wants the live checkout at main's tip, so one release on the old path (merged, waiting for main's run) left it behind, every later release failed that condition too and waited for a main run, and main's queue kept only the newest waiting run. Now a merge that `release.sh` made itself on a passing PR check and an up-to-date head (the PR head contained main's tip, and main's tip was then exactly the merge of the two) is recorded in `<paths.state>/releases/fast-ok.json` (written whole, under a lock file), whether that release deployed at the merge or took the old path for another reason. The live checkout counts as at the tip when every commit between it and main's tip is such a merge or a docs-only merge; the next release then deploys at its own merge, carrying the earlier one, and main's run for its merge covers both. The old path's merge of a branch that was not up to date is not recorded, so it still blocks until its own release deploys it. A failing main run takes its merge and every merge the rollback takes out off the ledger before the reset, so a rolled-back commit still on main never rides along; so does an old-path release whose covering run failed; when the entries cannot be taken out the whole file is removed. An old-path release whose own run fails while its merge is already live (a release rode along on it and deployed on top) is not "merged, not deployed": it takes the same rollback as a fast deploy, the rider with it, and reports "LIVE via ride-along, rolled back". Every ledger write also prunes the merges that are deployed already (ancestors of the live HEAD) or at or before the last good commit, and the gate counts only entries that descend from the live checkout. A file that cannot be read as a ledger (bad JSON, a key that is not a 40 or 64 character sha, an entry without an integer `epoch` and `pr`) is left alone and ignored: only docs-only merges count, as before. The by-hand rollback command in a red report ends with the ledger file to delete. Conditions (b) (no failed run since the last good commit) and the pending-verify records apply to the whole range as ever.
   **Which run covers a merge** (after several PRs merged within minutes of each other and releases failed at their time limit): main's workflow runs one run at a time and cancels a queued run when a newer push arrives, so the run on a release's merge commit M can be cancelled while a later run, on a commit that contains M, is the one that tests it. The old path waited for the run on main's tip, which was queued behind a long run, although the PR's own run on its merge had passed. Now M is covered by a main push run on M or on any later commit C that contains it (`git merge-base --is-ancestor M C`), and the runs are read oldest first, a cancelled one skipped, up to the first that has not passed: one still queued or going is waited for; the newest run that passed before it satisfies the release, which deploys to that run's commit (`DEPLOY_TO=<C>`); a run that failed ends the release as before, with this exception: when a run on M's own commit, or on a commit between M and the failing one, passed, the failure belongs to a later commit and the pass decides, so the release is judged by the oldest commit that failed, and the log says whose run decided. The 90-minute limit (`RELEASE_WAIT_MAIN`; a slow run on a loaded host could otherwise end a release) counts from when a covering run starts (in progress), not from the merge, and starts again for another run that starts; an outer cap of 3 hours from the merge (`RELEASE_CAP_MAIN`) keeps a release from waiting forever; the log line of a wait that gave up names both. The same rule serves the fast path's watch after its deploy: a cancelled run on its own merge no longer ends in `unknown` when a later run containing it passes; only cancelled runs and nothing else is `unknown` after the cap, and still never a rollback. **Step results**: GitHub fills in a job's step results some time after the run reports completed, and a release read main's run in that gap and failed a green run. A run that is completed and green whose `run every suite, measured` step has no conclusion yet is pending, read again at the next poll for `RELEASE_WAIT_STEPS` (600 s) at most; past it, or when that step concluded anything but success, the run fails as before.
   **Two releases never deploy at the same time**: the merge and the deploy run under an exclusive lock, `<paths.state>/releases/deploy.lock`, waited for up to 15 minutes (a release that cannot get it in that time fails at `deploy lock` before anything is merged). The wait for a PR's checks happens before and outside the lock, so no release waits for another release's CI, only for a deploy that is running, which takes seconds to a few minutes (the health check alone waits up to 3 minutes). The lock is let go while the release waits for main's tests run (after the fast deploy, or before the old path's deploy) and taken again for the deploy or the rollback, so a release waiting on main never holds another one's deploy; it is released when `deploy.sh` returns. It is taken by `release.sh`; `deploy.sh` run by hand takes none. Every merge `release.sh` makes passes `--match-head-commit` with the head the checks ran on (the PR head it read at the start, or the updated head after an `update-branch`), so a push after the checks cannot ride in on the merge.
   **How a session runs it:** one plain `release.sh N` per command (it starts its own unit and returns at once). Wait for its log, `<state>/releases/pr-N.log`, for a line with ` done: ` or ` FAILED `, in a `run_in_background` shell with `timeout`. Never chain waiters that start the next release when the previous log says done: a failed step stops every later one with no report. Auto mode also refuses a loop of `release.sh` runs.
   **Several PRs go in the release queue** (releases ran one after another with long idle gaps, each waiting for main's full run before its unit ended and the next was started, although nothing stops a release from starting while another waits on main's run): `release.sh queue N [N...]` records the PR numbers in order in `<paths.state>/releases/queue` (a PR queued already keeps its place). `release.sh queue` first reads the PR's check rows and refuses a PR with a failing, cancelled or timed-out row (exit 1, each such row printed with its state and link, nothing queued), and a PR whose rows cannot be read; pending and skipped rows do not refuse, and there is no bypass. When no queued release is running and the queue is not paused, the first one starts at once, as `release.sh N`, and stays in the queue file until it reaches *deployed*; from then on the queue's running release leaves the queue and starts the next queued PR's release itself when it reaches *deployed* (the deploy and its report are done, and it only waits on main's run; on the old path main's run has passed by then). A queued PR that fails before its merge (its checks fail, it conflicts, it is closed, a lock is not had) is reported exactly as such a failure is today, and skipped: it starts the next one, and its red report says "skipped in the release queue". A failure after the merge of a release **the queue started** (main's run failing for it: merged and not deployed on the old path, or rolled back after a deploy at the merge; its deploy failing) **pauses the queue** (`<paths.state>/releases/queue.paused`, with the PR and the step): no new release starts, the rollback and the red report run as before and say the queue is paused, and `release.sh queue --resume` goes on once main is fixed. A plain `release.sh N` that fails writes no pause. The pause is written before the deploy lock is let go (a rollback writes it first thing, a failed deploy before it releases the lock), so a release waiting for that lock finds it when it gets the lock. A pause also stops the release the queue had started already but not merged (the next one starts at each deploy, so one is usually running when main's run fails): after its checks pass and again before the deploy lock it fails at `queue paused` as a failure before the merge, with no hand-off, and stays first in the queue, so `--resume` releases it. The PRs a rollback took out with the failed one (releases deployed on top, or before it with their runs still waiting) are merged and stay on main, so they are not queued again (`release.sh N` on a merged PR fails at `pr state`): the red report and `queue.log` name them ("rolled back with it, merged and not live"), and the next release's merge deploys them once main is green (or `./deploy.sh` once main's tip run is green). A release the pause stopped before its merge is different: it is not merged, and stays first. A main run that cannot be read in time is not a failure and does not pause it: the merged PR leaves the queue and, if it still held the queue, the next one starts. `release.sh queue --list` shows the queue in order, the pause and the running release; `release.sh queue --drop N` takes a PR out. The running release is the one the queue last started (`queue.driver`); a release started by hand while it runs starts nothing from the queue, and one that finds no queued release running (the last one was killed, say) starts the queue again from its first entry, so the queue never stalls. A killed release is still in the queue file, first, so `queue --list` shows it and `queue --resume` starts it again (one already merged then fails at `pr state` as a skip and the queue goes on). A queued release takes no `--recycle`: release such a PR by hand; a queued PR whose changed files include `client.py`, `client/hooks/`, `hooks/` or `skills/` (a `SKILL.md`) gets a warning in the log and in its report that no recycle was flagged, and its report is not green. Every change to the queue is made under flock on `queue.lock` and logged to `queue.log`. When GitHub says the PR's `mergeable` is UNKNOWN (it recomputes for a while after main moves), the release reads it again every 10 s for up to 3 minutes; only CONFLICTING, or UNKNOWN past that, fails it at `mergeable` (a CONFLICTING that is only the tool-text snapshot is mended first, as described under "A branch behind main"; the release then reads `mergeable` again for the new head).
   **The merge queue, shadow** (salamander's `docs/mq.md`, step 4). salamander's own merge queue (`salamander mq`, run as a chain: each waiting PR is an entry built on the entry ahead of it, main plus the PRs ahead plus itself; every entry is pushed to its own `queue/main/g<n>` branch and tested by this repository's workflow, all at once, so the whole stack is tested in one pass; the entries merge to main in line order; a failing PR is dropped on its own and the entries behind it are rebuilt on the one ahead and tested again, about 3 extra runner runs for 4 PRs) is switched on each host by a host file, `~/.config/mergequeue/<owner>__<repo>.toml` (`XDG_CONFIG_HOME` honoured), with `mode = "off" | "shadow" | "on"`. **No file, or `off`, is today's `release.sh` exactly** (the default; nothing here runs). The repository's own rules are `.github/mergequeue.toml` (read from main's tip, so a PR cannot change its own): the required check is the `suites` job of `tests.yml`, which runs on a `queue/**` push as a pull request's does (the suites the change reaches by the newest map, `suites = "select"`; main's full measured run follows the merge); branch prefix `queue/main/`; `queue_mode = "chain"` (the queue's one mode; `inflight_max` is left to the chain's default of 6 entries tested at once); and a conflict on `tests/tool_text.snapshot.json` alone is mended in the entry's worktree by regenerating it (`python3 tools/tool_text.py update` then `check`), as `tools/snapshot_regen.py` does for one PR. **`shadow`**: right after a release has read its PR (open and mergeable, before it waits for the checks) `release.sh` also runs `salamander mq add <pr>`, under a short timeout (`RELEASE_MQ_ADD_TIMEOUT`, 20 s); the queue then tests the PR as an entry of its chain and journals what it would have merged, but in shadow it merges nothing, posts no status and no comment, so `release.sh` stays the only thing that merges and deploys. The PR is queued before the old path decides because once the old path has merged it the queue can no longer test it. When the release ends (whichever way), it records what it did and starts a unit, `stackshot-mq-shadow-<pr>-<run>` (`release.sh --mq-compare <pr> <run>`; <run> is the epoch and pid, so a rerun within the 5 hours has its own unit and its own record), which waits for the queue's verdict (`salamander mq wait`, a read of the queue's state file, at most `RELEASE_MQ_WAIT_CAP`, 5 hours) and appends one line to the release log, `<state>/releases/pr-N.log`: `merge queue (shadow): PR #N: agree|DISAGREE|no comparison: ... Old path: ... Queue ...`. A DISAGREE is the old path merging what the queue would not (or merging it, main's run then failing it while the queue's entry passed), or refusing at its checks, a conflict or the update what the queue would have merged; "no comparison" is a queue with no verdict (including a PR the queue ejected only because it left the group, closed by the old path's own merge: counted as neither agree nor DISAGREE), a release that stopped before it decided (a lock, a pause, a closed PR), or a PR the old path merged before the queue read it. The release never waits for the queue: a missing `salamander`, an `mq add` that errors or times out, or a unit that does not start is one log line and the release goes on unchanged. **`on`** (the merge step) is routed by **count**, at the moment the release queue would start a release. **One PR waiting** is released alone by the old path, unchanged: no `salamander mq` call at all, and both of its shortcuts (a PR already tested on main's tip merges without a new run, and `tools/retest_skip.py`) still apply. **Two or more waiting** go as **one hand-off of at most 4 PRs** (release.sh's own number, `MQ_HANDOFF_MAX`, not a setting of the rules file; the others stay first in the release queue for the next hand-off): the release queue starts `release.sh --group N1 N2...` (unit `stackshot-release-<first>`, which is the queue's driver), which first reads each PR's GitHub state (a PR merged already, by an earlier run of the group that was killed after the queue merged it, joins the deploy through its merge commit and is not handed over again; a closed one fails on its own), then hands the rest to the queue in one `salamander mq add N1 N2...`, waits for each with `salamander mq wait N` (in slices of `RELEASE_MQ_SLICE`, 5 minutes, with a look at whether the queue is paused or blocked, and whether release.sh's own queue has been paused, between slices, up to `RELEASE_MQ_WAIT_CAP`, 5 hours), and then deploys what the queue merged **once**, with the old path's own steps after its merge: the deploy lock, the fast gate (the queue's merge commits go into the fast-ok ledger first, their tree being exactly the one the group's run tested), `./deploy.sh` pinned to the merge, one session pick for the files of all the PRs, one green report and one `done: <sha>` line per PR (so waiters and board hooks work as ever), then main's run for the merge with the rollback and the pause. A PR the queue ejected or failed is reported as a failed release of that PR, with the queue's reason, and the rest still go out (the unit ends 1). Any failure of the queue itself (an `mq` error or a `salamander mq:` message, a wait past the cap, a queue paused or blocked, a pause of release.sh's own queue, a merge commit that cannot be found) is a clear log line, drops the PRs still open from the queue (a drop of a PR the queue does not hold, `is not in the line`, counts as dropped; any other failure keeps the marker only while `mq status` still lists the PR), and **pauses the release queue** (the unresolved PRs stay first in it; `release.sh queue --resume` tries them again): never a silent drop, and never a merge by the old path of a PR the queue also holds. **If any PR of the group has merged by then, the merged set is deployed all the same** (with the post-merge code, one `done: <sha>` per merged PR) and only the unresolved PRs are logged FAILED; a merged PR is logged FAILED only as `merged, not live` (a deploy that cannot happen: the fetch, the commit, or the deploy itself fails, or no commit can be named for it), with the command to run by hand. The queue merges the PRs of a hand-off one push at a time, so before a PR is dropped or reported failed its GitHub state is read again: one that is merged (the queue ejects it with `pull request is merged`, or the wait stops before its turn) is deployed with the group, its merge commit taken from GitHub or, when GitHub names none (the queue merges each PR into its entry with `merge --no-ff` and pushes the entry head to main by fast-forward, so a PR head is only the second parent of its merge commit), the commit of main's first-parent line that brought the PR's head in, found after a fetch (`rev-list --first-parent --ancestry-path <head>..origin/main`, the earliest); a PR for which neither can be found is reported `merged, not live` and leaves the release queue's file with the pause. A GitHub state that cannot be read is tried once more; if it still cannot, the PR is neither dropped from the merge queue nor called failed or not merged: it is reported unresolved (`pr state unreadable`), keeps its marker, and stays first in the release queue. **How the two paths exclude each other:** the host file must name this script's own deploy lock (`deploy_lock = "<paths.state>/releases/deploy.lock"`; otherwise `FAILED at mq mode`), because the queue's merge push takes that lock without waiting while a lone release holds it from its merge to the end of its deploy, so the queue never merges mid-release and a group's deploy never overlaps a push; the release queue starts one thing at a time (a group or a lone release); and a group writes a marker per PR (`<state>/releases/mq-on/pr-N`) before `mq add` and removes it once the queue no longer holds the PR, which the old path in mode on refuses (`FAILED at mq line`), at its start and again under the deploy lock just before its merge; a group refuses a PR whose own `stackshot-release-<pr>` unit is running (`FAILED at release running`), `--group` and `--run-group` refuse the same PR twice or more PRs than one hand-off (4), and `release.sh queue --drop N` of a PR already handed to the queue says so and names `salamander mq drop N` and the marker file instead of reporting it dropped (a stale marker, one whose group release is gone and which `salamander mq status` no longer lists, is removed by the same command, and the PR is dropped). The hand-off is at most 4 PRs, release.sh's own number: the chain tests those entries at once, merges them one PR at a time in line order, and the single deploy after the last of them covers all. The rules file carries no `group_max` or `bisect` (salamander only warns about them now), and `release.sh` reads neither. salamander's `ON_OPEN` switch must be open too: until then `salamander mq add` refuses mode on and a hand-off fails at `mq add` with its message and pauses the release queue. A host file that does not read (bad TOML, an unknown mode) is one log line and the old way. Tests: `tests/release_queue_scenario.py`, sections 17 and 18 (a fake `salamander mq` and a fake `systemd-run`, a scenario folder as `XDG_CONFIG_HOME`, so a real host file never reaches a test).
   `release.sh` picks what the running sessions need from the files the PR changed (the map is `session_need` in `release.sh`, the table [docs/session-reload.md](docs/session-reload.md)): nothing, a notice (`[fleet] notice_cmd`, when set) or a recycle, which only a file a session loads once at its start (the SessionStart hook) needs; then the open items anchored to the PR wait for a recycle. A recycle is never an item of its own; with no item anchored, the fleet tool is asked for one once the box is idle (`[fleet] recycle_when_idle`, when set). `release.sh <pr> --recycle` forces a recycle and `--no-recycle` forces nothing; `release.sh --pick <pr>` shows the pick first. A change to a tool or its parameters is a notice, not a recycle: claude.ai refreshes its cached tool list on its own within about a day, and until then a session closes or calls the new form through the MCP Portal's Code Mode.
5. **A minor fix** that restores intended behaviour with no design choice in it is the builder's to make, on a branch like any other change, the owning agent told, and a small one goes on CI alone. Anything with a design choice is the agent's PR.

## Branch names carry the builder

A branch is now named `<kind>/<short-topic>` (step 1 above, and *Commit and PR text* below), which carries no agent name; the rest of this section describes the routing by an agent-named prefix, which applies only to a branch that still has one. The router reads the head branch of a pull request that anchor-hub reports (a CI result,
a comment, a merge) and, when the prefix before the first slash is a background agent's name, passes the notice to that builder (router rule `anchor-builder`) and not to the item's
front mover. A branch named `<kind>/<short-topic>` is of any other shape here; a branch of any other shape (a person's, `main`, a subagent's
`worktree-agent-…`) routes as before, except that a CI result on any pull request, whoever's branch it is, goes to the project's builder too (router rule `anchor-ci`), never to a front agent. A builder's report on an item is written onto the item, not messaged to a front agent (the `message` tool; README, tool table);
a hand-back to a front agent mover is held three minutes and dropped when the item is closed in that time (README, *A front agent mover hears of its item at two moments only*).

## Commit and PR text

Commit messages, branch names, PR titles and PR bodies in this repository carry none of the instance owner's data: no board item ids, no owner or
colleague names, no machine names, no session or agent names, nothing about the one live instance. A change explains itself in plain
engineering terms: what it does, why, and what a reader of the diff needs to know. The link between a PR and a board item is kept outside git, on the board and in the
project's notes.

- **Branch names** are `<kind>/<short-topic>`, with `<kind>` one of `feat`, `fix`, `docs`, `ci`, `refactor`, `test`, `chore` (for example `fix/handoff-row-wrap`).
- **Allowed on purpose:** the `Co-Authored-By: Claude … <the Anthropic noreply address>` (or `Anthropic …`) and `Claude-Session:` trailer lines of a commit, and in a PR body the "Generated with [Claude Code]" line and the claude.ai/code/session URL line under it. A line like that is not read against the deny list (whole lines only; the generic patterns still read it). Any other `Co-Authored-By:` line, a colleague's name or a private address included, is ordinary text and is checked. The first line of a standard merge commit ("Merge branch 'main' into …", `git pull`'s "Merge branch '…' of … into …", "Merge pull request #N from …") is skipped, but the branch names in it are checked like a branch name; the owner and the URL in it are not.
- **CI enforces it** (`.github/workflows/clean-text.yml`, on every pull request, again when its title or body is edited): `tools/clean_text.py` reads the PR title, body, head branch and the message of every commit the PR adds
  to its base. It looks for board item ids (`board#N` anywhere in a word, so `_board#N` and `xboard#N` count and so does `dashboard#N`; `board-tmp-<name>#N`, the name made of letters, digits and hyphens) and links to a `https://<host>/items/<n>` path, and for the words on a deny list. The deny list is the owner's data, so it is not in the
  repository: it is the repository secret `CLEAN_TEXT_DENY` (one case-insensitive Python regex per line), given to the one step that runs the script. It is a secret and not a variable because the runner prints a step's variables in the log and masks only secrets. Where there is no secret (empty, unset, or a pull request from a fork) only the generic patterns run, and the log says the deny list was not available. A failure prints the field, the line number and, for a generic pattern, the offending line; a deny pattern is named by its line number in the secret (`deny pattern 3`) and neither it nor the line it hit is printed.
- **Text is refused before the push, not only after it** (a push to a public repository publishes what it carries; CI is the backstop). The tracked hooks in `.githooks/` do it: `commit-msg` refuses a commit whose message hits, and
  `pre-push` refuses a push whose branch name or new commit messages hit (for each pushed ref, the commits the remote being pushed to does not have yet; a branch delete is skipped). Only that remote counts: a commit that sits on another
  remote's tracking branch, a private one for instance, is not published by this push and is checked. A push by a URL is matched to the configured remote that has the URL; a URL no remote has is checked against all history (more, not less).
  `commit-msg` reads every line of the message, `#` lines included (`git commit -m` keeps them); it leaves out only what git itself writes into the editor template: everything below the scissors line of `commit -v`, and the
  `# On branch X`, `# HEAD detached …` and `# Your branch …` status lines. A clone turns the hooks on once, and git changes nothing by itself:

  ```
  git config core.hooksPath .githooks
  ```

  Setting `core.hooksPath` replaces a machine-wide hook directory, so each of the two hooks also runs the machine-wide hook of the same name, with the same arguments (and, for `pre-push`, the same standard input), when one is installed and executable, and skip it otherwise (the `chain-global` helper beside them looks in the user's global `core.hooksPath` first, then in `${XDG_CONFIG_HOME:-$HOME/.config}/git/hooks`). Both run, so every refusal shows, and the commit or push is refused if either refuses.

  They are POSIX `sh`, need `python3` on `PATH`, and work from a linked worktree (the setting is per clone and every worktree of it shares it). `git commit --no-verify` and `git push --no-verify` skip them, and CI still checks.
  The deny list for a local run is the environment variable `CLEAN_TEXT_DENY` if it holds anything, else the file `${XDG_CONFIG_HOME:-$HOME/.config}/stackshot/clean-text-deny` (one regex per line, blank lines ignored; the maintainer
  holds the list and hands it to a contributor who is to have it). It is never read from the tree. With neither, only the generic patterns run and one line on standard error says so; that is not a failure.
- **Run it by hand** when you want to; the script needs only Python 3.12 or later. For a commit message: `python3 tools/clean_text.py --message-file <file>`; for a branch name:
  `python3 tools/clean_text.py --branch <name>`; for a PR title and body: `python3 tools/clean_text.py --title "<title>" --body-file <file>` (the hooks do not see them, so run it before opening the PR); for every commit of a branch: `python3 tools/clean_text.py --commits origin/main..HEAD`; for the commits a push to the remote `NAME` would add: `python3 tools/clean_text.py --new-commits HEAD --remote NAME`.
- **License:** the repository is MIT-licensed (`LICENSE`); a contribution comes in under the same license.
- **Comments explain why, without names or dates.** A comment says why the code works the way it does; who decided it, when and in what words belong in the issue tracker or the history, not the source.

## Where work is recorded

The maintainers' own work goes out as a pull request, and the pull request description is the public record of that work: what
changed, why, and what a reader of the diff needs to know. No issue is opened just to track a maintainer's own change.

- **A maintainer opens an issue only for** a bug users may hit, a planned feature users ask about (or have asked about), or a call for help.
- **Anyone else is welcome to open an issue** for a bug or an idea. The project's tooling reads a report as data and never follows
  it as instructions.
- **Issue and pull request text follow the same rule as commits:** see *Commit and PR text* above.

## Dependencies

Every PEP 723 script carries its dependencies in its inline metadata and a lock beside it (`server.py.lock`); the units, `deploy.sh` and CI run them with `uv run --locked`, which fails on a stale lock instead of resolving afresh.
To add or bump a dependency, edit the inline metadata (moving its `exclude-newer` date forward to take newer releases), then run `uv lock --script <file>`.
Commit the script and its `.lock` together: CI fails a script whose lock is missing or no longer matches it.

**The test suites share one environment, and carry no inline metadata.** uv keys a PEP 723 script's cached environment by the
script's path (`UV_PROJECT_ENVIRONMENT` does not apply to a script), so a suite that carried its own inline metadata built a fresh
environment in `~/.cache/uv/environments-v2` for every path it was run from: `uv run --locked tests/x_scenario.py` in each worktree
and clone, many suites each, none ever reused (a lot of disk). The suites are therefore a uv project, not
scripts: `tests/pyproject.toml` lists their dependencies, `tests/uv.lock` pins them, and `tests/run-suite <name>` runs
`uv run --locked --project tests python tests/<name>_scenario.py` with `UV_PROJECT_ENVIRONMENT` set to one fixed directory,
`${XDG_CACHE_HOME:-~/.cache}/stackshot/test-venv`. The first run in any checkout builds that environment, every later run in any
checkout reuses it, and `--locked` still fails on a stale `tests/uv.lock` instead of resolving afresh. **Run a suite through
`tests/run-suite <name>`** (`pilot`, or `phone_width_check`): it shares the one environment and gives the run a scratch folder that is
removed afterwards. A bare `uv run --locked tests/x_scenario.py` still works but no longer adds anything to uv's cache: uv finds
`tests/pyproject.toml` from the script's folder and uses that project's own `tests/.venv` in the checkout (uv's default, ignored by Git,
removed with the worktree). `./tests/x_scenario.py` no longer runs, the suites have no shebang. To add or
bump a test dependency, edit `tests/pyproject.toml` and run `uv lock --project tests`; commit both files. A suite has no lock of its
own (CI's lock step checks the scripts that carry inline metadata, which the suites no longer do). The production scripts
(`server.py` and the rest) and the `tools/` scripts keep their inline metadata and locks and still run with `uv run --locked --script`.

## Scratch folders: a suite leaves nothing behind

A folder made with `tempfile.mkdtemp` and removed by one line at the very end of a suite is left in `/tmp` by a failing check, an
exception or an early exit, and folders left behind pile up in `/tmp`. Two things hold:

- **A suite makes its folders with `tests/_scratch.py`**: `import _scratch`, then `tmp = _scratch.mkdtemp(prefix="x-")`. They are removed,
  with whatever is in them, when the process ends: a pass, a failing check, an exception, `sys.exit`, `os._exit` (which the suites end
  with, and which skips `atexit`: the helper wraps it), SIGTERM and SIGHUP. Only the process that made a folder removes it, so a forked
  child's exit does not take its parent's away. `_scratch.track(path)` hands over a path made some other way (a folder the code under
  test names inside `tempfile.gettempdir()`). A suite never calls `tempfile.mkdtemp`, `mkstemp` or `NamedTemporaryFile` itself, and never
  names a `/tmp` path: it takes the folder from `tempfile`, which honours `$TMPDIR`. `tests/scratch_scenario.py` checks both.
- **`tests/run-suite` gives each run a `$TMPDIR` of its own** (`rs.XXXXXX` under the caller's `$TMPDIR`, short because a unix socket path
  is limited to 108 characters) and removes it when the suite ends, so what a subprocess or the code under test left goes too. uv keeps
  the caller's `$TMPDIR` (its one `uv-<hash>.lock` per project path stays there, and is the only thing a run leaves).

- **A running suite's folders hold a shared BSD lock** (`flock`, taken by `_scratch.mkdtemp` and `track` on each folder, and by `run-suite` on its `rs.*` folder). the host's age-based systemd-tmpfiles sweep clears old `/tmp` folders, which skips a locked folder and everything below it (tmpfiles.d(5)), so a long suite's folder is never taken while it runs. The lock drops by itself when the process ends or crashes, and a child process that outlives the suite does not keep it.

**To debug a suite, `KEEP_SCRATCH=1 tests/run-suite <name>`** leaves the folders and prints their paths (`scratch kept: …`); remove them yourself after.
To measure a suite: `d=$(mktemp -d); TMPDIR=$d tests/run-suite <name>; ls $d` shows only uv's lock file.
Run the suites with a `TMPDIR` outside any git repository (the default, `/tmp`, is): the `pilot` and `update` "not a git checkout" checks fail when the temp folder sits inside one.
A new suite is covered the same way, with nothing to register: it uses `_scratch`, and `tests/scratch_scenario.py` (a suite like the
others, so CI runs it when a change reaches it, and main always) fails on a suite that goes round it.

## Suite selection

A pull request (and a push to a release-queue branch, `queue/**`, and an entry of GitHub's merge queue, `merge_group`) runs only the suites its change reaches; a push to main runs every suite and measures them. `tests/suitemap.py`
does both (its docstring has the rules in full):

- **On main**, `measure` runs every suite under coverage.py (every Python process of a suite, subprocesses included) and, for
  the suites the push's change reaches and any not traced for a day, under strace (the files a suite opens, stats, runs or
  lists). The result, the map, goes to the Actions cache keyed by the commit. Then `audit` checks the choice the earlier map
  made for everything since its commit against the merged code's own measurement: a suite it should have run and did not
  fails that step by name, and so does a suite that failed on main after the PR skipped it, or a commit the audit cannot
  resolve (nothing was checked). **Main's measured run is split across six parallel jobs** (it was one long job on one runner while the
  other runners sat idle, and every release waits for it): the `shards` job of `tests.yml` makes the plan once (`tests/suitemap.py plan --of 6`: every suite in exactly one of six lists, the
  longest first into the list with the least measured time, by the map, else by a stable hash of the name, which is also what a cache miss in that job gives, for all six lists alike) and hands the six lists
  on as job outputs; the `measure` job is a matrix of 6 jobs on the labels the run used before, each measuring the list it is given and planning nothing (so a cache miss in one of them cannot make it
  double-run or skip a suite), and the `suites` job merges their maps (`tests/suitemap.py merge`), keeps and saves the map and audits as before. Its step `run every suite, measured`, the one
  `release.sh` reads, passes only when every shard passed and the merged map holds every suite exactly once, so `release.sh` and the CI-run poller read main's run as before;
  on a push to main the `suites` job runs on the light pool, since it only merges and audits. A pull request, a queue branch's push, a merge-queue entry and a manual run do not use the shards (a queue branch's `suites` job runs the selection, on the heavy pool). `tests/suitemap_scenario.py` checks
  that every suite is in exactly one list, that every shard reads the one plan, and that the matrix and `--of` agree with `SHARDS` in `tests/suitemap.py`. A suite that fails measured but passes on a plain rerun is a warning, not a failure: the map
  marks it `ok: false`, so every PR runs it until it measures clean, and `release.sh` names it in its report (which then goes
  to the keeper, not green), so a flaky suite stays in sight.
- **A queue branch gets a pull request's run**: a push to a branch named `queue/**` (the merge queue's entry branches: main plus the PRs ahead of one in line plus that PR) runs `tests.yml` as GitHub's merge-queue convention has it,
  the checks a PR runs: no plan and no six measuring shards, the `suites` job alone, running the suites the change reaches by the newest map (the same selection step as a PR's; observed, not measured here: a PR's selected run takes some minutes on a PR retest after catching up, and a queue branch's full sharded run takes tens of minutes, as practice runs showed), and any failure of the selection runs every suite.
  The job keeps its name `suites`, the check mq reads on an entry's head, and its result is read by the commit (`salamander ci-runs howardpark-ai/stackshot --sha <sha>`). `.github/mergequeue.toml` says so with `suites = "select"`, and `tests/suitemap_scenario.py` fails when the file and the workflow disagree.
  What a queue run no longer gives is the measured map and the selection audit: only a push to main does those (it measures every suite in the shards, saves and publishes the map and audits the selection, unchanged). The risk is a selection that misses a suite, which a PR's run accepts as well, and main's full run after the merge catches it by name.
  The poller's window is the newest 30 runs of the repository, which queue pushes share with main's.
- **A GitHub merge-queue entry gets the same run** (`merge_group`). The repository has a `merge_queue` ruleset on main, disabled for now, and `tests.yml` is ready for it: it triggers on `merge_group` (types `checks_requested`) so that the job `suites`, the check the ruleset requires, reports for an entry (a check that never reports makes the queue wait until it times out). An entry (branch `gh-readonly-queue/main/pr-<n>-<sha>`) runs exactly what a `queue/**` push runs: the selection, no plan, no shards, no measured map, no audit. The entry's branch is not in the `push` list (the `merge_group` event is the trigger; a push trigger too would run every entry twice). The event has no pull-request context, so the `tool-text` jobs skip on it, and the map's cache key uses the entry's `base_sha` where a PR uses its base commit (the restore falls back to the newest map). A run of an entry is never cancelled by another (the concurrency group holds the ref, and `cancel-in-progress` is true for a pull request only). `clean-text.yml` is left out: it is not a required check, and its inputs are all the pull request's title, body and branch, which an entry does not have; if it is ever made a required check of the queue, it needs a `merge_group` trigger and its own handling of those inputs. Our own queue (`queue/**`, `salamander mq`) stays live until the switch. Unproven until the ruleset is active: a real `merge_group` run (`tests/suitemap_scenario.py` pins the workflow's shape for the event, GitHub's own behavior it cannot).
- **On a PR**, `select` reads the newest map and runs the suites whose measured functions or files the change reaches: a
  function body reaches the suites that ran it; a module-level binding (a constant, a def, a class, the docstring) the code
  that reads the name, followed across imports and through the bindings that use it, and the suites whose own file names it;
  a module-level statement with effects at import (an unknown decorator, a call) every suite that ran the file; a
  registered tool's header or description (`@mcp.tool`) its callers and whatever lists the tools. A comment or a file no suite
  touches reaches none. A new file (added, or a rename's new path) reaches the suites that listed its directory; in a
  directory no measured suite lists, every suite, since code may look it up by a name nobody tried before (the checkout and
  `tests/` are listed by every suite: the import machinery lists the directories on `sys.path`). No map, a change to the harness (`.github/`, `tests/run-suite`, `tests/pyproject.toml`, `tests/uv.lock`,
  `tests/suitemap.py`) or a suite with no clean measurement: those run (all, for the first three).
- **A release is checked by main.** A PR's checks cover only its suites, so main's full run is the check of every suite. When
  the PR is up to date with main, `release.sh` deploys the merge at once and the main run that covers it comes after: a pass
  is recorded as the last good commit, a failure rolls the deploy back to it (see step 4 above). When the PR is
  behind main, `release.sh` brings it up to date first and waits for the PR's tests on the new head (step 4, *A branch behind main*), then deploys at the merge as above. A PR whose changes share no test group with main's new commits is not even retested (step 4, *No retest when nothing could differ*). Only what the fast path cannot vouch for (3 update rounds with main moving each time, step 4's conditions (a) and (b), an unreadable branch) takes the old path: `release.sh` merges, then waits for the run that covers its merge (step 4, *Which run covers a merge*) before deploying, and deploys only when it passes (merged and not
  deployed when it does not: fix forward). Every deploy goes to one commit (`DEPLOY_TO=<sha> ./deploy.sh`), the newest one containing the merge whose run passed, never to a
  tip with no passing run: a merge another release lands meanwhile is deployed by that release.
- **A new suite** is a new `tests/<name>_scenario.py`: CI finds it by name, nothing else to edit, and runs it on the PR that adds it.
- **A fixture never names a real box** when a suite compares it with the box it runs on (`socket.gethostname()`): CI's hosts
  differ from your own, so a fixture that named one box as the remote machine fails on the host that is that box. The remote machine is `far-host`.
- **Fixtures use invented names**: no real person, company, host or session name, in a fixture, a test comment or an expected string. `Acme`, `Pat`, `you@example.com`, `far-host` and `my-engineer` are the stand-ins; the clean-text job reads only the PR's text (its title, body, branch name and commit messages), not the files, so review is what catches a real name in a fixture.
- **An id match in a test is whole-word**: a test that looks for the id `ab-12` must not pass on `ab-123`. Match it with a boundary after it (`re.search(r"ab-12\b", text)`, or compare the whole token), never `"ab-12" in text`.
- **When the selection looks wrong**, the job summary lists each changed file with its reason. `tests/suitemap_scenario.py` checks
  the rules on a throwaway repository; a rule change comes with a check there.

## The tool-text gates

The owner's rule: **a tool's text changes in the same release as the tool.** What a session learns a stackshot tool from (its name, its parameters, its
description, the fixed labels of the lines it returns) is kept in one committed file, `tests/tool_text.snapshot.json`, and four gates keep a PR from changing
the tool and leaving the text behind. The first three are deterministic checks that CI runs; the fourth is a read by the builder's reviewer subagent before the merge. **No model call runs in a PR check**, and no CI job signs in to AWS.

1. **The snapshot** (`tests/run-suite tool_text`). The suite fails when the live registry differs from the snapshot, prints a readable diff (the words that
   changed, parameters added, removed or changed, labels gone or new) and the one command that refreshes it: **`python3 tools/tool_text.py update`**
   (it re-runs itself in the tests' uv environment), then commit the file with the change. `tool_text.py check` shows the same diff, `dump` prints the text.
   The labels (`mover:`, `then:`, `state:` …) are read from the source of the output helpers by an AST scan, a list kept in one place,
   `HELPERS` in `tools/tool_text.py`: a new function that builds a line a tool returns goes in that list in the same PR.
2. **The retired-terms lint** (`tests/run-suite retired_terms`; `tools/retired_terms.py` with `tests/retired_terms.toml`). Words the owner retired (`owner` → mover, `keeper of record` → mover or `created by`, `steward` → the router and the keepers) fail the build wherever text a session reads carries them: the string literals of the code, the
   hook texts, the tools' snapshot. A hit names the file, the line, the term and what to say. A legitimate use (the instance's owner, a stored key, the deprecated
   parameter's note) is an `allow` phrase in the toml with its reason beside it. The format is in the toml's header; sala copies the checker and writes its own list.
3. **The touched-tool check** (the `tool-text` job of `tests.yml`, pull requests only: `tools/tool_text.py touched --base <sha> --head <sha> --body-file <f>`).
   When a tool function (`@mcp.tool`) or an output helper has a changed body between the PR's fork point and its head, and the snapshot is unchanged, the job
   fails. A change that really leaves every sentence and label as it was (a refactor, a fix inside) says so in the PR body with one line,
   `tool-text: unchanged: <why no session reads a difference>`, and the job is re-run (it reads the body when it runs).
4. **The reviewer's read, before the merge** (no CI job; `tools/text_check.py`). The touched-tool check sees that a body changed, not whether the words still say what the code now
   does, and a script cannot judge that. So before merging a PR that changes **a tool's parameters or text, a help text, or a skill or rulebook line that names a command**
   (the changes that make an agent learn a command wrongly), the fresh reviewer subagent of item 4 in *The branch model* reads that text and checks it against the change: for a tool, the description,
   each parameter and the labels of the returned lines in `tests/tool_text.snapshot.json` against the diff; for a CLI, its help and the usage a wrong call prints; for a skill or a rulebook line,
   the line against the command it names. A mismatch is a finding, and the builder fixes the text and refreshes the snapshot (`python3 tools/tool_text.py update`) or says why the text is still true. **Small changes are skipped**:
   comments, docs, a one-line config change, a refactor that leaves every sentence and label as it was (the PR body's `tool-text: unchanged: <why>` line of gate 3 says so).
   To gather what the reviewer reads for a PR, run **`python3 tools/text_check.py pack --base <sha> --head <sha>`** by hand (or `--base origin/main --head <branch>`): it prints the tools the change reaches, the functions
   with a changed body, whether the PR changed the snapshot, the reached tools' text from the snapshot at the head and the diff of the watched files (hunks of the changed functions first), or one
   `nothing to read: <why>` line. The script uses the standard library only, calls no model, needs no AWS credentials, and **no workflow runs it**; `tests/run-suite text_pack` tests it. There is no switch, no repository variable and no
   PR-body escape line for this read: the reviewer's finding is answered in the PR.

**The brief's what-changed line is generated from the snapshot.** The server's start (`whatschanged.record`) compares the snapshot of its checkout with the copy kept
at the last start that changed it, `<paths.state>/tool_text.released.json`; a difference is appended, dated that day with a generated summary (tools added or
removed, parameters added, removed, renamed or changed, description and label changes by tool), to `<paths.state>/tool_text.history.json`. A deploy restarts the
server whenever a tool changed, so the start is the mark of a release, and no `deploy.sh` or `release.sh` step and no hand edit is involved. For 7 days after its
date the brief carries `stackshot changed on <date>: <summary>; see docs/design`. `tool_text.py summary` shows the line a change will
produce.

## Where CI runs: GitHub's hosted runners

Every job of the two workflows (`tests.yml`, `clean-text.yml`) runs on GitHub's hosted runners (`ubuntu-latest`). No repository variable is needed for that.

- **A trial from a branch**: `gh workflow run tests.yml --ref <branch>`. `tests.yml` also takes `-f suites="pilot release"` (names, space-separated) for a manual run of those suites, plainly; with no names it runs every suite, plainly, without the suite map.
  `clean-text.yml` on a manual run checks the branch's commits against `main`.
- **What a hosted runner gets.** `astral-sh/setup-uv` (every job runs it, with the Python the job needs: uv fetches the interpreter, so no `setup-python`), and the suites build their own fixtures with `git -c user.name=…` and a temp `HOME`, so no git identity or home folder is set up.
  The one install is `strace` (`apt-get`), only for the push to `main` that measures the suites (without it the suite map has no file half and every PR would run every suite). That step is gated on `runner.environment == 'github-hosted'`, true exactly where a job runs on a hosted runner.
  The time limits allow for a small runner: a suite 900 s, the whole job 180 min, the measured run's suite 3,600 s.
- **Minutes.** The standard hosted runners cost a public repository no minutes. A private copy (a fork or a mirror) uses its account's included minutes: a plain run of every suite takes about 15 minutes of the `suites` job and `clean-text` a minute (each job is rounded up to the minute),
  and a push to `main` measures every suite (strace and coverage, several times the plain time, in 6 shard jobs, each with its own setup minute or two) and costs the most. Check the allowance before enabling Actions on a private copy.
- **No CI job calls a model or signs in to AWS.** The earlier model check (a `tool-text-model` job that signed in through GitHub's OIDC token to an IAM role and called Bedrock) is gone; the repository variables and the secret it read
  (`TOOL_TEXT_MODEL_CHECK`, `TOOL_TEXT_AWS_REGION`, `TOOL_TEXT_MODEL`, `TOOL_TEXT_AWS_ROLE`) are read by no workflow now and are removed from the repository settings separately. No job asks for `id-token: write`.

## When the stall pass misfires

The stall pass (`stall.py`, README "The stall pass") moves an item on when its mover's pane has no turn running. When it takes a wrong step on an item, an agent does three things and never a fourth:

1. **Undo the step on the item** with `update` (the `get` tool says the same, and `update` points to it): set `mover` and `next` back after a hand-off (`cold`, `builder`); `status=open` with a new `next` after a close; nothing after a recovery request (the message to the fleet's builder cannot be unsent and the item was left with its mover). The `stall:` line stays in History as the record. A notice already sent (`resend`) cannot be unsent and needs nothing.
2. **Fix the cause through a normal PR** to stackshot (this file's branch model), handed to `my-engineer`: a wrong step is `not_due`, `action` or the registry signal reading the item wrong.
3. **If wrong steps reach the owner before the fix lands, ask him for a pause that ends by itself.** He answers on a board item, and `[stall] pause_item` names it.

**An agent never switches the pass off.** The server honors `enabled = false` or `paused_until` only when `pause_item` names a board item that carries the owner's own answer approving a pause (the chosen option or his comment says "pause"; an unrelated answer of his does not count) from the 4 hours before the server first saw the setting, and no pause lasts longer than 24 hours; a pause answered only after its cap has passed starts when the answer is honored, with one journal line saying so; any other setting is refused with one journal line (and doctor shows it).

## GitHub's hourly call budget

Everything on the host that uses `gh` or the server's `ghsync.token()` spends one shared hourly API budget that polling can exhaust: when GitHub answers
"API rate limit exceeded", ghsync queues its writes. Releases waiting on one main run that each polled `gh run list` and `gh run view` every few seconds were the main way to spend it. What a change here must keep to:

- **A wait polls slowly and shares.** release.sh's main wait looks every `RELEASE_POLL_MAIN` (60 s) and reuses a read another release made in the last `RELEASE_GH_TTL` (45 s) from `<state>/releases/gh-cache`. A new wait on a GitHub state does the same, or uses a conditional request.
- **A wait asks sala's CI-run poller first**: `salamander ci-runs howardpark-ai/stackshot --sha <sha> --max-age 120` reads a file the poller keeps, no GitHub call. Fresh and the commit's run still queued or in progress: keep waiting with no call. Completed, not listed (a 30-run window: a missing sha proves nothing), exit 3/4/5 or no `salamander`: the GitHub read, which alone decides pass or fail. release.sh does this in both its waits (`ci_going`).
- **A read repeated on a timer sends its ETag** (`GitHub.request(..., etag=True)`, `runners._get`): a 304 is not counted. anchor-hub's polls already do, and it keeps its ETags across a restart (a read position that does not, spends the hour's cap on every start).
- **A 403 or 429 is a wait for the reset, not a retry.** ghsync probes `GET /rate_limit` (it costs no call) and resumes when 50 calls are left.
- **A session waiting on a CI run uses `gh run watch <id> --interval 60`**: the default interval is 3 s, thousands of calls an hour for one watch.
- The newest X-RateLimit headers any ghsync or runners call saw are in `<state>/github/ratelimit.json`.

## Where the instance lives

The code carries no instance: `stackshot.example.toml` holds the defaults, and an instance's own `stackshot.toml` lives
with its data (the owner's, kept in his config repo), found through `$STACKSHOT_CONFIG` or
`~/.config/stackshot/stackshot.toml` (see `config.py`). Secrets are under `<paths.secrets>`, never in either repo. Units
are rendered from `units/*.in` by `install.sh` for whatever checkout path and user runs them.

On the server box, `~/.config/stackshot/stackshot.toml` is the live instance. A `server.py` run outside the production checkout
(`~/stackshot`, `PRODUCTION_CHECKOUT` in server.py) without `$STACKSHOT_CONFIG` is refused before it reads the store; run it only
with a temporary config (as the scenarios do). A start binds its port before anything else, so a second server on a port already
held exits without touching the store.

## The merge queue's replay cases

`salamander mq` is tested by replaying a set of past pull requests whose outcome the old release path already decided, on a practice base. `tools/mq_replay.py build-cases` makes the cases: it reads the release logs (`${STACKSHOT_LOGDIR:-~/.local/state/stackshot/releases}/pr-*.log`) and git history (read only: it never checks out, switches, pushes or fetches into the checkout it is given; fetch `origin` first) and writes `tests/mq_replay/cases.json`, which is checked in so the cases outlive the logs. Stdlib only, no lock file.

- **The cases** are the table `SELECTION` at the top of the tool (`[pr, attempt]` pairs); the data of each is regenerated from the logs and git, never typed in. A merged PR's base is `M^1` and its head the head the old path merged, with release.sh's `Merge branch 'main' into` commits peeled off; a refused attempt's base is main's first-parent tip before the `FAILED` line's time, its head the attempt's `(head <sha>)`; a group's base is the tip the old path first saw. Only a base that contains the commit that made `queue/**` run the workflow can run CI.
- **Every sha is checked**: one that main's history holds is read there, any other is fetched by itself from the remote into a scratch repository. A case with a sha it cannot get (or a refusal the queue has no equivalent for) is dropped, printed and recorded under `dropped`.
- **`python3 tools/mq_replay.py build-cases --check`** verifies `cases.json` against git without writing (shas present, the merge-tree of head and base is what the file says, a merged PR that merges clean has `M`'s tree); `--allow-missing` for a checkout that lacks a refused attempt's head, `--verify fetch` to get it from the remote. `--check` validates shas and trees, not how a base was derived: the group and refusal base rules are applied only when the cases are built.
- **A refused PR whose checks are left out** (case c13: CI is to decide) has no `expected_reason`; its `expect` field says what the replay should see (the PR fails on its own and the chain drops it, the other PRs pass). `--repo-owner LOGIN` (default: read from a github.com remote) is the repository's own owner: the file records an `owner` only for a head branch of a fork, and the build stops when no owner can be derived.
- `tests/mq_replay_scenario.py` runs the tool on a throwaway git world and fixture logs in the real shapes (no network), and checks the shape of the checked-in file.

### Running the replay: `run`, `report`, `clean`

`tools/mq_replay.py run` (code in `tools/mq_replay_run.py`, stdlib only) replays the cases on practice branches through the real `salamander mq` in shadow mode and compares each verdict with what the old release path decided.

- **Per case**: it pushes `practice/<run>/<case>` at the case's recorded base sha, writes `replay.json` (schema version 1: `ci`, the repository's `.github/mergequeue.toml` rules with `base` and `queue_prefix` pointing at the practice names, each PR's recorded head, branch and checks; a PR with no `owner` gets the repository's owner, derived from a github.com remote or `--slug`, and the run fails clearly if neither gives one) and a host config (`mode = "shadow"`, the remote, a clone, the replay path) into a folder of its own, and runs `salamander mq add` and `mq wait` with `XDG_STATE_HOME` and `XDG_CONFIG_HOME` set to that folder. The real queue's state folder is never given to a case; only the CI-run poller's folder is linked in, so waiting costs no GitHub call. The case's `XDG_CONFIG_HOME` would hide the box's `gh` login (it lives in `hosts.yml` under the real config folder) and git's XDG config from the queue's driver, so `<case config>/gh` and `<case config>/git` are symlinks to the real folders (`GH_CONFIG_DIR` honoured); cleanup removes the links as links and never reaches into what they point to. Without a `gh` config folder and a token the run says so at the start of each case.
- **Profiles**: `--profile build` (the default) runs every case with `ci = skip` (the entries are built, not pushed; `mq wait` exits 4); `--profile full` runs the cases that need a CI verdict (a merged PR, a group) with `ci = real`. `--cases c01,c05` picks cases, `--concurrency N` (default 2) sets how many run at once, `--keep` keeps each case's folder and clone (the practice branches are deleted all the same).
- **Match rules**: a merged PR must be `mq wait` exit 3 (exit 4 under `ci = skip`), and where the case records a merge tree, the group's tree must equal it (a conflict mended by the rules' `on_conflict` hook included; a `head_mode = "queue"` case is replayed at its queue-time head); a refused PR must be exit 1 with the same check names, or "conflicts with main" with the same files; a PR the case expects to fail alone (its `expect` field starts with `fails alone`) must be named failed on its own, dropped by the chain with the entries behind it rebuilt on the one ahead, while the case's other PRs pass. A mismatch row says which side to look at: CI, the queue, or the old path or the fixture.
- **Idle gate**: no case starts while a `stackshot-release-*.service` unit is active, the release queue file (`queue` in the folder `python3 config.py state releases` names, as `release.sh` reads it; `--logdir` overrides) is not empty, or a real merge-queue group is in any phase but `done` (`salamander mq status --json`; a status call that fails shuts the gate). It is read again before every case. When a release appears mid-run the run stops starting cases, cancels its own in-flight CI runs with `gh run cancel`, drops its PRs, waits for the case's driver to leave, cancels again by looking up the runs of the case's own `queue/practice/<run>/<case>/*` branches (a driver that was still building can push its group after the first cancel; GitHub lists a run a few seconds after its push, so when nothing is found the look is repeated once after `--settle` seconds, default 5; a run that still starts later runs against a deleted branch and is harmless), marks the case interrupted, cleans up and exits 75; `run --resume <id>` runs only the cases not done.
- **Guards and cleanup**: every ref the tool pushes or deletes must match `refs/heads/(queue/)?practice/...` (anything else is refused before git is called, and a delete with one bad ref deletes none); main, the PR branches and the real queue's state are never touched. Deletion is `git push --delete`, never the REST API. In a `finally` (pass, failure, SIGTERM) each case's `queue/practice/<run>/<case>/*` and `practice/<run>/<case>` refs, leftover groups, folders and clone are removed. A driver that does not leave after its PRs are dropped is stopped through its unit name, never killed by process name.
- **Stop signals**: `systemctl --user stop` and Ctrl-C reach the waiting `salamander mq wait` child together with the tool, so a wait ended by a signal is never a verdict: the case is interrupted (no row, resumable) and its CI runs are cancelled.
- **Detached**: `run --detach` starts the same run as the transient user unit `stackshot-mq-replay-<run>` (`systemd-run --user`, `TimeoutStopSec=300` so a SIGTERM's cleanup is not cut short; `GH_CONFIG_DIR` is forwarded into the unit when set, a token never is) and returns; plain `run` stays in the foreground. A run holds a lock, so two runs of one id cannot overlap. Exit codes: 0 all rows match, 1 a mismatch or an error row, 75 interrupted by the gate, 143 SIGTERM.
- **Report**: the table (case, PRs, head to base, the old path's outcome, the queue's verdict with its exit code and CI run link, match, note) is written to `${XDG_STATE_HOME:-~/.local/state}/stackshot/mq-replay/<run>/report.md` and printed; `report [--run ID]` prints it again (newest run by default).
- **Clean**: `clean --run ID` or `clean --older-than 1d` deletes a run's practice refs from the remote and its folders and stops that run's leftover driver units (`mq-<owner>__<repo>-<run>-<case>`, by exact name: the cases come from the run's `run.json` and from its refs, because a run id may hold `-` and a name prefix would also match another run's units; `--slug` names the repository when the remote is not a github.com url). `--dry-run` lists them. A run that still holds its lock is left alone whole, branches and units included, whatever its age (`--run` on it exits 1); a ref whose run age is unknown, and anything outside `practice/` and `queue/practice/`, are left alone too.
- `tests/mq_replay_run_scenario.py` (`tests/run-suite mq_replay_run`) runs all of it against a local bare repository with a fake `salamander`, `gh`, `systemctl` and `systemd-run` on `PATH`: matches, a forced mismatch, a conflict ejection, a failing PR dropped alone with its mate passing, isolation (a decoy queue state folder byte-identical, main unchanged, only practice refs added and removed), the gate at the start and mid-run with `--resume`, cleanup after a normal run, a failing case and SIGTERM, and the ref guard. No test reaches GitHub; the first real run is made by hand.
